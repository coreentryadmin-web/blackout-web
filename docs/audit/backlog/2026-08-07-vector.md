## [P1] META's rail went BACKWARDS mid-session — 35 samples vanished and the last bead regressed 6 minutes
`2026-08-07`

**Symptom** — A member watching META would see the bead rail **truncate backwards**: beads that were
already drawn out to 09:46 disappear, and the rail's leading edge snaps back to 09:40 and then sits
stale while the chart's price bars keep advancing. This is worse than a gap — data that was
successfully served is later un-served.

**Evidence** — the **identical request**
(`GET /api/market/vector/wall-history?ticker=META&dte=all&session=2026-08-07`) at two times:

| sampled (ET) | n | first | **last bead** | gaps > 120s |
| --- | --- | --- | --- | --- |
| 09:46:07 | **127** | 09:30:00 | **09:46:05** | 0 |
| 09:58:47 | **92** | 09:30:00 | **09:40:05** | 0 |

**35 samples lost and the leading edge moved 6 minutes into the past.** At the 09:58:47 read the rail
was **18.7 minutes stale**. The 92 samples it did return span 09:30:00–09:40:05 (605 s) at a clean
6.6 s average, i.e. it is a *complete, internally consistent rail for an earlier point in time* — the
rail was rolled back to its ~09:40 state, not corrupted.

Every other ticker in the same 09:58:47 sweep was current to 09:58:35 (SPX, SPY, NVDA, AMD, ASTS).
QQQ was mildly stale at 09:55:00. So this is per-ticker, not a global stall.

**Root cause — STRONGLY SUSPECTED, NOT CONFIRMED. Do not treat as proven.**
`loadSessionWallHistory` (`src/features/vector/lib/vector-wall-persist.ts:36-61`) is Redis-first and,
on a Redis miss, falls back to the **durable Postgres mirror** and re-warms Redis with whatever it
finds. But the Postgres write-through in `appendSessionWallSample` (`:91-100`) is fired as a
non-blocking `void (async () => {...})()` and is explicitly best-effort — Redis is authoritative. So
if the Redis key is evicted while the Postgres mirror is behind, the fallback re-warms Redis from a
**lagging** mirror, and every subsequent read serves the older, shorter rail. That matches the
symptom exactly: same start, fewer samples, leading edge in the past, internally consistent.

A second candidate is the documented lock-free read-modify-write race at `:64-72` (two replicas
interleaving); the union-merge is designed to bound that to "last write for the same bucket wins" and
should **not** be able to shorten a rail — so if the race is in fact the cause, the union-merge
guarantee is not holding and that is itself the bug.

I could not distinguish these from here: raw Redis and raw Postgres are both blocked in this sandbox.

**Next step to trace** — (a) compare the Redis key `vector:wall-history:META:2026-08-07` against
`loadSessionWallHistoryFromDb` for the same key at the same moment; (b) CloudWatch for
`[vector-wall-persist] db write-through failed META:` and `append failed META:` around 09:40–09:59
ET; (c) check ElastiCache eviction counters on `blackout-production-redis-rg` for that window.

**Suggested fix** — none until traced. If it is the stale-mirror re-warm, the honest fix is to make
the fallback refuse to overwrite a *longer* rail with a *shorter* one (a monotonic guard on
sample count / last-time when re-warming), which is a small, safe change independent of which
candidate is the true cause. **Deliberately leave alone:** do not make the Postgres write-through
blocking — it is non-blocking on purpose so persistence never stalls the live recorder.

**Status** — `BACKLOG — trace after close 2026-08-07`

## [P1] (3b) The 98% confidence is manufactured by the model's own drift, not by evidence — and NVDA's point forecast is not defensible
`2026-08-07`

**Symptom** — At 09:40 ET on expiry day, with NVDA trading at **221.59**, the endpoint forecasts a
close of **212.50 / projected 212.76** — a **4.10% drop** — and labels it **98% confidence**. If
that is drawn on a member's chart it reads as a near-certain 4% downside call on NVDA. It is not
one. ASTS showed the same 98% pre-open. 98% is exactly the model's clamp ceiling (`clamp(..., 0.02,
0.98)`), so the true model output is "100% of paths", i.e. the confidence has saturated.

**Evidence** — two independent confirmations.

*1. The drift is reproducible offline to the cent.* Re-implementing the MC kappa schedule
(`spx-pin-forecast-core.ts:520-544`) as a pure deterministic drift with `strengthPct = 0`, for
`spot 221.59 → maxPain 205, tMin 380, horizon 390, regime long_gamma, 26 steps`:

```
strengthPct=0.00  ->  212.76   (53.2% of the spot->magnet gap closed)   <-- LIVE VALUE 212.76
strengthPct=0.02  ->  208.76   (77.4%)
strengthPct=0.05  ->  206.19   (92.8%)
strengthPct=0.10  ->  205.14   (99.1%)
```

The live `projectedClose` of **212.76** matches the `strengthPct = 0` row exactly. That is not a
coincidence — it identifies the exact branch being taken (below).

*2. The confidence is a consequence of the drift, not a measurement.* `pinPct` is
`inBand / paths` (`:566`) where `band = snapBand(pin, strikeSpacing, tFrac)` (`:483-486`) is
`pin ± max(spacing/2, spacing·(0.5+tFrac))` — a width defined purely in **strike-spacing units**,
with no reference to the name's own volatility or expected move. Because the mean-reversion term
drags all 400 paths onto the same point, terminal dispersion collapses and essentially every path
lands in the band, so the ratio saturates the 0.98 clamp. High confidence is produced *by* the
aggressiveness of the drift assumption, which is precisely backwards.

*3. The prep layer computes the real magnet strength and the MC throws it away — live proof.*
At 09:51:19 ET the endpoint returned NVDA `magnet: {kind: "max_pain", strike: 207.5,
strengthPct: 0.23}`. So `p.magnetStrengthPct = 0.23` (a 23%-of-OI magnet) **is** computed and is
**served in the response**, while the MC loop that actually moves price used `strengthPct = 0`
(proven by the 212.76 match). The correct value is present in the same object and is discarded.

*4. The pin is unstable while the confidence never moves off its ceiling.* Across two samples five
minutes apart:

| time (ET) | NVDA spot | pin | projectedClose | confidence |
| --- | --- | --- | --- | --- |
| 09:40 | 221.59 | **212.5** | 212.76 | **98%** |
| 09:45:54 | 222.00 | **215.0** | — | **98%** |

The pin moved **2.5 points (1.1%) in five minutes** — but the confidence was 98% before the move and
98% after it. A number that claims 98% certainty about a close, and then relocates that close by a
full percent five minutes later without the certainty flinching, is not measuring certainty. This is
the clearest single demonstration that `pinPct` is reporting the tightness of the model's own path
bundle, not the reliability of its forecast.

*5. THE HEADLINE NUMBER — Vector's own expected-move surface says 10%, the forecast says 98%.*
`GET /api/market/vector/expected-move?ticker=NVDA` returned a **1σ move-to-close of ±2.71 points**
(band 219.35–224.76; 2σ 216.64–227.47) — computed from the **same chain, same spot, same instant**
as the forecast. Taking that 1σ as the honest distribution of NVDA's close and asking what
probability it assigns to the forecast's **own** published band:

```
NVDA pin band        = 211.43 .. 218.57   (half-width 3.57 pts = 1.32 sigma)
spot                 = 222.03             (band centre sits 2.59 sigma BELOW spot)

pin-forecast "confidence" that NVDA closes in that band : 98.0%
expected-move-implied P(close in that band)             : 10.1%
```

**A 9.7× overstatement, from two surfaces of the same product, on the same chart, at the same
second (09:58:30 ET).** Even granting the model its own band width, a 1.32σ-wide window would be
worth ~82% if it were centred on spot; it is worth 10% because it is centred 2.59σ away. The 98%
is the MC bundle's internal tightness, and it is blind to the fact that the bundle has been dragged
somewhere the market's own implied vol says it is very unlikely to go.

The forecast's 212.76 also sits **outside NVDA's own 2σ expected move** — the two Vector surfaces
flatly contradict each other.

Independent Polygon ground truth confirms the **magnet itself is correctly located** (NVDA max pain
with OI+dayVolume weighting = 207.5, matching the served magnet exactly — see the GREEN item below).
So this is not a bad-magnet bug; it is a bad-drift-and-bad-confidence bug on a good magnet.

**Root cause** — two distinct defects, both in `src/features/spx/lib/spx-pin-forecast-core.ts`:

1. **`strengthPct` is hard-zero in every non-short-gamma regime.** Lines 531-537:
   ```ts
   let target = p.maxPain ?? price;
   let wallOi = 0;
   if (reg === "short_gamma") {
     if (cwScore >= pwScore && w.callWall) { target = w.callWall.strike; wallOi = w.callWall.oi; }
     else if (w.putWall) { target = w.putWall.strike; wallOi = w.putWall.oi; }
   }
   const strengthPct = w.totalOi > 0 ? wallOi / w.totalOi : p.magnetStrengthPct;
   ```
   `wallOi` is only ever assigned inside the `short_gamma` branch. In `long_gamma` — where `target`
   is set to max pain — `wallOi` stays `0`, and since `w.totalOi > 0` on any real chain the ternary
   yields `strengthPct = 0`. The fallback to the prep-computed `p.magnetStrengthPct` (the *correct*
   value, already computed at `:355`) is only reachable when the chain has **zero total OI**, i.e.
   exactly never. So `magnetPullScale` is pinned at its `0.12` floor for every long-gamma name.

2. **The 0.12 "floor" is not a soft residual — it moves price 53% of the way to the magnet.**
   The comment at `:542` reads "Strength-scaled so thin far walls don't glue every path 100pts away
   from spot", and `magnetPullScale`'s own docblock (`:398-401`) cites the 2026-07-29 "projected
   close frozen 120pts below spot" incident as the reason the floor exists. But the floor is applied
   **per step and compounded over 26 steps**, so even at `strengthPct = 0` it closes 53.2% of the
   gap. The protection added on 2026-07-29 does not operate in this branch, and the same symptom has
   recurred — NVDA's projected close is frozen 8.8 points below spot.

   Note this makes defect 1 *not* safely fixable on its own: wiring in the real `p.magnetStrengthPct`
   would make the drift **worse** (92.8% of the gap at a 5% OI magnet), not better.

**Suggested fix** — after close, and measured before shipping:
- Pass the magnet strength that corresponds to the magnet actually being targeted (`p.magnetStrengthPct`
  when the target is max pain) instead of the hard `0`, **and** re-calibrate the floor/`base` so the
  long-gamma pull is bounded by something physical. The natural bound is the name's own expected
  move: a pin forecast should not be able to place `projectedClose` outside the 2σ band that
  `getVectorExpectedMove` computes from the same chain and the same spot.
- Stop reporting `inBand/paths` as "confidence" while the band is defined in strike-spacing units.
  Either express the band in units of the remaining expected move (making the number comparable
  across SPX and ASTS), or relabel it so it is not read as a probability. A number that hits its own
  clamp ceiling on two of seven names on its first live day is not calibrated.
- Add a guard/badge for the case actually observed: magnet more than 1σ from spot **and**
  `pinPct >= 0.9`. That combination is the model asserting near-certainty about a large move, which
  is the one thing it is least able to know.
- **Deliberately leave alone:** the short-gamma path (SPX/SPY/QQQ/AMD/META all returned sane pins
  30–87% within a few points of spot), the cone geometry (27 steps on all 14 probes), the
  `MC_BRIDGE_NOISE_FLOOR` fix, and `resolveForecastTarget` — all behaved correctly.

**Status** — `BACKLOG — fix after close 2026-08-07`. **This is the item to fix before the forecast
goes on a member's chart.**

## [P2] `expected-move.movePct` is quantized to zero by blanket 2-decimal rounding
`2026-08-07`

**Symptom** — Any consumer rendering the Vector expected-move percentage sees **0.00% for SPX**, and
wrong values for every other name. A member reading "1σ expected move: ±31 pts (0.00%)" is being
shown a self-contradictory band.

**Evidence** — `GET /api/market/vector/expected-move?ticker=<T>` at 09:47 ET:

| Ticker | spot | 1σ movePts | true movePct | **served movePct** | renders as |
| --- | --- | --- | --- | --- | --- |
| SPX | 7737.83 | 31 | 0.004006 | **0** | **0.00%** |
| NVDA | 222.06 | 2.71 | 0.012204 | **0.01** | 1.00% (true 1.22%) |
| ASTS | 69.78 | 2.55 | 0.036544 | **0.04** | 4.00% (true 3.65%) |

Raw SPX response: `{"ticker":"SPX","horizon":"all","expectedMove":{"atmIv":0.15,"dteDays":0.26,
"spot":7737.83,"movePct":0,"bands":[{"sigma":1,"movePts":31,"low":7706.83,"high":7768.83},
{"sigma":2,"movePts":62,"low":7675.83,"high":7799.83}],"expiry":"2026-08-07"}}`

**Root cause** — `src/app/api/market/vector/expected-move/route.ts:38-45` wraps the whole payload in
`roundFloats({...})` with the **default `dp = 2` and no `keyDp` override**. `movePct` is a *fraction*
(`move1 / spot` — `src/features/vector/lib/vector-expected-move.ts:89`, asserted to 1e-12 by
`vector-expected-move.test.ts:19`), so 2dp destroys it. This is the exact failure mode `round-floats.ts`
documents in its own header (lines 19-28): *"a single `dp` for a whole payload is … WRONG the moment a
payload mixes scales … the 2dp default would quantize it to 0.00 and DESTROY the number"* — the
`keyDp` mechanism exists for precisely this and was not used here. `atmIv` (0.15 / 0.46 / 1.36) is
quantized by the same call.

Known consumers that multiply by 100 and will surface the wrong number:
`src/features/vector/lib/vector-expected-move.ts:103`, `src/lib/bie/vector-desk-intel.ts:125`,
`src/lib/bie/scenario-read.ts:319`. `scenario-read.ts:322` additionally computes
`mult = Math.abs(movePct) / sigma1Pct`, which is a **division by zero** whenever `sigma1Pct` is the
quantized 0 — not yet traced end-to-end as to whether that path reads the HTTP route or the server
lib directly, so treat the div-zero as *suspected, unconfirmed*.

**Suggested fix** — pass `keyDp: { movePct: 6, atmIv: 4 }` (or equivalent) to the `roundFloats` call
in the expected-move route. **Deliberately leave alone:** the default 2dp for `spot`, `movePts`,
`low`, `high` — those are dollar amounts and 2dp is correct for them. Audit the other Vector routes
for the same blanket-`roundFloats` pattern on fractional fields at the same time.

**Status** — `BACKLOG — fix after close 2026-08-07`

## [P0] Legacy card shows the UNDERLYING's move as the option's P&L, and labels the stock's entry-band midpoint "entry prem" — −2% displayed while the named contract is −52%

**Date** 2026-08-07

**Symptom** — A member opens the Legacy tab, sees today's only play rendered as
`#1 · ACTIVE · MU  MU $880 CALL @ $25.27 — Aug 10, entry prem ~$25.27 · B · ★★★★☆ · 73 · 09:15 · PNL -2%`.
The instrument, the entry price and the exit rule printed on that same card are all
**option-premium** quantities; the number under "PNL" is the **stock's** percentage move. The
card's own `risk_note` says *"hard stop −60%"* — a premium-basis rule the deck never displays in
premium terms. A member managing to the displayed number believes the position is essentially
flat while it is actually down more than half, and closing in on the stated stop.

**Second, harder symptom on the expanded card** — the play-detail header renders
**"entry prem $881.47"**. `881.47` is the *stock* entry-band midpoint. The card's real entry
premium — `$25.27` — is printed two lines above it on the same card. So a member reading the
detail view is told the entry premium is $881.47 and the position is −2.6%, when the entry
premium is $25.27 and the position is −52%.

**Evidence** (all captured 2026-08-07, market open)

- Live DOM of `https://blackouttrades.com/nighthawk?view=legacy`, iPhone 430×932, authenticated
  temp admin session, `Routed: 62 ok, 0 fail`:
  `AFTERALL::{"rows":"#\nSTATUS\nPLAY\nRATING\nTIME\nPNL\n#1\nACTIVE\nMU MU $880 CALL @ $25.27 — Aug 10, entry prem ~$25.27\nB\n★★★★☆\n73\n09:15\n-2%"}`
- Expanded-card DOM at **2026-08-07T14:09:24Z**, verbatim:
  `MU · LONG / MU $880 CALL @ $25.27 — Aug 10, entry prem ~$25.27 / 73 SCORE / PRE-MARKET CONFIRMED / … / LIVE · MU $858.85 -2.6% from entry · 3s ago · **entry prem $881.47**`
  — and the cockpit strip on the same screen shows `P&L -0.1R`.
- `GET /api/market/nighthawk/edition` → play 1 = MU LONG,
  `options_play: "MU $880 CALL @ $25.27 — Aug 10, entry prem ~$25.27"`, `entry_premium: 25.27`,
  `entry_cost_per_contract: 2527`, `entry_range: "$859.43-$903.51"`,
  `risk_note: "Banger exit — … hard stop −60%…"`.
- Polygon/Massive `O:MU260810C00880000` at **2026-08-07T14:08:21Z**:
  `bid 11.85 / ask 12.25 / mid 12.05`, day close 12.95, previous_close 25.30 (the 25.30 prev
  close corroborates the published 25.27 entry premium as a real mark).
  **True premium P&L from $25.27: mid −52.3%, bid −53.1%.**
- Same instant, MU stock: last **860.93**, `todaysChangePerc −2.33`. Entry-band mid
  = (859.43 + 903.51)/2 = **881.47**. `(860.93 − 881.47)/881.47 = −2.33%` — an exact match for
  the **−2%** the deck printed. The displayed number is unambiguously the stock move.
- Magnitude of the misrepresentation on this single live row: **−2.3% shown vs −52.3% real**,
  a factor of ~22.

**Root cause** — `src/features/nighthawk/command-deck/use-legacy-quotes.ts:176-181` computes
`stockPnlPct = (price − entryMid) / entryMid` (entryMid parsed from the *stock* `entry_range`)
and line **212** assigns it straight into the play's `pnlPct` — the field the deck's PNL column
renders. `src/features/nighthawk/command-deck/adapters.ts:766-770` sets it up that way on
purpose (`entry: entryMid ?? fin(src.entry_premium)`, `mark: null`, `pnlPct: null`, with the
comment *"Stock entry mid drives P&L overlay (overlayLegacyQuotes) — option premium stays
separate."*). So the stock basis is a deliberate choice; what is **not** deliberate is that the
same row simultaneously advertises an option contract, an option entry premium, and an
option-premium stop rule, with no label distinguishing the basis. `mark` is never populated for
LEGACY, so the option is never marked at all.

The "entry prem" mislabel is the same root cause surfacing through a shared renderer:
`src/features/nighthawk/command-deck/PlayTerminal.tsx:292` prints
`· entry prem {usd(play.entry)}` unconditionally, and for LEGACY `play.entry` was set to the
stock band midpoint by `adapters.ts:767`. Every other horizon populates `entry` with a real
premium, which is why the label is correct everywhere except LEGACY.

**Suggested fix** — (0) stop labelling the stock midpoint "entry prem": either gate
`PlayTerminal.tsx:292` on `horizon !== "LEGACY"` or give the Legacy card its own
`entry stock $X` label; (a) label the column/value explicitly for LEGACY (`PNL (stock)`), and (b)
preferably mark the named contract: the Legacy card already carries a parseable OCC-shaped
`options_play` and an `entry_premium`, and the repo already has an option-mark lane
(`use-live-marks.ts`, `/api/market/zerodte/marks`) plus `occ-from-row.ts` — reuse it rather than
build a new one. Show BOTH (stock move + premium P&L) since the geometry panel is stock-basis by
design and the exit rule is premium-basis. **Leave alone:** `overlayLegacyQuotes`' progress bar,
stop/target crossing logic and `ExcursionViz` peak/trough — those are legitimately stock-basis
(they track the published stock target/stop) and changing them would break
`LegacyManageGeometry`, the single stop/target renderer settled on 2026-08-05.

**Status** — `BACKLOG — fix after close 2026-08-07`

## [P1] Legacy board renders EMPTY on load during RTH — the status lens latches on WATCH before morning-confirm lands, then never re-seeds

**Date** 2026-08-07

**Symptom** — A member opening `/nighthawk?view=legacy` during market hours sees
**"No watch plays right now."** and an empty deck, even though the board has one live play. The
counter row directly above reads `ALL 1 · OPEN 1 · WATCH 0 · CLOSED 0` — i.e. the UI is telling
the member there is 1 play and 0 watch plays while showing him the watch list. Today's entire
Legacy product is invisible until he manually clicks another chip.

**Evidence** (2026-08-07, live prod, authenticated, `Routed: 62 ok, 0 fail`)

- DOM introspection of the filter chips on first paint:
  `FILTERSTATE::{"btns":[{"t":"ALL 1","on":false},{"t":"OPEN 1","on":false},{"t":"WATCH 0","on":true},{"t":"CLOSED 0","on":false}],"empty":["No watch plays right now.","◂ select a play to break it down"]}`
  — `WATCH` carries the active class with a count of **0**; `OPEN` has **1** and is inactive.
- Screenshot `legacy-mobile.png` (430×932) shows the same: WATCH chip lit, body empty.
- **Reproduced independently in a second run** ~20 minutes later (2026-08-07T14:09Z, fresh
  session, fresh browser context, `Routed: 62 ok, 0 fail`) — byte-identical `FILTERSTATE`. Not a
  one-off race artifact.
- Clicking the `ALL` chip immediately reveals the row:
  `#1 ACTIVE MU MU $880 CALL @ $25.27 — Aug 10 … -2%`. So the data was present the whole time —
  purely a lens bug.
- Server side confirms the play is OPEN, not WATCH:
  `GET /api/nighthawk/play-status?date=2026-08-07` →
  `{"checked_at":"2026-08-07T13:15:14.593Z","plays":[{"rank":1,"ticker":"MU","status":"CONFIRMED","swingPromoted":true}],"summary":{"confirmed":1,"degraded":0,"invalidated":0,"unverified":0}}`.

**Root cause** — a seed/latch race across two independent client fetches:

1. `src/features/nighthawk/command-deck/containers.tsx:264-267` — `LegacyDeck` renders from the
   `edition` payload immediately, then fetches `/api/nighthawk/play-status` in a **separate**
   SWR key (`["legacy-confirm", editionFor]`).
2. `src/features/nighthawk/command-deck/adapters.ts:657` —
   `status = pulled ? "CLOSED" : ms === "INVALIDATED" ? "SKIP" : ms === "CONFIRMED" ? "OPEN" : "WATCH"`.
   With `morning_status` still `null` (play-status not back yet) **every** Legacy play is
   `"WATCH"` on first paint.
3. `src/features/nighthawk/command-deck/CommandDeck.tsx:129-141` — the status-lens seeder fires
   on the **first non-empty** board and then sets `filterSeeded = true`, permanently:
   `if (filterSeeded || plays.length === 0) return; setStatusFilter(defaultZeroDteStatusFilter({...})); setFilterSeeded(true);`
   At that moment `counts.open === 0`, `counts.watch === 1`, so
   `defaultZeroDteStatusFilter` (`deck-session-ui.ts:51-55`) returns **`"WATCH"`**.
4. play-status lands, statuses flip to OPEN, counts become `open 1 / watch 0` — but the one-shot
   latch has already fired, so the lens stays on WATCH over an empty set.

**Why it was not caught earlier** — `defaultZeroDteStatusFilter` returns `"ALL"` whenever the
session is not active (`deck-session-ui.ts:56`). The bug therefore **cannot reproduce after the
close**, which is exactly when a post-close digest lane is normally reviewed. It only bites
members during RTH, on the carry-until-close board.

**Suggested fix** — make the seed *provenance-aware* rather than time-once: do not consume the
board for seeding until the morning-confirm source has resolved (e.g. seed only when
`confirmData !== undefined`, or pass a `statusesResolved` flag from `LegacyDeck` into
`CommandDeck` and gate the effect on it). A cheap alternative that fixes the visible symptom
without touching the seed: in `CommandDeck`, if `filtered.length === 0 && plays.length > 0`,
fall back to `ALL` for rendering. **Leave alone:** the RTH-defaults-to-actionable behaviour
itself — it is correct and valuable on the 0DTE lane, where `open > 0` is true on first paint;
and `adapters.ts:657`'s `null → WATCH` default, which is the honest pre-confirm state.

**Status** — `BACKLOG — fix after close 2026-08-07`

## [P1] A published Legacy play can carry a stop INSIDE its own entry band — geometry gate only checks the band MIDPOINT, and the resulting fake R:R is what gets it past the gate

**Date** 2026-08-07

**Symptom** — Member sees a card reading *"RDDT … R:R 17.8:1 (strong)"*, entry
`$150.84-$158.58`, target `191.29`, **stop `152.65`**. The stop sits *inside* the entry band: a
member who fills anywhere in the bottom `$150.84–$152.65` (the lowest ~23% of the published
band) is stopped out the instant he is filled. The advertised 17.8:1 is not achievable at any
price in the band.

**Evidence**

- `GET /api/market/nighthawk/edition?date=2026-08-04` → rank 5:
  ```json
  {"ticker":"RDDT","direction":"LONG","entry_range":"$150.84-$158.58","target":"191.29",
   "stop":"152.65","rr_ratio":17.76,
   "thesis":"RDDT in mixed trend. R:R 17.8:1 (strong). 2-day bullish flow streak …"}
  ```
- Confirmed on the grading side too — `GET /api/track-record/plays` nighthawk row:
  `2026-08-04 | RDDT | LONG | B | open | entry 150.84–158.58 | target 191.29 | stop 152.65`.
- Contrast across the same and neighbouring editions: every other published card's `rr_ratio`
  lies in **0.75 – 1.96** (ANET 1.25, CRWV 1.67, SKHY 1.96, GOOGL 0.75, NVDA 0.75, DELL 1.00,
  AMD 1.77, LLY 0.88, AEM 1.27, MU 1.27). RDDT's 17.76 is a ~9× outlier — the tell.
- Arithmetic reproduction of the published 17.76 pins the basis exactly:
  midpoint 154.71 → `(191.29 − 154.71)/(154.71 − 152.65) = 36.58/2.06 = 17.76`. ✔
- Scanned **all 27** current nighthawk outcome rows for the same defect (LONG: stop < band low;
  SHORT: stop > band high). **RDDT 2026-08-04 is the only violation**; the other 26 are clean,
  including both SHORTs (SLV 2026-07-21 stop 54.72 > band high 51.23; LOW 2026-07-20 stop 221.05
  > band high 209.77).
- The engine already knows this class exists: `record.debrief.failure_modes` reports
  `band_detached n=4` over 30 days and `n=7` over 90 days.

**Root cause** — `src/features/nighthawk/lib/play-constraints.ts:157-172`,
`validatePlayGeometry`. Every directional check is against the entry-band **midpoint**:

```
if (target <= mid) drops.push(`LONG target … not above entry mid`)
if (stop  >= mid) drops.push(`LONG stop … not below entry mid`)
const reward = Math.abs(target - mid);
const risk   = Math.abs(stop   - mid);
if (risk > 0 && reward / risk < MIN_RR_RATIO) drops.push(…)
```

There is **no** check that a LONG's stop is below `entry_range_low` (or a SHORT's above
`entry_range_high`). RDDT: `stop 152.65 < mid 154.71` → passes; `risk = 2.06`, `reward = 36.58`
→ `R:R 17.76 ≥ MIN_RR_RATIO` → passes. The two gates are **perversely coupled**: the closer the
stop creeps into the band, the smaller `risk` becomes and the *larger* the R:R the gate sees —
so the broken geometry is exactly the geometry the gate rewards.

Note this is a *different* bug from the display-basis fix already shipped on 2026-08-06:
`computeRiskReward` (`play-levels.ts:122-140`) was correctly moved to the fill-edge basis (live
proof: today's MU card shows 1.27, which is the edge value `(1092.12−903.51)/(903.51−755.08)`,
not the mid value 1.667). But `validatePlayGeometry` was deliberately left on the mid basis
(`play-levels.ts:113-120` says so explicitly), and *that* is the gate a stop-inside-band play
walks through. RDDT was published 2026-08-04T00:53Z, before the display fix, which is why its
card still shows the mid-basis 17.76.

**Suggested fix** — add a band-containment drop to `validatePlayGeometry`: LONG requires
`stop < entry_range_low`, SHORT requires `stop > entry_range_high` (unconditional, cheap, and
independent of the R:R basis debate). Add a `play-constraints.test.ts` case pinned to the real
RDDT numbers. **Leave alone:** the `MIN_RR_RATIO` gate's mid basis — `play-levels.ts:113-120`
records a measured reason for not moving it (edge basis would push ~20 of 48 plays under 0.75
and reproduce the 2026-07-27 zero-play failure). Containment is an orthogonal, strictly-additive
guard that does not touch that trade-off.

**Status** — `BACKLOG — fix after close 2026-08-07`

## [P1] Legacy→Swing promoted rows freeze `dte` and the contract at promotion time — a contract expiring TODAY is served to members as "3DTE", and nothing ever expires them off the board

**Date** 2026-08-07

**Symptom** — On the Swings board, Legacy-promoted rows show a days-to-expiry that is the value
computed on the day they were promoted, not today. Three rows whose options **expire today**
(2026-08-07) are labelled **"3DTE"** and sit in the COMMITTED lane with `entryStatus`
`PRE_TRIGGER` / `EXTENDED_CHASE` — i.e. a member is invited to enter a 0-DTE contract believing
he has three days of runway. Because nothing prunes on expiry, these rows will keep being
carried after the contract has actually expired.

**Evidence** — `GET /api/market/nighthawk/horizons?view=swings`, 2026-08-07 (today):

Every served `dte` equals `expiry − promotion_date` exactly. **Control group in the same
payload:** the non-Legacy ledger rows are all correct today — KRE exp 2026-08-14 `dte 7` ✔,
FHN/KKR/SPCX exp 2026-08-21 `dte 14` ✔, MSFT exp 2026-08-14 `dte 7` ✔ — which isolates the

Corroborated by `GET /api/admin/swing/discovery-debug`:
`{"asOf":"2026-08-07T13:15:14.593Z","sessionDay":"2026-08-07","dossiers":19,"plays":13,"watch":14,"watchTickers":["BE","CG","SNDK","FSLR","RVMD","CRWV","SKHY","GOOGL","RDDT","NVDA","AMD","LLY","AEM","MU"]}` —
the 2026-08-04 cohort is still in `watch` three sessions later.

**Root cause** — two-part, both in the carry path:

- `src/lib/swing/legacy-confirm-promote.ts:196-204` builds the play once via
  `produceHorizonPlays([{ …, asOfYmd: editionFor, chainRows }])`; the contract's `dte` comes from
  `calendarDte(asOfYmd, snap.expiry)` (`src/lib/swing/contract-ranker.ts:304`) and the human
  `reason` string bakes `${c.dte}DTE` in at `contract-ranker.ts:252`. Both are then persisted
  verbatim into the serving snapshot.
- `src/lib/swing/legacy-confirm-promote.ts:327-341` (`carryLegacyPromotedIntoSnapshot`, added
  2026-08-04 to stop swing-discovery wiping Legacy names) re-attaches the **whole prior triple**
  — dossier, play, watch — into every subsequent snapshot with no expiry check and no
  recomputation, and `src/lib/swing/serving-lane.ts` (`discoverSwingFromPersisted`) serves
  `snap.plays` as-is: it re-stamps `firstSeenAt`, `signalKinds` and `flagUnderlyingPx` but never
  touches `contract` or `reason`. There is therefore no code path anywhere that ages, refreshes
  or retires a Legacy-promoted contract.

**Suggested fix** — in `carryLegacyPromotedIntoSnapshot`, (a) **drop** any triple whose
`play.contract.expiry < fresh.sessionDay` (expired contracts must leave the board), and
(b) recompute `contract.dte` (and the `NNDTE` substring in `reason`) against `fresh.sessionDay`
on carry, so a carried row ages honestly. A defensive recompute at serve time in
`discoverSwingFromPersisted` would also work and covers snapshots written by older code.
**Leave alone:** the carry mechanism itself — it exists to fix a real P1 (FINDINGS 2026-08-04,
Legacy names wiped by the discovery overwrite) — and the ledger/`livePlaysFromOpenPositions`
path, which computes `dte` live and is verifiably correct today.

## [P2] The morning re-anchored entry band is used to GRADE the play but is never shown to the member — the card keeps the stale overnight band

**Date** 2026-08-07

**Symptom** — Morning-confirm tells the member, in the status badge, that the entry was
re-anchored ("*MU pre-market 908.31 gapped above the entry range — entry re-anchored to
pre-market*") but never says to **what**. The card continues to display the original overnight
band. The member trades one band; the track record grades him against a different one.

**Evidence** (2026-08-07, live)

- `GET /api/nighthawk/play-status?date=2026-08-07` →
  `{"ticker":"MU","status":"CONFIRMED","reason":"MU pre-market 908.31 gapped above the entry range — entry re-anchored to pre-market","swingPromoted":true}`
- `GET /api/admin/cron-health`, job `nighthawk-morning-confirm`,
  `last_run_at 2026-08-07T13:15:15Z`, `meta.entry_bands_reanchored: **1**` — so a band WAS
  rewritten in `nighthawk_play_outcomes`.
- `GET /api/market/nighthawk/edition` at the same time still serves
  `entry_range: "$859.43-$903.51"` — the pre-gap band. Nothing in the payload carries the new
  band, and no field exists on the play for it.
- Divergence is material: the grader's band is anchored on 908.31; MU actually traded
  **854.50 – 904.80** today (Polygon day bar `o 903.60 h 904.80 l 854.50`), never touching
  908.31. A member filling in the published 859.43–903.51 band (very much available today) is
  graded as though he paid ~908.

**Root cause** — `src/app/api/cron/nighthawk-morning-confirm/route.ts:478-524`. The design note
at :485 states it outright: *"The published edition is never mutated — only the grading-side
entry band."* `reanchorNighthawkEntryBand` (`src/lib/db.ts:8470-8489`) does
`UPDATE nighthawk_play_outcomes SET entry_range_low/high` only. The edition route
(`/api/market/nighthawk/edition`) reads the immutable edition row plus the **pull** overlay
(`applyNighthawkPullOverlay`) — there is no equivalent re-anchor overlay, so the new band has no
route to the member.

**Suggested fix** — extend the existing read-time overlay pattern rather than mutating the
edition: have `withPullOverlay` (or a sibling `withReanchorOverlay`) also read the outcome row's
current `entry_range_low/high` and, when it differs from the published band, stamp a
`reanchored_entry_range` (plus `reanchored_at`) onto the play so the card can render
"entry re-anchored → $X–$Y". **Leave alone:** the "never mutate the published edition row"
rule — it is deliberate and correct; this is an overlay problem, not a mutation problem.

**Status** — `BACKLOG — fix after close 2026-08-07`

## [P2] `/api/market/nighthawk/edition` performs no validation on `?date=` — a garbage date silently serves today's edition, mislabelled `stale: true`

**Date** 2026-08-07

**Symptom** — Any caller (or a bad link) hitting the edition route with a non-date gets HTTP 200
and the current edition flagged as stale, rather than a 400. A member following such a link sees
a "stale" banner on data that is actually current.

**Evidence** (2026-08-07)

- `GET /api/market/nighthawk/edition?date=not-a-date` → **200**,
  `{"available":true,"edition_for":"2026-08-07","served_for":"2026-08-07","stale":true,"published_at":"2026-08-06T21:37:51.000Z","plays":[MU]}`
- `GET /api/market/nighthawk/edition?date=2026-08-10` (a future session) → **200**, same body,
  also `stale: true`.

**Root cause** — `src/app/api/market/nighthawk/edition/route.ts:191-192`:
`const explicitDate = req.nextUrl.searchParams.get("date"); const editionFor = explicitDate ?? nextTradingDayEt(todayEt());`
The raw string is passed straight into `fetchNighthawkEditionByDate` / the cache key. A
non-matching lookup falls through to `fetchLatestNighthawkEdition()`, whose `MAX_EDITION_AGE_DAYS`

## [P3] Record exclusion counts do not add up — `scoreable + unfilled + pulled` overshoots `resolved` by 2 (`unfilled` and `pulled` are overlapping sets)

**Date** 2026-08-07

**Symptom** — Anyone reading the record's own breakdown gets an arithmetic contradiction. The
headline ratios are NOT wrong; the exclusion accounting is un-reconcilable.

**Evidence** — `GET /api/market/nighthawk/record?days=30` (2026-08-07):
`segments.current = {resolved 50, scoreable 27, wins 0, losses 2, opens 25, ambiguous 0, unfilled 13, pulled 12, stop_data_unavailable 0, decided 2}`.

- The **core invariant HOLDS**: `wins + losses + opens + ambiguous = 0 + 2 + 25 + 0 = 27 = scoreable` ✔
- The exclusion sum does **not**: `27 + 13 + 12 + 0 = 52`, but `resolved = 50`. **Overshoot: 2.**
- Same 2-row gap at `days=90`: `56 + … ` → `resolved 56`, `scoreable 27 + unfilled 19 + pulled 12 = 58`.

**Root cause** — `src/features/nighthawk/lib/analytics.ts:405-409`:
```
const unfilled = rows.filter((r) => r.outcome === "unfilled");
const pulled   = rows.filter((r) => r.pulled === true);
const scoreable = rows.filter((r) => !isStopDataUnavailable(r) && r.outcome !== "unfilled" && r.pulled !== true);
```
`unfilled` and `pulled` are computed independently and **can overlap** — a play pulled pre-open
that also gapped away is counted in both. `scoreable` correctly excludes it once, so no rate is
double-counted; only the published breakdown is un-summable. (Live corroboration that the
overlap class is real: the AMZN 2026-08-03 card carries a `pulled_reason` that *begins* with the
gap-away sentence — *"AMZN pre-market 277.49 gapped above the entry range — entry re-anchored to
pre-market; Cortex fresh-veto: …"* — i.e. gap-away and pull genuinely co-occur.)

**Suggested fix** — publish a disjoint partition: either report `pulled` as the outer category
and `unfilled_not_pulled` inside it, or add an explicit `excluded_total` (the size of the union)
so a reader can reconcile without guessing. **Leave alone:** `scoreable` and every rate derived
from it — the exclusion logic is correct, only the reporting is ambiguous.

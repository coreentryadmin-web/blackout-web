Requested: "a deep massive CTO audit investigation into entire Swing system .. including architecture design api all panels largo integration like everything.. A to Z .. check each and every field .. values .. numbers .. and see if you can find any bugs, gaps, flaws, red flags."

This audit ran 18 parallel investigation agents, each grounded in real production data pulled live from `blackouttrades.com` (a temp admin/premium Clerk session, deleted after capture) — the 60-day swing track record (31 roll-chains), `GET /api/market/nighthawk/horizons?view=swings` (all 4 currently-committed live positions), and 7 full `GET /api/market/swing/play-brief` envelopes (4 open/HOLD/TRIM, 3 closed) — cross-referenced against the actual source. ## Critical findings

### 1. Rolled-chain closed brief shows a DIFFERENT leg's P&L under the requested leg's own identity

**Severity:** CRITICAL · **Category:** bug · **Subsystem:** brief-core

**Files:** `src/lib/swing/play-brief-resolve.ts:115-129`, `src/lib/swing/closed-plays.ts:106-135`, `src/lib/swing/play-brief-intel.ts:414-430`

**What's broken:** `loadClosedPlay()` in play-brief-resolve.ts (called with a specific `positionId`, e.g. 35) correctly finds that exact leg row, but then builds the deck source via `closedDeckSourcesFromChains([chain])` — a helper whose own test (`closed-plays.test.ts:69-83`, 'emits one row per resolved chain using chain-composite P&L (Q26)') documents that it DELIBERATELY overwrites the terminal leg's own `exitPnlPct`/`closedReason` with `record.composite.worstLegPnlPct` (the WORST leg across the whole roll chain), because it is designed for the CLOSED-deck LIST view (one summary row per chain). play-brief-resolve.ts reuses this same function for a single, positionId-keyed play-brief request and has no awareness of, or adjustment for, that override — so the brief's headline/identity (contract, ticker, positionId) correctly names the requested leg, but the P&L number attached to it can silently belong to an EARLIER, already-rolled-away leg of the same chain. Nothing in play-brief.ts, play-brief-resolve.ts, or the rendered sections discloses that the number is a chain composite rather than this leg's own outcome.

**Evidence:** Live data for playId=SWING:INTC:35: record.json shows the roll chain rooted at position 30 has two legs — {positionId:30, realizedPnlPct:-40.83, entry_premium:3.6, exit_mark:2.13} and {positionId:35 (the terminal/requested leg, rollSeq 1), realizedPnlPct:-33.19, entry_premium:2.26, exit_mark:1.51}, worstLegPnlPct=-40.83. The play-brief envelope fetched for exactly this playId (playbrief-SWING_INTC_35_closed.json) headlines 'STOPPED — INTC 90P 3DTE' (position 35's own contract) but its 'Outcome' section reports 'Exit P&L: -40.8%' — matching leg 30's -40.83%, NOT leg 35's own -33.19% (which would round to -33.2%). The 'Lessons' section compounds this by mixing sources: 'Peak was +25.7%' is computed from leg 35's OWN entryPremium/peakPremium (untouched by the override, per closedDeckSourceFromRow(terminal) and terminalPlayFromClosedSwing passing entryPremium/peakPremium through unmodified), while 'exited -40.8%' is leg 30's number — producing a 'Round-tripped past breakeven' narrative (play-brief-intel.ts:421) that describes a price journey no single real contract actually took (leg 35 itself never had a -40.8% exit; leg 30's own peak was never reconstructed by this code path).

**Suggested fix:** loadClosedPlay() should use a per-leg lookup (e.g. `closedDeckSourceFromRow(target)` directly) for a specific positionId request, reserving `closedDeckSourcesFromChains`'s chain-composite override for the actual list/deck view it was built and tested for. If a chain-composite figure is still desired for a specific-leg brief, it must be a clearly labeled additional field/section ('chain composite: -40.8% across 2 legs'), never presented as this leg's own 'Exit P&L'.

### 2. Closed-bucket collapse deletes GEX/wall/macro/flow intel with a false "folded into narrative" claim

**Severity:** CRITICAL · **Category:** bug · **Subsystem:** brief-narrative

**What's broken:** collapseRedundantIntelSections(sections, {hasNarrative, bucket}) accepts a `bucket` option but never reads it — the collapse decision (which titles in NARRATIVE_COVERED_TITLES get dropped) is identical for watch/open/closed. But tradeManagerNarrativeSection's CLOSED branch (play-brief-narrative.ts:425-429) only calls collectCoachingBullets(ctx, "closed", spot), which for bucket==="closed" (play-brief-narrative-coaching.ts:589-592) returns ONLY closedCoaching(play) — a short post-mortem (exit P&L vs peak, MFE-capture note, closed reason). It never runs the dealer-posture line, focal-level narration (GEX king, max pain, walls), flow narrative, or break-trigger code that only executes for non-closed buckets (lines 436-506). Meanwhile buildIntelSections (play-brief-intel.ts:603-673) generates GEX posture / Wall dynamics / Flow & positioning / Macro tape / Lane rank / Vector desk sections unconditionally from ecosystem/vector data (no bucket gate on those functions) and always runs them through collapseRedundantIntelSections. So for a CLOSED play, whenever closedCoaching produces any bullet (i.e. almost always, since play.status==="CLOSED" implies exitPnlPct/closedReason are set), hasNarrative=true and every title in NARRATIVE_COVERED_TITLES gets silently deleted from the brief — even though none of that content actually reached the narrative — and a note is appended to "Trade manager read" claiming "Desk detail for N sections folded into Trade manager read above." That claim is false for closed rows.

**Evidence:** Live production data (all 3 closed play-briefs in the snapshot) reproduces this identically: playbrief-SWING_AAPL_36_closed.json, playbrief-SWING_INTC_35_closed.json, and playbrief-SWING_MSTR_33_closed.json each render sections [Verdict, Outcome, Trade manager read, Why this setup, Chart technicals, Catalysts & news, Desk context, Data freshness, Watch levels, Lessons] — none of Lane rank/Levels on chart/GEX posture/Wall dynamics/Flow & positioning/Macro tape/Vector desk survive — and each "Trade manager read" body ends with '_Desk detail for 4 sections folded into Trade manager read above — expand via follow-up chips or Open Largo._' while the body's actual bullets are only e.g. (AAPL) '• Exited -56.2% vs peak +1.3% Round-tripped past breakeven ... Stop fired (stopped)...' — zero mention of GEX/walls/macro/flow. The same live envelope's own `levels` array (call wall 330, put wall 280, gamma flip 318.6, GEX king 330, max pain 300, all freshness: recent) proves that GEX data WAS available and would have populated a GEX posture / Levels on chart section pre-collapse, confirming real content was deleted, not merely absent upstream.

**Suggested fix:** Either (a) make collapseRedundantIntelSections actually use `bucket` — for bucket==="closed", only collapse titles that collectCoachingBullets' closed branch (closedCoaching) actually covers, which today is none of NARRATIVE_COVERED_TITLES, so closed should effectively skip the collapse entirely; or (b) extend the closed-bucket narrative to genuinely narrate the frozen-at-close GEX/wall/macro/flow context before collapsing those sections. Either way, the "folded into Trade manager read above" note should only ever be attached when the dropped content is demonstrably present in that section's body.

### 3. Swing thesis-health engine collapses to an identical 46% "Degraded" reading for every open position, regardless of actual play quality — upstream fields dead-wired post-commit

**Severity:** CRITICAL · **Category:** bug · **Subsystem:** largo-contract

**Files:** `src/lib/swing/thesis-health.ts:56-120`, `src/lib/swing/thesis-health.ts:213-268`, `src/features/nighthawk/command-deck/adapters.ts:844-861`, `src/lib/swing/play-brief.ts:38-52`, `src/features/nighthawk/command-deck/terminal-display.ts:30-38`

**What's broken:** computeSwingThesisHealth() weights five pillars (persistence 0.28, entry_geometry 0.22, flow_corroboration 0.20, regime 0.15, theta_budget 0.15) off five inputs read from the board row: setupState, entryStatus, signalKinds, regime, factors. All four LIVE committed swing rows fetched (NRG, NN, CG, CRWD) carry every one of those five fields as null in the production /horizons response, so every pillar except theta_budget falls to its 'no context' default branch (setupPersistenceScore default 0.4/0.35 'unknown', entryGeometryScore default 0.5/0.45 'n/a', signalScore empty-set 0.35/0.35 'no signals', regimeScore null-regime 0.45/0.45 'unread'). Working the weighted sum by hand with theta at its 'runway' value (0.85, true for both 12DTE and 19DTE rows here) gives 0.28*0.35+0.22*0.45+0.20*0.35+0.15*0.45+0.15*0.85 = 0.462 -> round to 46 — exactly the number every live envelope shows. The result: Ask Largo presents the SAME 'Thesis health 46% · Degraded' panel (via thesisHealthSection in play-brief.ts) and the SAME 'Thesis strength 46%' in the Verdict (via thesisStrengthPct, which just echoes play.thesisHealth.health) for CRWD — grade A+, score 87, the single best-graded play on the whole board — as for CG — grade C, score 3. A member cannot tell a genuinely strong position from a weak one via this panel; worse, the label 'Degraded' actively undersells the A+ play. This is dead-wired data precisely of the kind the standing Largo audit mandate calls out.

**Evidence:** Live /horizons committed rows (all four): setupState=None, entryStatus=None, signalKinds=None, regime=None, factors=None for NRG, NN, CG, and CRWD alike. Corresponding play-brief 'Thesis health' sections: CG '46% · Degraded' (grade C score 3); NN '46% · Degraded' (grade C score 23); NRG '46% · Degraded' (grade C score 27); CRWD '46% · Degraded' (grade A+ score 87) — byte-identical pillar labels 'unknown'/'n/a'/'no signals'/'unread' across all four (CRWD's persistence differs only because degradeFromManage() overwrote it to 'scale-out' — a live-manage-action override, not a real persistence read).

**Evidence:** route.ts lines 1-14 ("COMMITS NOTHING"); cron-registry.ts line ~213 ("WATCH-only, commits nothing"); route.ts lines 277-281 (`insertPosition: insertSwingPosition`, `promoteCommit: ...`, `insertShadowPosition: insertSwingShadowPosition`, `budget: resolveProductionPortfolioBudget()`); discovery.ts lines 619-643, 954-960 documenting that presence of `insertPosition` IS what authorizes real opens. This is a documentation-vs-reality gap on a system that risks real capital — anyone (including an audit like this one) reading either doc source would wrongly conclude the swing-discovery cron is inert/evidence-only and could under-scrutinize it or under-monitor its commit path.

### 5. manageAction freezes at TAKE_PARTIAL for the entire life of a scaled runner — Largo shows a stale/wrong management action

**Severity:** HIGH · **Category:** bug · **Subsystem:** live-mgmt

**Files:** `src/lib/swing/live-plays.ts:163-194 (manageObservablesFromEvent)`, `src/lib/swing/live-plays.ts:215-219 (livePlayFromSwingPosition call site)`

**What's broken:** livePlayFromSwingPosition seeds a fallback manageAction purely from row.status: `liveStatus === "TRIM" ? "TAKE_PARTIAL" : undefined` (line 216). manageObservablesFromEvent then only OVERWRITES that fallback when the latest manage-sync snapshot's action is literally one of "EXIT"|"STOP_OUT"|"TAKE_PARTIAL"|"EXIT_RUNNER" (lines 172-175). Once a position has scaled once (status flips to TRIM), deriveScaleOutAction (zerodte/scale-out.ts) can only ever return EXIT_RUNNER or HOLD for it (TAKE_PARTIAL requires !scaledAlready) — so on every subsequent 15-min active-refresh tick where the runner just sits above its trailing stop, manage-sync legitimately writes the honest verdict `action: "HOLD"` to the snapshot's event_json. But `HOLD` is not in the four-action allow-list, so the `if` in manageObservablesFromEvent is skipped and manageAction silently stays pinned at the row-status-derived "TAKE_PARTIAL" fallback — forever, until (if ever) EXIT_RUNNER/EXIT/STOP_OUT fires. The board and Ask Largo therefore keep telling the trader "Manage engine: TAKE_PARTIAL" (an active, new-sounding recommendation) when the engine's actual current verdict is HOLD (nothing new happening).

**Evidence:** Live production data confirms this exactly: playbrief-SWING_CRWD_19.json — entry $16.65, peak $38.25 (+129.7%), current mark $20.75 (+24.6%). Trail-from-peak level = 38.25*0.5 = $19.125; mark $20.75 is still above it, so the honest current verdict is HOLD (runner still above its trailing stop) per deriveScaleOutAction. Yet the envelope's "Management" section reads "Manage engine: **TAKE_PARTIAL**" and the raw horizons.json committed row carries `"manageAction": "TAKE_PARTIAL"` verbatim. Reproduced directly by calling livePlayFromSwingPosition with the exact CRWD row fields and a manage-snapshot event of `{rung:"hold", action:"HOLD"}` (the honest current-tick verdict): result was `manageAction: "TAKE_PARTIAL"` — confirming the code discards the fresh HOLD and falls back to the status-derived value. The three HOLD-status live rows (CG/NN/NRG) show no such stale action (they never hit the TRIM fallback branch), confirming the bug is specific to TRIM-status positions.

**Suggested fix:** manageObservablesFromEvent should also honor a fresh "HOLD"/"ADD" action from the manage snapshot (clearing/updating manageAction rather than leaving the stale fallback in place), or livePlayFromSwingPosition should stop seeding a TAKE_PARTIAL fallback from status alone and instead read the true action off the latest snapshot unconditionally (falling back to a status label like "MANAGING" rather than a specific stale action) when no fresh manage event is available.

### 6. dataHonestyCoaching's markIsSync check is inverted — every live position with a genuinely fresh, timestamped mark gets a false "mark not synced to live tape" caveat

**Severity:** HIGH · **Category:** bug · **Subsystem:** live-mgmt

**Files:** `src/lib/swing/play-brief-narrative-coaching.ts:535`, `src/features/nighthawk/command-deck/adapters.ts:928`, `src/lib/swing/play-brief-intel.ts:591,599`

**What's broken:** In the SWING/LEAPS TerminalPlay builder, `markIsSync: src.markAsOf == null` (adapters.ts:928) — i.e. markIsSync is TRUE precisely when there is NO freshness timestamp (an old-style, unknown-age sync quote), and FALSE when a real markAsOf timestamp is present (the good/fresh case). This is exactly how dataFreshnessSection (play-brief-intel.ts:589-599) reads it: `else if (play.markIsSync) { lines.push("Mark age unknown — sync quote without timestamp...") }` and `bias: play.markIsSync ? "bearish" : "neutral"` — markIsSync===true is treated as the bad/stale case there, correctly. But dataHonestyCoaching (play-brief-narrative-coaching.ts:535) checks the OPPOSITE polarity: `if (play.markIsSync === false) warnings.push("mark not synced to live tape")` — firing the warning on the GOOD case (markAsOf present) and staying silent on the actual bad case (markAsOf null, markIsSync true).

**Evidence:** All four currently-open live swing positions in the snapshot (CRWD, CG, NN, NRG) have a real markAsOf timestamp (e.g. CRWD "markAsOf": "2026-09-04T21:45:18.731Z") and each one's play-brief "Trade manager read" section carries the false caveat: "**Data caveat** — mark not synced to live tape · HELIX feed quiet..." even though the same envelope's own "Data freshness" section and "Position" section correctly show the fresh timestamp with no staleness complaint (e.g. CRWD Data freshness body is simply "Option mark as of **2026-09-04T21:45:18.731Z**" — no "mark age unknown" line). Conversely, the three CLOSED positions (AAPL/INTC/MSTR) — which genuinely have no markAsOf (markIsSync would be true) — correctly show "Mark age unknown" in Data freshness, but because they never reach dataHonestyCoaching (closed bucket short-circuits to closedCoaching), the inverted check's failure mode is masked there; the open-position sample makes the inversion unambiguous.

**Suggested fix:** Flip the condition to `if (play.markIsSync === true)` so the caveat fires when the mark genuinely has no freshness timestamp, matching the polarity already used consistently by dataFreshnessSection.

### 7. grade.ts's five-family multi-truth grader (EXECUTION/PATH/THESIS/MANAGEMENT/FINANCIAL) is fully unwired from production — every real graded position uses only the thin 'markfreeze' grade

**Severity:** HIGH · **Category:** flaw · **Subsystem:** grading

**Files:** `src/lib/swing/grade.ts`, `src/lib/swing/roll-plan.ts:82-100`, `src/lib/swing/roll.ts`, `src/lib/db.ts:7650-7684`, `docs/audit/OUTCOME-GRADING-SPEC.md:156-176`, `src/lib/horizon-outcomes.ts:23-35`

**What's broken:** grade.ts's exported `gradeSwingPosition()` (the pure, extensively-documented and unit-tested 'multi-family swing grader' that computes independent EXECUTION/PATH/THESIS/MANAGEMENT/FINANCIAL truths) is never imported or called by any production code path. The ONLY function that ever writes `grade_json`/`realized_pnl_pct` onto a real `swing_positions` row is `gradeParentFromMark` (roll-plan.ts:84-100), which computes a single number — `(mark - entry) / entry * 100` — and stamps `grade_json = {methodology: 'swing.roll.markfreeze.v1', basis, entry_premium, exit_mark, realized_pnl_pct, note}`. There is no cron, route, or admin tool anywhere in the repo that calls grade.ts's `gradeSwingPosition` against a live position (grep across src/ for imports of '@/lib/swing/grade' outside grade.ts itself and its test file returns zero production hits; cron-registry.ts lists only 'swing-discovery' and 'swing-active-refresh', neither of which is an EOD grading job). horizon-outcomes.ts even documents the gap explicitly ('a roll-time PARENT leg is frozen via the markfreeze path... whose grade_json does NOT carry the five-family SwingGrade shape... Reading grade_json.financial.scaleOutRealizedMult unconditionally would silently drop every roll-frozen leg') but treats it as a known constraint to route around rather than flagging that the referenced 'EOD multi-truth grader' does not exist as a running process. Meanwhile docs/audit/OUTCOME-GRADING-SPEC.md §6 presents grade.ts's five truths as THE swing grading methodology members/Largo see ('gradeSwingPosition... grades FIVE independent truth families... a member can read independently'), which is false for every position in the live ledger.

**Evidence:** Live proof: /tmp/.../swing-audit/record.json contains 31 roll-chains / 46+ legs; every single leg's `grade.methodology` is `'swing.roll.markfreeze.v1'` with grade keys exactly `{note, basis, exit_mark, methodology, entry_premium, realized_pnl_pct}` — none carry the `{v, subLane, direction, graderTimeframe, execution, path, thesis, management, financial}` shape grade.ts's `SwingGrade` interface defines (verified programmatically: `new Set(records.flatMap(r=>r.legs.map(l=>l.grade?.methodology)))` = `{'swing.roll.markfreeze.v1'}` only). Code trace: `grep -rn "swing/grade\"" src` and `grep -rln "import.*gradeSwingPosition" src` (excluding db.ts's differently-named persistence function and grade.ts's own test) both return no production call sites; `calibration.ts:71-72` explicitly states it 'never re-derives a grade... reads what was PINNED at commit/grade time' (i.e. realized_pnl_pct only); no UI component reads `grade_json.thesis.outcome`/`.financial.scaleOutRealizedMult`/`.execution.quality01` etc (grep across src/ for those paths outside grade.ts returns zero hits).

**Suggested fix:** Either (a) wire an actual EOD grading pass that calls grade.ts's gradeSwingPosition with real forward underlying/option bars and persists the rich SwingGrade alongside (or instead of) the markfreeze grade, delivering the differentiated EXECUTION/PATH/THESIS/MANAGEMENT/FINANCIAL truths the product docs promise, or (b) if the markfreeze-only approach is now the deliberate design, correct docs/audit/OUTCOME-GRADING-SPEC.md §6 and the in-code comments (roll-plan.ts:23-25, db.ts:1999-2000) to stop describing a 'multi-truth grader' and 'EOD grader' that doesn't run, and consider removing or clearly marking grade.ts as unused/experimental so future audits and calibration work don't build on an assumption that this data exists.

### 8. Ask Largo swing thesis-health is effectively constant across every live position — 4/5 pillars silently default because the live-position adapter never populates setupState/entryStatus/regime/signalKinds

**Severity:** HIGH · **Category:** bug · **Subsystem:** thesis-health

**Files:** `src/lib/swing/live-plays.ts:200-253`, `src/lib/swing/play-brief-resolve.ts:49-97`, `src/lib/swing/thesis-health.ts:56-108,213-260`

**What's broken:** computeSwingThesisHealth() itself (thesis-health.ts) is real, non-trivial weighted scoring logic — it is NOT a hardcoded stub. But the upstream adapter for OPEN/HOLD/TRIM (live/committed) positions never supplies the four inputs (setupState, entryStatus, regime, signalKinds) that drive Persistence, Entry geometry, Signal stack, and Regime fit — 85% of the pillar weight (0.28+0.22+0.20+0.15). `livePlayFromSwingPosition` in live-plays.ts (the function that maps an open ledger row to a HorizonPlay) returns an object (lines 230-253) that omits `setupState`, `entryStatus`, `regime`, `signalKinds`, and `factors` entirely. `horizonRowToDeckSource` in play-brief-resolve.ts then reads `p.setupState ?? null` etc (all null/undefined), and thesis-health.ts's per-pillar functions fall through to their documented generic defaults: setupPersistenceScore(undefined)->{current:0.35,label:'unknown'}, entryGeometryScore(undefined)->{current:0.45,label:'n/a'}, signalScore(undefined)->{current:0.35,label:'no signals'}, regimeScore(null,undefined)->{current:0.45,label:'unread'}. Only theta_budget (driven by DTE, which IS present) varies. Net effect: the composite 'Thesis health' score and its pillar breakdown render nearly identically for every live position regardless of the actual thesis quality, which is exactly the 'constant scaffold' symptom flagged (unanswered) on PR #4076 — confirmed still live in production as of this audit, even though the scoring function's code is real.

**Evidence:** Cross-checked all 4 currently-committed play-brief envelopes (/tmp/.../swing-audit/playbrief-SWING_{NRG_34,NN_32,CG_25,CRWD_19}.json), which have wildly different real states: NRG +98.0% P&L (HOLD), NN 0.0% P&L (HOLD), CG +33.7% P&L (HOLD), CRWD +24.6% P&L (TRIM, peak +129.7%). All four render the exact same 'Thesis health' section: **46% · Degraded**, with identical pillar labels — 'Persistence — unknown (Δ -1.0 pts)', 'Entry geometry — n/a (Δ -1.0 pts)', 'Signal stack — no signals (Δ +0.0 pts)', 'Regime fit — unread (Δ +0.0 pts)' — differing only in the DTE number embedded in the Theta budget line ('12DTE runway' / '19DTE runway'), and in CRWD's Persistence label ('scale-out'), which is a post-hoc string overwrite from degradeFromManage() based on manageAction, not real setup data. A 98%-profitable position and a flat position report the identical generic thesis-health verdict.

**25. [MEDIUM] Earnings day-count in swing-catalyst.ts uses UTC calendar date instead of the ET session day, causing a systematic off-by-one during the OVERNIGHT discovery phase**
*bug · discovery · `src/lib/swing/swing-catalyst.ts`, `src/lib/swing/swing-ingest.ts`, `src/lib/swing/scan-cadence.ts`, `src/lib/swing/v2/gates.ts`*

`parseEarningsWindows` (swing-catalyst.ts:151) computes 'today' as `new Date(asOfMs).toISOString().slice(0, 10)` — a UTC calendar date — and then diffs every earnings row's YMD against that via `daysBetweenYmd` (line 160). But the swing engine's own session day is always the ET calendar date (`todayEt()` in et-date.ts, used everywhere else — e.g. `sessionDay` in the swing-discovery route). ET is behind UTC, so for the OVERNIGHT discovery phase (20:00–24:00 ET, `scan-cadence.ts` SWING_SCAN_PHASES) the UTC calendar date has already rolled over to the NEXT day for the entire 4-hour window, every single day, in both EDT and EST (and additionally for the last ~1 hour of the PRIMARY POST_CLOSE phase during EST/winter, since POST_CLOSE 19:00–20:00 ET falls after the UTC day-roll in winter). This makes the computed 'daysUntil'/'daysAgo' one day off from the true ET-relative count for every affected scan: `earnings.nextEarnings.daysUntil` is systematically understated by 1, which inflates the pre-earnings proximity read (`preEarnings01 = clamp01(1 - daysUntil/(intendedDte+1))`, swing-catalyst.ts:239-243) for every OVERNIGHT-phase candidate, and can flip a borderline `earningsInWindow` (daysUntil<=intendedDte) from false to true at the boundary. In the specific case where a name's earnings date equals the true ET 'today', the off-by-one pushes `delta` negative, so the print is misclassified into the PAST bucket (`lastEarnings`) instead of the FUTURE bucket (`nextEarnings`) — `earningsInWindow` then reads false for a name that should be counted as having an imminent/day-of print. `earningsInWindow` is not a cosmetic field: it feeds `catalystSignal()`'s pillar discount (swing-pillars.ts), the EVENT_DRIVEN archetype's `catalystInWindow01` fit, and G-S3 in v2/gates.ts, the commit-time print-protection gate that is supposed to block a fresh COMMIT into a name reporting earnings inside the holding window.

**26. [MEDIUM] Entry-validity deadline clamp can produce a deadline already in the past**
*bug · entry-gate · `src/lib/swing/entry-model.ts`, `src/lib/swing/entry-model.test.ts`*

deriveEntryPlan()'s entry-validity deadline (entry-model.ts:97-105) computes `deadlineMs = nowMs + validityDays*DAY_MS`, then clamps it to `expMs - DAY_MS` whenever that clamp would fire before the un-clamped value — but the clamp target (`expMs - DAY_MS`) is computed purely from the contract's expiry, with no floor at `nowMs`.

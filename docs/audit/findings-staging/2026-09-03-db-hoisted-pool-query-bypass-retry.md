## 2026-09-03 — [FINDING, P2 correctness/reliability, DB] 18 functions (~30 call sites) in `db.ts` still bypassed `dbQuery`'s transient-error retry after #3407 — a second call shape the earlier sweep's own regex couldn't see — FIXED

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **What prompted this** | PR #3407 (merged earlier the same day) routed 135 raw `pool.query` call sites through `dbQuery`'s retry+backoff, specifically to stop the `[play-engine-heartbeat] ... Cannot use a pool after calling end on the pool` failure mode a pool-teardown race can trigger on any unretried query. Given the size and blast-radius of that fix, re-verified it for completeness rather than assuming full coverage — the standing "re-verify old claims" discipline. |
| **Investigation** | #3407's own fix and its regression test (`db.test.ts`'s "no stray raw pool.query" sweep) both target exactly one call shape: the chained form `(await getPool()).query(...)`, matched via the regex `/\(await getPool\(\)\)\.query/g`. Grepping `src/lib/db.ts` for every `await getPool()` call found a SECOND shape neither the fix nor its test could see: hoist the pool into a local first — `const pool = await getPool(); ... pool.query(...)` — used throughout the file, especially in multi-query/`Promise.all` functions. That form was completely untouched by #3407. |
| **Root cause** | #3407's regex is anchored on the literal `(await getPool())` parenthesization immediately followed by `.query`. A hoisted local (`const pool = await getPool();` on its own line, `pool.query(...)` several lines later) never matches that pattern — the sweep is syntactically blind to it, not logically wrong about what it does match. |
| **Scope confirmed** | 18 functions, ~30 raw `pool.query`/`p.query` call sites, all in `src/lib/db.ts`: `insertHelixSignalOutcomes`, `syncPlaybookArmedPollCounts`, `upsertPlaybookInstances`, `insertPlaybookInstanceEvents`, `fetchPlayLifecycleCounts`, `fetchSpxAdminRollups` (8 sites), `upsertZeroDteSetupLog`, `resetNullGradedZeroDteRows` (2 sites), `insertSwingShadowPosition`, `insertBieKnowledge`, `updateBieKnowledgeEmbeddings`, `upsertNighthawkPlayOutcomes`, `fetchNighthawkOutcomeAnalytics` (2 sites), `fetchNighthawkFunnelStats` (2 sites), and all four Meridian snapshot/estimate-revision read+write functions (`recordMeridianReportSnapshot`, `readMeridianReportSnapshots`, `recordMeridianEstimateRevision`, `readRecentMeridianEstimateRevisions`). Several are hot-path/user-facing — `upsertPlaybookInstances`, `upsertNighthawkPlayOutcomes`, `fetchSpxAdminRollups`, the Meridian writers — exactly the class of function #3407 targeted. |
| **Confirmed legitimate exceptions (left untouched)** | `runMigrations` (bootstrap, runs before `ensureSchema`/`dbQuery`'s schema exists — routing it through `dbQuery` would be circular); `deleteUserDataForClerkId` and `insertOpenSpxPlay` (real multi-statement `BEGIN`/`COMMIT` transactions that must stay pinned to one connection); `dbClient` (returns a raw client for the *caller* to manage a transaction with); `pingDatabaseConnectivity` (deliberately raw — `dbQuery`'s retry would mask a real outage behind a false-healthy read, defeating the health check); `getDatabasePoolStats` (reads `pool.totalCount`/`idleCount`/`waitingCount` — never calls `.query` at all); `acquireHeldLock`/`releaseHeldLock` (session-level advisory locks, which MUST stay on one held connection for their whole lifetime — the file's own comment above them explains why `pool.query()`'s random-connection-per-call semantics would silently leak the lock). |
| **Fix** | For every genuine bypass: removed the hoisted `const pool = await getPool();` / `const p = await getPool();` line and replaced each `pool.query(`/`p.query(` (plain and generic-typed `pool.query<T>(` forms) with `dbQuery(`/`dbQuery<T>(`. No SQL, parameter, or control-flow changes — purely swapping the executor, identical to #3407's own fix shape. |
| **Blast radius** | One file (`src/lib/db.ts`). No other file calls these functions differently as a result — `dbQuery`'s signature (`text, values?`) is a drop-in match for `pool.query`'s. |
| **Regression guard** | Generalized `db.test.ts`'s existing "no stray raw pool.query" sweep test (which only caught the chained shape) into a new test that ALSO scans for the hoisted-variable shape across the whole file, with an explicit, commented allowlist for the 8 legitimate exceptions above (matched by enclosing function name, with an additional automatic skip for any hoist immediately followed by `.connect()`, which is the transaction-client shape). Confirmed RED pre-fix (`git stash src/lib/db.ts`, keep the test: 1 new assertion fails, naming the first offending function) and GREEN post-fix (21/21 in `db.test.ts`). This closes the blind spot for BOTH existing code and any future function that reintroduces either bypass shape. |
| **Gates** | `npx tsc --noEmit` clean (Node 20.20.2). Full `npm test`: 11942 passed / 5 failed / 2 skipped — the 5 failures are the documented sandbox-only artifact (`zerodte-service`/board-convergence tests hitting `getaddrinfo ENOTFOUND postgres.railway.internal` / `Connection terminated due to connection timeout` — no real Postgres reachable from this sandbox; CLAUDE.md's own environment-realities section documents this does not reproduce on GitHub Actions `verify`), confirmed unrelated to this change (same 5 failures, same error signatures, present before this fix touched any file). |

| **What this closes** | The same-day chain of `get_market_oi_change`/`get_screener`/`get_group_greek_flow`/`get_platform_snapshot`/`get_earnings` truncation fixes (#3155 → #3159 → #3162 → #3166 → #3171, plus this session's `2026-08-29-largo-truncation-*` findings-staging entries). Each round's live `largo-truncation-probe.mjs` re-check kept reporting `TRUNCATED` even after #3166's `fitRowsToBudget` and #3171's `fitEnvelopeToBudget` — both of which measure actual serialized bytes at runtime and should be nearly impossible to still overflow. That was the genuine mystery this entry resolves. |
| **The resolution** | The app logs the exact outcome of every transport-cap check server-side: `tool-guard.ts`'s size check fires a `[largo] tools: N calls, Xms total, K TRUNCATED — <tool> Xms TRUNCATED <bytes>/16000` line whenever `raw.length > MAX_TOOL_RESULT_CHARS` actually happens, and a plain `[largo] tools: N calls, Xms total — <tool> Xms` line (no `TRUNCATED` suffix, no byte count) when it doesn't. Pulled these directly from CloudWatch (`/ecs/blackout-production`) for the exact timestamps of a fresh probe run (2026-08-30 00:11-00:12 UTC, well after #3171's deploy fully settled — ECS confirmed single PRIMARY deployment, image tag matching the post-#3171 commit, running==desired): **all five tools' log lines show NO `TRUNCATED` suffix and no over-cap byte count.** The transport genuinely did not cut any of them. Compare to the CONTROL tool (`get_zerodte_rejections`) in the same window, which logged `TRUNCATED 568995/16000` and `TRUNCATED 273719/16000` — a real, large, expected truncation, proving the log line itself is a reliable ground truth and the absence of it for the five fitted tools is meaningful, not an artifact of under-logging. |
| **So why did the probe keep saying TRUNCATED?** | The probe asks the model one question ("does the raw tool result end with `…[truncated]`?") and trusts the model's self-report. #3173 (landed mid-investigation, credited to a Cursor agent) diagnosed and partially fixed one real ambiguity: the fitted objects this whole fix chain produces legitimately carry boolean fields literally named `truncated`, `rows_truncated`, `related_news_truncated` (the "this is a sample, not the universe" honesty signal this repo's fitting functions are built around) — and the model was answering TRUNCATED on seeing those words appear in the JSON, not on seeing the real `…[truncated]` transport marker. #3173 added an explicit disambiguation clause to the probe question. **Re-tested after that fix was in place (2026-08-30 00:11 UTC): the model STILL answered TRUNCATED for 3 of 5 tools**, and named `truncated` as the "last visible key" each time — i.e. the disambiguation instruction did not fully overcome the model's tendency to key off that literal word appearing in its own tool result, even with explicit "this doesn't count" guidance right next to it. The server logs from the SAME calls prove definitively that no transport cut occurred. |
| **Why the server log is the right instrument here and the LLM-judge probe was not, for this specific class of false positive** | The probe's entire design (documented in its own header) relies on the model being a reliable enough judge of "did I see the cut marker" that a CONTROL case can validate the run. That premise holds for genuine over-cap payloads (the control fires correctly, every time, all day). It breaks specifically when the payload's own honest legitimate content contains the literal substring the model is asked to detect — a case this fix chain itself created, by design, only today. The server-side log doesn't have this ambiguity: it's a direct `raw.length > MAX_TOOL_RESULT_CHARS` comparison with no model in the loop. |
| **Recommended follow-up for the probe (not fixed here — audit tooling, not product code, and this exact file has had multiple concurrent editors today)** | The instructional disambiguation in #3173 was a reasonable first attempt but is demonstrably insufficient on its own. Two independent, stronger fixes, either of which would remove the ambiguity at the root instead of instructing around it: (1) rename the fitting functions' honesty-flag fields to avoid the bare substring "truncated" (e.g. `sample_capped`/`rows_capped`/`is_sample` instead of `truncated`/`rows_truncated`) — the fields' meaning is unchanged, only the literal word that collides with the probe's question goes away; (2) have the probe cross-check against the server log directly (as this entry did manually) rather than trusting the model's self-report alone, at least for tools known to carry a `truncated`-shaped field — CloudWatch access is not available to every session, so this would need to be optional/best-effort. |

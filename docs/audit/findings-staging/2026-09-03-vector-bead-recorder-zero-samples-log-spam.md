## 2026-09-03 — [FINDING, P3 performance/observability, Vector] `vector-bead-recorder`'s "zero samples recorded" warning fired 100+ times in 30 minutes during RTH, unrate-limited — redundant echo of an already-alarmed condition, not a distinct fault — FIXED

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **What prompted this** | A live CloudWatch sweep (`/ecs/blackout-production`, last 30 min, during RTH) turned up `[vector-bead-recorder] zero samples recorded (0/N failed, Xms)` firing over 100 times in the window — high enough volume to investigate before assuming it was either a real bug or pure noise, per the standing "measure before guessing" discipline. |
| **Investigation** | Confirmed live against the same log streams: the "zero samples" warn and a genuine successful sweep (`19-20/20` tickers recorded, ~8s elapsed) both come from the same shard-leader, seconds apart. The zero-samples instances all had near-instant elapsed times (1-17ms) and `0/N failed` — meaning every attempted ticker landed in the `busy` skip bucket (`VectorBeadRecordResult.busy`: "Skipped because the previous record is still running. Expected self-throttling, not a fault"), not a real failure. Only one genuine per-ticker `DARK` event fired in the whole 60-minute sample. The wall-history rail was NOT going dark — it kept recording, just at the degraded ~8-10s cadence the sibling `SWEEP OVER BUDGET` line (rate-limited, `evaluateSweepBudget`) already alarms on. |
| **Root cause** | `vector-bead-recorder-leader.ts`'s zero-samples warn (`result.total > 0 && result.recorded === 0`) had NO rate limit, unlike its sibling `SWEEP OVER BUDGET` alarm one block below it, which already uses a `{lastLoggedAt}`-gated 60s rate limit (`evaluateSweepBudget`) for the exact same underlying condition (a shard's real sweep running longer than its 5s tick budget). A tick that lands mid-overrun finds every ticker in the shared universe already `busy`, returns almost instantly with nothing new recorded, and fires the unconditional warn — so one slow 8s sweep produces not just the one rate-limited "SWEEP OVER BUDGET" line but also 1-2 additional, unlimited "zero samples" lines per overrun, at whatever rate the 5s tick timer re-fires while the sweep is still running. The identical shape exists in the sibling active-viewer lane (`recordActiveNonUniverseWallSamples`'s own zero-samples warn, same file). |
| **Why this matters even though nothing was broken** | High-volume, non-actionable warn-level noise on a hot path buries genuinely rare signals (the one `DARK` event, real `failed > 0` passes) in the same log stream, and adds needless CloudWatch ingestion volume for a condition the codebase already alarms on elsewhere. Not a correctness bug — the rail kept recording — but a real log-hygiene defect worth fixing directly, same "measure, then fix small and self-contained" bar as this session's other perf/infra fixes. |
| **Fix** | Added `shouldLogZeroSamples(failed, nowMs, state)` to `vector-bead-recorder-logic.ts`, mirroring `evaluateSweepBudget`'s existing `{lastLoggedAt}` rate-limit pattern: a genuine failure (`failed > 0`) is **never** rate-limited — that's new information every time, the same rule `trackTickerFailures` already applies per-ticker — but a pure all-busy zero-samples pass (`failed === 0`) is capped at one log line per 60s. Wired into both call sites in `vector-bead-recorder-leader.ts` (universe lane and active lane), each with its own rate-limit state to keep the two lanes' log cadences independently honest, matching the file's existing "kept SEPARATE" convention for per-lane state. |
| **Blast radius** | Two files. No behavior change to the recorder itself — sample recording, busy/deferred skip logic, and the `SWEEP OVER BUDGET`/`DARK` alarms are all untouched. Only the zero-samples warn's log frequency changes. |
| **Regression guard** | `vector-bead-recorder-logic.test.ts`: 3 new tests on `shouldLogZeroSamples` — a genuine failure is never rate-limited; an all-busy pass logs once then goes quiet for 60s, then fires again a minute later; switching from a real failure to an all-busy pass starts its own independent 60s window. `vector-bead-recorder-leader.test.ts` (new file): 3 source-text tests confirming both call sites are actually wired through the gate with their own separate state variables. Confirmed RED pre-fix (`git stash` both source files, keep the tests: 6/18 fail — exactly the new assertions) and GREEN post-fix (18/18). |
| **Gates** | `npx tsc --noEmit` clean (Node 20.20.2). Full `npm test`: 11919 passed / 0 failed / 2 skipped. |

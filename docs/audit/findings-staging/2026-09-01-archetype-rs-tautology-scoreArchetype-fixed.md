## 2026-09-01 — [P1, 0DTE thesis-first] archetype.ts RS-tautology zeroed MOMENTUM_CONTINUATION/FLOW_FOLLOWING scoring — FIXED

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **Context** | Surfaced by all three adversarial reviews of the `nighthawk-0dte-redesign` workflow's evidence-bus rebuild synthesis, as a live bug already present in the codebase — separate from the already-fixed `momentum_rs_floor` tautology in `archetype-gates.ts` (task list #56). |
| **Root cause** | `archetype.ts`'s `RULES` table listed `RS` as a **core rail** for both `FLOW_FOLLOWING` (`core: ["FLOW", "RS"]`) and `MOMENTUM_CONTINUATION` (`core: ["MOMENTUM", "RS"]`). `scoreArchetype()` refuses to score a rule at all unless every listed core rail is present: `const present = rule.core.filter((r) => scores[r] != null); if (present.length < Math.min(2, rule.core.length)) return 0;`. `RS` (`rails/rs.ts`'s `scoreRsRail`) only ever returns a hit once its own internal score already clears 55 — and in production it never fires at all, because `legacyBridgeExtrasFromSetup`/`thesisEvidenceToLegacyExtras` never populate the session-% inputs the rail needs (`stock_session_pct`/`qqq_session_pct`/`sector_session_pct`/`d10_alpha`). So `scores.RS` is null on effectively every real setup, `present.length` for these two rules can never reach 2, and `scoreArchetype` returned **0 for MOMENTUM_CONTINUATION and FLOW_FOLLOWING on almost every real setup — regardless of how strong FLOW or MOMENTUM actually was.** This is the exact same tautology already fixed one layer down in `archetype-gates.ts`'s gate (`momentum_rs_floor`), recurring one layer up in the scoring function that feeds `classifyTradeArchetype`. |
| **Evidence** | `classifyTradeArchetype({ MOMENTUM: 85, BREAKOUT: 61 }, null)` — a setup where MOMENTUM is clearly the dominant, strong signal — pre-fix returned `archetype: "BREAKOUT"` (BREAKOUT's own two-rail average of 73 was the only nonzero RULES score, since MOMENTUM_CONTINUATION always scored 0), silently misclassifying a genuinely strong momentum setup as a weaker breakout read. Post-fix it correctly returns `archetype: "MOMENTUM_CONTINUATION", confidence: 85`. Separately, `classifyTradeArchetype({ MOMENTUM: 30 }, null)` pre-fix fell through to the confidence-0 fallback path (`fallbackScore = scores[fallbackRail]`, no `minCoreAvg` check at all) and returned `archetype: "MOMENTUM_CONTINUATION", confidence: 30` — the RIGHT label by accident, but via a path that bypasses the intended 65-floor gating entirely, meaning even a genuinely weak MOMENTUM read (well below the 65 bar the rule's author intended) could still get classified with a nonzero confidence. 4 of the 8 new regression tests in `archetype.test.ts` were confirmed to FAIL against the pre-fix code (verified by `git stash` before fixing and re-running), proving these are real regressions, not tautological passes. |
| **Fix** | Removed `RS` from `core` for `FLOW_FOLLOWING` and `MOMENTUM_CONTINUATION` in `archetype.ts`'s `RULES` table — mirroring the exact precedent already shipped in `archetype-gates.ts`'s `MOMENTUM_CONTINUATION`/`FLOW_FOLLOWING` cases ("Removed rather than gated: there is currently no way to tell 'RS fetched and weak' from 'RS never fetched'"). `minCoreAvg` (65 for both) was left unchanged — since RS-inclusion never actually contributed a nonzero score in production anyway, the effective bar these two archetypes must clear is unchanged from what the original two-rail-average design intended, just no longer gated behind an unsatisfiable presence check. |
| **What was deliberately NOT changed** | The `minCoreAvg` thresholds themselves (65 for both) — not recalibrated, since that would be a separate, evidence-driven design decision, not a bug fix. All six other archetypes' `core` lists (`BREAKOUT`, `MEAN_REVERSION`, `GAMMA_BREAK`, `CATALYST_CONTINUATION`, `FAILED_BREAKOUT`, `VOL_EXPANSION`) — none list `RS` as a core rail, so none were affected by or need this fix. `archetype-gates.ts`'s own already-shipped fix — untouched, this PR fixes the scoring-layer sibling of that bug, not the gate itself. `rails/rs.ts`'s `scoreRsRail` itself, and the missing session-% input wiring in `legacyBridgeExtrasFromSetup`/`thesisEvidenceToLegacyExtras` that causes RS to never fire in the first place — that is the deeper root cause of BOTH tautologies (this one and the already-fixed gate one) and is a larger, separate fix (wiring real session-% data into the legacy bridge) left for a dedicated follow-up. |
| **Blast radius checked** | `RULES`/`ArchetypeRule` are private to `archetype.ts` — no external importers (confirmed via whole-repo grep). `classifyTradeArchetype`/`scoreForArchetype` are called from exactly one place, `pipeline.ts`'s `buildMergedThesisFromHits` — read end-to-end, confirmed `archetype_score: Math.max(archetype_score, match.confidence)` correctly now reflects a real RULES-scored value for these two archetypes instead of always taking the fallback path's cruder number. |

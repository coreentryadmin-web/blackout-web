## 2026-09-04 — [BUG, P1 member-facing] Vector's own GEX wall computation served call/put walls on the wrong side of spot — the exact bug class PR #2417 fixed elsewhere was never applied to computeGexWalls

> **kind:** FINDING

| Field | Value |
|-------|-------|
| **Status** | FIXED |
| **Found by** | Parallel live-production audit workflow, 2026-09-04 (Vector desk / GEX heatmap area), independently verified by 2 adversarial refuters — confirmed |
| **Evidence** | Live authenticated requests against production, 2026-09-04 (temp Clerk premium+admin session, deleted after): `GET /api/market/vector/walls?ticker=IBIT&dte=0dte\|weekly\|monthly\|all` — spot=46.06 — every single horizon returned `callWalls[0].strike=46` (46.00 < 46.06 spot), a "call wall / resistance" priced BELOW current spot on all four toggle positions a member can select. `GET /api/market/vector/walls?ticker=NDX&dte=weekly` → put wall 29600 vs spot 29482.32 (118pts ABOVE spot); `dte=all` → `callWalls[0]=29275` (below spot) AND `putWalls[0]=29600` (above spot) SIMULTANEOUSLY in one payload. `GET /api/market/vector/universe` — programmatic scan of all 83 rows found 17-18 with `topCallWall < spot` or `topPutWall > spot`, including the flagship `SPX: spot 7747.71, topPutWall 8000`. The SAME matrix's own `gex.put_wall` field (canonical, `GET /api/market/gex-heatmap?ticker=SPX`) reads 7500 (correctly constrained below spot) at the identical instant — proving the canonical route was already fixed and Vector's own wall surfaces were not. |
| **Root cause** | `computeGexWalls()` (`src/lib/providers/gex-wall-levels.ts`) ranks strikes into callWalls/putWalls purely by the SIGN of net gamma (positive→call bucket, negative→put bucket) and by share of total \|gamma\|, with no spot parameter and no constraint that a callWalls entry sit at/above spot or a putWalls entry at/below it. Its sibling, `wallsFromStrikeTotals(strikeTotals, spot)` in `gex-cross-validation-core.ts`, DOES enforce that constraint, and PR #2417 (2026-08-20) migrated five separate wall-serving producers onto the constrained function — but explicitly left `computeGexWalls` untouched, reasoning its callers "read the SAME live WS ladder independently." Those callers ARE the Vector desk's own primary GEX-lens wall surfaces: `vector-dte-walls-core.ts`'s `perExpiryWallsFromContracts` (feeds `GET /api/market/vector/walls`, the chart's own DTE-toggle overlay), `vector-universe.ts`'s `buildVectorUniverseRow` (feeds the Scanner table, Largo's `vector-analytics.ts` tool, x-content), `vector-snapshot.ts`'s `getVectorGexWalls`/`getVectorGexWallsForHorizon` (SSE/SSR feed + DTE-horizon overlay), `vector-gex-reconstruct.ts`'s `reconstructGexRail` (historical wall-history rail, also read by Night Hawk Cortex's `wall-trend.ts` source via the persisted samples), and the zerodte PIN engine's `pin-temporal-stability.ts`/`pin-discovery.ts`. The fix landed on the canonical matrix but never propagated to the much larger set of call sites that constitute the Vector desk's own wall computation. |
| **Fix** | Added an optional `spot` parameter to `computeGexWalls(ladder, { maxPerSide, spot })` that applies the IDENTICAL side-constraint `wallsFromStrikeTotals` already uses (callWalls entry must have `strike > spot`, putWalls entry `strike < spot`; no fallback to the wrong side — an unqualified side returns empty, never a fabricated wrong-side pick). Omitting `spot` preserves the exact prior unconstrained behavior byte-for-byte, which matters because the VEX/vanna lens reuses this same function and has NO inherent above/below-spot geometry (documented in the file's own NAMING comment) — the VEX call sites were deliberately left unconstrained. Threaded `spot` through every GEX-lens call site that had it readily available: `vector-dte-walls-core.ts` (already a parameter), `vector-universe.ts` (already fetched, GEX call only — VEX call untouched), `vector-gex-reconstruct.ts` (already destructured per sample), `pin-temporal-stability.ts`/`pin-discovery.ts` (already in scope). `vector-snapshot.ts` needed a small state addition — a `fallbackSpot` field on the per-ticker in-memory state, populated from the same `fetchGexHeatmap` call that already populates `fallbackStrikeTotals` (same staleness tolerance as the existing fallback data) — since neither the WS-ladder branch nor the REST-fallback branch of `getVectorGexWalls` previously tracked spot at all. |
| **Blast radius** | 7 files changed (1 core function + 6 callers). Two files named in the original finding's file list needed NO code change: `rail-levels.ts` and `wall-trend.ts` don't call `computeGexWalls` directly — they only render/consume already-computed levels, so both inherit the fix transitively once their upstream producers (`vector-snapshot.ts`, `vector-gex-reconstruct.ts`) are fixed. `pin-discovery.ts`'s use was already safe against the inversion itself (`.find(w => w.strike === pos.call_wall)` on an already-canonically-constrained strike, not `.callWalls[0]`) but was updated anyway for defense-in-depth/consistency, since `pos.spot` was trivially in scope. `pin-temporal-stability.ts` is currently DEFAULT-OFF (`PIN_TEMPORAL_STABILITY` env flag, per INTENTIONAL-DESIGN.md item #3) but was fixed on the same principle — a two-line change with spot already in scope, closing the same bug class before the flag is ever turned on. VEX/vanna lens call sites (`vector-universe.ts`'s `vexWalls`, `vector-snapshot.ts`'s `cachedVexWalls` in two places) were deliberately left unconstrained — passing spot there would be a NEW bug, not a fix, per the file's own documented lens-agnostic design. |

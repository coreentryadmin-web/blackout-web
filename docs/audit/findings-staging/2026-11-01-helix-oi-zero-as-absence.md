## HELIX live tape — `fmtOi` rendered a genuine 0 open-interest reading as absent data, contradicting the same row's own "NEW" badge

| | |
|---|---|
| **Area** | Helix (`src/features/helix/lib/helix-flow-format.ts`) |
| **Status** | FIXED |
| **Severity** | P3 (data-correctness, member-facing UI) |

### Root cause

`fmtOi` formats the HELIX live-tape's **OI** (open interest) cell from `flow.open_interest`, the
count of contracts currently outstanding on a strike. The guard was:

```ts
if (n == null || !Number.isFinite(n) || n <= 0) return "—";
```

`n <= 0` folds a genuine `open_interest === 0` reading into the same `"—"` no-data glyph used for a
print that never reported OI at all. `open_interest === 0` is not an edge case — it is the single
most informative value the field can report: every contract traded on that strike is necessarily
new, because none existed beforehand to close.

This is the identical bug shape #7248 fixed for `fmtAskPct` (same file, `ask_pct`), and the same
file already carries, one line away, a reader of this exact field that gets it right:
`helix-position-intent.ts`'s `positionIntent` absence check is
`open_interest == null || !Number.isFinite(oi) || oi < 0` — `oi === 0` falls straight through to a
real verdict: `{ intent: "opening", basis: "no_open_interest", openInterest: 0 }`. That verdict
drives `openingBadgeLabel` → a `"NEW"` badge whose tooltip (`positionIntentTitle`) states the fact
outright: *"New positioning: N contracts traded on a strike with no open interest — every lot is
newly opened."*

`HelixFlowTable.tsx` builds both the `signals` badges (including this "NEW" badge) and the `oi`
cell text from the **same `flow` object, in the same row** (`vRow.index` → one `flow`, passed to
both `flowSignals(flow, ctx)` for the signals column and `fmtOi(flow.open_interest)` for the OI
column). So for a real 0-OI print, the row rendered a gold "NEW" badge whose hover text explicitly
asserts "no open interest" right beside an OI cell reading "—" — the exact same cell's own
underlying field claiming, in the same row, both "this value is known and is 0" and "this value was
never reported." A member (or Largo reading the tape) has no way to reconcile the two from the
rendered text alone.

### Evidence

`fmtOi(0)` returned `"—"` before the fix. New RED tests
(`src/features/helix/lib/helix-flow-format.test.ts`) asserted `fmtOi(0) === "0"` and failed pre-fix
(1 failing / 30 passing in that file — confirmed via `git stash` on just the fix file). After the
fix, all 31 tests in the file pass, including the new negative/non-finite tests
(`fmtOi(null)`/`fmtOi(undefined)`/`fmtOi(-1)`/`fmtOi(NaN)`/`fmtOi(Infinity)` still render `"—"`) and
the abbreviation tests (`fmtOi(12_345) === "12.3K"`, `fmtOi(2_500_000) === "2.5M"`).

`tsc --noEmit` clean. `helix-position-intent.test.ts` (9/9) re-run clean — untouched, confirms the
contradiction traced above rather than any regression in that file.

### Blast radius

`fmtOi` (the exported one in `helix-flow-format.ts`) has two call sites repo-wide:
`HelixFlowTable.tsx`'s `oi` tape column and `ContractDrilldownDrawer.tsx`'s "Open int." stat — both
fixed by this one change, since both call the same function. A same-named but unrelated local
`fmtOi` in `src/features/nighthawk/lib/option-chain-prompt.ts` (a different file, different
signature — takes `number`, not `number | null | undefined`, formats Night Hawk's option-chain
prompt text) was checked and is out of scope: it is a separate function entirely, not a sibling
instance of this bug, and Night Hawk is excluded from this audit lane regardless.

### Fix rationale

Narrowed `n <= 0` to `n < 0`, mirroring #7248's `fmtAskPct` fix exactly. `open_interest`'s
documented range is `>= 0` (a non-negative contract count), so negative stays invalid/out-of-range
(defensive, unchanged — OI cannot legitimately be negative), while 0 and every positive count now
render their real value. No behavior changes for any `open_interest` value other than exactly `0`.

## 2026-08-31 — [FINDING, P2 reliability] `resetPoolForRetry()` tears down the shared DB pool out from under concurrent unrelated queries, turning one transient blip into a cascading multi-subsystem failure — OPEN, write-up only

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **What prompted this** | Hourly DISCOVERY CloudWatch sweep (`/ecs/blackout-production`, trailing 60min, 2026-08-31 ~12:20 UTC). No ECS deploy was in flight at the time (`describe_services` showed the last deployment completed 12h earlier, at 00:26:56 UTC, steady state since 06:27) — so this was not deploy-time pool churn, it was a genuine live-traffic DB blip. |
| **The data** | Within a **17-second window** (12:20:52–12:21:09 UTC) five *unrelated* subsystems all logged DB failures at once: `[spx-play-store] hydrateSessionCountersFromDb failed`, `[rth-warm-leader] tick error`, `[cron/flow-ingest]`, `[cron-run/flow-ingest] log failed`, `[cron-run/uw-cache-refresh] log failed`, `[api-telemetry-persist]`, and `[error-sink] persist failed`. Two distinct error signatures appear interleaved: `timeout exceeded when trying to connect` (the real, transient underlying failure — most likely an RDS/PgBouncer blip, self-resolved: **zero** DB errors in the following 14 minutes) and `Cannot use a pool after calling end on the pool` (a `pg`-library error thrown when `.query()`/`.connect()` is called on a `Pool` instance after `.end()` has already been invoked on it — this is not a database-side error at all, it's a client-side use-after-teardown). One line, `[db] query failed while already reporting a failure — DB likely fully down`, reads like a full-outage signal but is explained below as a symptom of the race, not evidence the DB was actually down. |
| **Root cause** | `src/lib/db.ts`. `pool`/`poolInit` (line ~10-ish, module scope) are a **process-wide singleton** shared by every `dbQuery()` caller. `dbQuery()` (line 2409) retries up to `PG_QUERY_RETRIES` (default 3) on a transient error, and on each retryable failure calls `resetPoolForRetry()` (line 2358): `await pool.end(); pool = null; poolInit = null;` — unconditionally, with **no coordination with other in-flight callers**. Sequence that produces the burst: (1) request A calls `dbQuery`, `getPool()` returns the current pool `P1`; (2) request B (a different subsystem, e.g. `error-sink`) concurrently also holds/awaits `P1` from an earlier `getPool()` call; (3) A's query on `P1` genuinely times out (real PgBouncer/RDS blip) → A's catch block calls `resetPoolForRetry()`, which calls `P1.end()` and nulls the module-level `pool`; (4) B, which was about to (or is mid-flight) call `.query()`/`.connect()` on the SAME `P1` object, now hits `Cannot use a pool after calling end on the pool` — a synchronous client-side throw, not a PG connection error, so `isTransientPgError(err)` (in `src/lib/db-transient.ts`) almost certainly returns `false` for it, meaning B gets **zero retries** and fails immediately, purely because A's unrelated retry logic reached in and killed the pool B was using. This is a classic shared-mutable-singleton teardown race, not a database outage — the DB itself recovered within the same second (see the interleaved fresh `timeout exceeded` lines from *other* callers that DID get a legitimate retry against a freshly-recreated pool). |
| **Why this shipped clean** | The retry+reset logic was added deliberately and for a real reason — PR (Cursor, 2026-07-02, `fcd6e4b6f`) `fix(db): retry transient PgBouncer errors in dbQuery`, written to stop a *single* cron's `server_login_retry` blips from being amplified into failed `cron_job_runs` rows (ops issue #242). That fix is correct for the case it targeted: one caller, one query, no concurrency. It was never evaluated against the case where **multiple unrelated subsystems share the same pool at the same instant** (which is the normal steady-state of this app — cron jobs, `error-sink`, telemetry, and request handlers all call `dbQuery` concurrently), where tearing down the *entire shared pool* to recover *one* caller's connection collaterally kills every other caller's in-flight or about-to-start query on that same pool object. |
| **Blast radius** | `dbQuery()` is the single low-level entry point for `src/lib/db.ts`, used across ~74 call sites in ~32 files (per the file's own `reportQueryFailure` comment) — every cron, the error-capture path itself (`error-sink.ts` → `captureError` → `dbQuery`, which is why `error-sink` shows up as a VICTIM in this exact burst — a doubly bad outcome, since it means the error-reporting pipeline can itself be knocked out by the same race it's trying to record), telemetry persistence, session/position stores, etc. Any transient PgBouncer/RDS blip that happens to coincide with concurrent traffic from more than one subsystem (i.e. almost any blip during market hours) will reproduce this fan-out. |
| **Why not fixed directly this cycle** | This is exactly the kind of change the standing DISCOVERY-lane policy reserves for a write-up rather than a unilateral fix: it's the single most shared, most business-critical module in the codebase (every DB read/write in the app funnels through `dbQuery`), the correct concurrency-safe fix requires a real design decision (see below) rather than a one-line patch, and validating it needs realistic concurrent load that this sandbox cannot safely generate against production. Getting this subtly wrong (e.g. removing the pool-reset recovery path entirely, which exists for a real, previously-fixed incident) risks trading a rare cascading-burst failure mode for a return of the *original* problem (a genuinely dead pool never getting recreated). |
| **Suggested fix direction** | The core issue is "any one caller can unilaterally end a pool other callers still hold a reference to." Two independent, complementary changes suggest themselves for whoever owns `src/lib/db.ts`: (1) **Guard the reset with pool identity** — capture the specific `Pool` instance each `dbQuery` attempt is operating on (`const p = await getPool();`), and in `resetPoolForRetry(p)` only end + null the module-level `pool` if `pool === p` (i.e., nobody else has already replaced it) — this alone prevents *compounding* resets/double-`.end()` calls when multiple callers fail on the same dead pool near-simultaneously, though it does not by itself protect a caller who is mid-flight on `p` at the exact moment another caller decides `p` is dead. (2) **Don't synchronously kill a pool other holders may still be using** — e.g. only call `.end()` after a short grace/quiescence window, or track a "generation" counter so `getPool()` calls that raced against a reset transparently get handed the new pool instead of the stale reference, and any caller that still ends up with a stale reference treats `Cannot use a pool after calling end on the pool` as a transient/retryable condition in `isTransientPgError` rather than a terminal one (this specific fix is the cheapest one and doesn't touch pool lifecycle semantics at all — it just stops the error from being fatal to the *victim* caller). Whichever direction is chosen, a regression test can reproduce this deterministically with a fake/mock `Pool` (two overlapping `dbQuery` calls against a stub that fails-then-recovers, asserting the second caller retries successfully instead of throwing the synthetic teardown error). |
| **Status** | OPEN — flagged for whoever owns `src/lib/db.ts` / core infra reliability; no code change made this cycle |

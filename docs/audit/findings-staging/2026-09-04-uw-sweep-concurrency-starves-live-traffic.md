## 2026-09-04 — [PERF, P1 platform-wide] Background UW sweeps monopolize the shared cluster-wide concurrency ceiling, starving live member requests during RTH

> **kind:** FINDING

| Field | Value |
|-------|-------|
| **Status** | FIXED |
| **Evidence** | Live CloudWatch (2026-09-03 RTH, `AWS/ApplicationELB` on `blackout-production-app`'s target group): `TargetResponseTime` read **Max ~115-119s** (repeatedly within ~4s of the ALB's 120s idle timeout) and **p99 11-39s** across at least 8 separate 5-minute windows in one session (13:45, 14:00, 14:10, 15:15, 16:40, 18:30, 18:45, 19:10 UTC), while p50 stayed a healthy 0.2-0.5s the whole time — the classic tail-latency signature (one saturating background job, not a fleet-capacity problem; per this file's own standing audit-mandate guidance). Cross-referencing `elapsed=` in `/ecs/blackout-production` CloudWatch Logs for those exact windows found four crons each running 90-286s per invocation with `budgetHit=true` (i.e. **no cron-overlap** — a single, non-overlapping run): `vector-dark-pool-warm` 286328ms/160405ms, `vector-pick-sweep` 169393ms/150666ms, `vector-full-state-snapshot` 133578ms/116319ms/90026ms, `bie-full-state-snapshot` 71992ms/68870ms/61251ms. |
| **Root cause** | All four crons sweep the whole Vector universe (55-84 tickers) through the SAME cluster-wide Unusual Whales rate limiter (`uw-rate-limiter.ts`) live member requests (dark-pool tape, flow, desk refresh) also depend on — `UW_GLOBAL_MAX_CONCURRENCY` defaults to just **2** slots, cluster-wide. Each of these crons already carries an overlap guard (`sharedCacheSetNx`) that correctly stops a SECOND instance of the SAME cron from running concurrently (shipped in three separate prior fixes, all citing this identical ALB-tail-latency symptom — see the block comments already in `vector-full-state-snapshot/route.ts` lines 32-46 and `vector-pick-sweep/route.ts` lines 12-36, both independently measuring the same phenomenon on 2026-09-01/09-02). But an overlap guard only prevents a second run of the *same* cron — it does nothing about a *single* run occupying both of the only 2 global concurrency slots continuously for up to ~5 minutes, evenly racing a live member's request for the same slots the whole time. `uw-hunt-budget.ts` already solves the analogous problem for Night Hawk hunts (a per-hunt live-call budget via `AsyncLocalStorage`) but its own header explicitly EXEMPTS crons from that gate on the stated assumption they run "off-peak, trusted, they ARE the warmers" — an assumption that does not hold for these four crons, which are scheduled to run continuously *throughout* RTH by design (`vector-full-state-snapshot`'s own header: "Every RTH tick..."), i.e. exactly when live traffic is also heaviest. |
| **Fix** | Added `runWithBackgroundUwSweep()` to `src/lib/providers/uw-rate-limiter.ts` — an `AsyncLocalStorage`-scoped context (same mechanism as the existing hunt-budget, chosen because these crons call many layers deep into shared library code — `computeVectorFullState`, `buildBieFullState`, `warmVectorDarkPool` — that cannot practically be threaded with an explicit flag). While active, `reserveForLiveTraffic()` reduces the caller's view of the UW concurrency ceiling by exactly one slot (floor 1) on BOTH admission paths: the cluster-wide Redis semaphore (`acquireGlobalRedisConcurrencySlot`, the real ceiling whenever Redis is up) and the per-replica local fallback (`effectiveMaxConcurrency`, the only ceiling when Redis is down). Both tagged and untagged callers still increment/decrement the SAME shared Redis counter — only the *limit* a tagged caller compares its own admission against changes — so live/foreground traffic (which always checks the FULL ceiling) is completely unaffected and can still fill every slot; a tagged sweep simply can never claim the *last* slot for itself, guaranteeing at least one slot stays reachable for live traffic even mid-sweep. Wired into all four identified crons' background dispatch (`vector-full-state-snapshot`, `vector-dark-pool-warm`, `bie-full-state-snapshot`, `vector-pick-sweep`) by wrapping their existing `runXxx(started)` background function in `runWithBackgroundUwSweep(() => runXxx(started))` at the `after()` dispatch site — no change to any internal logic, no threading through library call graphs. |
| **Blast radius** | Only the 4 named crons' background dispatch closures changed call sites; the shared rate limiter's default (untagged) behavior is byte-identical for every other caller (live desk, other crons, Night Hawk hunts) — verified by the new isolation test proving a concurrent untagged call sees the full, unreduced ceiling regardless of a tagged sweep running alongside it. Did not touch Polygon's rate limiter (`polygon-rate-limiter.ts`, separately PERMISSIVE at 150rps/48-concurrency — not the measured bottleneck) nor the existing overlap guards (kept as-is; they solve a different problem — same-cron double-invocation — and remain necessary). |
| **Deliberately left unchanged** | Did not raise `UW_GLOBAL_MAX_CONCURRENCY` itself (that is the real upstream UW Advanced ceiling, not ours to raise) and did not add a total-call budget cap (unlike the hunt case, these crons legitimately need hundreds of calls to complete a full universe sweep — a small cap like the hunt's default 12 would gut data completeness for no benefit, since the actual measured mechanism is simultaneous slot *occupancy*, not total call *count*). |
| **Tests** | `src/lib/providers/uw-rate-limiter.test.ts` — 4 new tests: the reservation is a no-op outside the tagged context; it reserves exactly one slot inside it (at both a 2- and 3-slot ceiling); it never floors below 1; and — the critical correctness property — a concurrent UNTAGGED call running alongside a tagged one still sees the FULL ceiling (AsyncLocalStorage isolation, proving live traffic is genuinely unaffected).

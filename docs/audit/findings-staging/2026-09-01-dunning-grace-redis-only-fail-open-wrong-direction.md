## 2026-09-01 — [FINDING, P2 billing] Whop dunning-grace is Redis-only and fails open toward REVOKING access — the hourly reconcile cron can persist the downgrade — OPEN, write-up only

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **What prompted this** | Following up on `whop-revocation.ts` (the refund/chargeback denylist), which was deliberately upgraded from Redis-only to dual Postgres+Redis storage — its own header comment explains why: *"The old Redis-only storage meant every revocation silently un-revoked for the duration of any Redis outage... now a Redis miss falls through to Postgres and only fails open when BOTH stores are unreachable."* Reading the sibling billing-gate file, `whop-dunning.ts` (past-due payment-retry grace), found it never received the same treatment — it is still pure Redis, and its own doc comment states the fail-open direction explicitly: `/** True when a past_due membership is within webhook-granted grace. Fail-open false on Redis miss. */`. |
| **Why this is the OPPOSITE, and worse-shaped, asymmetry** | `whop-revocation.ts`'s Redis-only gap failed open toward GRANTING access (a revoked member briefly kept premium during an outage — an availability/goodwill cost, caught and fixed). `whop-dunning.ts`'s Redis-only gap fails open toward REVOKING access: a `past_due` membership legitimately inside its webhook-granted 7-day payment-retry grace window (`markMembershipDunningGrace`, `whop-dunning.ts:24-27`) reads as "NOT in grace" on any Redis miss/outage, which — traced through `resolveTierFromMembership` (`whop.ts:81-92`, `if (membership.status === "past_due" && !opts?.dunningGraceIds?.has(membership.id)) return null;`) and `resolveBillingKindFromMembership` (`whop.ts:140-155`, same gate) — resolves that PAYING, grace-period member straight to `free`. This is a real member-experience/support-cost bug, not a security hole: it costs the business a legitimately-paying customer's access, the opposite direction from the security-motivated revocation fix. |
| **Why the blast radius is a persisted write, not just a transient read** | `src/app/api/cron/membership-reconcile/route.ts` runs on a schedule and calls `reconcileAllMemberships()` (`membership.ts:271`), whose whole documented purpose is to *"heal both directions on a schedule"* by re-resolving and WRITING each user's tier via `syncWhopMembershipForEmail` (confirmed: `syncOne` in the reconcile loop calls it and its `updatedUserIds` result feeds `publishTierChanged`). If a Redis blip happens to overlap with a reconcile pass, the reconcile doesn't just transiently misread the grace-period member — it PERSISTS `tier: "free"` to their Clerk `publicMetadata`, the same mechanism this file already documents fixing once for a different gap (`membership.ts:302-310`, "BUG FIXED HERE" — a churned community-tier reconcile miss, PR #3234, visible in this session's own git log at `728815ea5`). The member only self-heals on the NEXT successful webhook or reconcile pass after Redis recovers — in the meantime they see a real access loss for a payment problem they were told they had a week to fix. |
| **Not purely theoretical** | ElastiCache (`blackout-production-redis-rg`) is documented elsewhere in this repo's own audit tooling as Multi-AZ with failover checks (`zerodte-e2e-suite.mjs`'s INFRA section), so a full outage should be rare — but `sharedCacheGet` returning a miss isn't limited to a full outage: TTL expiry mis-timing, a transient network blip (the exact ETIMEDOUT class this session's CloudWatch sweeps have repeatedly observed against this same Redis cluster — see the 2026-08-31 findings on `[rth-warm-leader] redis error: connect ETIMEDOUT` and similar), or a cold cache after a deploy would all read identically to "not in grace" here. This isn't a hypothetical infra-is-down scenario; it's any of the ordinary transient blips this repo already has independent evidence of happening periodically. |
| **Why not fixed directly this cycle** | The correct fix mirrors `whop-revocation.ts`'s already-proven pattern exactly (new `whop_dunning_grace` Postgres table, dual-write in `markMembershipDunningGrace`/`clearMembershipDunningGrace`, Postgres fallback in `isMembershipInDunningGrace` on a Redis miss) — but that's a new migration + schema + write-path change to a live billing-critical file, not a one-line fix. Per this lane's standing policy, a change of that shape and blast radius (real member entitlements, a table migration) belongs to the owning billing lane's review, not an unattended sweep session shipping it unilaterally. |
| **Suggested fix shape** | Mirror `whop-revocation.ts` precisely: add a durable Postgres table (e.g. `whop_dunning_grace(membership_id TEXT PRIMARY KEY, expires_at TIMESTAMPTZ)`), have `markMembershipDunningGrace` write both stores (Redis hot path + Postgres durable, matching the grace TTL as an expiry timestamp since Postgres has no native TTL), have `clearMembershipDunningGrace` delete from both, and have `isMembershipInDunningGrace` fall through to a Postgres `expires_at > now()` check on a Redis miss before returning false — "only fails open toward denial when BOTH stores are unreachable or genuinely expired," the same durability bar the revocation file already established as this codebase's own standard for a billing-state cache. |
| **Status** | OPEN — flagged for the owning billing lane; no code change made this cycle |

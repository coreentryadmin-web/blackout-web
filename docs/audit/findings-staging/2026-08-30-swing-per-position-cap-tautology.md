## 2026-08-30 — [FINDING, P3 Swing] `per_position` cap check is a tautology (`x > x`) — structurally always false — OPEN, write-up only

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **Severity** | P3 — the whole allocation module is advisory-only (`enforce: false`, nothing sized or blocked), so no member action is currently gated on this. It is still a real logic bug: one of four documented safety caps silently does nothing, and the API's own doc comments describe behavior the code cannot produce. |
| **Where** | `src/lib/swing/swing-allocation.ts`, `allocateSwingBook`, lines 221 and 234. |
| **Symptom** | ```ts\nconst proposedPct = caps.perPositionPct; // never resized — enforce:false\n...\n{\n  cap: "per_position",\n  wouldBreach: proposedPct > caps.perPositionPct,\n  ...\n}\n``` `proposedPct` is unconditionally set to `caps.perPositionPct` itself two lines above the comparison. `wouldBreach: proposedPct > caps.perPositionPct` is therefore `caps.perPositionPct > caps.perPositionPct` — structurally always `false`, for every ranked decision, regardless of input. |
| **Consequence** | `positionsOverCap` (`SwingCapsApplied`, doc'd as "Tickers whose proposed weight exceeded the per-position cap") can never contain a ticker — permanently `[]`. Its own doc comment claims this is "only possible via injected existing weights," but the `existing` positions loop (lines 203–210) only accumulates each entry's weight into `themePct`/`bookPct`/`weekCount` aggregates — it never compares an individual existing position's own weight against `caps.perPositionPct`, so there is no code path, injected or otherwise, that can make this flag fire. A caller reading `capsApplied.positionsOverCap === []` cannot distinguish "no position ever breaches" from "this check is dead code." |
| **Confirmed uncovered** | `src/lib/swing/swing-allocation.test.ts` never asserts on `positionsOverCap` or the `per_position` flag's `wouldBreach` value — consistent with the check having always been unreachable and untested. |
| **Not a deliberate no-op** | Unlike other intentional no-ops documented in the same file (e.g. `DEFAULT_PORTFOLIO_BUDGET`, which carries an explicit comment), no comment here marks this as a stub or acknowledges it is unreachable — this reads as an oversight, not a design choice. |
| **Why not fixed directly this cycle** | The correct fix is ambiguous enough to need an owner decision, not a guess: since every NEW ranked decision's `proposedPct` is hardcoded to exactly `caps.perPositionPct` by design ("never resized"), a new position can never itself exceed the cap — the only way a genuine per-position breach can exist is an EXISTING book position whose real weight (`e.weightPct`) already exceeds `caps.perPositionPct` before any new allocation runs. Fixing this correctly means tracking each existing position's own weight per-ticker (the current `existing` loop only aggregates into theme/book/week sums, losing per-ticker identity) and flagging those specific tickers into `positionsOverCap` — a real, if small, restructuring of the aggregation loop, in a lane (Swing) already actively worked this week (PR #3158 landed 2026-08-29). Guessing at the exact intended semantics here risks shipping an advisory signal that's confidently wrong in a new way, which is worse than the current harmless-but-dead no-op. |
| **Suggested fix shape** | In the `existing` loop, additionally track each ticker's own weight (not just the aggregate sums), and after the loop, push any ticker whose `e.weightPct` (or the `caps.perPositionPct` fallback used when it's non-finite) exceeds `caps.perPositionPct` into `positionsOverCap` directly — this doesn't need to live inside the per-decision `capFlags` loop at all, since it's a property of the existing book, not of a newly ranked candidate. The `per_position` `SwingCapFlag` on each decision could then either be dropped (it can never fire for a new position by construction) or repurposed to reflect whether THAT decision's ticker already has an existing position over cap. |
| **Status** | OPEN — flagged for the Swing lane, no code change made |

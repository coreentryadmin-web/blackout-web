## 2026-10-18 — [FINDING, P1, Ask Largo × Night Hawk Swings / Anthropic tool loop] `anthropicToolLoop`'s wall-clock loop budget only re-checked the clock BETWEEN rounds — a single round's own tool fan-out had no deadline of its own, so one stalled tool call could blow past the whole loop's budget regardless of how much was left — FIXED

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **Severity** | P1 — this is the mechanism behind a live member-facing burst-latency incident: 9/85 Deep-mode turns in a 33-minute window answered `false` (no usable text), and the worst observed turn ran 121197ms — 61% over Deep mode's own 75000ms loop budget — against a 120s ALB idle timeout that a sufficiently late turn can still hit. |
| **Trigger** | Standing Ask Largo × Night Hawk Swings ownership mandate's non-skippable deep-dive, following up on a live CloudWatch burst-latency signal surfaced for Largo's Deep-mode turns (2026-10-18 11:36–12:09 UTC). |
| **Root cause** | `anthropicToolLoop` (`src/lib/providers/anthropic.ts`) enforces its wall-clock `loopBudgetMs` with a single check at the TOP of each loop iteration (`if (loopBudgetMs > 0 && round > 0 && Date.now() - loopStartedAt >= loopBudgetMs)`) — it only runs BEFORE that round's `client.messages.create`/`stream` call starts. Nothing re-checked the clock while the round's OWN `const results = await Promise.all(toolCalls.map(...))` tool-execution fan-out was in flight. That await had no deadline of its own: if any one tool call inside it stalled — queued behind the shared UW rate limiter (`throttleUwCoalesced`/`acquireSlot`, bounded by `UW_QUEUE_MAX_WAIT_MS`, default 20s), a slow Polygon chain fetch, or a cold GEX matrix rebuild — the ENTIRE round, and therefore potentially the entire loop, blocked until that call's own worst-case ceiling resolved (traced: `uwGetSafe`'s own retry budget plus `acquireSlot`'s queue wait plus the HTTP fetch's own timeout puts a single `fetchUwXxx` call's worst case at roughly 35s for one attempt — already enough to consume most of Deep mode's 75000ms loop budget if it lands inside a round whose earlier model-create/stream call already spent meaningful time). `get_gex`'s own internal 4-way `Promise.all` fan-out (`run-tool.ts`) is a concrete, near-universal Largo tool whose own worst member can bottleneck the whole call this way. |
| **Evidence** | Live CloudWatch burst, 2026-10-18 11:36–12:09 UTC: 85 Deep-mode (`largoDepthConfig("deep").loopBudgetMs === 75000`) turns, mean `total_ms` ≈ 47000, worst `total_ms` 121197 (+41000ms, +61%, over the 75000ms loop budget it was supposed to be bounded by), 9/85 turns `answered:false`, correlated `queue_wait_ms` up to 18428 on the UW rate-limiter admission queue in the same window. Prior 14-day log history of `"[anthropic] tool loop hit its ${budget}ms wall-clock budget"` warnings: 7 of 8 fired after only round 1-2 — i.e. ONE round's own duration, not the cumulative sum of many rounds, consumed the whole budget, which is only possible if that one round's tool fan-out (not the between-round boundary) is where the overrun happens. RED→GREEN proven: new file `src/lib/providers/anthropic-round-tool-budget.test.ts` (10 tests covering the pure `raceToolRoundAgainstBudget` helper directly — sentinel-on-timeout, real-value-on-settle, negative-`remainingMs` clamp — plus source-level regression assertions that the loop body is actually wired to the race, the timeout path returns before the `tool_result` message is pushed, an omitted/zero budget still awaits unconditionally, and the race applies on every round including round 0) failed 9/10 (`git stash` isolating `anthropic.ts`, restored with `git stash pop`) before the fix and passed 10/10 after. `npx tsc --noEmit` clean. Full sibling suite re-run clean: `loop-budget.test.ts` + `anthropic-empty-round-visibility.test.ts` + `anthropic-stream-guard.test.ts` + `tool-count-claims.test.ts` (23 tests) unaffected before and after. |
| **Blast radius** | One shared function, `anthropicToolLoop` in `src/lib/providers/anthropic.ts` — its ONLY caller is `src/lib/largo-terminal.ts` (two call sites: the concrete/non-stream path and the deep/stream path, both of which already pass `loopBudgetMs: largoLoopBudgetMs(depth)`; confirmed by repo-wide grep — no other caller of `anthropicToolLoop` exists, so commentary/digest/cron callers that omit `loopBudgetMs` are structurally unaffected: the new guard is gated behind `if (loopBudgetMs > 0)`, identical to the pre-existing between-round check's own gate). The edited block (`const results = await Promise.all(toolCalls.map(...))` → raced) is SHARED tail code for both the streaming (Deep) and non-streaming (Concrete) branches, which converge above it — one change covers both depths. No change to `ToolLoopStopReason`, `classifyEmptyAnswer`, or any downstream caller: the timeout path reuses the existing `"loop_budget"` stop reason, which `empty-answer-fallback.ts`'s `classifyEmptyAnswer` already maps to the correct member-facing "timeout" copy. |
| **Fix rationale** | Added a small, pure, SDK-free helper (`TOOL_ROUND_BUDGET_EXCEEDED` sentinel + `raceToolRoundAgainstBudget`) next to the file's existing SDK-free helpers (`shouldFallBackToEscalationModel`, `extractTextFromLastAssistant`) for the same reason they exist there: the Anthropic client is not dependency-injected (`getClient()` calls `new Anthropic(...)` directly), so loop logic has to be factored out to be unit-testable at all. The tool-execution `Promise.all` is now raced against whatever budget remains (`loopStartedAt + loopBudgetMs - Date.now()`) whenever `loopBudgetMs > 0`; on a timeout it logs and returns via the existing `"loop_budget"` stop reason BEFORE the `tool_result` message is constructed, so no placeholder/fabricated tool results are ever pushed for calls that never settled. Applied unconditionally on every round including round 0 (no `round > 0` floor, unlike the between-round check) — by the time this code runs, round 0's own model response has already arrived, so the "give the loop at least one attempt" purpose that floor protects is already satisfied; this mirrors the existing mid-loop spend-ceiling check, which also carries no round floor. Deliberately does NOT add cancellation: there is no `AbortSignal` threaded from `anthropicToolLoop`'s `runTool` parameter down into `makeGuardedToolRunner`/the ~140 individual provider fetchers, so an abandoned call keeps running to its own natural completion in the background — it still releases its UW/Polygon rate-limiter slot whenever it settles, and each call is already individually try/caught into `{error}`, so there is no unhandled-rejection risk from orphaning it. Real cancellation plumbing is a materially larger, separate change, explicitly out of scope for this smallest-correct-fix. One UX wrinkle unique to this fix, flagged for the record rather than treated as a reason to hold the PR: on the streaming (Deep) path a member can now see a `tool_start` SSE event for a call that never gets a matching completion signal before the turn ends — every other existing early-exit (spend ceiling, round-create failure, max-rounds) only ever happens between fully-completed rounds. The separate, smaller follow-up considered (short-TTL `uwCacheGet` dedup for 4 hot uncached UW reads) was deliberately NOT bundled into this PR — it is additive and independent, and shipping it here would widen this PR's blast radius for no correctness gain on the burst-latency mechanism itself. |
| **Status** | FIXED — see PR (branch `fix/largo-deep-round-tool-fanout-budget`). |

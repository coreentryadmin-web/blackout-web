## 2026-09-03 — [FINDING, P2 performance/correctness, Vector] `vector-pick-sweep`'s cross-replica overlap lock (TTL 480s) expires mid-sweep when a real sweep runs longer than 480s, letting the next scheduled fire start a SECOND concurrent sweep — the exact overlap the lock exists to prevent — FIXED

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **What prompted this** | STANDING PERFORMANCE/LATENCY AUDIT MANDATE sweep: pulled `AWS/ApplicationELB` `TargetResponseTime` for `blackout-production-app` over the last 3 hours of RTH (2026-09-03 16:47-19:32 UTC) — Max sat at 90-120s in every 15-minute window, a persistent (not one-off) tail. Grepped CloudWatch Logs `/ecs/blackout-production` for `elapsed=` to find the driver, per the mandate's own "check every cron's own schedule against its own measured elapsed= runtime" method. |
| **Investigation** | `vector-pick-sweep` (schedule: every 2 min during RTH, `1-59/2 11-21 * * 1-5`) had already been given a `sharedCacheSetNx` overlap guard on 2026-09-01 after a single measured elapsed=301362ms (5m1s) run — the same class of fix as `swing-discovery`/`banger-discovery`/`thermal-discord`. Re-measuring on 2026-09-03 found the guard in place and functioning as coded, but sweep runtimes had gotten WORSE since the original fix, not better: elapsed=693684ms and 644588ms both observed in the 3-hour window, both above the guard's own 480s (8min) TTL. Cross-referencing raw log timestamps confirmed real overlap: a sweep that started ~16:55:38 (its "done" line logged 17:06:52, elapsed=693684ms) had its Redis lock expire at ~17:03:38 — a SECOND sweep then acquired the now-free lock, started ~17:05:16, and finished 17:09:31 (elapsed=123220ms) while the FIRST sweep was still running. Same pattern again at 18:33-18:44 UTC (elapsed=644588ms overlapping with a 138410ms run). |
| **Root cause** | `OVERLAP_LOCK_TTL_SEC` was set to 480s, deliberately chosen to match this cron's `stale_after_min: 8` alerting threshold (the value that was safe against the single 301362ms measurement available on 2026-09-01). The lock's job is to hold for AT LEAST as long as the sweep it's guarding could plausibly run; once real elapsed times regularly exceeded that TTL, the lock started expiring while its own sweep was still in flight, defeating the guard exactly in the overlap scenario it was built to prevent. This is very likely self-reinforcing: once two sweeps overlap, they contend for the SAME cluster-wide Polygon/UW rate limiters (`GLOBAL_MAX_RPS=2`, `GLOBAL_MAX_CONCURRENCY=2-3`) that real member requests also depend on, which plausibly explains why runtimes climbed further above the 2026-09-01 baseline (301s) instead of settling back down after the original fix — an overlap-then-slower-then-more-overlap loop, not a one-time regression. |
| **Why this matters** | The overlap guard's entire purpose is to keep the shared Polygon/UW rate limiter from being hit by two concurrent sweeps at once — a TTL shorter than real observed runtime silently reintroduces the exact contention the guard was written to remove, which is consistent with the sustained ALB `TargetResponseTime` Max (90-120s across every window measured, not a single spike) real members are experiencing during RTH. |
| **Fix** | Raised `OVERLAP_LOCK_TTL_SEC` from 480 to 900 (15 min) — comfortable margin above the worst measured 694s without materially weakening the safety net (a genuinely crashed/stuck sweep still self-heals within 15 minutes, not never). Raised the matching `stale_after_min` for `vector-pick-sweep` in `cron-registry.ts` from 8 to 15 to keep the two in lockstep, per the route file's own stated intent. Did NOT touch the sweep's own per-ticker work, the rate limiter, or the schedule interval — the guard mechanism itself (`sharedCacheSetNx`/fail-open/release-in-finally) was already correct and is left untouched; only the TTL constant that had fallen behind real measured runtime changed. |
| **Blast radius** | Two files (`route.ts`, `cron-registry.ts`). No other cron shares this TTL constant. Member-facing behavior unchanged except for reduced rate-limiter contention during long sweeps. |
| **Regression guard** | `route.test.ts`: updated the existing TTL-value assertion (480 → 900) and added a new test asserting the TTL stays comfortably above the worst measured runtime (694s) rather than merely matching a schedule interval — so a future regression back to a too-short TTL fails a test instead of silently reintroducing the overlap. Confirmed RED pre-fix (`git stash` the two source files, keep the tests: 2/6 new/updated assertions fail — exactly the TTL-value and TTL-margin checks) and GREEN post-fix (6/6). |
| **Gates** | `npx tsc --noEmit` clean (Node 20.20.2). Full `npm test` run — see PR for the exact pass count; the 5 `zerodte-service.test.ts`/`board-convergence` failures seen in this sandbox's full-suite runs are a documented sandbox-only artifact (CLAUDE.md's environment-realities section) that does NOT reproduce on GitHub Actions `verify` — confirmed unrelated to this change (untouched files) and confirmed against the real CI run before merge. |

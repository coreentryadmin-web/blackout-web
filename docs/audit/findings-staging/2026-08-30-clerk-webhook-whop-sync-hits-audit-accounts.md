## 2026-08-30 — [FINDING, P3 billing/webhooks] Clerk webhook's Whop sync ran for internal audit accounts, spamming ERROR-level logs and hitting Whop's API for memberships that can never exist — FIXED

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **Symptom** | Live CloudWatch sweep (`/ecs/blackout-production`, 2026-08-30 ~11:38 and 12:15 UTC) found repeated `console.error`-level `[clerk-webhook] Whop sync failed for <id> (seo-audit-<timestamp>@blackouttrades.com): a: Not Found` entries — a Clerk `user.updated` webhook firing for a SEO-lane temp audit account, then a genuine outbound call to Whop's API 404ing because a synthetic non-paying test account has no Whop membership to find. |
| **Root cause** | `src/app/api/webhooks/clerk/route.ts`'s `POST` handler calls three side-effecting things after provisioning/updating a user row: `startWelcomeSequence(...)`, `notifyOpsDiscord(...)`, and `syncWhopForClerkUser(...)` (which wraps `syncWhopMembershipForEmail`). The first two are already gated with `if (!isInternalAuditEmail(email))`, each carrying its own doc comment explaining why (a measured 99.9% welcome-email bounce rate from these disposable addresses; an ops channel that would otherwise be >90% bot noise). The THIRD call — `await syncWhopForClerkUser(userId, email, {...})` — had no such gate, and ran unconditionally for every `user.created`/`user.updated` event. |
| **Why this matters** | `scripts/audit/lib/clerk-audit-user.mjs` and its callers mint dozens of temp Clerk accounts against PRODUCTION every day (per this repo's own CLAUDE.md operating notes) — every one of them fires this webhook at least once (create) and often again (any metadata/session update). Each unmatched call: (1) makes a real, wasted outbound HTTP call to Whop's API, and (2) logs at ERROR severity, which drowns out a genuine Whop sync failure for a real paying member in the same log stream — exactly the "channel trained to ignore itself" failure mode the two adjacent comments in this same function already warn about for welcome-email/ops-Discord noise. This is not a new pattern requiring a design decision — it is the same established policy, just not applied to this third call site. |
| **Blast radius** | Single call site (`syncWhopForClerkUser` inside the `user.created`/`user.updated` branch of the webhook handler) — both event types converge on the same line, so both were affected identically. No other caller of `syncWhopForClerkUser`/`syncWhopMembershipForEmail` exists outside this file. |
| **Fix** | Wrapped the call in the same `if (!isInternalAuditEmail(email))` gate already used two blocks above it, with a comment explaining the specific cost (wasted Whop calls + ERROR-log noise) this closes. Audit accounts still get their DB row provisioned/updated normally — only the Whop membership sync (which can never find anything for a synthetic account) is skipped, mirroring the existing welcome-email/ops-Discord behavior exactly. |
| **Regression guard** | New `src/app/api/webhooks/clerk/route.test.ts` — full route-level test (`mock.module` on `next/headers`, `svix`'s `Webhook` class, `@/lib/db`, `@/lib/admin-users`, `@/lib/membership`, `@/lib/tier-cache`, `@/lib/welcome-sequence`, `@/features/spx/lib/spx-play-notify`; `isInternalAuditEmail` left REAL since it's exactly what's under test). One test posts a `user.updated` event for `seo-audit-<ts>@blackouttrades.com` and asserts `syncWhopMembershipForEmail` is never called (DB row update still happens); one posts `user.created` for a real member email and asserts the sync IS called. Confirmed **failing** (1/2) against the pre-fix handler via `git stash` toggle, passing (2/2) post-fix — a real behavioral test of the actual gate, not a source-text match. |
| **Gates** | `npx tsc --noEmit` clean · `npx eslint` clean on both touched files · `route.test.ts` 2/2 pass (Node 20.20.2, `--experimental-test-module-mocks`) · full `npm test` at this commit: **11442 pass / 0 fail / 2 skipped**. |
| **Status** | FIXED |

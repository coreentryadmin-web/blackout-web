## Membership reconcile cron never re-checks churned COMMUNITY subscribers for downgrade — FIXED

> **kind:** `FINDING`

Billing/subscription-lifecycle audit per standing instruction — Whop webhook handling, Clerk
`publicMetadata.tier` sync, subscription state transitions, grace-period date math, and the
billing lifecycle email trigger conditions. `#3215`/`#3212` ("membership-sync-skip-audit-accounts")
was excluded as in-scope-but-already-fixed (audit-account exclusion, not core billing correctness) —
this is a different bug in the same file, confirmed via `git log`/blame to predate today's fix wave
(last touched `54654b19a`, 2026-08-07).

| Field | Detail |
|---|---|
| **Symptom** | `reconcileAllMemberships()` (`src/lib/membership.ts`) is the hourly self-healing sweep whose own doc-comment says it fixes missed webhooks "in BOTH directions" — including "the revenue leak where a churned/refunded user keeps premium because no `deactivated` webhook arrived." Step 2 (the downgrade-direction discovery pass) built its candidate email set by paging every Clerk user and testing `tier === "premium"` only. A user on the `community` tier (SPX Slayer, $49/mo, added by #1159 — 5 months after this reconcile loop was written) whose Whop membership actually lapses is invisible to this filter, so step 3 never re-resolves them and they never get downgraded by the cron. |
| **Root cause** | `community` tier was added to the tier model (`Tier = "free" \| "community" \| "premium"`, `#1159`) as a full sibling of `premium` — it grants real, ongoing, paid desk access (`/dashboard`) — but `#1159` never touched the reconcile loop's premium-only filter (confirmed via `git log -p --follow -- src/lib/membership.ts`: the `tier === "premium"` line in step 2 is unchanged since before the community-tier commit). Since the Whop webhook is explicitly documented elsewhere in this file as "fire-and-forget" and the reconcile cron exists *specifically* as the backstop for a dropped/failed `membership.deactivated` delivery, a community subscriber who churns/refunds/disputes right when that one webhook attempt is lost has **no other path back to `free`** — nothing else in the codebase re-resolves a `community`-tagged Clerk user against Whop. |
| **Why not caught earlier** | `reconcileAllMemberships` has no dependency-injected Clerk/Whop client and no existing test coverage at all (`grep -rl reconcileAllMemberships src --include=*.test.ts` — zero hits before this fix), so the community-tier PR's review had nothing to run against this function; the asymmetry is invisible from reading `#1159`'s own diff (it only touches `resolveTierFromMembership(s)`/`resolveBillingKindFromMembership(s)` in `whop.ts`, never `membership.ts`'s reconcile loop) and only shows up by reading the reconcile loop itself side-by-side with the tier model it claims to fully cover. |
| **Evidence** | `git log -p --follow -- src/lib/membership.ts \| grep -n 'tier === "premium"'` shows the step-2 filter present, unchanged in shape, since the function's original commit — the community-tier PR (`52fb465f4`, `feat: add community tier — SPX Slayer ($49) gets /dashboard access (#1159)`) does not appear in that file's history for this line at all. Extracted the filter to a pure, unit-tested predicate (`isPaidTierForReconcileDowngradeCheck`) and ran it red/green via `git stash`: **red** — calling the not-yet-existing function throws `TypeError: is not a function` (2/2 fail); **green** — 2/2 pass post-fix. Also ran the two pre-existing membership tests (`membership-sync-limit.test.ts`, `membership-tiebreak.test.ts`) alongside — still 6/6 pass, confirming no regression to the untouched paths. |
| **Blast radius** | Single call site (`reconcileAllMemberships` step 2, `src/lib/membership.ts`) — no duplicate implementation of "which tiers does the reconcile downgrade sweep cover" exists elsewhere (confirmed via repo-wide grep for `tier === "premium"` scoped to reconcile-shaped loops; the webhook route's real-time path already handles both tiers correctly via `syncWhopMembershipForEmail`/`syncWhopMembershipAndNotify`, which never special-cased premium — this bug was reconcile-loop-only). The billing-lifecycle email dispatch (`billing-lifecycle-email.ts`) is unaffected: it fires off the SAME `syncWhopMembershipForEmail` result the webhook route already produces per-event, so a community member's real-time downgrade (when the webhook itself succeeds) already emailed correctly — this fix only closes the gap for the case the reconcile cron exists to cover, i.e. when that one webhook delivery is lost. |
| **Fix rationale** | Extended the step-2 filter to `tier === "premium" \|\| tier === "community"` (via a new exported pure predicate, `isPaidTierForReconcileDowngradeCheck`, so the "which tiers are self-healed" question is independently unit-tested rather than re-inlined). Did not change the PRIMARY-email selection logic in the same block (already correct per the existing audit-launch-path-#7 comment) or step 1 (upgrade-direction discovery), which already enumerates memberships by Whop-side status regardless of tier and was never premium-only. Left `reconcileAllMemberships`'s own doc-comment corrected to say "premium OR community" instead of "premium" so the next reader doesn't reintroduce the same gap for a future third tier. |
| **Regression guard** | `src/lib/membership-reconcile-downgrade.test.ts` (new) — pins `isPaidTierForReconcileDowngradeCheck("premium")` and `("community")` both `true`, and `("free")`/`("")`/`("admin")` all `false`. This is the exact predicate `reconcileAllMemberships` now calls, so a future revert of the filter (or a future tier added without updating this predicate) fails this test immediately instead of silently reintroducing the blind spot. |
| **Gates** | `npx tsc --noEmit` clean (Node 20.20.2). `npx tsx --test src/lib/membership-reconcile-downgrade.test.ts src/lib/membership-sync-limit.test.ts src/lib/membership-tiebreak.test.ts` — 6/6 pass. Confirmed red-then-green via `git stash` on the isolated new test file. |
| **Status** | FIXED |

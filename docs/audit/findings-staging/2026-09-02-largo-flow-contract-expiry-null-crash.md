| **Root cause** | Pulled the actual server-side error from CloudWatch (`/ecs/blackout-production`, last 15 min): `TypeError: Cannot read properties of null (reading 'expiry')`, logged from `largo-terminal.ts`'s catch-all in `runLargoQuery`. Traced to `extractFlowContracts` in `src/lib/largo/core/market-evidence.ts`. The walker's guard `if (premium != null && premium > 0 && (strike != null || occ)) { ... }` only proves that **at least one** of `strike`/`occ` is non-null — not both. The push below it then did `expiry: expiry ?? occ!.expiry` — a non-null assertion that is only safe when `strike == null` (which is the branch that forces `occ` to be truthy per the guard). When a row instead has a real `strike` but no `expiry` field and no parseable OCC `symbol`/`contract` (exactly what a positioning-summary row looks like — no raw option chain, just aggregate greeks/walls), the guard passes on `strike != null` alone while `occ` is genuinely `null`, and `occ!.expiry` throws. |
| **Why it surfaced now and not before** | The 2026-08-21 finding's root cause (the tool never being called at all, short-circuited earlier in the pipeline) has evidently been fixed or changed shape since — `get_positioning` now runs — which is progress, but it exposed this second, previously-unreached bug one step further into the same turn. A generic `try/catch` around the whole turn (`largo-terminal.ts`) means both bugs produce the identical member-facing message, so the second one read as a recurrence of the first until the actual stack trace was pulled from CloudWatch. |
| **Evidence** | Live CloudWatch log group `/ecs/blackout-production`, filtered on `"largo/runLargoQuery"` over the last 15 minutes: two paired `TypeError: Cannot read properties of null (reading 'expiry')` / `[largo/runLargoQuery] detail: Cannot read properties of null (reading 'expiry')` lines, timed to match the probe's SPY questions. |
| **Fix** | `expiry: expiry ?? occ!.expiry` → `expiry: expiry ?? occ?.expiry ?? ""`. `classifyOptionHorizon` (same file) already treats a null/empty expiry as `"UNKNOWN"` rather than crashing or guessing, so an unresolvable expiry now degrades honestly (the flow contract still surfaces, with an honest `UNKNOWN` horizon) instead of aborting the entire Largo turn. Checked every other consumer of `FlowContractRef.expiry` in the same file (`fc.expiry.slice(5)` in the horizon-mislabel prose check, `lower.includes(fc.expiry)`) — both are safe on an empty string (`"".slice(5)` → `""`, `.includes("")` → true but gated behind other conditions that still require a genuine mention), so no other consumer needed touching. |
| **Blast radius** | `extractFlowContracts` feeds `MarketEvidence.flowContracts`, which is read by `validateProseAgainstEvidence` (horizon-mislabel / precise-rec checks) and `assessEditionActionability` — every Largo turn that captures ANY tool result containing option-like rows (not just `get_positioning`; any prefetch or tool result walked by this function) was one strike-only, expiry-less row away from this crash. Not thermal- or SPY-specific — the walker recurses into every nested object up to depth 5 across `capturedResults`, so any desk's tool payload with this exact shape (strike present, expiry absent, symbol unparseable) would trigger it. |

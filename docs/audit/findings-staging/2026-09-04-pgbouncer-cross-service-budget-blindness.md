## 2026-09-04 — [BUG, P2 platform-wide] PgBouncer/RDS-Proxy connection-budget self-check was blind to sibling services and to the real autoscaling ceiling

> **kind:** FINDING

| Field | Value |
|-------|-------|
| **Status** | FIXED |
| **Found by** | Parallel live-production audit workflow, 2026-09-04 (SPX Slayer play system / `src/lib/db.ts` area). Adversarial review split (1 refuted the SPX-specific attribution after an exhaustive log search found no SPX-tagged hits; 1 confirmed the full claim, independently reproducing the exact cited evidence — 2740 events, the identical log-stream counts — and additionally found SPX-tagged hits (`hydrateSessionCountersFromDb`, `logSpxEcosystemShadowFactors`) in the 2026-09-02→09-03 window). The underlying cross-service/autoscaling-ceiling budget gap is undisputed by both reviewers regardless of the SPX-specific framing; this fix addresses that root cause directly rather than SPX specifically. |
| **Evidence** | Live Secrets Manager (`blackout-production/app/env`): `REPLICA_COUNT=8`, `PG_POOL_MAX=2` (web); market-worker task-def env `REPLICA_COUNT=1`, `PG_POOL_MAX=4`; `PGBOUNCER_DEFAULT_POOL_SIZE=20`. `8×2 + 1×4 = 20` exactly — zero headroom. Application Auto Scaling `describe_scalable_targets`: `blackout-production-web` MinCapacity=8, MaxCapacity=12 — i.e. `REPLICA_COUNT` (used in the pool math) is only the floor. Live CloudWatch metric `RunningTaskCount` for the web service, 2026-09-01: routinely spikes to 9-10 throughout the day (not a rare edge case). Live CloudWatch Logs `/ecs/blackout-production`, filter `"[db] transient query error"`, 2026-09-01 14:09-14:19 UTC: 2740 events across exactly 5 log streams (1038/855/765/45/37), correlating with the exact `RunningTaskCount` spike window. `AWS/RDS DatabaseConnections` was pinned at 22-24 during the same incident window while `CPUUtilization` stayed 6-12% (ruling out general compute pressure as the bottleneck — this is specifically the connection-count ceiling). |
| **Root cause** | `src/lib/db.ts`'s `SAFE_PG_POOL_MAX_DEFAULT = floor(PGBOUNCER_DEFAULT_POOL_SIZE / REPLICA_COUNT)` and its oversubscription `console.warn` guard were both evaluated per-process using only that process's own env vars — no visibility into (1) what a sibling ECS service (e.g. `blackout-production-market-worker`) was already consuming from the SAME shared PgBouncer/RDS-Proxy budget, or (2) the real Application Auto Scaling ceiling above the hardcoded `REPLICA_COUNT` floor. At the nominal 8-replica baseline, web (8×2=16) + market-worker (1×4=4) already equalled the full budget (20) — zero headroom for a rolling-deploy overlap, an autoscale-out event, or ordinary burst traffic. Both independently-passing self-checks summed to exactly 100% of the shared budget. |
| **Fix** | Added two new, backward-compatible env-driven inputs to `src/lib/db.ts`'s pool-sizing math, both defaulting to values that reproduce the EXACT prior computation when unset: `REPLICA_COUNT_MAX` (the service's real autoscaling ceiling — defaults to `REPLICA_COUNT`, clamped to never go below the floor) and `PGBOUNCER_RESERVED_FOR_OTHER_SERVICES` (connections a sibling service is known to consume from the shared budget — defaults to 0). `computeSafePgPoolMaxDefault` gained an optional third parameter (`reservedForOtherServices = 0`) that subtracts the reservation before dividing across replicas, with a floor of 1 available slot so an absurd reservation can't divide by zero or negative. `SAFE_PG_POOL_MAX_DEFAULT` now derives from the CEILING (`REPLICA_COUNT_MAX_FOR_POOL`) and the reservation rather than just the floor. Added a second oversubscription warning that checks `poolMax × REPLICA_COUNT_MAX_FOR_POOL + PGBOUNCER_RESERVED_FOR_OTHER_SERVICES` against the budget, alongside the existing floor-based one — this is the check that actually catches the scenario the finding describes (clean at the floor, oversubscribed at the real ceiling). |
| **Blast radius** | One file (`src/lib/db.ts`), one exported pure function's signature extended (only additive — `computeSafePgPoolMaxDefault` has exactly one caller, the module-level `SAFE_PG_POOL_MAX_DEFAULT` const). Deliberately did NOT touch production Secrets Manager or any ECS task definition — the new env vars (`REPLICA_COUNT_MAX`, `PGBOUNCER_RESERVED_FOR_OTHER_SERVICES`) default to the exact prior behavior when unset, so this PR changes NOTHING about current production pool sizing on its own. Actually closing the zero-headroom gap requires a follow-up operational step: set `REPLICA_COUNT_MAX=12` on `blackout-production-web` (matching its real MaxCapacity) and `PGBOUNCER_RESERVED_FOR_OTHER_SERVICES` on each service to its siblings' known consumption (e.g. web sets it to market-worker's `1×4=4`, and vice versa) — deliberately left as a follow-up rather than executed in this pass, since it means writing to the shared 98-key `blackout-production/app/env` secret that ECS injects fleet-wide, and the exact target numbers (how much headroom to reserve, whether to also raise `PGBOUNCER_DEFAULT_POOL_SIZE` on the RDS Proxy side) are an operational/capacity decision, not a code-correctness one. |
| **Tests** | 5 new tests in `db.test.ts`: `reservedForOtherServices` actually carves out sibling consumption (chosen so the pre-fix 2-arg call and the post-fix 3-arg call diverge — floor(20/5)=4 vs floor((20-4)/5)=3), omitting it preserves the exact prior result, an absurd reservation clamps to 1 slot rather than dividing by zero/negative, a negative reservation is treated as 0, and a source-text pin confirming the module-level wiring actually passes the new ceiling/reservation constants (module-load-time env-derived constants can't be re-imported with different env in the same test process, so the wiring itself is pinned by source text rather than re-derived — the pure function is exhaustively covered separately).

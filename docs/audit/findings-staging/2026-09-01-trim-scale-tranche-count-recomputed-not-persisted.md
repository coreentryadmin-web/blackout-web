## 2026-09-01 — [product, 0DTE exit engine] trim_scale's tranche-banking mechanism was structurally unreachable — the default exit mode for A/B-tier plays never actually banked a partial trim — FIXED (flag-gated, ships disarmed)

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **Context** | User asked for a deep architectural audit of the whole 0DTE pipeline (`nighthawk-0dte-redesign` workflow, 15 agents). Independent adversarial review of the resulting redesign plan flagged an already-documented "[P1, LIVE, DOCUMENTED IN-REPO]" gap — exit-sync.ts's own comment on the 2026-08-27 dead-zone fix says "there is no persisted trim-count column yet" — that the plan's `concrete_change_list` never actually addressed despite reviewing the governor-exits section. Verified the claim directly against the shipped code before acting on it. |
| **Root cause** | `exit-sync.ts` computed `trimsTaken` (how many trim-scale tranches the caller has "already banked") by RE-COMPUTING `trimTranchesArmed(peak, regime)` on every tick — the EXACT SAME pure function `exit-engine.ts`'s `decideTrimScale` ALSO calls internally to compute `armed` (how many tranches the peak has armed). Feeding a fresh recompute of a value back in as if it were an independently-tracked "already taken" count makes `armed > taken` structurally unable to ever be `true`, on every single evaluation, not just at a threshold-crossing edge case. Two live consequences: (a) the trim ladder's own banking branch (`decideTrimScale`'s "3. Trim ladder", `exit-engine.ts:393-405`) could never fire — a tranche is never actually banked; (b) the 2026-08-27 dead-zone guard's `!trimAvailable` check (written specifically to stop the coarse breakeven-floor EXIT from dumping the whole position when a tranche was armed) was permanently a no-op, since `trimAvailable = armed > taken` is always `false` — so the exact SLS/TSM regression that guard exists to prevent was silently still happening at the identical crossing point (peak +20% in the neutral regime, where the trim-scale tranche-1 arm and the shared ratchet-style breakeven-floor arm coincide). `trim_scale` is the shipped DEFAULT exit mode for A-tier and B-tier plays (`resolveExitModeForTier`, "the E5 study proved trim_scale dominates ratchet in EVERY backtest window") — this bug meant the desk's best-tier setups were, in the exact scenario the mode was built to handle, functionally degrading toward ratchet's dumb breakeven-dump behavior instead of the E5-measured partial scale-out (⅓@+25%/⅓@+50%/run). The gap traces to a design-time confusion documented in `evaluateLedgerRowExit`'s own old comment ("TRIM is already derived + persisted by the peak latch; the engine's TRIM can only agree with it") — true for RATCHET mode (its single trim is keyed to `derivePlayStatus`'s persisted `status` field) but never true for trim_scale's 0/1/2 tranche counter, which had no equivalent persisted home. |
| **Evidence** | Read `exit-engine.ts`'s `decideTrimScale` (lines 306-420) and confirmed `taken = floor(input.trimsTaken)` while `armed = trimTranchesArmed(peakPnlPct, regime)` are computed from the identical inputs `exit-sync.ts` passed in, both via the identical `trimTranchesArmed` function — so `taken === armed` on every call by construction. Read `evaluateLedgerRowExit`'s two real call sites (`live-marks.ts`'s ~1s lane, `scan.ts`'s cron sync) and confirmed both discard every non-EXIT decision (`if (decision.action !== "EXIT") return null`), so a TRIM decision — even if one could fire — had zero write consequence anywhere; nothing in the schema persisted a real "thirds banked" count. New regression test (`exit-sync.test.ts`, "trim_scale dead-zone BUG (unchanged while ZERODTE_TRIM_BANK_LIVE is off)") reproduces the exact live scenario directly against `evaluateLedgerRowExit`: entry 4.0, peak 4.8 (+20%, neutral regime — the documented SLS/TSM crossing point), mark back to 4.0 (breakeven) — confirms the row still exits via `ratchet_breakeven_floor`/`ratchet_early_profit_floor`, dumping the whole position, exactly reproducing the bug. A companion test with the fix enabled (`trimsTaken=0` genuinely distinct from `armed=1`) confirms the SAME inputs instead bank tranche 1 and leave the row open. |
| **Fix** | Added a real, monotonic, persisted `trims_taken` column to `zerodte_setup_log` (idempotent `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`, `db.ts`), latched via `GREATEST` in `updateZeroDteLiveState` exactly like `peak_premium`/`trough_premium` already are (a stale writer can only raise it, never regress a tranche a fresher writer already banked; frozen once `status = 'CLOSED'`). `evaluateLedgerRowExit` now fires a new `deps.onTrimBank(trimsTaken)` callback when a trim_scale tranche has genuinely just armed (`decision.reason` is `trim_scale_first`/`trim_scale_second`) — never for ratchet's own single `plan_target_trim`, whose "already trimmed" fact is still correctly carried by the row's persisted `status` field, unchanged. Both real call sites (`live-marks.ts`, `scan.ts`) now wire `onTrimBank` to `updateZeroDteLiveState(..., { trimsTaken })`. Gated behind a new env flag, `ZERODTE_TRIM_BANK_LIVE` (off by default, mirrors the existing `ZERODTE_TRIM_REGIME_LIVE`/`GOVERNOR_ENFORCE_LOSS_HALT` pattern): while off, `trimsTaken` is still recomputed via the legacy `trimTranchesArmed(peak, regime)` path — byte-identical to today's shipped (buggy) behavior — so merging this PR changes nothing live. Flipping the flag on is a deliberate follow-up once a real session's shadow behavior has been reviewed, per this codebase's own calibration-first discipline and the redesign audit's adversarial review (which explicitly asked for a flag-gated rollback lever on any change that alters live exit timing for A/B-tier's default mode). |
| **What was deliberately NOT changed** | `decideTrimScale`/`evaluateExitState` (exit-engine.ts) — the pure engine logic was already correct GIVEN a real `trimsTaken` input; the bug was entirely in how the IO shell (`exit-sync.ts`) computed that input, not in the engine. Ratchet mode's own single-trim mechanism — unaffected, still correctly carried by `status`. The trend/range tranche threshold values themselves (still v1-heuristic, still gated separately by `ZERODTE_TRIM_REGIME_LIVE`) — out of scope, this fix is about persistence, not threshold calibration. |
| **Blast radius checked** | Grepped every caller of `updateZeroDteLiveState` (2: `live-marks.ts`, `scan.ts` — both updated) and every caller of `evaluateLedgerRowExit` (same 2). Confirmed `fetchZeroDteSetupLog`/`fetchZeroDteSetupLogRange` use `SELECT *`, so the new column flows through automatically once mapped in `mapZeroDteLogRow`. Confirmed no other reader of `ZeroDteSetupLogRow` assumes a fixed field set that would break on an added property. |
| **Regression guard** | `db.test.ts`: new test pins the `trims_taken` SQL SET clause (GREATEST-monotonic, frozen at CLOSED, untouched when the param is omitted) by source inspection, same idiom as the existing `peak_premium`/`trough_premium` test. `exit-sync.test.ts`: 4 new tests — `resolveTrimBankLive` off-by-default coverage; the dead-zone bug reproduced byte-for-byte while the flag is off; the fix verified directly (tranche banks, `onTrimBank` fires, row stays open) with the flag on. Full suite: `src/lib/zerodte/*.test.ts` 1215 pass / 0 fail / 1 pre-existing skip; `db.test.ts` 14/14; `scan.test.ts` 26/26; `live-marks.test.ts` 31/31 (Node 20, `--experimental-test-module-mocks`). `npx tsc --noEmit` clean. |
| **Status** | FIXED — merged disarmed (`ZERODTE_TRIM_BANK_LIVE` unset). Flipping it live is a deliberate operator follow-up, not part of this PR. |

## 2026-08-31 — [FINDING, P2 Largo/Vector correctness] Vector's gex-ladder route silently truncates when Largo reaches it via `call_internal_api` — FIXED

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **What prompted this** | End-to-end live audit of Night Hawk + Vector today (2026-08-31), verifying recent PR #3242/WS-11/moneyness-gate/pinned-stop fixes are holding. `zerodte-e2e-healthcheck.mjs` was clean (legitimate pre-open AMBERs, 0 committed plays yet this session). `vector-rth-quick-check.mjs`'s gex-ladder size check printed `18865 chars (117.9% of 16k Largo cap reference)` for SPX 0DTE — the script only *logs* this, it never asserted against it, so the number sat there unflagged until read by eye. |
| **Root cause** | `GET /api/market/vector/gex-ladder?ticker=SPX&dte=0dte` returns `{ticker,spot,asOf,horizon,ladder:{spot,rows,maxAbs},depth,depthSpot}`. `buildGexLadder`'s default `maxRows=200` (`src/features/vector/lib/vector-gex-ladder.ts`) serializes to **18,858 chars** live for SPX (measured 2026-08-31 13:47 UTC, RTH) — **118% of `MAX_TOOL_RESULT_CHARS` (16,000, `src/lib/providers/tool-result-cap.ts`)**. `ladder.rows` (the 200-entry array) serializes BEFORE `ladder.maxAbs` — the per-row magnitude normalizer every bar's width/intensity depends on — and before the top-level `depth`/`depthSpot` fields. The transport's own cap is a raw tail-cut (`raw.slice(0, MAX_TOOL_RESULT_CHARS) + "…[truncated]"`, `anthropic.ts` line ~901), so an over-cap call drops `maxAbs`/`depth`/`depthSpot` entirely and cuts off roughly a third of the ladder (everything below strike 7325 on the 2026-08-31 SPX snapshot — including the most negative put wall on the board). Largo does not reach this route through a named tool with its own fitter (like every other oversized tool in `market-data-fits.ts`/`platform-snapshot-fit.ts`/etc.) — it reaches it generically through `call_internal_api` (`route-registry.ts` `class:"read"`, confirmed registered at line 104), whose only argument is an arbitrary `path` string. `callInternalApiRead` (`src/lib/bie/internal-api.ts`) does a governed GET and returns the parsed body completely unfitted — no size awareness at all. |
| **Why it wasn't caught by the existing truncation tooling** | `largo-truncation-probe.mjs`'s `LANE_TOOLS` list enumerates named tools with fixed argument recipes; `call_internal_api` isn't in it because its argument (`path`) is arbitrary rather than fixed, so no prior sweep — including the ones that found and fixed #2433/#2436/#2480 — ever exercised this specific path. `vector-rth-quick-check.mjs` measures the route's raw size but only logs it (no assertion), so the 118% number had been silently informational rather than a gate. |
| **Evidence** | Live fetch 2026-08-31 13:47 UTC via `scripts/audit/lib/audit-auth-fetch.mjs` (temp Clerk premium session): `JSON.stringify(res.json).length === 18858`; wrapped as `call_internal_api` would return it (`{ok,status,path,area,data}`) → **18,945 chars**, vs the 16,000 transport cap. `ladder.rows.length === 200`, two `isKing` rows (call king 7700, put king 7650). Confirmed the char-16000 boundary in the wrapped string lands mid-array (`"strike":7325,...`), well before `ladder.maxAbs`/`depth`/`depthSpot`. |
| **Blast radius** | Single route (`/api/market/vector/gex-ladder`) reached through the single generic tool (`call_internal_api`). No other named Largo tool was found to route through this specific path. The FIX is scoped there; `market-data-fits.ts`'s comment on the new function explicitly says to extend the same interception point if another `call_internal_api` route is later measured to overflow, rather than re-deriving a generic solution speculatively — no evidence any other route currently does. |
| **Fix** | Added `fitGexLadderForModel` (`src/lib/largo/market-data-fits.ts`), following the file's existing budget-bound convention (`fitEnvelopeToBudget`, not a fixed row count — the file's own history shows three rounds of fixed-count guesses each live-truncating anyway). Row **priority**, not array order, decides what survives a cut: the crowned king per side (`isKing`) is kept first (the single most load-bearing row — the exact strike the banner/chart/desk terminal all cite), then remaining rows ordered nearest-to-spot; kept rows are re-sorted back to the route's own descending-strike display order before returning, so a partial ladder still reads top-to-bottom like the full one. `maxAbs`/`depth`/`depthSpot`/`spot`/`asOf` are part of the base object on every budget iteration, so they can never be the field that gets cut regardless of how many rows survive. Wired into `run-tool.ts`'s `call_internal_api` case: after the governed fetch, if `result.path` starts with `/api/market/vector/gex-ladder` and `result.ok`, apply the fitter to `result.data` before returning. Every other `call_internal_api` path is unaffected. |
| **Fix rationale — why interception in `call_internal_api`, not in the route itself** | The route's own response shape (`ladder.rows` before `maxAbs`, array-order descending-by-strike) is correct for its actual UI consumer (`VectorGexLadder.tsx` — the panel wants exactly that order, and product consumers get the full 200-row payload unmodified, matching this repo's "product-first, fit only at the Largo boundary" convention stated at the top of `market-data-fits.ts`). Trimming at the route would degrade what members see for no reason. Trimming generically inside `callInternalApiRead` for every route was considered and rejected for this fix: it is genuinely generic (arbitrary path, arbitrary shape), and no other route is currently proven to overflow — a speculative generic array-capper risks corrupting unrelated JSON shapes it was never tested against, matching the "prove `.ok`, then something you did explains a truncated field" investigative discipline this repo already documents. Scoping to the one measured-overflowing path, in the same style as every other named-tool fix in this file, keeps the change small and testable while leaving a documented seam to extend if a second route is measured. |
| **Regression test** | `src/lib/largo/market-data-fits.test.ts` — 7 new tests using a live-shaped fixture (200 rows, 5pt strikes, spot 7673.58, real kings/maxAbs from the 2026-08-31 SPX capture): proves the fixture itself reproduces the overflow (sanity), proves the fitted result stays under the transport cap, proves `maxAbs`/`spot`/`asOf`/`depthSpot` always survive, proves both per-side kings always survive, proves kept rows are nearest-to-spot rather than an arbitrary head-of-array slice (the array's own order is descending-by-strike, so a naive head cut would never reach spot at all), proves display order is restored, and proves an under-cap input passes through untouched. Verified RED (function did not exist) via `git stash` before the fix, GREEN (16/16 pass) after. `npx tsc --noEmit -p .` clean. |
| **Status** | FIXED — PR opened, CI pending at time of write-up (see PR for current status). |

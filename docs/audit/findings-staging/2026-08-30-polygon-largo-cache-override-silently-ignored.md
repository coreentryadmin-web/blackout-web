## 2026-08-30 — [FINDING, P2 shared-infra] PR #3187's homepage-ISR fix deployed but did NOT work — `cache: "no-store"` silently survived the merge — FIXED

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **What this corrects** | PR #3187 ("prev-bar GEX fallback must not defeat homepage ISR," merged 2026-08-29 23:01 UTC) threaded an optional `{ next: { revalidate: 3600 } }` override through `polygon-largo.ts`'s `polygonGet`/`fetchPreviousDayBar` to stop a nested `no-store` fetch from forcing the marketing homepage into fully-dynamic rendering. The PR was correctly scoped and its own regression test passed — but the fix does not actually work in production. |
| **Live evidence it never worked** | Confirmed via `ecs describe-services`/`describe-task-definition`: production has been running task definition `blackout-production-web:1149` (image tag = commit `c7056988a`, a commit strictly AFTER #3187 in history) since 09:37:46 UTC — over 10 hours before this check. Despite that, a live CloudWatch sweep (2026-08-30, ~11:16 UTC) found the **exact same error signature #3187 was meant to close** — `[polygon-largo] /v2/aggs/ticker/SPY/prev failed: Dynamic server usage:... no-store fetch` — still firing repeatedly, most recently 3 minutes before the check (10:50, 10:57, 11:13 UTC). The fix was deployed and inert. |
| **Root cause** | `polygonGet`'s options object was built as `{ headers: {...}, cache: "no-store", ...fetchInit }`. A trailing spread only overrides a key when the spread object itself sets that key — `fetchSpotFromPrevBar`'s call only ever passed `{ next: { revalidate: 3600 } }`, never `cache`, so the hardcoded `cache: "no-store"` two lines above survived untouched into the real `fetch()` call, alongside the newly-added `next.revalidate`. Next.js's fetch patch treats `cache` and `next.revalidate` as mutually exclusive, and `cache: "no-store"` wins when both are present — so the "fix" merely added a key that never took effect. |
| **Why #3187's own test didn't catch it** | Its regression test (`polygon-options-gex.test.ts`) was a **source-text regex match** — `assert.match(src, /fetchPreviousDayBar\(symbol,\s*\{\s*next:\s*\{\s*revalidate:\s*3600\s*\}\s*\}\)/)` — confirming the call was *written*, never that the resulting merged fetch-options object actually omits `cache`. A test that inspects text, not behavior, cannot fail on a bug that only manifests in how two objects merge at runtime. |
| **A second, unrelated cause of the same blind spot** | While building the real regression test for this, discovered that `npx tsx --test <file>` (the invocation used earlier this session to judge whether `mock.module`-based tests "run in this sandbox") was missing the `--experimental-test-module-mocks` flag that `scripts/run-tests.mjs` (i.e. `npm test`, the actual CI command) always passes. Every `mock.module`-based test in this repo — including `largo-terminal.test.ts`, previously reported elsewhere as unable to run here — passes cleanly once invoked as `node --import tsx --experimental-test-module-mocks --test <file>`, matching `npm test`'s real invocation. A companion correction for the specific finding that leaned on the wrong conclusion (`2026-08-30-bie-orphan-files-more-entangled-than-noted.md`) is filed separately. |
| **Fix** | Replaced the trailing-spread merge with an explicit either/or: when `fetchInit.next` is provided, build the fetch options WITHOUT a `cache` key at all; otherwise fall back to the original default (`fetchInit?.cache ?? "no-store"`). The two shapes can never both carry `cache` and `next.revalidate` at once. |
| **Blast radius** | Single function (`polygonGet`), single file. The only caller passing `fetchInit` is `fetchSpotFromPrevBar`; every other `polygonGet`/`fetchPreviousDayBar`/`fetchAggBarsWithDiagnostics` caller (dozens, across Largo/0DTE/SPX/Vector) passes no `fetchInit` and gets the exact same `cache: "no-store"` default as before — verified by the second new test. |
| **Regression guard** | New `polygon-largo.test.ts` (didn't exist before), using `mock.module` on `./polygon-rate-limiter` to capture the ACTUAL options object `polygonTrackedFetch` receives (not source text): one test asserts `cache` is genuinely absent when `next.revalidate` is requested; one asserts the unchanged default for every other caller. Confirmed **failing** against the pre-fix code (`git stash` toggle: 1/2 failed with `actual: 'no-store', expected: undefined`) and passing post-fix. |
| **Gates** | `npx tsc --noEmit` clean · `npx eslint` clean on both touched files · `polygon-largo.test.ts` 2/2 pass · `polygon-options-gex.test.ts` 54/54 pass (re-run with the correct `--experimental-test-module-mocks` flag) · full `npm test` **11453 pass / 0 fail / 2 skipped** (Node 20.20.2). |
| **CI-only failure, caught and fixed post-open** | This PR's own `verify` CI run failed on `polygon-largo.test.ts` — both new tests, `bar`/`capturedInit` came back null despite the mock being wired correctly. Root cause: `polygonGet()` checks `polygonConfigured()` (`Boolean(process.env.POLYGON_API_KEY)`) and returns `null` BEFORE ever calling the mocked `polygonTrackedFetch` — this sandbox shell happens to carry a real `POLYGON_API_KEY` (used for live audits), so the tests passed locally and only failed in CI's clean env, where no such key exists. Fixed by setting a fake `process.env.POLYGON_API_KEY` at the top of the test file (same hermetic-fixture pattern `largo-terminal.test.ts` uses for `ANTHROPIC_API_KEY`) and reproduced the CI failure/fix locally with `env -u POLYGON_API_KEY node --import tsx --experimental-test-module-mocks --test src/lib/providers/polygon-largo.test.ts` (2/2 fail before the fixture, 2/2 pass after). A reminder that this sandbox's own leaked live credentials can mask a test's real CI behavior — worth checking `env -u <ANY_LIVE_KEY>` when a new hermetic test's local pass is the only evidence before pushing. |
| **Status** | FIXED |

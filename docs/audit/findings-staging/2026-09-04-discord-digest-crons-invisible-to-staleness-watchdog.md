| **Why this matters** | `buildCronHealthSnapshot()` (`src/lib/admin-cron-health.ts`) builds the entire admin cron-health board and feeds `cron-staleness-watchdog`'s Discord alerting by mapping over `CRON_JOBS` only (`const jobs = CRON_JOBS.map((job) => {...})` — confirmed by grep, no other iteration source). A cron key absent from that array is never evaluated for staleness, never self-healed (`CRON_WATCHDOG_SELF_HEAL`), and never painted red on the admin board — it simply does not exist from the monitor's point of view, even though it is running in production and posting to real Discord channels members can see. This is precisely the failure shape `cron-staleness-watchdog/route.ts`'s own header comment describes as the reason it exists (the #90 outage: "live-data warmers died ~3 days, nothing alerted") — except here the gap isn't a dead cron writing no row; it's a live, healthy cron whose rows nobody is watching. If any of these three silently stalls (a stuck Discord webhook, a crashed dependency, a rotated `CRON_SECRET`), the FIRST anyone would know is a member noticing the public Dark Pool / Thermal / HELIX Discord channel has gone quiet — not an internal alert. |

| **What this corrects** | `docs/audit/FINDINGS.md`'s "#3187's homepage ISR fix was necessarily narrow — two more no-store call sites in the same build path still recur" (2026-08-30) traced a recurring `Error: Page changed from static to dynamic at runtime /` naming `https://api.unusualwhales.com/api/stock/SPX/spot-exposures/expiry-strike?expirations[]=...&limit=500` to `fetchUwSpotExposuresExpiryStrike` (`unusual-whales.ts:2284`), claiming it "reaches these in its PRIMARY (non-fallback) spot-resolution path" of "the same homepage → `buildPublicGexSnapshot` → `fetchGexHeatmap` chain." Went to implement the suggested fix (thread a `next.revalidate` override through it, mirroring #3202's proven pattern) and could not find the call path the claim depends on. |
| **What a full trace actually shows** | `buildPublicGexSnapshot` (`public-gex-snapshot.ts`) imports only `fetchGexHeatmap`, no UW module at all. `fetchGexHeatmap`'s own UW touchpoints (`polygon-options-gex.ts`) are: (1) `resolveSpotSnapshot`'s last-resort branch, which dynamically imports `resolveSpotFromUwStockState` from `spot-fallback.ts` — that calls `fetchUwStockState`, a DIFFERENT function, not the one in question; (2) a degraded-matrix fallback (line ~2937-2938, "when Polygon chain snapshots return 403/empty") that dynamically imports `fetchUwSpotExposuresByStrike` — a SIMILARLY-NAMED but DIFFERENT function hitting `/api/stock/{ticker}/spot-exposures/strike` (no "expiry-" segment, and no `expirations[]` param — confirmed by reading its 2-line body). Neither of these two real UW touchpoints is `fetchUwSpotExposuresExpiryStrike`. |
| **The function the original finding named has exactly two real callers, neither in `/`'s render tree** | Repo-wide grep (all `.ts`/`.tsx`/`.mjs`, `src/` and `scripts/`, not just `src/lib`) for the literal call: `src/lib/largo/run-tool.ts:1370` (a Largo BIE tool — `get_gex_rows` or similar — invoked only from a member's Largo terminal session, via its own dedicated route, never as part of rendering `/`) and `src/lib/live-api-integrations.ts:31` (a URL-template registry/catalog entry, not executable code — it never calls anything). A sibling function with an identical call shape, `fetchUwOdteSpotExposuresByStrike` (`unusual-whales.ts:443`, same endpoint, same `expirations[]` param), is reachable only via `fetchUwOdteGexLadder`, which itself has **zero callers anywhere in the codebase** — fully dead, so it cannot be the source either. |
| **Why the original claim was plausible but wrong** | It matched by URL path + query parameters against the CloudWatch log (`expirations[]=2026-08-31&limit=500` is a distinctive, exact match for this function's call shape) rather than by tracing actual import/call edges from `buildPublicGexSnapshot` down. The match is real and precise — but matching *what a function would produce if called* is not the same as showing *it is actually called from the page in question*, and here it isn't. |
| **What this means for the suggested fix** | Threading a `next.revalidate` override into `fetchUwSpotExposuresExpiryStrike` (as the original finding's "suggested fix shape" proposed) would compile, look correct, and change **nothing** about the actual recurring error — the function it patches is not in the call path that produces it. Flagging this now, before anyone builds that fix on the earlier finding's evidence, is the point of this correction. |
| **What remains genuinely unresolved** | The true source of this recurring `expiry-strike` call inside `/`'s render is not identified. Live evidence that it is real and recurring is solid (5 occurrences in a fresh ~20-minute CloudWatch window, same exact URL/params, Next.js's own error explicitly names route `/`) — only the earlier finding's explanation of WHERE it comes from is what's being retracted here. Two directions worth checking next, neither attempted in this pass: (1) whether Next.js's dynamic-usage error can misattribute a concurrent, unrelated in-flight request's fetch to whatever route is also mid-render in the same server worker at that instant (would make the "at runtime /" attribution itself unreliable) — no time was spent verifying this against Next.js's own source/changelog; (2) a live, authenticated trace (temp Clerk session hitting `/` directly while watching CloudWatch in real time) to catch the actual triggering request rather than reasoning from static call-graph analysis alone. |
| **The Polygon half of the original finding is unaffected** | `fetchIndexSnapshot`'s call sites at `polygon-options-gex.ts:1280`/`:1314` (inside `resolveSpotSnapshot`) are real and confirmed — that part of the original trace holds. Investigated implementing its suggested fix too and backed off for a different, narrower reason: `resolveSpotSnapshot` is a shared real-time spot resolver also used by Thermal/Vector/SPX Slayer live dashboards (not isolated to the homepage build path), so a safe opt-in cache override would need to thread through 5 call-chain hops (`buildPublicGexSnapshot` → `fetchGexHeatmap` → `resolveSpotSnapshot` → `fetchIndexSnapshot` → `fetchIndexSnapshots` → `polygonGet`) all serving live-sensitive consumers — a materially larger and riskier change than #3202's single-hop precedent, and exactly the kind of shared-infrastructure edit the original finding was right to defer to the owning lane rather than guess at. |

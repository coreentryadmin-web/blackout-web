## 2026-08-29 — [FINDING, P1 Largo] Fixed-row-count truncation caps failed live THREE times in one day — switched to a runtime byte budget — FIXED

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **Symptom** | `get_market_oi_change`, `get_screener`, and `get_group_greek_flow` were each "fixed" for 16k transport-cap truncation twice in one day (#3155 → #3159 → #3162), and **still truncated live in production after the third deploy**. Live-reprobed 2026-08-29 22:15 UTC via `largo-truncation-probe.mjs` (control `get_zerodte_rejections` PROVEN) immediately after confirming, via `boto3`/ECS `describe_services`, that the ECS service was running 8/8 tasks on the EXACT image tag matching #3162's merge commit — ruling out deploy-propagation lag as the explanation. |
| **Timeline of the three failed attempts** | #3155: `get_market_oi_change` capped to 20 (est. ~300 bytes/entry) — TRUNCATED. #3159 (this session): re-measured live at ~635 bytes/entry, re-capped to 15 — deployed, **still TRUNCATED**. #3162 (a different lane, merged while this session was investigating): re-cut to 8 — deployed, ECS-confirmed fully rolled out, **still TRUNCATED**. Identical pattern for `get_screener` (15 → 6 → 3, all TRUNCATED) and `get_group_greek_flow`'s raw rows (15 → 8, both TRUNCATED). Only `get_platform_snapshot` (fixed via reusing `fitSpxStructureForModel`, not a fixed-count guess) held on re-verification. |
| **Root cause of the fixed-count approach failing repeatedly** | Every one of the three rounds measured average entry bytes via a one-time sandbox fetch (`UW_API_KEY` calls against the live UW API from this environment) and derived a row-count cap meant to stay under the transport's 16,000-char `MAX_TOOL_RESULT_CHARS`. Live production measurements consistently ran higher than the sandbox measurement for reasons not conclusively pinned down (ECS deploy state, task definition image tag, and Redis cache write/read paths were all inspected directly and found consistent with expectations) — but regardless of the exact cause, **a fixed row count is a bet that a point-in-time entry-size measurement holds everywhere and always**, and that bet lost three times running. |
| **Fix** | Rewrote `fitMarketOiChangeForModel`, `fitScreenerForModel`, `fitGroupGreekFlowForModel`, and `fitGroupGreekFlowRowsForModel` (`market-data-fits.ts`) to use `fitRowsToBudget` (`fit-tool-result.ts`) — an existing helper in this codebase, already used by `fitSpxStructureForModel`, that measures the **actual serialized byte size of the assembled object incrementally at runtime** and stops adding rows once the budget (`LARGO_RESULT_CHAR_BUDGET`, 87.5% of the transport cap) is reached. `maxShown`/`maxRows` is kept as a secondary ceiling (so a window of very small rows can't put an unreasonably long list in front of the model), but the byte budget is what actually prevents truncation — it cannot go stale relative to its own measurement, unlike a static count. Also applied the same fix pre-emptively to `fitEarningsRelatedNewsForModel` (a companion same-day fix, not yet deployed at the time) rather than risk it becoming a fourth failure. |
| **Call-site cleanup** | `run-tool.ts`'s three call sites (`get_market_oi_change`, `get_screener`, the `get_group_greek_flow` market-wide summary branch) dropped their explicit fixed-count overrides (`8`, `3`, `8`) so each function's own budget-bound default applies. |
| **Live re-verification, measured directly (not just via the probe)** | Fetched real live data (`fetchUwMarketOiChange(30)`, `fetchUwScreenerStocks(25)`, `fetchUwGroupGreekFlow("mag7")`) and ran it through the new fitters in-process: `get_market_oi_change` → 12,773 bytes (20 of 30 rows kept), `get_screener` → 13,717 bytes (7 of 25 kept), `get_group_greek_flow` rows → 10,764 bytes (15 of 391 kept) — all comfortably under the 16,000 cap, and notably each kept a **different** row count than any of the three fixed guesses ever used, which is exactly the point: the right count depends on the data, not on a constant chosen ahead of time. |
| **Regression guard** | Rewrote `market-data-fits.test.ts`'s tests for these four functions to run each fitter at BOTH the originally-measured entry size AND a deliberately much larger synthetic one (simulating exactly the kind of prod-vs-sandbox discrepancy that broke the fixed counts), asserting the fitted payload stays under the transport cap at both sizes — a fixture sized at exactly one measurement can't prove a self-correcting property, so both are required for the tests to mean anything. |

## 2026-08-31 — [FIX, P1 P&L integrity] Vector pick-leaders' `premium_pct_from_entry` silently drifts off a moving "entry" basis different from the displayed frozen `entry_mid` — FIXED

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **Context** | User asked to check Vector's plays for today and why the P&L display looked off. Live pulled `GET /api/market/vector/pick-closures/board` (2026-08-31 ~11:29 ET). |
| **Root cause** | `vector-pick-sweep.ts`'s `sweepVectorPickForTicker` re-ranks the candidate pool from the live option chain on **every sweep pass** (`vector-pick-sweep` cron, ~2min RTH). For a given ticker/rank/role/occ, the pick's `premium` (used as the fallback "entry") is whatever the live chain quotes on THIS pass — not a value pinned at first sight. Every pass computed `entryMid = pick.entryMid ?? pick.premium ?? null` and fed it BOTH into `evaluateVectorPickLiveStatus` (producing `premiumPctFromEntry`) AND into the leader upsert's `entryMid` field. But `upsertVectorPickLeader`'s `ON CONFLICT DO UPDATE SET` clause deliberately does **not** include `entry_mid` — it is first-write-wins, the same discipline as the 0DTE ledger's `entry_premium`. So on any pass after the first, the row's *displayed* `entry_mid` stays pinned to its original value while `premium_pct_from_entry` gets silently recomputed against a **different, current-pass** entry number — the two fields visibly stop reconciling. |
| **Evidence (live)** | `GET /api/market/vector/pick-closures/board`, 2026-08-31 ~11:29 ET: QQQ leader showed `entry_mid: 1.94`, `live_mid: 1.39`, `premium_pct_from_entry: -2.11` — but `(1.39-1.94)/1.94 = -28.4%`, not -2.11%. The number DOES reconcile against `pick_context.premium: 1.42` (the current pass's re-ranked premium): `(1.39-1.42)/1.42 = -2.1%` ✓. Same shape on SPY: displayed `entry_mid: 1.85` next to `premium_pct_from_entry: 0.48`, which only reconciles against `pick_context.premium: 1.04` (≈`(1.05-1.04)/1.04`), not against the displayed 1.85. |
| **Fix** | Added `fetchVectorPickLeaderEntryMid(leaderKey)` (`vector-pick-leaders-db.ts`) to look up the row's frozen `entry_mid` before each pass computes live status, and a pure `resolveVectorPickEntryMid(frozen, pickEntryMid, pickPremium)` helper (`vector-pick-sweep-core.ts`) that prefers the frozen value when a row already exists, falling back to the fresh pick's own fields only for a genuinely new leader. `sweepVectorPickForTicker` now calls this before `evaluateVectorPickLiveStatus`, so `premium_pct_from_entry` is always measured against the exact number the member sees as `entry_mid`. |
| **What was deliberately NOT changed** | The re-ranking/re-pricing logic itself (`buildRankedVectorPicks`) — a live chain re-ranking every pass is intentional and correct for picking NEW leaders. Only the entry basis used once a leader row already exists changed. `entry_mid`'s first-write-wins semantics in the DB were already correct; the bug was the JS-side % computation not honoring them. |
| **Evidence (tests)** | `resolveVectorPickEntryMid` new tests in `vector-pick-sweep-core.test.ts` — 3 cases (frozen value wins over a differing fresh pick premium; new-leader fallback chain; a frozen `0` is honored, not treated as absent). Git-stash proved RED (3/3 new subtests fail without the helper) → GREEN (16/16 pass) with the fix restored. `npx tsc --noEmit` clean (Node 20.20.2). |
| **Blast radius** | `vector-pick-sweep.ts` (the sole caller of `evaluateVectorPickLiveStatus` in the sweep), `vector-pick-leaders-db.ts` (new read helper), `vector-pick-sweep-core.ts` (new pure helper). No schema change — `entry_mid`'s DB semantics were already first-write-wins; this makes the JS-side % calc actually respect that. Every consumer of `premium_pct_from_entry`/`peak_premium_pct` (Winners/Runners classification, the `/vector` board, `pick-closures/board` API) now gets a number that reconciles with the `entry_mid` displayed alongside it. |
| **Status** | FIXED — merged pending CI. |

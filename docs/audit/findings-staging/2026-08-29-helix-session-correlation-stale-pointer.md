## 2026-08-29 — [FINDING, P3 Helix] Time-lagged flow correlation: a shared two-pointer index across lag windows undercounted the 10/15-min lags relative to the 5-min one — FIXED

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **Symptom** | `computeSessionFlowCorrelations` (`src/features/helix/lib/helix-session-correlation.ts`), which powers the Session Correlation Matrix panel ("which tickers tend to print in the same direction shortly after a leader print"), could report a **larger** lag window (10 or 15 min) with **fewer** `followerHits` than the 5-min window for the identical leader/follower pair — mathematically impossible, since a wider time window is a strict superset of a narrower one and can only match equal or more hits. |
| **Root cause** | `followerIdx`, a two-pointer index into the follower ticker's sorted print list, was declared once per `(leader, follower)` pair — *outside* the `for (const lagMin of lags)` loop — but the `while` loop that advances it only ever moves forward, never resets. `HELIX_CORRELATION_LAGS_MIN` defaults to `[5, 10, 15]`, and each lag pass re-walks the SAME `leaderList` from its start. After the 5-min pass finishes (having advanced `followerIdx` to wherever it ended up, near/at the end of the follower list), the 10-min pass restarts its leader walk from the earliest print — but `followerIdx` is stuck near the end, so `followerHitWithinLag` starts searching from the wrong position and misses follower prints that occurred earlier in time but are still valid matches for the wider window. |
| **Concrete repro** | Two SPY leader prints (14:00, 14:20), each followed 3 minutes later by a same-direction QQQ print — both pairs are well within all three lag windows, so every lag should report `followerHits=2`. Pre-fix, executed directly: `lag=5min → hits=2`, `lag=10min → hits=1`, `lag=15min → hits=1`. |
| **User impact** | The Session Correlation Matrix's 10-min and 15-min lag rates were systematically undercounted relative to the 5-min rate whenever multiple leader prints exist in a session (the normal case, not an edge case). A member or Largo reading "10-min correlation is weaker than 5-min" for a pair could be seeing an artifact of iteration order, not a real signal decay. Single consumer confirmed (`SessionCorrelationMatrix.tsx`) — pure display, no downstream trading/gating logic reads this function's output. |
| **Why not caught earlier** | The existing test suite (`helix-session-correlation.test.ts`) only ever passed a single lag value (`{ lags: [5] }`) to the function, never the multi-lag default `[5, 10, 15]` — so `followerIdx` never crossed a lag-pass boundary in any existing test, and the shared-pointer bug was structurally invisible to it. |
| **Fix** | Moved `let followerIdx = 0;` inside the `for (const lagMin of lags)` loop, so each lag pass gets its own fresh pointer and re-walks the follower list from the start — matching the fact that each pass also re-walks `leaderList` from the start. |
| **Regression guard** | New test: `"a larger lag window never scores FEWER hits than a smaller one (monotonicity)"` — the repro above, run through the real multi-lag default, asserting `followerHits` at lag 5/10/15 are all equal. Confirmed failing pre-fix (`1 !== 2` at lag=10/15) and passing post-fix. |
| **Found by** | A background read-only investigation targeted at Helix — a surface with comparatively little direct code activity in recent `git log` — as part of Discovery's ongoing sweep, reading through 13 core Helix computation files before finding this in the 13th. Independently reproduced by direct execution before the fix was written. |

| **Status** | FIXED. |

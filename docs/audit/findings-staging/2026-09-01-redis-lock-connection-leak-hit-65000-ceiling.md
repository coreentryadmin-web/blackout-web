## 2026-09-01 — [P1, infra] rth-warm-leader.ts + vector-bead-recorder-leader.ts leaked one unclosed Redis connection per tick, pegging ElastiCache at its 65,000-connection ceiling for 30+ minutes mid-RTH — FIXED

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **Context** | User flagged "so many CloudWatch errors" during the live 0DTE/Vector deep-dive session. Pulled recent `/ecs/blackout-production` and `/ecs/blackout-production-market-worker` log groups. |
| **Symptom** | 1000+ `redis error` lines (API-capped, actual count higher) across `vector-bead-recorder`, `rth-warm-leader`, `bie-redis-probe`, `uw-rate-limiter` — `write EPIPE`, `read ECONNRESET`, then `connect ETIMEDOUT` — clustered 13:31-14:03 UTC (9:31-10:03 ET), i.e. the first ~35 minutes of today's RTH. Concurrent `[db] transient query error: timeout exceeded when trying to connect` on Postgres. |
| **Root cause** | `CloudWatch/AWS/ElastiCache CurrConnections` on the primary node (`blackout-production-redis-rg-001`) was pegged FLAT at exactly 65,000-65,002 from 13:33 to 14:03 UTC — a hard connection ceiling, not organic load (CPU 11-17%, FreeableMemory 1.7-2.2GB, zero swap, all healthy throughout). `getLockRedis()` in both `src/lib/rth-warm-leader.ts` and `src/lib/vector-bead-recorder-leader.ts` called `makeRedis(...)` (which does `new Redis(...)` + `.connect()`) on **every invocation**, with no caching and no `.disconnect()`/`.quit()` anywhere in either file. `vector-bead-recorder-leader.ts`'s `readHeldSlots()` calls `getLockRedis()` on every 5-second universe tick; both files' `startLeaderRefresh()` calls it every 15 seconds, forever, once leadership is held — one new leaked TCP connection per interval, per ECS replica, for the life of the container. Two sibling modules on the same shared Redis cluster (`uw-rate-limiter.ts`, `redis-health.ts`) were checked and are correctly implemented — one caches+reuses (`if (sharedRedis) return sharedRedis`), the other explicitly `.disconnect()`s in a `finally` block ("one-shot probe... never held open") — confirming this is a defect isolated to the two leader-lock files, not a systemic pattern. Their own error volume in the logs is a downstream symptom (failing to get a connection slot on an already-saturated cluster), not an independent leak source. |
| **Why today** | A slow per-process leak (1 connection/15s minimum, 1/5s in the vector-bead-recorder case) only saturates a 65,000-connection ceiling after enough continuous container uptime — consistent with this surfacing today rather than being visibly broken since it shipped. `vector-bead-recorder-leader.ts`'s leader-lock pattern is explicitly commented as copied "same pattern as rth-warm-leader.ts", which is exactly how the bug propagated to both. |
| **Fix** | Added a module-level `cachedLockRedis` variable to both files' `getLockRedis()` — return the cached client if present, otherwise connect once and cache it, mirroring the already-correct pattern in `uw-rate-limiter.ts`. No behavior change to the lock semantics themselves (SETNX/renew/release logic untouched) — purely fixes the connection lifecycle. |
| **Evidence of recovery** | `CurrConnections` began declining once the day's first ECS deploy (from PR #3256, unrelated) cycled in fresh containers: 65,002 → 60,226 (14:08) → 53,665 → 46,521 → 41,197 → 32,886 (14:18 UTC). This is NOT a durable fix — a redeploy resets the leak's clock, it does not remove it — hence this PR. |
| **What was deliberately NOT done** | No new unit test was added for `getLockRedis()`'s caching behavior — neither file has any existing Redis-mocking test harness (unlike `scan.test.ts`'s `mock.module` pattern for a different subsystem), and building one from scratch was judged disproportionate to a 3-line, visually-verifiable fix during a live incident. Verified instead via `npx tsc --noEmit` (clean) and the full existing test suites for both files' siblings (`rth-warm-leader.test.ts`, `uw-rate-limiter.test.ts`, `redis-health.test.ts`, `vector-bead-recorder-logic.test.ts`, `leader-lock-fencing.test.ts` — 38/38 pass, Node 20). |
| **Status** | FIXED — PR pending. |

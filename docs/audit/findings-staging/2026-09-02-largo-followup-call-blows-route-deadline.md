## 2026-09-02 — [FINDING, P1 Largo/core] `generateLargoFollowups`'s second Anthropic round-trip blows past the route deadline — a hard-won multi-desk synthesis answer is discarded entirely — FIXED

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **How found** | Operator asked to act as Largo's product owner and fire hard, realistic questions at the live production `/api/market/largo/query` endpoint (authenticated member path, `scripts/audit/largo-stress-suite.mjs`). Fired a genuinely hard cross-product synthesis question a real power user would ask: *"Why is SPX bullish or bearish right now, what does Helix show on the tape, how does Thermal's dealer positioning align, and what would invalidate the Night Hawk thesis?"* |
| **Symptom** | HTTP 503, `100358ms`, member-visible body: `"This question ran long before the desk could finish. Try Quick read, or ask about one ticker or one desk."` — a bare timeout with the answer fully discarded, not a partial or degraded read. |
| **Root cause** | The route wraps `runLargoQuery` in a hard `Promise.race` against `largoMemberRouteDeadlineMs()` (100s) — `largoRouteDeadlineRace` in `src/app/api/market/largo/query/route.ts` — and if the deadline timer wins the race it REJECTS, discarding whatever `runLargoQuery` had already produced. The tool loop itself is deliberately budgeted under that deadline (`largoLoopBudgetMs`, 75s for deep mode, clamped below `largoToolLoopBudgetMs()`) specifically to leave ~25s of headroom for post-loop work. But `generateLargoFollowups` (`src/lib/largo-terminal.ts`) makes a SECOND, entirely separate Anthropic round-trip AFTER the tool loop returns — one that ISN'T accounted for by either budget. That call has its own `timeoutMs: 14_000` and `maxRetries: 1`, so in the worst case it alone can cost up to ~28s — more than the entire headroom the loop budget was supposed to leave. Confirmed live: CloudWatch `/ecs/blackout-production` logged `[market/largo/query] exceeded 100000ms route deadline` at the exact moment of the probe's 100358ms response. |
| **Why it wasn't caught earlier** | `src/lib/largo/loop-budget.test.ts` and `src/lib/largo/deep-depth-block.test.ts` already test that the LOOP budget stays safely under the route deadline with margin to spare — but neither accounts for `generateLargoFollowups`'s independent, unbudgeted call, which sits entirely outside the loop both budgets were written to bound. A budget test that only checks the loop, on a turn whose real cost includes a second uncounted LLM call, passes cleanly while the real system still blows the deadline. |
| **Fix** | `generateLargoFollowups` now takes an optional 4th arg, `remainingBudgetMs` — the caller's remaining route-deadline headroom (`largoMemberRouteDeadlineMs() - (Date.now() - startedAt)`, passed from both `runLargoQuery` and `runLargoQueryStream`, the two call sites). Once headroom is below `FOLLOWUP_MIN_REMAINING_MS` (`FOLLOWUP_CALL_TIMEOUT_MS` (14s) + 8s margin), the function skips the LLM call outright and falls back to the free, synchronous `deterministicLargoFollowups` — the member still gets their hard-won answer plus generic-but-real follow-ups, instead of nothing. Omitting the 4th arg preserves the old always-attempt behavior (no other call site exists). |
| **Fix rationale** | Considered raising the route deadline or shrinking the loop budget further instead — rejected both: the route deadline is already near the ALB's own upstream timeout ceiling (widening it risks a raw ALB 504 with zero graceful handling instead of this route's own honest message), and shrinking the loop budget further would cut into the tool loop's own real work margin to solve a problem the loop isn't causing. Budgeting the SPECIFIC unaccounted call is the narrower, correct fix — it leaves both existing budgets untouched and only trims a "nice to have" (LLM-personalized follow-ups) when time is genuinely tight, never the primary answer. |
| **Blast radius** | Both `generateLargoFollowups` call sites in `largo-terminal.ts` (the non-streaming and streaming turn paths) — the only two callers of this function. No other function shares this shape (checked: no other post-tool-loop Anthropic call sits between the tool loop's return and the route's response). |
| **Regression guard** | `src/lib/largo-terminal.test.ts`, three new tests: (1) a low `remainingBudgetMs` (5s) skips the LLM call entirely and still returns non-empty deterministic follow-ups; (2) ample headroom (60s) attempts the call as before; (3) omitting the arg preserves old always-attempt behavior (back-compat). Verified via git-stash: test (1) fails pre-fix (`1 !== 0` — the call fired anyway), passes post-fix; (2) and (3) pass in both states (proving the fix doesn't change existing behavior when headroom is ample or unspecified). |
| **Not fully closed** | This closes the SPECIFIC mechanism measured live (the follow-up call). The same live adversarial pass also surfaced two DIFFERENT-shaped defects on other multi-tool cross-product questions (`lane-comparison`, `conflict-probe`: 6-8 real tools called successfully, yet the turn still returns the generic "I couldn't pull enough live data" decline) — that is a distinct code path (`classifyEmptyAnswer`'s `no_data` fallthrough, not the route-deadline race) and is being investigated separately, not folded into this fix to keep this PR single-issue. |
| **Gates** | `npx tsc --noEmit` clean · `node --import tsx --experimental-test-module-mocks --test src/lib/largo-terminal.test.ts` 16/16 · full `npm test` — 1 unrelated pre-existing failure confirmed present on `origin/main` before this change (`LegacyPickLogBoard.test.ts`, from PR #3297/nighthawk lane, reproduced independently via git-stash with none of this PR's changes applied) — everything else pass, 0 other fail. |
| **Status** | FIXED. |

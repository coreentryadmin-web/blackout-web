### Reproduction (prod, 2026-10-26, session with 500-row cap, "STALE 500 · 52h ago")

1. Minted a temp premium Clerk session (`mintClerkPremiumSession`), opened `https://blackouttrades.com/flows` at desktop viewport (1440×900, `--desktop`).
2. `node proxy-browser.cjs .../flows out.png --viewport 1440x900 --desktop --wait 9000 --full` — this does a 9s initial wait, up to 15s `networkidle` wait, then `scrollThrough()` (incremental `window.scrollTo` in 900px steps, 700ms settle each, capped at 40 steps — a page this tall needs ~24 steps, comfortably under the cap) before the full-page screenshot. Total elapsed budget before the shot: 30-40+ seconds.
3. Result: `document.body.scrollHeight = 21095px`. A horizontal-band scan of the PNG (sampling max pixel value every 100px of height) found real content continuously from y≈0 to y≈17100, then **flat black (`max <= 8`, i.e. nothing painted) from y≈17200 to y≈20900 — roughly 3700px, about four full 900px viewports** — before the page's own static footer ("Educational. Not advice. You decide.") resumes at y≈21000. Zoomed crops at both boundaries confirm it directly: the table's last visible row is a real print (`10/23/2026 - 15:54 · MXL · C · 11/20/26 · 70 · $399K`), immediately followed by pure background, no "Load older prints" button, no skeleton, nothing — all the way to the footer.
4. Separately, with a fresh session, evaluated the live DOM directly: `window.scrollTo(0, document.body.scrollHeight)` once, wait 2s, then query `[data-helix-tape-row]`. **All 500 rows (`data-index` 0-499) are present in the DOM with real, non-empty text content and a consistent measured height (41.25px each)** — sampled indices 0, 50, 100, …, 490, 495, 499 all returned real print rows (tickers, strikes, premiums), none blank. So the data the blank gap is "covering" genuinely exists and genuinely renders correctly — just not during the realistic incremental-scroll pass that produced the screenshot in step 3.
5. Also confirmed: `.helix-tape-scroll`'s `scrollHeight === clientHeight` (20601px both) — i.e. the div is **not actually an independently-scrolling, viewport-bounded container** on this route despite its CSS (`flex:1 1 auto; min-height:0; overflow:auto`, `globals.css` `.helix-tape-scroll`) being written for exactly that. `.helix-tape`'s own `flex flex-1 flex-col min-h-0` only bounds a flex child's height when an ancestor actually constrains the flex column's own height (e.g. a `h-screen` shell); `FlowFeed.tsx`/the `/flows` route has no such ancestor (grepped — no `h-screen`/`min-h-screen`/height-bounded wrapper), so the whole page is a normal long-scrolling document and `.helix-tape-scroll` just grows to its full content height. The window, not this div, is the thing that actually scrolls.

### Root cause (confirmed facts vs. open question)

**Confirmed:** `useVirtualizer`'s `getScrollElement` is bound to `.helix-tape-scroll` (`scrollRef.current`), the element that per point 5 above never itself receives a native `scroll` event on this route — the window does. react-virtual recalculates its rendered range off its scroll element's own `scrollTop`/resize signals, not off `window`'s scroll position. Despite that mismatch, the list does eventually reach 100% rendered (confirmed in step 4) — almost certainly via its `measureElement` ResizeObserver path (each newly-rendered row's real measured height feeds back into `getTotalSize()` and can grow the scroll element's own reported size, which is itself observed, cascading into more of the range being treated as "in view") rather than via any `scroll`-event-driven recalculation, since the latter structurally can't fire here.

**Open / not yet pinned down by this pass:** *why* that cascade reliably finishes within ~2s of a direct scroll-to-bottom jump (step 4) but did not finish — or never triggers at all without that specific jump — within the ~30-40s budget of a realistic incremental scroll-through (step 3), leaving roughly the last 80-100 of 500 rows (indices ~410-499, all confirmed real and non-empty) permanently unpainted for that session. Candidates worth checking before patching: (a) whether `scrollThrough`'s intermediate `window.scrollTo` calls land inside a range react-virtual's resize-observer cascade considers "no longer growing" and stops short; (b) whether the cascade requires a true `scroll`/resize event that only a hard jump to the true document bottom happens to produce (e.g. a last-element `IntersectionObserver` or similar used elsewhere in the tape); (c) whether this is purely a timing race against the 40-step/28s cap in `scrollThrough()` specifically (i.e. real users who scroll slower or faster might see different cutoff points), which would make the *screenshot tool's* pacing a red herring and the *underlying* mismatch (scroll element ≠ actual scrolling element) the only thing that matters for members.

### Why this matters for a real member, not just this tool

The reproduction in step 3 approximates a human scrolling down the tape at a normal pace (not an instant jump) — exactly how a member would scroll through HELIX's flow history after returning to a stale/weekend session (the "STALE 500 · 52h ago" state this was captured under is a completely ordinary off-hours condition, not an edge case). If the underlying mismatch in point 5 is what step 3 is actually exercising, a member doing the same thing would see the same large dead zone over real historical prints partway down the tape — not a cosmetic clipping issue (like the already-fixed STACK/NEW/REPEAT badge clipping bug earlier in `FINDINGS.md`) but rows **silently failing to appear at all** despite being loaded and correct.

### Ruled out this pass (already fixed/intentional, not re-reported)

While looking at this same desk for a contradiction, two candidates turned out to be already-handled by very recent work and are **not** part of this finding:
- `HelixSessionPulseBar`'s "Aggression read: Unreadable / No ask-side data" vs. `HighScorePrints`' per-row aggressor labels (same `displayAlerts` pool) — `helix-session-pulse.ts`'s own doc comment and `helix-session-pulse.test.ts` (bug-fix dated 2026-10-25, i.e. the day before this pass) show this exact "two-labels-disagree" shape was already found, deliberately resolved (both "no readable premium" and "undetermined > readable" collapse to one "Unreadable" state on purpose), and tested.
- `NetPremiumLeaderboard`'s arrow (aggression-aware direction) disagreeing with its `net` premium's arithmetic sign (calls − puts) — `NetPremiumLeaderboard.tsx` lines 88-92 and its own `title` tooltip explicitly document this as an intentional split (measured 2026-08-23, 7/10 top tickers disagree) with the arrow and the sign answering two different, both-true questions.

### Suggested next step (not implemented here)

Instrument (temporarily, locally) `virtualizer.getVirtualItems().length` across a real `scrollThrough()`-style incremental scroll on a 500-row session to see exactly where/if it stalls, before deciding between (a) rewiring the virtualizer to react to `window` scroll/resize directly since `.helix-tape-scroll` structurally can't be the real scroll element on this un-height-bounded route, or (b) restoring an actual height bound on `.helix-tape`/`.helix-tape-scroll` on the `/flows` route so the CSS that already exists for exactly this (`overflow:auto`, `flex:1 1 auto; min-height:0`) does what it was written to do, making the div the genuine scroll element the virtualizer already assumes it is. Both are real, non-trivial layout changes to a shared, single-consumer-but-heavily-used component — left for a deliberate fix rather than a same-pass patch.

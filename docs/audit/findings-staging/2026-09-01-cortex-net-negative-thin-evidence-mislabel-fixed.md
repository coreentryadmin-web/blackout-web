## 2026-09-01 — [P1, 0DTE Cortex] thin-evidence block mislabeled NET_NEGATIVE, describing non-negative scores as "against" the direction — FIXED

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **Context** | One of the Phase-0 items surfaced during the `nighthawk-0dte-redesign` workflow's audit ("the Cortex NET_NEGATIVE mislabel fix touching 5+ consumers"). Investigated fresh from the code (not from the workflow's own notes) to independently confirm the defect before fixing. |
| **Root cause** | `assessCortexVerdict` (`cortex-gate.ts`) has two separate code paths that both returned `decision: "NET_NEGATIVE"`: (1) the genuine case, `if (verdict.score < 0) return { decision: "NET_NEGATIVE", ... }`, which fires first; (2) the thin-evidence gate, `if (answering < THIN_EVIDENCE_MIN_SOURCES && verdict.score < THIN_EVIDENCE_SCORE_FLOOR) return { decision: "NET_NEGATIVE", ... }`. Because path (1) already returns for every genuinely negative score, path (2) can only ever be reached with `verdict.score >= 0` — `THIN_EVIDENCE_SCORE_FLOOR = 0.5` is a strictly positive constant, so this branch fires for scores in `[0, 0.5)` when too few sources answered. Labeling that case `NET_NEGATIVE` was factually wrong: `cortexGateBlocks`'s reason text for `NET_NEGATIVE` reads `"Cortex evidence nets ${score} against this ${direction}..."`, which for a thin-but-positive score (e.g. `+0.1`) literally described supporting evidence as opposing the direction — confirmed directly in the existing test suite, whose own test title read *"a bare +0.1 from <2 sources is blocked as NET_NEGATIVE"* without anyone flagging that a positive number being called NET_NEGATIVE is self-contradictory. |
| **Evidence** | `assessCortexVerdict({ score: 0.1, supports: [...one thin item...], absent: [...7 of 8 sources...] })` returned `decision: "NET_NEGATIVE"` and `cortexGateBlocks(...)` produced `reason: "Cortex evidence nets +0.1 against this short..."` — a positive score described as opposing evidence. The block itself was always correct (thin evidence should not clear the bar); only the label and reason text describing *why* were wrong. |
| **Fix** | Added a new decision value, `THIN_EVIDENCE`, distinct from `NET_NEGATIVE`. The thin-evidence branch in `assessCortexVerdict` now returns `decision: "THIN_EVIDENCE"` instead of reusing `NET_NEGATIVE`. `cortexGateBlocks` gained its own `THIN_EVIDENCE` case with an accurate reason (`"Only N of M Cortex sources answered... net [score] does not clear the floor... even though the score itself is not negative"`) and its own code, `cortex_thin_evidence`. Updated every consumer that reads the decision string or the block code to include the new value: `ZeroDteCortexDecision`/`ZeroDteCortexAssessment`/`ZeroDteCortexSummary`/`ZeroDteCortexEntryContext` type unions (`cortex-gate.ts`), `ZeroDteGateFailure` (`board.ts`, adds `"cortex_thin_evidence"`), `PaneCortexView`/`CORTEX_DECISIONS`/`readCortexView`'s cast (`pane.ts`), `GATE_LABELS`/`isCortexBlockCode` (`pane.ts` — the latter is load-bearing: it drives SKIP-card highlighting in `ZeroDteBoard.tsx` AND filters Largo's "Cortex skips" reporting in `cortex-read.ts`, so omitting it there would have made thin-evidence blocks silently disappear from both), and `cortexScore()`'s block-detection OR-chain (`thesis-health.ts` — omitting it there would have made a thin-evidence-blocked row's health score silently flip to a `PASS`-shaped reading, since `score` is a real non-null number that would otherwise fall through to the PASS branch). |
| **What was deliberately NOT changed** | `tiers.ts`'s `W_CORTEX_NEGATIVE` weighting — investigated and confirmed it derives from the raw `input.cortexScore < 0` number directly, never from the decision string, so it was never actually affected by this mislabel and needed no change. The genuine `NET_NEGATIVE` path (`verdict.score < 0`) and its reason text — untouched; a real negative score is still `NET_NEGATIVE` and still cites "against" correctly. `THIN_EVIDENCE_MIN_SOURCES`/`THIN_EVIDENCE_SCORE_FLOOR` values themselves — not recalibrated, this is a labeling fix, not a threshold change. `categorizeGateBlocks`/`classifyGateBlock` (`playbook-gate-categories.ts`) — confirmed it classifies by reason-text regex, has no cortex-specific pattern either before or after, and both `cortex_net_negative` and `cortex_thin_evidence` fall through to the same `"quality"` default as before, so no change needed. |
| **Blast radius checked** | Whole-repo grep for `NET_NEGATIVE` and `cortex_net_negative` before and after, tracing every hit to either a now-correct call site or an accurate illustrative comment (`scan.ts`, `cortex-read.ts` doc comments use "cortex_net_negative" as one example among the family of Cortex blocks, not an exhaustive claim — left as-is). `spx-play-outcomes.ts`/`entry-context.ts` (importers of `ZeroDteCortexEntryContext`) confirmed to consume the type only structurally, no literal decision comparisons. |
| **Regression guard** | `cortex-gate.test.ts`: 33/33 pass — includes an updated test proving the thin-evidence block is now `THIN_EVIDENCE`/`cortex_thin_evidence` with a reason matching `/not negative/` and NOT matching `/nets \+0\.1 against/`, plus a new test proving a genuinely negative thin-evidence case (`score: -0.3`, few sources) still correctly resolves to `NET_NEGATIVE`. `pane.test.ts`/`thesis-health.test.ts`/`tiers.test.ts`/`spx-play-engine.test.ts`: 63/63 pass. Full `src/lib/zerodte/*.test.ts` + `thesis/*.test.ts` + `src/features/spx/lib/*.test.ts` + `src/lib/bie/*.test.ts` combined: 2692 pass / 0 fail / 1 pre-existing skip (Node 20, `--experimental-test-module-mocks`). `npx tsc --noEmit` clean. |
| **Status** | FIXED — PR pending. |

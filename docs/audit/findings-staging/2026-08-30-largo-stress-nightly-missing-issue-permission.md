## 2026-08-30 — [FINDING, P3 CI/tooling] `largo-stress-nightly.yml`'s own failure alert was silently broken — the exact mechanism that hid PR #3203's regression for hours — FIXED

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **What this follows up on** | PR #3219 (this repo, same day) restored `src/lib/bie/decompose.ts` after PR #3203 (this DISCOVERY lane, earlier this cycle) wrongly deleted it as dead code, breaking `scripts/largo-stress-run.mjs`. #3219's own write-up noted in passing: *"the workflow's own failure-reporting step is separately broken (missing issue-creation permission), so the breakage produced no alert."* That second bug was never itself fixed — went to close it. |
| **Root cause** | `.github/workflows/largo-stress-nightly.yml`'s "Open ops issue on failure" step calls `github.rest.issues.create` via `actions/github-script@v9`, but the workflow file declared no `permissions:` block at all. Without one, the default `GITHUB_TOKEN` gets this repo's default (read-only) scope for issues, so the failure-reporting step itself fails — a second, compounding failure on top of whatever broke the actual stress run, with no external symptom beyond a red Actions run nobody was watching. |
| **Live evidence this is a real, working pattern elsewhere in the repo** | `.github/workflows/ops-auto-fix.yml` already declares exactly `permissions: {contents: read, issues: write}` for the same reason (its own issue-creation on production-error sweeps). `largo-stress-nightly.yml` was simply never given the same grant when its own failure-reporting step was added — an oversight, not a design choice; every other GITHUB_TOKEN-permission workflow in this repo (`agent-pr-release.yml`, `automerge.yml`, `codeql.yml`, `dependabot-auto-merge.yml`, `ecr-push-production.yml`, `rth-autonomous-open.yml`) declares its own scoped `permissions:` block rather than relying on the ambient default. |
| **Why this matters beyond the one incident** | This is the mechanism, not just one broken alert: any future regression in the Largo stress bank fails exactly the same way — the stress run fails, the "alert on failure" step ALSO silently fails, and nothing pages anyone until a manual sweep of the Actions tab happens to notice. #3203's `decompose.ts` deletion sat broken from ~11:56 UTC until #3219 found it via exactly that kind of manual sweep, not a report. |
| **Fix** | Added `permissions: {contents: read, issues: write}` to `largo-stress-nightly.yml`, matching `ops-auto-fix.yml`'s proven pattern exactly (same two keys, same values). |
| **Regression guard** | New `src/largo-stress-nightly-permissions.test.ts` — generalized rather than pinned to one file: scans every `.github/workflows/*.yml` for any that call `github.rest.issues.create`, and asserts each one declares a top-level `issues: write` permission. Currently matches only `largo-stress-nightly.yml` (the only workflow calling `issues.create` directly today), but the guard is written to catch any FUTURE workflow added the same way, not just this one file. Confirmed **failing** against the pre-fix workflow file via `git stash` toggle, passing post-fix. Same source-text-guard convention this repo already uses for workflow files (`automerge-token-recursion.test.ts`) — no YAML-parser dependency needed. |
| **Gates** | `npx tsc --noEmit` clean · `npx eslint` clean · new test 2/2 pass (Node 20.20.2) · `python3 -c "import yaml; yaml.safe_load(...)"` confirms the edited workflow file is still valid YAML · full `npm test` at this commit: **11501 pass / 0 fail / 2 skipped**. Not independently verified: an actual live GitHub Actions run exercising the fixed permission (the bug is in the GitHub Actions permission system itself, unreachable from local `npm run` tests) — the next scheduled nightly run (`30 6 * * *` UTC) or an operator-triggered `workflow_dispatch` is the first real confirmation. |
| **Status** | FIXED |

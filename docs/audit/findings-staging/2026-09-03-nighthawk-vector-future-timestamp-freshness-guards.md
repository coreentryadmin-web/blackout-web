## 2026-09-03 — [FINDING, P2 correctness, Night Hawk/Vector] 4 more staleness/freshness checks read a future-dated timestamp as trustworthy — FIXED

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **What prompted this** | Companion to `docs/audit/findings-staging/2026-09-03-spx-future-timestamp-freshness-guards.md` (same sweep, same session): the same sweep of SPX Slayer/Night Hawk/Vector/Banger for the future-timestamp-freshness bug pattern (16 sites already fixed this session before this sweep) also found 4 sites outside SPX Slayer, covered here. Banger had none (only same-process `duration_ms` logging, no eligible sites). |
| **Root cause / sites** | (1) `morning-confirm-verdict.ts`'s `isMorningConfirmStale` — `checked_at` is written by a separate cron process; a future-dated value never exceeded `MORNING_CONFIRM_STALE_MS`, leaving the "as of" qualifier off a frozen 9am verdict badge whose real age can't be verified. (2) `ZeroDteBoard.tsx`'s `resolveZeroDteFreshness` — plain client/server clock skew on `asOfMs` always read "live"; notably, this component's *sibling* staleness path already imports `marks-math.ts`'s `isZeroDteMarkStale` (correctly guarded) elsewhere in the same file — this specific function was simply missed when that guard was added. (3) `scorer.ts`'s `congressTradeDecayMultiplier` — a `filed_at`/disclosure date from an EXTERNAL congressional-trade feed (known to carry messy/malformed dates) in the future produced a negative `ageDays` that satisfied `<= 7`, handing a bad date the MAXIMUM 1.0x recency multiplier instead of the 0.4x floor every other unverifiable date gets — this one actively boosts a scoring signal on bad data, not just marks it fresh. (4) `vector-universe-merge.ts`'s `mergeUniverseSnapshot` — a future-dated `asOf`/`updatedAt` (cross-process clock skew across ECS tasks writing the shared universe snapshot) carried an untrustworthy row forward indefinitely instead of expiring it. |
| **Fix** | Sites 1-3 import and use the existing `ZERODTE_MARK_FUTURE_TOLERANCE_MS` constant (60s, from `marks-math.ts`, the same one used across this session's SPX Slayer fixes) rather than reinventing a tolerance. Site 4 (Vector) defines its own local `FUTURE_STAMP_TOLERANCE_MS` matching the same 60s value and Helix's `FUTURE_PRINT_TOLERANCE_MS` shape, kept local rather than importing across the zerodte/vector boundary since this file is otherwise dependency-free by design (per its own header). Each guard rejects — treats as untrustworthy/stale/discounted — a timestamp more than the tolerance ahead of `now`, rather than reading it as freshest-possible. |
| **Blast radius** | Four files, one call site each. No thresholds, schedules, or unrelated logic changed. |
| **Regression guard** | Proper behavioral tests for the 2 easily-testable sites: `morning-confirm-verdict.test.ts` (2 new tests — well-future is stale, a few seconds ahead is ordinary skew and not stale) and `vector-universe-merge.test.ts` (2 new tests, following the file's existing `row(ticker, ageMs)` negative-age convention for future-dating). Source-text regression tests for the 2 DB/React-component sites where the function is unexported or the component isn't otherwise unit-tested, matching this session's established convention: new `scorer-congress-decay-freshness.test.ts` and `ZeroDteBoard-freshness.test.ts`. Confirmed RED pre-fix (`git stash` all 4 source files, keep the tests: exactly the 6 new assertions fail) and GREEN post-fix (41/41 across all 4 test files). |
| **Gates** | `npx tsc --noEmit` clean (Node 20.20.2). Full `npm test`: 11966 passed / 5 failed / 2 skipped — the 5 failures are the documented pre-existing sandbox-only DB-connectivity artifact (same signatures as every other run this session, unrelated files). |

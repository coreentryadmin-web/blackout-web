## 2026-08-23 — [FINDING, P2 tooling] `ecr-push-production.yml`'s `push` trigger repeatedly failed to fire on member-facing merges — no run created at all

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **Symptom** | Multiple times in one session, a squash-merge to `main` that touched deploy-trigger paths (`src/**`, etc.) produced **zero** workflow runs for `ecr-push-production.yml` — not queued, not in-progress, not cancelled. `GET /actions/workflows/ecr-push-production.yml/runs` simply had no entry for the commit. This is distinct from the previously-documented ~1hr end-to-end deploy latency (#2669) — that is a slow-but-present run; this is an **absent** run for a commit that should have triggered one. |
| **Evidence** | Observed at least 3 times across this coordinator session: (1) commit `df0e4356`/#2647 and 5 others — no run created for ~65+ minutes despite all touching deploy paths (documented live in #2669's PR thread); (2) commits `9da026d0`/`54902743`/`7bd99a49` (#2673/#2671/#2670) — no run created despite `src/**` changes, confirmed via `git diff --name-only <prev>..<tip>`; (3) commits `1c5a4cd9`..`17407a93` (#2691 through #2704, 8 commits) — same pattern, confirmed the same way. Each time, `workflow_dispatch` was used as a manual workaround and completed successfully once triggered. |
| **Root cause** | **UNKNOWN.** The workflow's `on.push.paths` filter is correctly scoped (confirmed `src/**` files were in every affected diff) and `concurrency: {group: ecr-push-production, cancel-in-progress: false}` should queue rather than drop overlapping runs — but a queued run should still appear in the runs list with `status: queued`, and none did. This looks like a GitHub webhook-delivery gap (push event never reaching Actions, or a `check_suite` being silently skipped) rather than anything in the workflow YAML itself. Diagnosing further needs access this sandbox does not have: repo Settings → Webhooks → Recent Deliveries, or GitHub App event delivery logs. |
| **Blast radius** | Every merge to `main` is theoretically at risk of a silently-undeployed member-facing fix — the failure mode is invisible from a green PR (`_COMMON.md`'s "merged is not done" rule exists partly for this reason). The mitigation (coordinator manually dispatches `workflow_dispatch` after validating each merge wave) has caught it every time so far, but it is a human/agent catching a symptom, not a fix. |
| **Deliberately NOT fixed here** | Root cause needs GitHub admin-level access (webhook delivery logs) this sandbox does not have. Flagging for whoever has that access, or for a future session with it, to check: Settings → Webhooks → Recent Deliveries on this repo, filtered to `push` events around the timestamps above. |
| **Status** | OPEN — mitigated by manual `workflow_dispatch` each time it recurs, not root-caused. Whoever picks this up next: reproduce is trivial (merge anything touching `src/**` and watch `GET .../runs` for a few minutes), the hard part is the webhook-delivery visibility this sandbox lacks. |

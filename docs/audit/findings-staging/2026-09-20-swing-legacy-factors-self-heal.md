## 2026-09-20 — [FINDING, P1 correctness] Legacy-promoted swing plays' "Why this play was picked" factors didn't sum to score — 5th occurrence, fixed by making the guard self-healing — FIXED

> **kind:** `FINDING`

| Field | Value |
|-------|-------|
| **Status** | FIXED |
| **What prompted this** | Standing Ask Largo × Night Hawk Swings ownership mandate — investigating a specific lead that `GET /api/market/nighthawk/horizons?view=swings` still showed LITE (score 71, factors summing to 70.1) and SMCI (score 91, factors summing to 84.5) with the OLD 5-factor granular breakdown (Structure/Regime/Volatility/Flow/Data quality), even though #5298 (merged ~11:29 UTC today, 8/8 ECS targets confirmed on the fix's task def) had just shipped `serving-lane.ts`'s `enrichPlay` respecting a pinned `play.factors`. This is the 5th occurrence of the same bug class: `#4826`/`#4832` (banger-lane-merge.ts / vector-lane-enrich.ts), `#4843` (legacy-confirm-promote.ts's own writer), `#4837` (live-plays.ts / attachThesisExplanation), `#5298` (serving-lane.ts's enrichPlay) — every one a variant of "a score is shown next to a factor breakdown that was computed from a DIFFERENT run and doesn't sum to it." |
| **Live repro** | Minted a temp Clerk premium+admin session (`scripts/audit/lib/audit-auth-fetch.mjs`). `GET /api/market/nighthawk/horizons?view=swings` → `board.lanes.SWING.committed` contained LITE (`score:71`, `factors:[{Structure,42.1},{Regime,10.1},{Volatility,8.6},{Flow,5.7},{Data quality,3.6}]` sum 70.1) and SMCI (`score:91`, `factors:[{Structure,50},{Volatility,21.2},{Regime,13.3}]` sum 84.5) — both carrying `commitGateBlockedBy:["legacy:exempt"]`, `signalKinds:["NIGHT HAWK"]`, and `reason` ending "· Legacy morning confirm (2026-09-17)" / "(2026-09-18)" — genuinely Legacy-promoted rows, not a rendering confusion with an organic play. `GET /api/admin/swing/discovery-debug` showed the persisted swing serving snapshot was itself stale: `asOf: 2026-09-18T20:37:29.665Z` (~40h old at the time of the repro, `swing-discovery`'s carry-forward writer not having refreshed since), `dossiers:126` vs `plays:4, watch:4` (`watchTickers: ["CRWD","LITE","SMCI","HPE"]`). |
| **Root cause investigation** | Read `legacy-confirm-promote.ts`'s `buildLegacySwingArtifacts` (the sole writer of `commitGateBlockedBy:["legacy:exempt"]` in the repo, confirmed by grep) end to end: as currently written (since `#4843`, 2026-09-12), it unconditionally overrides `factors` with the single-entry `[{label:"Night Hawk edition score", points: swingPlay.score}]` — it CANNOT structurally produce a 5-entry dossier-shaped breakdown. Verified via ECS task-definition history (`describe_task_definition` across every revision) that `#4843` was live on BOTH `blackout-production-web` (deployed 2026-09-12 09:24 UTC, 36min after merge) AND `blackout-production-market-worker` (the revision active at LITE's own `firstSeenAt`, 2026-09-17T13:15 UTC, already had `#4843` as a `git merge-base --is-ancestor` ancestor) — so this is NOT a simple "the writer's fix hadn't deployed yet" gap; whatever produced the bad persisted value, it happened despite both the correct writer AND the correct (pre-`#5298`) `attachThesisExplanation` guard already being live. `carryLegacyPromotedIntoSnapshot`/`refreshCarriedLegacyPlay` (the day-to-day carry-forward the stale snapshot has been running on) only ever refreshes a Legacy row's CONTRACT (expiry/staleness) — it never re-validates or re-derives `factors`, so once a bad value is written for ANY reason (a transient write-time race between the two independently-deploying ECS services, a since-fixed bug in an intermediate build, a hand-run backfill, or a cause this investigation could not pin down from the sandbox's read-only access — no direct Redis read was available to inspect the raw persisted bytes), it rides untouched indefinitely. Both prior read-side fixes (`#4837`'s `attachThesisExplanation`, `#5298`'s `enrichPlay`) share the identical unsafe assumption: `Array.isArray(play.factors) && play.factors.length > 0` was treated as PROOF the array was a trustworthy pin, when it only proves non-emptiness — it can preserve a genuinely-pinned array, but it can never detect or repair one that was already wrong. |
| **Fix** | `serving-lane.ts` gains `factorsSumToScore(factors, score, tolerance=0.15)` (floating-point-safety tolerance only — `contributionsToFactors`'s own invariant is an EXACT sum by construction, so a real cross-run mismatch is never sub-tenth) and `isLegacyExemptPlay(play)` (checks `commitGateBlockedBy.includes(LEGACY_COMMIT_GATE_EXEMPT)`, imported from the leaf `entry-gate-constants.ts` to avoid a cycle with `legacy-confirm-promote.ts`, which itself imports `serving-lane.ts`). `enrichPlay`'s `factors: pinnedFactors ? play.factors : meta.factors` becomes `factors: resolvedFactorsFor(play, meta.factors)`, which (1) trusts `play.factors` only when it actually sums to `play.score`, (2) REPAIRS (rather than replaces with a fresh, equally-mismatched dossier decomposition) a Legacy-exempt play's bad factors to the correct single-entry shape, and (3) otherwise falls back to `meta.factors` exactly as before `#5298` (unaffected organic-discovery behavior). `attachThesisExplanation` gets the identical treatment for defense in depth, even though a live/committed Legacy row is rare (Legacy promotions are serve-only, `bucketGraduated:false`). |
| **Blast radius** | Both call sites of the previous "non-empty ⇒ trust it" check (`enrichPlay`, `attachThesisExplanation`) — confirmed the ONLY two places in `src/lib/swing/serving-lane.ts` that gate on pinned factors. No other Legacy-exempt-tagged writer exists (grepped `LEGACY_COMMIT_GATE_EXEMPT`/`"legacy:exempt"` repo-wide: exactly one definition, one write site). Organic (non-Legacy) plays are unaffected — their `factors` is either absent (falls straight to `meta.factors`, unchanged) or genuinely sums to score by construction (Banger/Vector-lane factors, live-plays.ts's `pinnedFactorsFromFeatureVector` — all pass `factorsSumToScore` and are preserved as before). |
| **Fix rationale** | Considered just re-verifying/re-running `promoteLegacyConfirmedToSwing` for the two affected tickers as a one-off backfill instead of a code change — rejected as insufficient on its own: it would clear today's two symptoms but leave the underlying gap (a persisted value, once bad for ANY reason, is never re-validated) open for the 6th occurrence. The self-healing check is a durable structural fix: it makes the invariant ("factors sum to score") something the READ path actively verifies every time, not something the WRITE path is trusted to have gotten right forever. Repairing (not merely rejecting) a bad Legacy row's factors, using the Legacy-specific single-factor shape rather than falling through to a fresh dossier decomposition, was deliberate — a generic fallback to `meta.factors` for a Legacy-exempt row would just re-commit the identical class of bug with different numbers (the dossier's synthetic pillar score is a different run's number by design, per `swing-pillars.ts`'s own documented invariant). |
| **Regression guard** | `src/lib/swing/serving-lane.test.ts`: new test `"a Legacy-exempt play whose PERSISTED factors do NOT sum to its own score gets REPAIRED, not trusted or dossier-replaced (2026-09-20, 5th occurrence)"` — feeds `enrichPlay` (via `getSwingServingLane`) a play with `commitGateBlockedBy:["legacy:exempt"]`, `score:71`, and the EXACT live-observed bad 5-entry breakdown (sum 70.1); asserts the served row's factors are repaired to `[{label:"Night Hawk edition score", points:71}]`. All 17 pre-existing tests in the file (including the `#5298` and `#4837` regression tests for the CORRECT-pin-is-preserved case) still pass unchanged. Full `npm test` (Node 20.20.2, `/opt/node20`): see run log. `npx tsc --noEmit`: clean. |

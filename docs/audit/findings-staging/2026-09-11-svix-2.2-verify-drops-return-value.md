### What was actually wrong — a real regression, not a types quirk

Yesterday's finding correctly identified the `tsc` symptom but stopped short of determining whether
`svix@2.3.0`'s new types were catching a **real** behavior change (in which case forcing the cast
would be dangerous) or just being stricter about something still safe (in which case widening the
cast to `as unknown as WebhookEvent` would be the correct fix). It is the former, and the proof is
in svix's own shipped code, not speculation:

Scratch-installed all four relevant versions in isolation (`npm install svix@<version> --prefix
/tmp/.../svix-probe-<version> --no-save`, never touching this repo's `package.json`/lockfile) and
diffed the compiled `dist/index.mjs`'s `Webhook.verify()` body directly:

**`svix@2.1.0`** (currently pinned in `package.json`, what production actually runs):
```js
verify(payload, headers_) {
  const headers = {};
  for (const key of Object.keys(headers_)) headers[key.toLowerCase()] = headers_[key];
  headers["webhook-id"] = headers["svix-id"] ?? headers["webhook-id"] ?? "";
  headers["webhook-signature"] = headers["svix-signature"] ?? headers["webhook-signature"] ?? "";
  headers["webhook-timestamp"] = headers["svix-timestamp"] ?? headers["webhook-timestamp"] ?? "";
  return this.inner.verify(payload, headers);   // <-- returns the verified/parsed event
}
```

**`svix@2.2.0`, `2.3.0` (what #4806/#4707 try to bump to), and `2.5.0` (the current `latest` on
npm as of this check)** — all three identical in the part that matters:
```js
verify(payload, headers_) {
  const headers = {};
  for (const key of Object.keys(headers_)) headers[key.toLowerCase()] = headers_[key];
  headers["webhook-id"] = headers["svix-id"] ?? headers["webhook-id"] ?? "";
  headers["webhook-signature"] = headers["svix-signature"] ?? headers["webhook-signature"] ?? "";
  headers["webhook-timestamp"] = headers["svix-timestamp"] ?? headers["webhook-timestamp"] ?? "";
  this.inner.verify(payload, headers, { jsonParse: false });   // <-- NOT returned, discarded
}
```
No `return` keyword. The TypeScript source (`svix`'s own `src/webhook.ts`, bundled alongside the
dist) even declares the method's return type as the literal `: undefined` — the type system is
being **honest** about what the function now does; the regression is upstream, not in our types.

Root cause of the regression: `svix@2.2.0` switched the inner call to `{ jsonParse: false }`
(previously the inner `standardwebhooks` `Webhook.verify()` was called with no options, defaulting
to parsing) — but the outer `svix` wrapper's `verify()` never picked up returning that raw result,
so the parsed/verified payload is computed and then thrown away every single call, unconditionally,
regardless of whether the signature was valid or not.

### Confirms the boundary precisely

| Version | `verify()` returns the payload? |
|---|---|
| 2.1.0 (pinned today) | Yes |
| 2.2.0 | **No** |
| 2.3.0 (target of #4806/#4707) | **No** |
| 2.5.0 (latest on npm, checked 2026-09-11) | **No** |

So this is not a one-version blip that a newer patch already fixed — every published `svix` release
from 2.2.0 through today's latest (2.5.0) carries it.

### Why forcing the cast would have been a real production break, not a lint nuisance

`src/app/api/webhooks/clerk/route.ts`:
```ts
evt = wh.verify(body, { 'svix-id': ..., 'svix-timestamp': ..., 'svix-signature': ... }) as WebhookEvent;
...
const { type, data } = evt;
```
If someone "fixed" yesterday's `tsc` error the obvious way — widening to `wh.verify(...) as unknown
as WebhookEvent` — the code would compile, `npm test`/`tsc --noEmit` would pass, and CI would go
green. But at runtime, with `svix>=2.2.0`, `wh.verify(...)` always evaluates to `undefined` (valid
signature or not — the discard happens unconditionally, before any success/failure branching), so
`evt` would be `undefined` and `const { type, data } = evt` would throw a `TypeError: Cannot
destructure property 'type' of 'undefined'` on **every single Clerk webhook delivery** — silently
taking down `user.created`/`user.updated` processing (tier sync, welcome-sequence emails) in
production, caught by nothing short of an actual live webhook firing and erroring. This is exactly
the failure mode yesterday's finding flagged as a possibility ("verifying that change doesn't mask a
real 'verify() can return undefined' case") — now confirmed as the actual, current behavior of every
publicly available `svix` release newer than what we run.

### Fix

No code changed — `route.ts` is already correct for the version we actually run (`svix@^2.1.0`), and
there is no motivation to touch working code to pre-emptively support a broken future dependency.
The fix is `.github/dependabot.yml`: added an `ignore` entry pinning `svix` below `2.2.0`, so
dependabot stops re-bundling this specific broken bump into the shared `minor-and-patch` group every
week — which is what was blocking ~14 other, unrelated, genuinely-safe patch/minor bumps (PRs #4707
and #4806 both carried 14-15 total package updates, all held hostage by this one red check). Once
svix ships a release that restores the `return`, this `ignore` entry should be removed.

### Blast radius

- **`route.ts` itself**: unaffected, no runtime risk today — `svix@^2.1.0` is what's actually
  installed and deployed; verified via `git log`/`package.json` that `main` has never carried
  `svix>=2.2.0`.
- **Every other call site of `wh.verify`**: grepped `grep -rn "new Webhook(" src` — `route.ts` is the
  only Clerk-webhook consumer in the app; no other file constructs a `svix` `Webhook` instance, so
  this is a single-call-site risk, fully covered by the dependabot pin.
- **Dependabot PRs #4707 and #4806**: both stay open/stuck as dependabot's own PRs (not touched here,
  per this session's standing policy of not hand-editing another automation's PR branch) — they
  should be superseded automatically on dependabot's next scheduled run now that the `ignore` rule
  excludes `svix` from future group bumps. Not verified live (that happens on dependabot's own
  schedule, outside this session's control), noted here so a future pass doesn't have to re-diagnose
  if #4707/#4806 are still open next week without the svix line in their diff.

## 2026-09-04 — [PERF, P1 platform-wide] uw-cache-refresh was the one remaining cron missing the background-sweep UW-concurrency reservation

> **kind:** FINDING

| Field | Value |
|-------|-------|
| **Status** | FIXED |
| **Found by** | Parallel live-production audit workflow, 2026-09-04 (cron-fleet concurrency sweep area), independently verified by 2 adversarial refuters — confirmed |
| **Evidence** | Live EventBridge (`blackout-production-uw-cache-refresh`, `cron(*/2 11-21 ? * MON-FRI *)`, ENABLED). Live CloudWatch Logs `/ecs/blackout-production`, 2026-09-03 18:00-20:30 UTC (RTH), filter `"cron/uw-cache-refresh"`: routine `elapsed=` runs of 20,436ms / 45,387ms / 45,218ms / 40,779ms / 61,929ms / 60,022ms / 65,758ms / 56,224ms, every run reporting `refreshed=24 failed=0` (the full 24-way fan-out completes, no per-task failures). Same window, filter `"queue budget exceeded"`: **939** real `[uw] flow-alerts failed: [unusual_whales] rate-limiter queue budget exceeded at global_rps: waited ~20000-21645ms of 20000ms` events, clustering inside or at the very start of this cron's own measured run windows (e.g. failures at 18:20:21 fall inside the 18:20:22-18:21:02 run; failures at 18:28:28 land at the start of the 18:28:22-18:29:02 run). A same-length window outside this cron's scheduled hours (00:00-02:29 UTC, off-hours) shows only 27 such failures — a ~35x lower rate. |
| **Root cause** | `runUwCacheRefreshTasks()` (`src/app/api/cron/uw-cache-refresh/route.ts`) builds 24 independent UW/Polygon fetch closures (5 sector tides + 3 index tickers × 3 fetches + 5 market-wide singles + 2 flow-per-strike aggregations) and fires them all in one `Promise.allSettled` every 2 minutes throughout RTH+extended hours. Every closure that misses cache goes through `throttleUw`/`throttleUwCoalesced`, admitting against the same cluster-wide ~2 RPS / 2-3-concurrent-slot UW ceiling live member requests (flow-alerts, desk reads) also queue on. This is the exact same bug shape fixed in PR #3479 for `vector-dark-pool-warm`/`vector-pick-sweep`/`vector-full-state-snapshot`/`bie-full-state-snapshot` — a bulk cron fan-out monopolizing the tiny shared UW concurrency pool for a large fraction of every scheduling cycle — but this cron was not included in that sweep (`grep -rl runWithBackgroundUwSweep src/app/api/cron/` returned only the 4 already-fixed routes) and was the one remaining un-tagged caller. |
| **Fix** | Wrapped the existing background dispatch (`dispatchRefresh` inside `after()`) in `runWithBackgroundUwSweep(() => runUwCacheRefreshTasks(started, redis))` — identical mechanism, identical call-site shape to the four crons fixed in PR #3479. No change to the 24-task list, no change to caching behavior; this only reserves one of the (as few as 2) global UW concurrency slots for live traffic while this cron's fan-out is mid-run. |
| **Blast radius** | One file, one call site. Did not add a `runUwPool`-style concurrency cap to the 24-way fan-out itself (unlike `vector-dark-pool-warm`'s earlier fix) — that fix was for a DIFFERENT failure mode (per-ticker admission-queue timeouts, `83-95%` failures observed live at the time). This cron's own live logs consistently show `failed=0` across every sampled run, i.e. no evidence of that failure mode here; adding an unevidenced concurrency cap would be scope creep per the standing audit-mandate discipline against fixing a class of problem that isn't actually measured to be present. |
| **Tests** | 2 new tests in `src/app/api/cron/uw-cache-refresh/route.test.ts` (new file — this route had none before): imports `runWithBackgroundUwSweep` from the shared rate limiter; the background dispatch closure calls it wrapping `runUwCacheRefreshTasks`, and the old untagged call is confirmed gone.

## 2026-08-30 — [FINDING, P2 SPX] "Dealer GEX" long confirmation missed its own upper bound — a support wall 600pts above spot passed as confirming — FIXED

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **Symptom** | `evaluatePlayConfirmations`'s "Dealer GEX" soft confirmation check (`src/features/spx/lib/spx-play-confirmations.ts`), for a LONG play, could report **passed: true** off a GEX wall sitting hundreds of points *above* the current SPX price — the opposite of what "GEX support" is supposed to mean for a long entry. |
| **Root cause** | The long branch read `desk.gex_walls?.some((w) => w.kind === "support" && w.strike >= price - 10)` — bounded on the LOWER side only, with **no upper bound at all**. The sibling SHORT branch a few lines below is correctly bounded on **both** sides: `w.strike >= price - 2 && w.strike <= price + 12`. `kind` is assigned once, at wall-build time (`spx-desk-merge.ts` / `gamma-desk.ts`: `kind: w.strike > spot ? "resistance" : "support"`), against whatever spot the desk snapshot used at that moment — it is a label frozen at build time, not re-evaluated against the live tick this confirmation check runs against a few desk-poll cycles later. Once price drifts down after that snapshot, a wall that was genuinely below spot when classified stays tagged `"support"` while sitting far *above* the desk's current price. The unbounded long check accepted any such wall regardless of distance; the comment directly above the code even says the intent ("a wall at SPX 4000 while price is at 5600 is irrelevant") but the code only ever tested the far-below case, never the far-above one — a direction-asymmetric bug that existed in the same function, in the same commit, next to the branch that got it right. |
| **Evidence** | Added `src/features/spx/lib/spx-play-confirmations.test.ts`. Before the fix: `evaluatePlayConfirmations(desk={price:5600}, direction="long")` with a single `gex_walls: [{strike: 6200, kind: "support", ...}]` (600 pts above spot) returned the "Dealer GEX" check as **passed: true**. Git-stash red/green proof: with the fix stashed, `npx tsx --test spx-play-confirmations.test.ts` → 2 pass / **1 fail** (the new "far above" case); with the fix restored → 3 pass / 0 fail. The short branch's existing bound was independently re-verified unchanged (a resistance wall 600pts *below* spot correctly still fails). |
| **Blast radius** | Contained to this one function/branch. Grepped every other `kind === "support"` / `kind === "resistance"` site in the repo (`playbook-shadow-matcher.ts`, `spx-play-intel.ts`, `spx-desk-synthesis.ts`) — all three only ever filter for the nearest wall in the natural direction (resistance ≥ spot, unbounded above is correct there since resistance is expected above price) and are not the same asymmetric-bound pattern. This confirmation is `required: false` (a soft signal, doesn't hard-block on its own) but it still feeds `passed_count` against `playMinConfirmationsRequired()`, so on a live board a long play could accumulate one extra false-positive confirmation point off a stale/irrelevant wall label, nudging a borderline setup over the confirmation-count bar it should not have cleared. |
| **Fix rationale** | Mirrored the short branch's structure exactly: `w.strike >= price - 10 && w.strike <= price + 2` (kept the existing −10 floor from the original comment/intent, added a +2 ceiling as the long-side analogue of the short branch's −2 floor). Deliberately did not touch the short branch (already correct) or widen/narrow either bound's magnitude — this is a symmetry fix, not a threshold retune, so it carries no calibration risk. Added an in-code comment on the long branch explaining the staleness mechanism so a future reader does not reintroduce the same asymmetry. |
| **Verification** | `npx tsc --noEmit` clean. `npx tsx --test src/features/spx/lib/spx-play-confirmations.test.ts` → 3 pass / 0 fail (Node 20.20.2). Pre-existing, unrelated failure in `spx-play-gates.test.ts` confirmed present on stock `origin/main` (reproduced with this branch's change fully stashed) — not caused by or related to this fix. |
| **Status** | FIXED — see PR (this branch `fix/spx-gex-long-support-unbounded`). |

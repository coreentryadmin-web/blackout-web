## 2026-09-04 — [BUG, P2 member-facing] Meridian earnings TIMELINE showed a live "implied move" beside "· printed" for the same same-day print

> **kind:** FINDING

| Field | Value |
|-------|-------|
| **Status** | FIXED |
| **Found by** | DISCOVERY lane, sweeping Meridian for the same bug shape #3474/#3482 had just fixed in the earnings-detail intel panel, looking for a sibling instance in a different Meridian surface. |
| **Where** | `overlayTimelineExpectedMoves` (`src/lib/meridian/meridian-benzinga-earnings-core.ts`), called from `loadMeridianEarningsTimeline` (`src/lib/meridian/meridian-timeline-server.ts:176`) — feeds the Meridian **calendar/timeline strip** (`meridian-timeline.ts`'s `buildTimelineItems`), a different surface from the earnings-detail intel panel #3474/#3482 already fixed. |
| **Evidence** | `loadMeridianEarningsTimeline` filters Benzinga rows to `r.date >= todayYmd` (line 139) — it does **not** drop today's date once that print has already reported. Every timeline row already carries `is_printed` (set upstream in `benzingaToCalendarRow`/`benzingaRowToTimelineInput` directly from Benzinga's `actual_eps`/`actual_revenue` presence on that row — a reliable, row-specific signal, no history lookup needed), but `overlayTimelineExpectedMoves` ignored it and unconditionally stamped the LIVE `batchLoadEarningsExpectedMovePct` chain-IV read (`meridian-earnings-expected-move.ts`, no `earningsAlreadyPrinted`-style gate of its own either) onto every row keyed by ticker. `meridian-timeline.ts`'s `buildTimelineItems` then concatenates both into the one string a member reads: `subtitle = name + " ~X% implied move" + (row.is_printed ? " · printed" : ...) + impChip` — e.g. a same-day BMO print, read mid-session, would render `"NVIDIA ~7.7% implied move · printed"`, asserting a forward-looking pre-print expectation for an event the same label says has already happened. The live chain by that point prices the POST-print regime, not the pre-print one — the identical stale/misleading-IV defect #3482's own write-up describes (LULU: post-crash chain IV served as "Options-implied move ~50.3%" hours after the print), arriving independently in the calendar lane rather than the detail panel. |
| **Root cause** | `overlayTimelineExpectedMoves` is a pure keyed-by-ticker overlay with no awareness of per-row print status, even though the row already carries that status (`is_printed`) by the time the function runs — this repo's own established fix for this exact bug shape (#3474/#3482, `resolveIntelExpectedMove`) withholds once printed rather than relabeling; this function simply hadn't been given the same treatment yet. Not the same code path as #3482 (that fix lives entirely in `meridian-earnings-intel*.ts`, the single-ticker detail-panel loader) — a second, independent instance of the same shape in the multi-ticker timeline loader, exactly the kind of "duplicated logic in a second file" the PR write-up policy asks to check for. |
| **Fix** | `overlayTimelineExpectedMoves` now returns the row unchanged (skips the overlay entirely) when `row.is_printed` is true, before looking up `emByTicker`. Minimal, surgical: no change to `is_printed`'s upstream derivation, no change to `batchLoadEarningsExpectedMovePct`/`rankEarningsForExpectedMove`, no change to the render string in `meridian-timeline.ts` (once `expected_move_pct` is null, the `em` fragment already renders as `""` there). |
| **Blast radius** | Single call site (`meridian-timeline-server.ts:176`) → single render site (`meridian-timeline.ts` lines ~198-201 and ~230-232, both already null-guarded on `expected_move_pct`). Not fixed here (deliberately, to keep this PR single-issue): the scarce 36-name chain-pull budget (`meridian-em-priority.ts`) can still rank and spend a pull on an already-printed row before this overlay discards the result — a pure efficiency win (spend the budget where the answer is still displayed), not a correctness bug, since the display-side fix here already prevents the misleading render regardless. A natural follow-up would filter `is_printed` rows out of the candidate list built in `meridian-timeline-server.ts:167-172` before it reaches `batchLoadEarningsExpectedMovePct`. |
| **Tests** | New test in `meridian-benzinga-earnings-core.test.ts`: `overlayTimelineExpectedMoves withholds the live chain-IV overlay once the row has already printed` — a row with `is_printed: true` and a real `emByTicker` entry keeps `expected_move_pct: null` post-overlay.

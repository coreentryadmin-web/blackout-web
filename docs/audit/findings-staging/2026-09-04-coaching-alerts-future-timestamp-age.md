## 2026-09-04 — [FINDING, P3 correctness, SPX coaching desk] `GET /api/coaching/alerts` could report a negative `age_minutes` for a fresh alert on any RDS-vs-app clock skew — FIXED

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **What prompted this** | Fresh DISCOVERY sweep (avoiding files already claimed by today's active lanes — checked `git log --all` / open PRs first). This session's own recent history shows the exact same bug shape found and fixed repeatedly across the product today (`2026-09-03-future-timestamp-freshness-badges.md`: FlowFeed.tsx, GexHeatmap.tsx, meridian-viz.tsx, helix-session-pulse.ts) — a raw `now - t` age computation with no future-timestamp guard. Swept `Date.now() - ` call sites for one none of those passes had reached, and found a genuinely new instance in the SPX coaching-alerts route (untouched by any branch in `git log --all -- src/app/api/coaching/alerts/route.ts` before this fix, and not part of any currently-open PR's diff). |
| **Root cause** | `GET /api/coaching/alerts` computed `ageMs = Date.now() - new Date(r.generated_at).getTime()` inline, then `age_minutes: Math.floor(ageMs / 60_000)`. `generated_at` is `TIMESTAMPTZ NOT NULL DEFAULT NOW()` — stamped by the **RDS server's own clock** — while `Date.now()` here runs on the **ECS app process's** clock. Any moment the DB clock reads even slightly ahead of the app clock (ordinary NTP jitter, or a container whose clock hasn't fully converged) makes the raw age negative. `Math.floor` rounds a negative number AWAY from zero (`Math.floor(-0.0001) === -1`), so this was reachable at **a single millisecond** of skew, not a full minute of drift — a brand-new alert could read as `age_minutes: -1` (or more negative as skew grows) instead of the correct "just now" / `0`. |
| **Evidence** | New `src/lib/coaching-alert-age.test.ts`, confirmed RED pre-fix: temporarily removed the `Math.max(0, …)` clamp (`sed` on the extracted helper, not a stash — this is a brand-new file so there's no prior committed version to stash against) and reran — 2/7 assertions failed exactly as predicted (`Expected values to be strictly equal: -1 !== 0`) for both the 30s-skew and 1ms-skew cases. Restored the fix: 7/7 pass. |
| **Why this matters, and why it's P3 not higher** | This is a paid SPX coaching desk (`authorizeMarketDeskApi` — premium session or cron only), and a negative "-1 minutes ago" reads as visibly broken/untrustworthy on a money surface, matching the pattern the sibling freshness-badge fixes already treat as worth fixing. It's P3 rather than higher because (unlike those sibling fixes) `generated_at` is a **trusted, app-controlled DB clock**, not an untrusted external API timestamp (UW `alerted_at`, Benzinga print time) — so the realistic skew window is small (sub-second NTP jitter on AWS-managed infra), not an attacker- or upstream-controlled arbitrary future date. No current frontend `.tsx` consumer of this route's `age_minutes`/`stale` fields was found in this repo (the coaching desk may be consumed by the iOS app, which lives outside this repo), so member-visible impact could not be directly confirmed — but the route is real, live (`POST` fires every RTH minute via the `coaching-alerts` cron per `cron-registry.ts`), and any consumer reading `age_minutes` gets the wrong number in exactly this window. |
| **Fix** | Extracted the inline computation into a pure, testable helper — `src/lib/coaching-alert-age.ts`'s `coachingAlertAgeFields(generatedAt, nowMs)` — and clamped the age at zero (`Math.max(0, nowMs - t)`) before deriving `ageMinutes`/`stale`, matching the same DISPLAY-clamp convention `meridian-viz.tsx` already uses for this exact class of skew. The route (`src/app/api/coaching/alerts/route.ts`) now calls the helper instead of computing inline. `stale` was already correct in the negative-age direction (a negative/near-zero age was never `> 1hr`, so it never mis-reported "stale"); this fix only corrects the displayed `age_minutes` magnitude. |
| **Blast radius** | One route (`GET /api/coaching/alerts`), one new pure helper it now imports. `POST /api/coaching/alerts` (the cron writer) and `src/app/api/platform/intel/route.ts`'s own separate `coaching_alerts` query (which filters/orders in SQL and does no client-side age math) are unaffected — checked and left untouched. |
| **Deliberately unchanged** | The `stale` threshold (60 minutes) and the underlying `generated_at` write path (still `DEFAULT NOW()`, no explicit app-clock timestamp) — the fix is entirely at the read-side age derivation, the same boundary every sibling fix in this class has used. |
| **Regression guard** | `src/lib/coaching-alert-age.test.ts`, 7 tests: null/undefined/unparseable `generatedAt` all null-safe; ordinary past timestamps age and go stale correctly; a 30s-future skew clamps to `ageMinutes: 0` (not `-1`); the reachable-at-1ms case (`+1ms`) also clamps to `0` (not `-1`); a `Date` object input works the same as a string/ISO input. Confirmed RED pre-fix / GREEN post-fix as described above. |
| **Gates** | `npx tsc --noEmit` clean (Node 20.20.2). `npx tsx --test src/lib/coaching-alert-age.test.ts`: 7/7 pass. |

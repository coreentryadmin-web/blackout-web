## 2026-09-03 — [FINDING, P3 Infra] `recordCronJobRun` bypassed dbQuery's transient-error retry — spurious "log failed" warnings on the pool-teardown race — FIXED

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **What prompted this** | Operator-requested close audit of all live plays across SPX Slayer, Night Hawk 0DTE, Legacy, and Vector. During that audit, `/api/market/spx/play` returned the route's degraded fallback (`degradedPlayPayload()`) on 1 of 12 polls within ~90s of live RTH traffic, with the route's own `console.error("[market/spx/play]", error)` swallowing the real cause. Investigating via CloudWatch Logs turned up a related, independently-reproducible bug on a neighboring code path: `[cron-run/spx-evaluate] log failed: Error: Cannot use a pool after calling end on the pool`, fired twice live in the same session (15:21:22 UTC and 15:35:49 UTC). |
| **Root cause** | `recordCronJobRun` (`src/lib/db.ts`) used a raw `(await getPool()).query(...)` for both its INSERT and its 5%-sampled 30-day retention DELETE, instead of the shared `dbQuery()` wrapper every other write in the file goes through. `dbQuery` already has a transient-error retry loop (`isTransientPgError` + `resetPoolForRetry`) specifically built to catch this exact race — `db-transient.ts`'s own comment documents it: `resetPoolForRetry()` tears down the shared module-level pool as soon as ANY caller sees a transient error, with no coordination against other concurrent callers still holding that same pool reference; a caller mid-flight on a pool another caller just ended gets a synchronous pg-library throw ("Cannot use a pool after calling end on the pool") that is a client-side use-after-teardown, not a real DB failure — and is meant to be silently retried on a fresh pool. `recordCronJobRun`'s raw pool call bypassed that retry entirely, so `logCronRun`'s own `try { recordCronJobRun(...) } catch { console.warn(...) }` guard swallowed the failure into a bare warning instead of it self-healing like every other write already does. |
| **Confirmed live, not assumed** | Two occurrences of `[cron-run/spx-evaluate] log failed: Error: Cannot use a pool after calling end on the pool` in CloudWatch Logs `/ecs/blackout-production` within one live RTH session (2026-09-03). |
| **Fix** | Routed both `recordCronJobRun` writes through `dbQuery()` instead of a raw `(await getPool()).query(...)`, matching the convention already used by every other read/write in `db.ts` (confirmed by grep — `recordCronJobRun` was the one write path still bypassing it). |
| **Blast radius** | Single function, two call sites within it (insert + retention prune). `recordCronJobRun` is called only from `logCronRun` (`src/lib/cron-run.ts`), which every cron route calls to record its own run — so every cron benefits from this fix, not just `spx-evaluate`. The cron *runs themselves* were never broken by this bug (they complete their real work before calling `logCronRun`); only the incidental "record that I ran" write was fragile. |
| **What was deliberately left unchanged** | The intermittent `/api/market/spx/play` degraded-fallback response itself — its route swallows the real exception into an unlabeled `console.error`, so the root cause there could not be conclusively isolated from outside the process in this pass. It may or may not be the same pool-teardown race (the route's `getSpxPlayState()`/`peekSpxPlayState()` already goes through `dbQuery` if it hits Postgres at all, so if it IS this race, it should already self-heal via `dbQuery`'s own retry — meaning the degraded response was likely a single, already-retried failure, not evidence of a second unretried bug). Not fabricating a second fix without clearer evidence — flagging as a follow-up if the degraded-fallback rate is re-measured and still non-trivial. |
| **Regression guard** | `src/lib/db.test.ts`: new test `recordCronJobRun: both writes go through dbQuery, not a raw pool.query` — source-inspection style (same idiom as this file's other `dbQuery`/pool-race tests), asserts both writes call `dbQuery(...)` and that the function body contains no raw `pool.query` call. Confirmed RED pre-fix (temporarily reverted only `db.ts`, test failed 1/17) and GREEN post-fix (17/17). |
| **Gates** | `npx tsc --noEmit` clean (Node 20.20.2). Full `npm test`: 11904 pass / 0 fail / 2 skipped. |
| **Status** | FIXED |

## 2026-10-13 — [FINDING, P3 helix/correctness, data-honesty] Flow-anomaly skew ratio printed from exact premiums disagreed with the independently-rounded $ amounts shown beside it — FIXED

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **What was broken** | `skewDetail()` (`src/app/api/cron/market-regime-detector/flow-anomaly-detection.ts`) rendered a `DIRECTIONAL_FLOW_SKEW` anomaly's ratio as `${ratio.toFixed(0)}:1`, computed from the EXACT, unrounded call/put premiums — while the two dollar amounts printed right next to it (`millions()`) each independently round to 1 decimal. Live repro 2026-10-13, MSTR flow anomaly surfaced in a swing play-brief's "Flow & positioning" section (Ask Largo standing-mandate deep-dive): `"extreme call skew (29:1 call/put) — $1.6M calls vs $0.1M puts"`. A member doing the obvious mental math from the two numbers actually shown gets 1.6/0.1 = 16, not the stated 29 — the stated ratio and the evidence beside it disagree. |
| **Root cause** | `millions(v)` formats each side's premium independently via `(v / 1_000_000).toFixed(1)`, discarding everything past one decimal place. `skewDetail()` never applied that same rounding before computing the printed ratio — it divided the two FULL-PRECISION premiums (e.g. 1,600,000 / 55,000 = 29.09 → "29:1"), then displayed each premium separately rounded to the nearest $0.1M (1.6 and 0.1). The precise ratio is correct and was never the bug; what's wrong is pairing it with rounded evidence it doesn't reconcile with. This is the same class of defect this exact function was already fixed for once before (2026-08-19, the `ONE_SIDED_RATIO` 99:1-sentinel-presented-as-a-measurement bug, same file) — a derived number that doesn't match what the member is shown alongside it. |
| **Fix** | Added `roundedMillions(v)` — the same rounding `millions()` applies, returned as a number (0 for the `<$0.1M` floor case). `skewDetail()` now derives the PRINTED ratio from `roundedMillions(dominantPrem) / roundedMillions(otherPrem)` — the same two rounded figures shown beside it — falling back to the precise `ratio` only when the smaller side rounds to zero (the pre-existing `<$0.1M` branch, where there is no rounded denominator to reconcile against in the first place). Gating (`callRatio`/`putRatio` against `SKEW_RATIO_THRESHOLD`) and the persisted `metric_value` are completely untouched — both still read the precise premiums; only the member-facing display string changes. |
| **Evidence** | New regression test `"REGRESSION: the printed ratio reconciles with the rounded $ amounts shown beside it"` (`flow-anomaly-detection.test.ts`): call=$1,600,000, put=$55,000 (exact ratio 29.09). RED against the pre-fix source — asserted "16:1" but got "29:1" (`actual: 'MSTR: extreme call skew (29:1 call/put) — $1.6M calls vs $0.1M puts'`). GREEN after the fix — 16/16 tests pass in the file, including the two pre-existing precision-sensitive tests this touches directly: "a genuinely measured ratio is still printed as a ratio" (1.2M/0.1M → 12:1, unaffected) and "a non-zero premium that rounds to $0.0M is shown as <$0.1M, not as zero" (the `<$0.1M` fallback path, unaffected). `tsc --noEmit` clean. Sibling suites `flow-anomaly-detector-regression.test.ts`, `flow-anomaly-scope.test.ts`, `flow-anomaly-near-misses.test.ts` — 33/33 pass, no regressions. |
| **Blast radius** | `skewDetail()` has exactly one call site (`detectFlowAnomalies` in the same file) and is not duplicated anywhere else in the repo (grepped for `toFixed(0)}:1`/`skewDetail` repo-wide — only this file and its tests). `metric_value`/gating/severity/direction are unchanged by construction, so every downstream consumer of the anomaly record (near-miss accumulator, the `/flows` board, the Ask Largo swing play-brief's "Flow & positioning"/"Trade manager read" HELIX tape line) is affected only in the cosmetic display string, never in which anomalies fire or how they're scored. |
| **Status** | FIXED — branch `fix/flow-skew-ratio-display-precision`. |

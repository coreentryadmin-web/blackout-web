## 2026-08-29 — [FINDING, P3 tooling/CI-waste] data-correctness cron's markdown scorecard was git-tracked, causing repeated no-op "chore: stray placeholder" PRs — FIXED

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **Symptom** | `git log` shows six merged PRs, several untitled ones plus #3087, #3113, #3132, whose only content is `docs/auto/data-correctness-<date>.md` — either an entirely empty file or a one-line "nothing to report" placeholder someone hand-wrote before committing it. Same family of waste as the companion finding filed alongside this one (`2026-08-29-x-intel-rotation-state-uncommitted.md`, PR #3156): a file some run mutates locally with nobody's script committing it, so it sits as a stray diff until an unrelated session sweeps it into its own standalone chore PR — a full `verify` CI run each time, for no code change. |
| **Root cause** | `src/app/api/cron/data-correctness/route.ts` writes this scorecard as explicitly **best-effort local convenience output**: `docs/DATA_CORRECTNESS.md` documents it as emitted "when the FS is writable", and the durable record is `logCronRun`'s structured payload, not this file. Production's ECS root FS is mostly not writable, so in production this write almost never actually happens. But the file lived at a git-tracked path (`docs/auto/`), so any local/sandbox session that ran the correctness sweep against a writable checkout — even a run that found nothing to flag — produced a diff nobody's tooling ever committed. |
| **Why this is the mirror image of the companion finding, not a duplicate** | The x-intel rotation-state fix (#3156) solved the identical *symptom* — an uncommitted stray diff from a local run — by auto-committing it, because that state has to survive across ephemeral sessions to do its job (never repeat a shot/hook). This file has no such requirement: its own documentation says the durable copy already lives in the cron run log, so tracking it in git was never buying anything except a periodic archive nobody asked for. The correct fix here is the opposite of #3156's: stop tracking it, not auto-commit it. |
| **Fix** | Added `docs/auto/data-correctness-*.md` to `.gitignore` (with the rationale inline, matching the file's existing convention of explaining each throwaway-diagnostics rule) and untracked the two already-committed copies (`git rm --cached`, kept on disk). New test in `src/repo-hygiene.test.ts`, next to its existing node_modules-symlink hygiene test, asserts no matching path is ever tracked again. |
| **Regression guard** | `src/repo-hygiene.test.ts`: `"data-correctness cron's markdown scorecard is never tracked in git"` — fails if any `docs/auto/data-correctness-*.md` path reappears in `git ls-files`. |
| **Gates** | `npx tsc --noEmit` clean · `npx eslint` clean · targeted suite (`src/repo-hygiene.test.ts`) 3/3 pass · `git check-ignore -v docs/auto/data-correctness-2026-08-29.md` confirms the new rule matches (Node 20.20.2). |
| **Status** | FIXED. |

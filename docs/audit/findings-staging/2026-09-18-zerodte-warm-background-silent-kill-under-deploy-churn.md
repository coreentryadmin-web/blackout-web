## 2026-09-18 — [FINDING, P0/P1 0DTE, live-incident write-up only] `zerodte-warm`'s background warm work is silently SIGKILLed mid-flight during high-frequency deploys, hidden from `cron_job_runs` by the synchronous "ok" response

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **What this is** | Investigation of live P0 issue #5213 ("RTH stale cron: zerodte-warm — market_hours_stale during RTH") during the 16:15 UTC DISCOVERY cycle. Root-caused and posted to the issue (comment [5732886788](https://github.com/coreentryadmin-web/blackout-web/issues/5213#issuecomment-5732886788)); no code changed — this belongs to the 0DTE lane to fix. |
| **The trap this almost caused** | `GET /api/market/zerodte/board` reads `upstream_ok: true`, ~20s fresh — the board looks completely healthy to members. A shallow check would (and initially did, for me) conclude the P0 was a false positive. It is not: `GET /api/admin/cron-health`'s `zerodte-warm` entry independently reports `market_hours_stale: true`, `zerodte_scan_heartbeat.last_tick_at` 32+ minutes stale (`critical_stale: true`), while `last_run_at` is only 2 minutes old with `status: "skipped"` (rate-limited). Two different freshness signals disagree, and only one of them is lying. |
| **Root cause** | `src/app/api/cron/zerodte-warm/route.ts` dispatches the real work (`warmZeroDteBoard()` + `refreshZeroDteBoardSnapshot()`, which includes `recordZeroDteScanTick("cron")` — the heartbeat this alert tracks) as fire-and-forget (`void dispatchWarm()`), returning a synchronous `"accepted"` HTTP response — logged to `cron_job_runs` as `status: "ok"` — **before** the background work even starts. CloudWatch confirms the background chain genuinely takes ~4-5 minutes (`[cron/zerodte-warm] background done ... elapsed=243716ms` / `elapsed=285569ms`, only 2 completions in the 45-minute window checked, none since 15:44:47Z). The `blackout-web` ECS task definition's container `stopTimeout` is unset, defaulting to the standard 30-second SIGTERM-to-SIGKILL grace period — nowhere close to covering a 4-5 minute background task. ECS task churn was measured unusually high during the incident (8 running tasks, start times spread 1.8-43 minutes old, i.e. new tasks roughly every 3-15 min), consistent with the exceptional PR-merge velocity today (15+ merges to `main` in 3 hours from the swing/nighthawk lanes, each triggering `ecr-push-production.yml`). Any in-flight background warm whose hosting task gets recycled for the next deploy is silently killed mid-chain — no exception to catch, no log line, the process simply dies — while the earlier synchronous "ok" already masked it in `cron_job_runs`, the exact table `admin-cron-health.ts` trusts for staleness. |
| **Why the board stays fresh anyway — and why that's dangerous, not reassuring** | `route.ts`'s own comment: the live member-poll path (`getZeroDteBoardPayload`, serving `/api/market/zerodte/board` and `/api/market/nighthawk/horizons`) calls `scanZeroDteBoard()` **directly**, bypassing `warmZeroDteBoard()`'s heartbeat wrapper entirely. Real member traffic (and other automated healthchecks) keeps the board's own freshness signal green even while the cron's dedicated work — `persistZeroDteScan`, `persistDiscoveryDetectedEvents`, `persistDiscoveryGateBlockedEvents`, ledger live-state sync — can go dark for 30+ minutes with zero visible symptom on the member-facing surface. This is precisely the failure shape `market_hours_stale`/the #90 silent-death flag exists to catch, and it caught it correctly here. |
| **Not a new bug class — recurrence of a documented one** | `route.ts`'s own header already describes a 2026-09-08 incident with the identical symptom ("the FAST synchronous handshake kept succeeding while the DEFERRED work silently, repeatedly failed to run to completion... spanning a full production redeploy"), fixed at the time by making the fire-and-forget dispatch unconditional rather than relying on `after()`. That fix addressed one failure mode (an `after()` callback never firing at all) but not this one (a genuinely-dispatched background chain getting killed mid-execution by a short container stop-timeout under sustained deploy churn) — the same root shape, a different specific mechanism. |
| **What was NOT done** | Did not touch `route.ts`, the ECS task definition, or deploy pipeline config. Deciding between (a) extending `stopTimeout` to actually cover the background work's real runtime, (b) making `warmZeroDteBoard()` resilient to being killed mid-chain (checkpointing, or splitting into shorter idempotent sub-steps), or (c) reducing deploy frequency/batching merges during high-velocity sessions is a real architecture call for whoever owns this cron — not something to guess at from a read-only investigation. Flagged directly on issue #5213 for the assigned agent/lane. |
| **Status** | Live-verified root cause, write-up only — no fix applied. Issue #5213 remains open; whoever picks it up should re-verify current staleness first (deploy churn may have settled by the time this is read) before treating the diagnosis as still-active. |

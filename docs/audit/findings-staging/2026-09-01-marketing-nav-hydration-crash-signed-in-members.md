## 2026-09-01 — [P1, production, homepage/marketing pages] every signed-in member intermittently hit "Something went wrong" on the ISR homepage/marketing pages — React #418 hydration crash — FIXED

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **Context** | Direct, hands-on live-production exploration (not a code-reading review) — minted a real authenticated admin+premium Clerk session and walked the site with `proxy-browser.cjs`, per the standing instruction to test production like a real member rather than conclude from source alone. First page loaded, desktop viewport, authenticated: the homepage rendered the app's own error boundary ("SOMETHING WENT WRONG — We couldn't load this page") instead of the homepage. |
| **Root cause** | `blackouttrades.com/` lives under `src/app/(marketing)/`, which is ISR (`revalidate = 3600` in `(marketing)/layout.tsx`) — the served HTML is a cached snapshot with no per-request cookie access, so it always bakes in `serverSignedIn=false` (or whatever the last regeneration saw) for the nav. `NavAuthLinks.tsx`'s own comment already documents the intended design: "`__client_uat` wins on the FIRST client render." The bug is in HOW `useMarketingSignedIn` (`src/lib/use-marketing-signed-in.ts`) implemented that: `useState(() => resolveClientSignedIn(serverSignedIn))` — a lazy initializer that reads `document.cookie` (via `resolveClientSignedIn`/`readClientSignedIn`, `src/lib/client-signed-in.ts`) DURING the render React uses to reconcile against the server-rendered HTML. For any genuinely signed-in visitor, that reads `__client_uat > 0` → `true`, while the cached server HTML said `false` — a real, deterministic divergence on the very first render, not a race. Because the two states render structurally different markup (`NavAuthLinks` swaps a single `<Link>Open desk</Link>` for a `<>` fragment with TWO links — `Sign in` + `Get access` — not a same-position text edit), React's hydration reconciler can't patch it as a text-node diff and throws "Hydration failed" (minified React error #418). |
| **Evidence** | Reproduced live against production with `page.on('pageerror')` capture (not inferred from source): an anonymous desktop load of `/` rendered clean (0 errors); the SAME URL with a real authenticated Clerk session threw `Minified React error #418` on BOTH desktop (1440px) and mobile (430px) viewports — so this is not viewport-specific. It is also not deterministic: one authenticated desktop load was caught by the marketing error boundary and rendered "Something went wrong" in place of the homepage; a separately-authenticated mobile load with the same underlying bug instead silently self-healed (React's standard hydration-mismatch recovery: discard the mismatched SSR output, redo the render fully client-side) and displayed correctly with no visible symptom — matching React 18's documented recovery behavior, which is not guaranteed to always succeed silently. Confirmed the SAME crash, same authenticated session, on `/learn`, `/faq` and `/pricing` too (all three `Minified React error #418`, identical stack) — every page that mounts `MarketingPageShell`/`StaticMarketingNav` shares the one buggy hook, so the blast radius is every `(marketing)` page, not just the homepage. `/account` (the `(site)`-gated page, same session) loaded without incident, isolating the bug to the `(marketing)` route group's nav specifically, not a site-wide auth-rendering problem. `/upgrade` is itself a `(marketing)` page and an earlier screenshot in this same pass showed it rendering the ANONYMOUS "Sign in"/"Get access" nav despite the authenticated session — almost certainly the same bug manifesting as a silent stale-value recovery rather than a visible crash (consistent with the non-determinism above), not independently root-caused further since the fix here (match the server's first render, then upgrade via effect) resolves it the same way regardless of which failure mode a given load hits. |
| **Fix** | `useMarketingSignedIn`'s initial state is now `serverSignedIn` verbatim — identical to what the server rendered, so the first client render can never mismatch. The existing first `useEffect` (previously redundant with the lazy initializer) is now the SOLE mechanism that upgrades to the live `__client_uat` cookie, firing in a normal post-hydration commit — a safe, ordinary re-render, not a hydration reconciliation — so a signed-in member still sees the nav flip to "Open desk" within one tick of mount, just without racing the hydration check that crashes. The second `useEffect` (verifies the live Clerk session via `/api/auth/me` so an expired cookie doesn't keep showing "Open desk") is untouched. |
| **What was deliberately NOT changed** | `resolveClientSignedIn`/`readClientSignedIn` (`client-signed-in.ts`) — both correct, general-purpose, independently tested; the bug was only in WHEN `use-marketing-signed-in.ts` called the former (during hydration vs. after). `resolveClientSignedIn` is now unused in production code but left in place with its own tests intact — it's a small, correct utility, not the source of the bug, and removing it is out of scope for this fix. `NavAuthLinks.tsx`'s Link↔Fragment structural swap itself — untouched; the fix removes the MISMATCH, not the legitimate difference in what a signed-in vs signed-out visitor should see. |
| **Blast radius checked** | Grepped every consumer of `NavAuthLinks` (`StaticMarketingNav.tsx`, `MarketingMobileNav.tsx`, `MarketingPageShell.tsx`, `Nav.tsx`, `(marketing)/layout.tsx`) — all go through the same `useMarketingSignedIn` hook, so all are fixed by the one change; none needed a separate patch. `Nav.tsx`'s OWN separate `readClientSignedIn()` usage (the `(site)/layout.tsx`-rendered desk nav, a different component with its own `initialSignedIn` prop threaded from a real server-side cookie check in `layout.tsx`) was checked and is a different, already-correct pattern — out of scope, not touched. |
| **Regression guard** | New test in `use-marketing-signed-in.test.ts` pins the hydration-safe pattern (`useState(serverSignedIn)` verbatim, matched by source regex per this file's existing shape-testing convention — no DOM renderer is available in this repo's plain `node:test` setup). Verified the new test FAILS against the pre-fix code (`git stash` the fix only, run the test, confirmed 1 fail; restored, confirmed 1 pass) before relying on it. Full suite: 11556 pass / 0 fail / 2 skip (Node 20). `tsc --noEmit` clean. `eslint` clean on all three touched files. |
| **Status** | FIXED. |

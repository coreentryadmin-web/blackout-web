## 2026-09-01 — [P2, production, Vector wall-history durable mirror] cross-replica multi-row UPSERT deadlocks on `vector_wall_history`, silently dropping whole batches — FIXED

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **Context** | Follow-up to the same day's `/dashboard` hydration-crash finding — while pulling production error telemetry (`GET /api/admin/errors`) to check whether the React #418 defect class existed anywhere else, found a different, unrelated real bug in the same sweep: 4 `deadlock detected` errors on `INSERT INTO vector_wall_history` over a ~29h window (2026-08-31 19:23 → 2026-09-01 14:03). |
| **Root cause** | `persistWallSamplesToDb` (`src/features/vector/lib/vector-wall-db.ts`) builds ONE multi-row `INSERT ... ON CONFLICT (ticker, session_ymd, bucket_time) DO UPDATE` per flush, in whatever order its caller's array happened to be in. That caller, `flushDurableWallSamples` (`vector-wall-persist.ts`), drains a **module-level, per-process** `durableQueue` (a `Map`, so its own iteration order is insertion order) on its own ~2s timer. Production runs 8 `blackout-production-web` replicas, and `WallWriteSource` (`vector-wall-write.ts`) shows multiple independent writers feeding this queue per replica — `sse-hub` explicitly writes "one write per bucket per (ticker, horizon) **per replica**" (that file's own comment), so a popular ticker like SPX/QQQ gets written from many replicas concurrently. Two replicas' flush cycles landing at the same moment, each with an overlapping ticker set but a DIFFERENT internal order (replica A's Map filled in one client-connection order, replica B's in another), is the textbook multi-row-UPSERT deadlock: transaction A locks row (SPX, …) then wants (QQQ, …) while transaction B holds (QQQ, …) and wants (SPX, …) — a circular wait Postgres detects and kills one side of. |
| **Evidence** | Production telemetry (not inference): 4 `error` events, `source: "db_query"`, on the exact `INSERT INTO vector_wall_history (ticker, session_ymd, bucket_time, walls, gamma_...` statement, message `deadlock detected`, at 2026-08-31T19:23:29Z, 2026-09-01T13:41:34Z, 13:59:43Z, 14:03:19Z. Confirmed the multi-writer/multi-replica shape by reading `WallWriteSource`'s full union (`bead-recorder-universe`/`bead-recorder-active`/`cron-universe-snapshot`/`sse-hub`/`dynamic-ticker-warm`/`walls-warm`) and `persistWallSampleDebounced`'s own doc comment ("one write per bucket per (ticker, horizon) per replica"), plus `flushDurableWallSamples`'s in-process `durableFlushInFlight` guard — which only prevents overlap WITHIN one process, confirming the module-level queue is per-replica, not shared. |
| **Fix** | Sort every batch by the exact `(ticker, session_ymd, bucket_time)` ON CONFLICT target — the multi-row INSERT's row order — before building the SQL, via a new pure `sortWallSamplesForUpsert` helper (`vector-wall-db-row.ts`, alongside the existing pure `rowToWallSample` mapper). Any two concurrent writers (any two replicas, or a replica vs. the bead recorder vs. a cron snapshot) now acquire row locks in the SAME global order regardless of which order their own in-process batch happened to accumulate in — the circular wait required for this deadlock shape becomes structurally impossible. No retry logic added and none needed: sorting removes the precondition for the deadlock rather than working around its symptom. |
| **What was deliberately NOT changed** | The per-replica queue/flush architecture itself (`durableQueue`, the 2s timer, the `durableFlushInFlight` single-flight guard) — all correct and already documented as the fix for a DIFFERENT, earlier incident (2026-08-12 connection-pool exhaustion, same file's own comment). This finding is about row LOCK ORDER within a batch, not batch construction or timing. `dbQuery`/the connection pool — untouched. |
| **Blast radius checked** | `persistWallSamplesToDb` is the only multi-row UPSERT against `vector_wall_history` in the codebase (grepped `vector_wall_history` across `src/` — 6 files, only this one builds a dynamic multi-row VALUES list; `persistWallSampleToDb`, the single-row sibling, can't deadlock against itself the same way since ONE row only ever needs ONE lock — though it can still deadlock against a concurrent multi-row batch if that batch's un-sorted order put the single row's ticker last; sorting the multi-row side is sufficient because Postgres's deadlock detector only needs one consistent partial order to break the cycle, and single-row transactions hold their one lock only briefly). No other table in the repo has this same "many concurrent replicas batch-upsert overlapping keys" shape (checked: other durable-mirror writers — GEX heatmap snapshots, play records — are either single-writer cron paths or single-row upserts). |
| **Regression guard** | New tests in `vector-wall-db.test.ts`: two independently-ordered "replica" input arrays sort to an IDENTICAL output order (the property the fix actually needs — not just "some" deterministic order, but the SAME one everywhere), plus a no-mutation check and a session_ymd-before-bucket_time ordering check. `sortWallSamplesForUpsert` lives in the pure, `server-only`-free `vector-wall-db-row.ts` (same reason `rowToWallSample` lives there — this repo's `tsx --test` setup can't import a `server-only` module), so it's directly unit-testable without a DB. Full suite 11559/0/2 (Node 20, one existing test file extended — total count differs slightly run-to-run only because of which branch/base commit is checked out, not a regression). `tsc --noEmit` clean. `eslint` clean on all three touched files. |
| **Status** | FIXED. |

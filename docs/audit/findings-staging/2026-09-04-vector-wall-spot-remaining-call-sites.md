## 2026-09-04 — [BUG, P2 member-facing] Two GEX-wall call sites excluded from PR #3495 while it was in flight — narrowed-horizon wall history writer and the 0DTE-scope wall producer both still picked the wrong side of spot

| **Evidence** | Same bug class, same live evidence already captured in #3495's finding (IBIT `callWalls[0]` below spot on all four DTE horizons; NDX serving an inverted wall on BOTH sides at `dte=all`; 17-18/83 Vector-universe tickers including SPX with a wall on the wrong side of spot). This finding adds the two remaining code paths that reproduce the identical root cause: (1) `buildVectorUniverseRow`'s narrowed-horizon (`horizonWalls`) computation in `vector-universe.ts`, which persists into the durable `vector:wall-history:{ticker}:{ymd}` rail under the `0dte`/`weekly`/`monthly` horizon keys — every 0DTE/weekly/monthly bead a member's chart replays for a wrong-side-of-spot ticker was durably wrong, not just transiently served; (2) `recomputeScopedGexLevels` in `gex-odte-scope.ts`, whose only production consumer (`buildOdteMatrixRows` in `vector-odte-matrix-rows.ts`) flags `isCallWall`/`isPutWall` on Vector's 0DTE matrix rail rows straight off its result. |
| **Root cause** | (1) `vector-universe.ts`'s main `gexWalls` computation (a few lines above) already passes `spot: spot ?? undefined` into `computeGexWalls` — the #3495 fix — but the narrowed-horizon `horizonWalls` computation a few dozen lines further down, which sums a SUBSET of expiry columns from the same in-memory matrix (`strikeTotalsForHorizonFromCells`) and runs the result through the same `computeGexWalls` reduction, called it without `spot` at all. Same function, same file, same fetch — one call site had the fix, the sibling twenty lines away did not, because #3495 excluded this file while its own diff was touching it. (2) `recomputeScopedGexLevels` never used `wallsFromStrikeTotals`'s side-constrained pattern in the first place — it independently re-implements "argmax positive value / argmin negative value" with zero spot awareness, the same bug class PR #2417 (2026-08-20) fixed for `wallsFromStrikeTotals`/`deriveWalls`/`computeGexRegime` but never migrated here, because this function was excluded from #3495's scope for the same reason as (1). |
| **Fix** | (1) Added `spot: spot ?? undefined` to the `computeGexWalls(totals, { maxPerSide: VECTOR_WALL_NODES_PER_SIDE })` call inside the narrowed-horizon loop in `buildVectorUniverseRow` — identical shape to the main `gexWalls` call directly above it in the same function. (2) Added the same side-constraint `wallsFromStrikeTotals`/`computeGexWalls` use to `recomputeScopedGexLevels`'s scan loop: a callWall candidate must have `strike > spot`, a putWall candidate `strike < spot` (both strict — a strike exactly at spot qualifies as neither, matching the existing convention). `king` (argmax `|value|`, from the separately-imported `kingFromStrikeTotals`) is intentionally left unconstrained, matching every other wall producer in this codebase — the King node answers "where is the largest gamma concentration", not "what is resistance/support", so it has no spot-relative geometry to enforce. `spot<=0` (the `spot ?? 0` fallback `buildOdteMatrixRows` uses when spot is unresolved) leaves the pick unconstrained rather than nulling every wall, matching the `constrained = spot > 0` convention `wallsFromStrikeTotals`/`computeGexWalls` already use. One deliberate NON-fix, documented in place: `SpxGexMatrixHeatmap.tsx`'s `columnExtremeWalls` passes `spot=0` to `recomputeScopedGexLevels` on purpose — it wants the RAW per-expiry-column extreme gamma strike (not a spot-relative resistance/support read), and `spot<=0` is exactly the escape hatch that preserves that call site's historical behavior. Its stale comment ("callWall/putWall selection doesn't depend on spot at all") was corrected to say why 0 is passed deliberately now that the function *can* be spot-constrained. |

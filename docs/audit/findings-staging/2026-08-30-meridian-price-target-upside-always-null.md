## Meridian: analyst "Street PT" upside% was hardcoded null, silently hiding the whole price-target line — FIXED

> **kind:** `FINDING`

Meridian-lane pass in the "check product by product" audit sweep (Meridian had not had a dedicated pass yet today). Found by reading `src/lib/meridian/*` end-to-end (a pure-logic defect — no live UI needed to prove it, just tracing the field from producer to consumer).

| Field | Detail |
|---|---|
| **Symptom** | `MeridianEarningsIntelPanel`'s "Financials context" card never shows the "Street PT $X (Y% upside)" line — for ANY ticker, at any time, including names that have a real, live Benzinga analyst price target. |
| **Root cause** | `buildMeridianFinancialsContext` (`src/lib/meridian/meridian-financials-context.ts`) hardcoded `price_target_upside_pct: null` unconditionally, no matter what the fundamentals bundle carried — there was no code path that could ever set it to a real number. The consumer, `MeridianEarningsIntelPanel.tsx` line 81, gates the entire PT line on `financials.price_target != null && financials.price_target_upside_pct != null` — **both** halves must be non-null. Since the second half was permanently null, the whole `<li>` was dead: even a ticker with `price_target: 550` from a fresh Benzinga article never displayed it. This is the same class of defect FINDINGS has caught before in this codebase (a field that always reads absent quietly deletes a feature rather than degrading it) — this is the Meridian instance of it. `BenzingaPriceTarget` (the real type of `bundle.price_target`) was checked and confirmed to carry only the raw dollar target, never an upside — so there was genuinely nothing upstream to forward; the missing input was the CURRENT PRICE to compare the target against, which the function never received as a parameter at all. |
| **Evidence** | Traced the whole chain: `meridian-financials-context.ts` → the literal `price_target_upside_pct: null` (unconditional, no branch) → `meridian-earnings-intel.ts`'s two call sites, both `buildMeridianFinancialsContext(fundamentals)` with a single argument → `MeridianEarningsIntelPanel.tsx:81`'s `&&`-gated render. Confirmed via `git log -p` that the field has read `null` unconditionally since the file was introduced in #2253 and was never touched since. Confirmed via grep that `price_target_upside_pct` has exactly one producer (this function) and one non-test consumer (the panel), so there is no other place upside is (or was ever) computed. Wrote a failing regression test first (`buildMeridianFinancialsContext computes price_target_upside_pct from spot`) and confirmed it fails on the pre-fix code (`undefined !== 550` — the whole context object degenerated further once the test bundle's minimal ratios/signals were added, then passed clean post-fix), then confirmed it passes after the fix; full file `node --import tsx --test src/lib/meridian/meridian-earnings-intel-core.test.ts` went 17/18 pre-fix → 18/18 post-fix. |
| **Blast radius** | Single producer, single consumer — `buildMeridianFinancialsContext` and `MeridianEarningsIntelPanel.tsx`. Both `meridian-earnings-intel.ts` call sites (the earnings-report path and the top-level `roundFloats({...})` return) needed the new `spot` argument threaded through; both already had `spot` in scope in the same function (`meridian-earnings-intel.ts:190`), so no new data fetch was required — the value was already computed, just never passed to this one function. |
| **Fix rationale** | `spot` is now an explicit, optional second argument to `buildMeridianFinancialsContext`. Optional so any caller that only wants the other fields keeps compiling without a change. `price_target_upside_pct = (target − spot) / spot × 100`, computed only when target and spot are both finite numbers AND `spot > 0` — a percentage relative to a zero/negative/non-finite spot isn't a real number and must stay honestly null rather than becoming `Infinity`/`NaN`/a nonsense negative-base ratio. Considered computing upside from a value inside `BenzingaPriceTarget` itself instead — rejected, because that type genuinely carries no current-price field (verified against `polygon.ts`'s parser, which only extracts the target dollar figure from article text); the current price has to come from the caller, which already has it. |
| **Why not caught earlier** | The one existing test for this function (`buildMeridianFinancialsContext maps fundamentals bundle`) passed a fixture with `price_target: { price_target: 550, upside_pct: 12.5 }` — a field (`upside_pct`) that does not exist on the real `BenzingaPriceTarget` type at all, only surviving because the test bypasses type-checking with `as Parameters<...>[0]`. The test never asserted on `price_target_upside_pct` in the output, so a hardcoded `null` return sailed through unnoticed; the fixture's bogus extra field made it look, on a skim, like upside data was already flowing in. Corrected the fixture in the same PR (dropped the nonexistent field) so it can't keep misleading a future reader. |
| **Regression guard** | New test in `meridian-earnings-intel-core.test.ts`: $550 target vs $500 spot → `+10`; no spot supplied → `null` (honest absence, not fabricated); spot `0`/`NaN`/negative → `null` in all three cases (never `Infinity`/`NaN` leaking to the UI); no price target at all → `null` regardless of spot. |
| **Gates** | `npx tsc --noEmit` clean (Node 20.20.2) · `node --import tsx --test src/lib/meridian/meridian-earnings-intel-core.test.ts` 18/18 pass, confirmed RED (17/18) on the pre-fix code via `git stash`. |
| **Status** | FIXED |

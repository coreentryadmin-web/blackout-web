## 2026-09-04 — [FINDING, P4 correctness, admin GEX health panel] `peekGexHeatmapCache` could report a negative `age_sec` for a fresh cache entry on cross-replica clock skew — FIXED

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **What prompted this** | Fresh DISCOVERY sweep (checked `git fetch origin main`, `git log origin/main --oneline -30`, and open PRs first — #3477/#3478/#2810 excluded per dispatch, #3479 touches only `uw-rate-limiter.ts` + 4 cron routes, none of which overlap this file). This session's own recent history shows the exact same bug shape found and fixed repeatedly today (`2026-09-04-coaching-alerts-future-timestamp-age.md`, and before that `2026-09-03-future-timestamp-freshness-badges.md`'s FlowFeed/GexHeatmap/meridian-viz/helix-session-pulse fixes) — a raw `Date.now() - t` age computation with no future-timestamp guard. Swept every remaining `Date.now() - (new Date(...)|entry\.\w+)` call site in `src/` that none of those passes had reached, cross-checking each candidate against whether the compared timestamp actually crosses a clock boundary (a same-process in-memory write compared against the same process's own `Date.now()` is not exploitable — several candidates fell into that bucket and were correctly left alone). Found one genuinely new, exploitable instance. |
| **Root cause** | `peekGexHeatmapCache` (`src/lib/providers/polygon-options-gex.ts`) reads the shared `gex-heatmap:{ticker}` cache entry — either the in-memory `cachedHeatmaps` mirror **or a Redis fallback**, and Redis is written by whichever ECS replica last rebuilt that ticker's matrix, not necessarily the replica serving this admin-panel request. It computed `const ageMs = Date.now() - entry.at;` then `age_sec: Math.round(ageMs / 1000)` with no floor. `entry.at` is a `Date.now()` stamp from the WRITING replica's clock; the reading replica's `Date.now()` can read fractionally behind it on ordinary cross-container NTP jitter (the exact same clock-boundary shape the coaching-alerts and WATCH-record fixes already corrected this week — see `src/lib/coaching-alert-age.ts` and `src/features/spx/lib/spx-play-watch.ts`'s 2026-09-03 fix). `Math.round` does not save this: `Math.round(-0.4)` is `0` but `Math.round(-2000/1000)` is `-2` — reachable the moment skew exceeds ~0.5s, not just a full second. |
| **Evidence** | New `src/lib/providers/polygon-options-gex.test.ts` tests, confirmed RED pre-fix: temporarily removed the `Math.max(0, …)` clamp from the newly-extracted `clampedCacheAgeSec` helper and reran — `clampedCacheAgeSec: an entry.at from the future (cross-replica clock skew) clamps to 0, never negative` failed exactly as predicted (`-2 !== 0` for a 2s-skew case). Restored the fix: 58/58 pass in the file (2 new + 56 pre-existing, all green). |
| **Blast radius** | `peekGexHeatmapCache`'s `age_sec` field feeds `src/lib/admin-gex-health.ts` (Thermal admin health panel) and is rendered directly at `src/components/admin/AdminBieDashboard.tsx:1014` (`` `${t.age_sec}s` ``) — an admin could see e.g. `-2s` for a matrix that had just been rebuilt on another replica. The sibling `stale` field and `src/app/api/market/gex-heatmap/route.ts` / `batch/route.ts`'s `age_sec >= ttl_sec` background-warm trigger both use the **raw, unclamped** `ageMs` internally (deliberately unchanged — see below), so no behavioral decision was affected, only the displayed number. |
| **Why P4, not higher** | Admin-only surface (not member-facing), display-only impact (the one place `age_sec` drives behavior — the background-warm trigger — is unaffected because a skew-negative `ageMs` can never exceed a real `ttl_sec`, so the comparison outcome is identical either way), and the skew window is sub-second AWS-managed-clock jitter rather than an attacker- or upstream-controlled arbitrary future date — same reasoning the coaching-alerts P3 write-up used, one notch down for the narrower (admin-only) audience. |
| **Fix** | Extracted a pure, testable helper — `clampedCacheAgeSec(entryAtMs, nowMs)` — that floors the age at 0 seconds, and swapped `peekGexHeatmapCache`'s `age_sec` computation to call it. Left the `stale` verdict computed from the **raw** `ageMs` (a skew-negative value is always `< gexHeatmapMaxStaleMs()`, so clamping first would not change the outcome — kept unclamped to match pre-existing semantics exactly rather than introduce an unrelated behavioral change). |
| **Deliberately unchanged** | `stale` logic, the `ttl_sec`/background-warm trigger in `route.ts`/`batch/route.ts`, and the underlying cache-write path (`entry.at` stays a plain `Date.now()` stamp, no explicit clock-sync attempt) — the fix is entirely at the read-side age derivation, the same boundary every sibling fix in this class has used. |
| **Regression guard** | `src/lib/providers/polygon-options-gex.test.ts`, 2 new tests: ordinary past entries age normally (5s, 90s cases); a future `entryAtMs` (2s skew, and the reachable-at-1ms case) clamps to `0` rather than going negative. Confirmed RED pre-fix / GREEN post-fix as described above. |
| **Gates** | `npx tsc --noEmit` clean (Node 20.20.2). `node --import tsx --experimental-test-module-mocks --test src/lib/providers/polygon-options-gex.test.ts`: 58/58 pass. |
| **Status** | FIXED. |

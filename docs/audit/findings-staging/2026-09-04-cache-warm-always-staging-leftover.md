## 2026-09-04 — [PERF, P1 cross-cron] `CACHE_WARM_ALWAYS` leftover staging knob runs 4 warm crons 24/7, correlates with real ALB tail-latency

> **kind:** FINDING

| Field | Value |
|-------|-------|
| **Status** | FIXED |
| **Root cause** | `shouldRunCacheWarmer()` (`src/lib/cache-warmer-gate.ts`) gates `desk-warm`, `zerodte-warm`, `heatmap-warm`, and `meridian-warm` to a weekday 4:00 AM–8:00 PM ET "extended warm window" via `isEtExtendedWarmHours()` — *except* it also bypassed that gate whenever `process.env.CACHE_WARM_ALWAYS === "1"`. The function's own comment said this was a **staging-only** knob ("Staging sets CACHE_WARM_ALWAYS=1 so EventBridge ticks keep caches hot off cash RTH too"). Staging (`blackout-staging-*`) was fully decommissioned 2026-07-25 (see this file's own "Vector E2E validation — STAGING DECOMMISSIONED" section) — but the **production** secret `blackout-production/app/env` still carries `CACHE_WARM_ALWAYS=1` as a leftover, confirmed live via Secrets Manager on 2026-09-04. With no staging left to intentionally target, that leftover value was silently making all four warm crons ignore their hours gate and run continuously, including deep overnight hours when no member is looking at any of these desks. |
| **Evidence** | Measured live, 2026-09-04, 6h overnight window (00:21–06:18 UTC, i.e. 20:21–02:18 ET — entirely outside the intended 4am–8pm ET window): (1) CloudWatch Logs `/ecs/blackout-production` filtered on `elapsed=` showed **40+ `[cron/desk-warm] background done ... elapsed=`** lines, 10s–33s each, running every 1–3 minutes essentially the whole night (the `desk-warm` in-app leader heals every ~90s per its own code comment). (2) `AWS/ECS` `CPUUtilization` on `blackout-production-web` showed **Average 2–8% but Max 80–90% in nearly every 15-minute bucket** across the full window — the single-task event-loop-saturation signature of a periodic CPU-bound burst (JSON parsing of multi-KB UW/Polygon payloads, GEX matrix + bootstrap-bundle assembly), not fleet-wide load. (3) `AWS/ApplicationELB` `TargetResponseTime` on `blackout-production-app`'s target group over the same window: **p50 37–79ms, p90 91–377ms (both healthy) but p99 1.7–3.6s and Max 9–41 SECONDS**, in every 30-min bucket — the exact "low average, high p99/Max = tail-latency from one saturating background job, not fleet capacity" pattern this repo's standing performance/latency audit mandate (top of this file) names explicitly. All three signals point at the same root: a CPU-bound warm job repeatedly saturating individual web-tier containers for no reason during hours the gate was explicitly built to skip. |
| **Fix** | Removed the `CACHE_WARM_ALWAYS` escape hatch from `shouldRunCacheWarmer()` entirely — it has no live intended consumer now that staging is gone, and dead-but-still-honored knobs are exactly how a leftover value like this gets set (or stays set) in production without anyone noticing. `force=1` (the explicit per-request query param, already wired into all 4 routes for on-demand/debug warms) remains the only bypass. Updated the 3 routes whose skip-reason message advertised `CACHE_WARM_ALWAYS=1` as an option (`desk-warm`, `zerodte-warm`, `heatmap-warm`) to stop mentioning it. `meridian-warm`'s skip message never named the env var so needed no text change. |
| **Blast radius** | All 4 crons sharing `shouldRunCacheWarmer`: `desk-warm`, `zerodte-warm`, `heatmap-warm`, `meridian-warm`. This fix is a pure code change — it neutralizes the leftover secret value without touching Secrets Manager (out of caution: flipping a live production secret is an immediate, unreviewed behavior change outside the normal PR/CI pipeline, and this fix achieves the same outcome through the reviewed path instead). The stale `CACHE_WARM_ALWAYS=1` value can be removed from `blackout-production/app/env` separately as optional cleanup once this deploys — after deploy it is inert either way. |
| **Tests** | `src/lib/cache-warmer-gate.test.ts` — rewrote the test that used to assert the bypass (`"CACHE_WARM_ALWAYS bypasses hours"`) into a regression pin (`"a leftover CACHE_WARM_ALWAYS env var no longer bypasses hours"`) asserting the exact opposite: even with `CACHE_WARM_ALWAYS=1` set in the environment, an outside-hours timestamp is `false` and an inside-hours timestamp is still `true`. Verified RED against pre-fix `cache-warmer-gate.ts` (assertion failed `true !== false`) and GREEN against the fix via `git stash`. Full `npm test` on Node 20 (`export PATH=/opt/node20/bin:$PATH`): 12109/12117 pass, 6 fail — matches this session's established sandbox-only baseline (unrelated to this change), zero new failures. `npx tsc --noEmit` clean. |

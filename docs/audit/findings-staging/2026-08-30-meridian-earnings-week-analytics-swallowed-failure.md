## 2026-08-30 — [FINDING, P3 Meridian] `earnings_week_analytics`'s historical-prints fetch is silently swallowed on failure — same design defect as the 2026-08-18 finding, different field — OPEN

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **Severity** | P3 — a secondary aggregate rollup, not the primary calendar/print-history path (which already throws-on-failure per the 2026-08-18 fix) |
| **Where** | `src/lib/meridian/meridian-benzinga-earnings.ts`, `loadBenzingaEarningsBundle`, lines ~91–100 |
| **Symptom** | ```ts\nconst hist = await fetchBenzingaStructuredEarnings({ tickers: weekTickers, dateLte: todayYmd, limit: 100, sort: "date.desc" }).catch(() => ({ rows: [] as BenzingaStructuredEarnings[] }));\nhistoricalRows = hist.rows;\n```<br>then `earnings_week_analytics: buildEarningsWeekAnalytics(earnings_week, historicalRows)`. When the fetch fails, `historicalRows` is silently `[]` with **no error flag anywhere** — not even the `error: "cache_error"` shape this exact file already uses two lines away (line 209/217, and again in the outer `.catch()` at line 143). `buildEarningsWeekAnalytics` (`meridian-benzinga-analytics.ts`) then returns a "clean" result: `eps_beat_rate: null`, `headline: "${weekRows.length} mega-cap names this window"` — identical to what it would honestly return if there simply were no historical prints yet. A member (or an admin diagnosing why the week analytics panel looks thin) cannot tell "no data exists" from "the fetch broke" from this payload. |
| **Why this is the same class of bug as the 2026-08-18 finding** | That finding's own stated fix requirement was: *"the fix has to surface the failure — an error/entitled flag on the event payload... and must not cache a failed result."* This code path does neither for `historicalRows` specifically, even though the surrounding function (`loadBenzingaEarningsBundle`) already applies exactly that pattern to its OTHER two upstream calls in the same `Promise.all`-adjacent block (`windowRes`/`revisionRes` both carry `entitled`/`error`). The one that got missed is the one added later, scoped to the mega-cap week grid specifically (the comment above it dates to a dedupe fix, not the original 2026-08-18 defect — this fetch was likely added or reshaped afterward and didn't inherit the pattern). |
| **Why not fixed directly this cycle** | Doing this properly means threading a real error signal through the whole chain, not just patching the `.catch()`: `historicalRows`'s failure would need to become an `earnings_week_analytics_error` (or similar) field threaded through `loadBenzingaEarningsBundle`'s return type → `meridian-snapshot.ts` (line 85) → `meridian-timeline-server.ts` (lines 87, 212) → `MeridianEarningsWeekAnalytics` in `features/meridian/lib/meridian-types.ts` (line 887) → whatever UI panel renders the week-analytics headline. That's a multi-file, cross-layer plumbing change in a lane (Meridian) this DISCOVERY session has already made two other changes to this cycle — per this lane's standing policy, a change of that shape gets written up for the owning lane rather than built unilaterally by a sweep session. |
| **Suggested fix shape** | Mirror the existing pattern exactly: `.catch(() => ({ rows: [] as BenzingaStructuredEarnings[], error: "cache_error" as const }))`, thread `hist.error` alongside `historicalRows` into `buildEarningsWeekAnalytics` (or a sibling field next to `earnings_week_analytics` in the bundle return), and have the UI panel that renders the week-analytics headline show a "couldn't load" state instead of a bare beat-rate-less headline when that error is set — same shape as the `calendar_error` field the 2026-08-18 fix already added to `meridian-earnings-enrich.ts`. |
| **Status** | OPEN — flagged for the Meridian lane, no code change made |

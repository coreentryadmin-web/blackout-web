## 2026-09-04 — [PERF, P2 infra-capacity] ElastiCache Redis primary chronically at 94-99.9% of its effective memory budget, evicting up to 620 keys/hour during RTH

> **kind:** FINDING

| Field | Value |
|-------|-------|
| **Status** | OPEN — requires a production infrastructure decision (node resize vs parameter change vs TTL/footprint audit) with real cost/availability tradeoffs; deliberately not executed unilaterally |
| **Root cause** | `blackout-production-redis-rg-001` (cache.m6g.large, parameter group `blackout-production-redis7`: `reserved-memory-percent=25`, `maxmemory-policy=volatile-lru`) never drops below ~94% `DatabaseMemoryUsagePercentage` even off-hours, and climbs to 99.6-99.9% every RTH session, with real `Evictions` counts (not just a percentage warning) reaching 620 in a single hour and totaling ~2260 across one RTH window. The underlying node itself has real physical headroom (`FreeableMemory` 1.8-2.1GB against `BytesUsedForCache` 4.77-5.13GB, i.e. ~26-30% of total node memory genuinely free) — this is specifically the *effective usable-memory budget* (node capacity minus the 25% reservation) being undersized for the working set, not raw hardware exhaustion. Under `volatile-lru`, eviction only ever hits TTL'd keys, but during exactly the hours load is highest, up to hundreds of TTL'd cache entries per hour are being dropped before their TTL naturally expired — forcing whatever depends on them (market-data caches, warmed snapshots) to recompute/refetch from origin, adding latency exactly when it's least wanted. |
| **Evidence** | Live CloudWatch (`AWS/ElastiCache`, `blackout-production-redis-rg-001`): `DatabaseMemoryUsagePercentage` baseline ~94% off-hours, 99.6-99.9% during RTH; `Evictions` peaking at 620/hour (17:00-18:00 UTC on the measured day), ~2260 total across the 13:00-20:00 UTC RTH window; `FreeableMemory` 1.8-2.1GB, `BytesUsedForCache` 4.77-5.13GB. Parameter group confirmed via `describe_cache_parameters`: `reserved-memory-percent=25`, `maxmemory-policy=volatile-lru`. Not previously documented in `docs/audit/FINDINGS.md` or `findings-staging/` under any Redis/memory/eviction search — this is a new observation as of 2026-09-04. |
| **Blast radius** | Any short-TTL Redis-cached read across the platform (desk/GEX/flow/Vector-universe warm caches and similar) is a candidate for premature eviction during RTH, forcing a cold recompute on the next read — the exact "warm cache stops actually being warm" failure mode several of this repo's other cron-warm fixes exist to prevent, just from memory pressure rather than a missing warm cycle. |
| **Why not applied directly** | Three plausible remedies exist, each with real tradeoffs the finding itself names, and none is a pure zero-cost/zero-risk config toggle: <br>1. **Upsize the node** (`cache.m6g.large` → `xlarge`) — genuinely fixes it, but is an ongoing AWS cost increase and (depending on ElastiCache's replace-and-cutover mechanics for a resize) can carry a brief connection blip on a live production cache serving real trading-desk traffic. <br>2. **Reduce `reserved-memory-percent`** (e.g. 25% → 15%) — zero additional cost, directionally safe given the confirmed physical headroom, but is a live parameter-group change to a shared production Redis primary, and depending on which ElastiCache parameters are "immediately modifiable" vs "apply on next reboot," could itself require a broader capacity/measurement decision than a one-line edit. <br>3. **Audit cache-key TTL/footprint** to shrink the working set — the most surgical option but requires real investigation across every warm-cache writer to find what's actually consuming the ~5GB, not a single-file fix. <br>Given the live-cost and availability-blast-radius considerations on options 1-2, and the genuine measurement work needed to properly scope option 3, this was deliberately left as a documented finding for an explicit operator decision rather than executed unilaterally — consistent with this session's standing discipline on infrastructure changes with real ongoing cost or availability tradeoffs (as distinct from the additive, zero-behavioral-change PgBouncer config finding logged alongside this one, which was also left for authorization but for a different reason — an auto-mode classifier block, not a judgment call about which remedy to pick). |
| **Recommended next step** | Whichever remedy is chosen, measure `Evictions` trending back toward the near-zero off-RTH baseline as the success criterion. If option 2 (reduce `reserved-memory-percent`) is chosen, it's the cheapest to try first and reversible by restoring the prior value. |

## 2026-09-02 — [P1, correctness/UX] Homepage gamma promo showed the literal frozen ISR seed's "Snapshot warming up — check back shortly" text directly beside its own "Live" / "Refreshes live every 5 seconds" copy, on every page load, for the ~1-8s the mount-fetch takes to correct it — FIXED

> **kind:** `FINDING`

| Field | Value |
|-------|-------|
| **Reported by** | User, fresh production check: "Production is currently returning GEX snapshot initializing → initializing → Snapshot warming up — check back shortly. The page simultaneously advertises Live and Refreshes live every 5 seconds," explicitly noting this "has failed across checks separated by hours" and asking for the public snapshot API, provider dependency, cache initialization, cold-start behavior, hydration path, and per-instance cache recreation to be inspected. |
| **What I verified live before concluding anything** | `GET /api/public/gex-snapshot?ticker=SPX` returned `available:true` with real data instantly (no degraded/warming state) — the backend is healthy right now, not in an outage. `curl -sD -` on the homepage showed `cf-cache-status: HIT`, `age: 4572` (76 minutes) despite `cache-control: private, no-cache, no-store, must-revalidate, max-age=0` — Cloudflare is edge-caching the homepage HTML against the origin's own no-store directive, exactly the mechanism already documented in this repo's CLAUDE.md ("Access reality" §5) and in the PR #3368 fix note on `HomeLiveDeskStrip.tsx`. A real headless-browser render through the CONNECT-tunnel proxy (`proxy-browser.cjs`'s tunnel helper) confirmed: at T=0 (first paint) the gamma promo panel read literally "Snapshot warming up — check back shortly" with `posture: —`/no levels; by T≈8s (one poll cycle later) it had self-corrected to real SPX data (spot 7,666.6, call/put walls, live regime) with zero console/page errors. So the underlying data path, the client polling loop, and the previous session's `HomeLiveDeskStrip` self-heal fix (#3368) all work correctly — the bug is specifically that `HomeGammaPromo.tsx` (the OTHER gamma panel on the homepage, the one whose exact quoted copy matches the user's report) displays the frozen SSR seed's `read` text unconditionally while its own corrective fetch is already in flight. |
| **Root cause** | `HomeGammaPromo`'s `!showLevels` branch rendered `<p>{snapshot.read}</p>` with no distinction between "genuinely unavailable, nothing to do" and "a corrective fetch fired on mount and just hasn't resolved yet." Its `loading` state was also seeded `useState(false)`, so even the FIRST paint — before the mount effect has had a chance to run — showed the frozen `initial.read` string as if it were a live verdict. Because the homepage route is `export const revalidate = 3600` (ISR) AND Cloudflare-edge-cached for up to `edge_ttl 7200` for anonymous visitors, whatever `buildPublicGexSnapshot("SPX")` happened to return at ONE ISR regeneration (here, apparently a moment the shared last-good cache read also missed — `resolveMiss()` only returns a true `emptySnapshot()` when `loadLastGood()` finds nothing, which given the 24h last-good TTL should be rare, but a Redis blip during that specific regeneration would produce exactly this) gets baked into the served HTML for up to ~3 hours. Every anonymous visitor's FIRST paint during that window shows that frozen text as fact, contradicting the "Live" pill and "Refreshes live every 5 seconds" bullet sitting right next to it — even though the actual data path recovers and every real browser self-heals within one poll cycle. |
| **Why "per-instance/per-deployment cache" was investigated and ruled out** | The user's own hypothesis list included "whether the cache is accidentally being recreated per deployment/instance." Read `src/lib/shared-cache.ts`: the in-memory `Map` is explicitly documented as "the Redis-FALLBACK copy... `Never block member polls on a wedged ElastiCache hop — fall through to in-memory`" — i.e. Redis (ElastiCache) is the primary, genuinely cross-instance/cross-deploy store; the in-memory map only takes over during an actual Redis outage. So this is not a per-instance cache-recreation bug in steady state — confirmed by reading the code rather than assumed. |
| **Fix** | `HomeGammaPromo.tsx`: (1) `loading` is now seeded synchronously — `useState(() => !hasLevels(initial))` — so the very first paint never shows the frozen seed's text when the seed has no real levels (a corrective fetch is about to fire regardless). (2) The `!showLevels` branch now renders `loading ? "Loading live gamma levels…" : snapshot.read` — the raw (possibly stale-and-wrong) seed text is only shown once a real fetch has actually completed and confirmed the state, never while one is in flight. (3) Extracted the repeated `spot != null && (available || degraded)` check into a shared `hasLevels()` helper (was duplicated as `showLevels`); fixed a latent `boolean | undefined` looseness in the process (`degraded` is optional) with an explicit `Boolean(...)`. No change to `public-gex-snapshot.ts`'s existing last-good/degraded fallback machinery — that layer was already correct; the gap was purely client-side display logic not distinguishing "loading" from "confirmed unavailable." |
| **Scope note — why this doesn't fully explain "checks separated by hours"** | If the user's checks are themselves JS-executing (a real browser, or a headless-browser tool), this fix eliminates the visible flash entirely — the very first paint will show a neutral loading state, never the frozen "warming up" text. If instead the check method is a plain HTTP fetch/scraper that never executes client JS (plausible given the report's technical framing), it would ALWAYS see whatever the frozen ISR/edge-cached HTML says, indefinitely, regardless of any client-side fix — because no client JS ever runs for it. That residual case is a genuine architectural tradeoff of a public, unauthenticated, edge-cached marketing page and is not something a client-side change can close; the mitigations available there are (a) shortening the edge TTL specifically for this fragment, or (b) never letting the SSR path bake a raw `emptySnapshot()` into a cacheable response at all (always retry last-good with a wider tolerance before falling back to the literal empty object). Flagging this distinction rather than claiming the fix here is a complete guarantee for every possible check method. |

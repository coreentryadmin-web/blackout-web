## 2026-09-01 — [FINDING, P4 infra/Vector, audit-hygiene] `vector-bead-record`'s declared "1 min EventBridge backup" is not actually deployed — the real backup is entirely in-app, sharing its primary's own failure domain — OPEN, write-up only

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **What prompted this** | Cross-checking `cron-registry.ts`'s 42 registered job keys against the LIVE deployed EventBridge rule set (`boto3 events.list_rules(NamePrefix='blackout-production')`, 46 rules, 2026-09-01) as a fresh angle on the class of bug CLAUDE.md's own `helix-score-signal.mjs` note documents ("`helix-signal-outcomes` fully registered in `cron-registry.ts` yet absent from blackout-infra's deployed `cron-jobs.json`, verified 2026-08-23"). Re-checking that specific case first: `helix-signal-outcomes` **is now live** (`blackout-production-helix-signal-outcomes ENABLED`) — that gap is closed, not something to re-report. But the same cross-check surfaced a different, real instance of the pattern: `vector-bead-record` is the one registered key with no matching deployed rule anywhere in the 46. |
| **This is not a silent outage — evidence it's actually running** | CloudWatch shows `[rth-warm-leader] backup warm 'vector-bead-record' ok (Nms)` firing repeatedly and successfully across multiple hours today (this session independently observed it at 12:01, 12:02, 12:45, 12:46, 13:04, 13:14, 13:15 UTC in an earlier sweep, and again ~21:xx UTC in this one) — so the data IS being kept warm. This finding is about the DEPLOYMENT-TOPOLOGY gap and its documentation, not a live product defect. |
| **What's actually covering it, and why the registry's own label is misleading** | `cron-registry.ts`'s `vector-bead-record` entry (`schedule_label: "Every 1 min backup (market hours); in-app leader at 5s"`) describes three layers: (1) an in-app 5s primary writer, `vector-bead-recorder-leader.ts`; (2) a 1-minute EventBridge-triggered HTTP backup hitting `/api/cron/vector-bead-record` (route confirmed present at `src/app/api/cron/vector-bead-record/route.ts`); (3) implicitly, the generic `rth-warm-leader.ts` catch-all. Layer (2) does not exist as a deployed rule. What's actually running is layer (3): `rth-warm-leader-logic.ts:12` sets this job's own heal-after threshold to **10/60 min = 10 seconds** — tighter than EventBridge's 1-minute floor could ever achieve (the module's own comment: `"EventBridge's native cron floor is 5 minutes, not 1"`) — so in practice the real backup is faster than the label describes, not missing in effect. The label is stale, not the coverage. |
| **The residual risk this label-staleness was hiding** | Both the primary (`vector-bead-recorder-leader.ts`, 5s tick) and the only real backup (`rth-warm-leader.ts`, 15s tick dispatching this job at a 10s heal threshold) are in-process mechanisms living inside the same always-on web ECS service, both gated by `isEtExtendedWarmHours()`, and both depend on the SAME Redis SETNX leader-election path (`getLockRedis`/`tryAcquireLead`, fail-closed on Redis-down in multi-replica per `wsLeaderShouldFailOpenWithoutRedis()`). Every OTHER `market_hours_only` cron in the registry has a genuinely independent third layer — a real EventBridge rule hitting its route on a fixed external clock, unaffected by whatever state the web ECS service or its Redis leader-election is in. `vector-bead-record` is the one job in the registry whose declared "second layer" doesn't exist, so its true failure domain is narrower than its own schedule_label claims: an ECS-wide stall of the web service (a bad deploy, a boot hang) or a sustained Redis outage removes BOTH of its layers simultaneously, not just one, because both live in the same process family and share the same lock dependency — unlike a job with a real EventBridge backup, which would keep firing from outside that blast radius. |
| **Why not fixed directly this cycle** | This is an infrastructure-provisioning question (would a new EventBridge rule need to be added in `blackout-infra`'s terraform, a separate repo this sandbox does not have access to per the standing terraform-drift caution in CLAUDE.md — "most resources were applied MANUALLY," "never `terraform apply` against production"), not a `blackout-web` code change. It's also a judgment call the owning lane should make deliberately: given the 10s in-app heal is already faster than any EventBridge cadence could be, a 1-min EventBridge rule would primarily buy failure-domain independence (surviving an ECS-wide stall), not speed — worth weighing against the cost of one more scheduled resource. |
| **Two small, low-risk pieces someone in `blackout-web` COULD pick up separately** | (1) **Fix the stale label** — `cron-registry.ts`'s `schedule_label` for `vector-bead-record` claims a backup that isn't deployed; either correct it to describe what's actually running (in-app-only, 10s heal, no independent EventBridge layer) or, if an EventBridge rule gets added in infra, leave the label as-is and this note becomes moot. (2) If genuine failure-domain independence is wanted, add `vector-bead-record` to whatever `blackout-infra` mechanism generates the other 45 rules (this repo's own `cron-registry.ts` already carries the route/path/schedule metadata needed to derive it) — but that's the infra lane's call, not something to guess through from here. |
| **Status** | OPEN — deployment-topology gap confirmed live (boto3 `list_rules`, 2026-09-01) and correctly NOT an active outage (in-app backup demonstrably covers it, repeatedly, today); flagged for whoever owns Vector's cron topology / `blackout-infra`. No code change made this cycle. |

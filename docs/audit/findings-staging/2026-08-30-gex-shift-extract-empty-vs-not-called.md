## 2026-08-30 — [FINDING, P3 Largo] `extractGexShifts` conflated "tool called, nothing moved" with "tool never called" — FIXED

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **Symptom** | `src/lib/largo/core/gex-shift-extract.ts`'s own doc comment states its explicit contract: *"Returns null rather than an empty table when the tool was not called — 'no shifts' and 'we did not look' are different, and only the first should render a table saying nothing moved."* The implementation didn't honor it: when a matching tool result was found (`updated_strikes` present as an array) but produced zero valid `shifts`, line 77's `if (!shifts.length) continue;` treated a genuinely-empty array (tool ran, nothing moved) identically to every row being malformed (ambiguous) — both fell through to searching other captured results and, if none matched, to `return null`, which the caller/renderer reads as "we did not look." |
| **Concrete repro** | `extractGexShifts([{ ticker: "SPX", asof: "T1", previous_asof: "T0", updated_strikes: [] }])` returned `null` before this fix. This is not a synthetic edge case: `gexMatrixChangesForLargo` (`src/lib/largo/gex-matrix-changes.ts`) returns exactly this shape — `updated_strikes: []` — on its own documented "Spot moved but no strike exceeded the change threshold" path. |
| **Root cause** | The `!shifts.length` check didn't distinguish `raw.length === 0` (the source array was genuinely empty) from `raw.length > 0` but every row failed to parse (ambiguous — cannot claim nothing moved). Both took the same `continue` path. |
| **Fix** | Split the check: when `shifts.length === 0` AND the raw `updated_strikes` array was itself empty, return `{ shifts: [], asOf, previousAsOf }` immediately — a real, checked result. When `shifts.length === 0` but `raw.length > 0` (every row malformed), the original ambiguous-fallthrough behavior is unchanged. |
| **Blast radius / why this is safe** | `extractGexShifts` has exactly one caller, `src/lib/largo/answer-contract.ts` (`gexShifts: extractGexShifts(capturedResults)?.shifts`), which now receives `[]` instead of `undefined` in the genuine no-move case. The only consumer of that field, `LargoDeskRead.tsx`, already gates rendering on `envelope.gexShifts?.length` — falsy for both `undefined` and `[]` — so this fix has **zero observable UI change today**; it corrects the internal envelope semantics (checked-empty vs. never-checked) that the file's own contract already promised, for whatever downstream reasoning (Largo's own model, future features) might later distinguish the two states. |
| **Why not caught earlier** | `gex-shift-extract.test.ts` had a test named exactly for this distinction ("not-called and nothing-moved are different — one is null, one is a table") but only exercised "tool truly never called" and "called with every row malformed" — never the genuinely-empty-array case, so the gap shipped silently. |
| **Regression guard** | New test: a result shaped exactly like `gexMatrixChangesForLargo`'s real no-move payload (`updated_strikes: []`, real `asof`/`previous_asof`) must return a non-null table with `shifts: []` and the correct timestamps. Confirmed **failing** against pre-fix code (`git stash` toggle: 1/8 failure) and passing post-fix. |

| **Status** | FIXED |

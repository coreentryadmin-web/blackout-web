## Meridian: History tab's Beat/Miss Streak displayed EPS surprise ~100x too large (percent copied into a fraction-expecting formatter) — FIXED

> **kind:** `FINDING`

A second, deeper dedicated Meridian bug-hunt pass (the product's first fix today,
`printHistorySummary` pooling unsettled reactions, is unrelated — PR #3211, merged).

| Field | Detail |
|---|---|
| **Symptom** | The History tab's Quarterly Beat/Miss Streak card (`MeridianBeatStreak`, rendered by `MeridianEarningsHistoryPanel`) displayed the average EPS surprise, every per-entry tooltip, and every streak-bar height inflated by ~100x — e.g. a real −0.7% surprise rendered as **"-70.0%"**. |
| **Root cause** | `EarningsAnalyticsRow.eps_surprise_pct`/`revenue_surprise_pct` are a FRACTION convention (0.0447 = 4.47%) everywhere in `meridian-earnings-analytics-core.ts` — `fmtSurprisePct` multiplies by 100, and the streak-bar height (`MeridianEarningsAnalytics.tsx`) multiplies by 200. But `printHistoryToAnalyticsRows` (the adapter that lets the Beat/Miss Streak read real per-ticker `print_history`) copied `p.surprise_pct`/`p.revenue_surprise_pct` straight through — and `print_history`'s fields are already a DISPLAY PERCENT: `benzingaRowsToPrintHistory` (`meridian-benzinga-earnings-core.ts`) stores them via `benzingaSurpriseToDisplayPct`, which multiplies the raw ratio by 100 before storing. So an already-×100 value flowed into a formatter that multiplies by 100 again. |
| **Concrete example** | DKS: `eps_estimate: 2.9, eps_actual: 2.88` → real surprise ≈ −0.69% → `print_history.surprise_pct` stores `-0.7` (a display percent). `printHistoryToAnalyticsRows` copied `-0.7` straight into `eps_surprise_pct`. `buildBeatMissStreak`'s `avgEpsSurprisePct` averaged these already-percent values, and the streak card's `<Delta value={s.avgEpsSurprisePct} />` → `fmtSurprisePct(-0.7)` → `-0.7 * 100 = -70` → **"-70.0%"** instead of the correct **"-0.7%"**. Same inflation on every entry's tooltip (`fmtSurprisePct(e.eps_surprise_pct)`) and the streak-bar height (`Math.abs(eps_surprise_pct * 200)` — every real print's bar clamped to max height, losing the intended visual scale entirely). |
| **Why this matters** | This is the shipped History tab for essentially every earnings name a member views — `MeridianEarningsHistoryPanel` is the sole consumer of `printHistoryToAnalyticsRows`, and `MeridianBeatStreak` is the sole consumer of `buildBeatMissStreak` in production. |
| **Fix** | `printHistoryToAnalyticsRows` now divides `p.surprise_pct`/`p.revenue_surprise_pct` by 100 before assigning to `eps_surprise_pct`/`revenue_surprise_pct`, converting the print_history display-percent back to the fraction convention the rest of the file (and `fmtSurprisePct`) already assumes. `surpriseQuadrant` (sign-only comparison) is unaffected by the scale either way. |
| **Blast radius** | `src/lib/meridian/meridian-earnings-analytics-core.ts`'s `printHistoryToAnalyticsRows` only — its single downstream consumer chain (`MeridianEarningsHistoryPanel` → `printHistoryToAnalyticsRows` → `buildBeatMissStreak` → `MeridianBeatStreak`). The market-wide-calendar producer (`buildEarningsAnalyticsRows`, a different, already-correct fraction-scale source used by the Week Pulse/Track Record panels) is untouched. |
| **Why not caught earlier** | The existing test for `printHistoryToAnalyticsRows` (`"a real print_history row feeds buildBeatMissStreak correctly"`) only asserted structural properties (row count, ticker, date, graded count) — never the actual `eps_surprise_pct` value or its formatted output through `fmtSurprisePct`, so the 100x unit collision was invisible to the suite. |
| **Regression guard** | Two new tests: `printHistoryToAnalyticsRows` converts a display-percent surprise (`-0.7`, `6.25`) to the correct fraction (`-0.007`, `0.0625`) and formats correctly through the shared `fmtSurprisePct` (`"-0.7%"`); a null surprise stays null through the conversion. Confirmed **failing** pre-fix (`git stash` toggle: 1 failure) and passing post-fix (16/16). |
| **Gates** | `npx tsc --noEmit` clean · `meridian-earnings-analytics-core.test.ts` 16/16 pass · full `npm test` 11479 pass / 0 fail / 2 skipped (Node 20.20.2). |
| **Status** | FIXED |

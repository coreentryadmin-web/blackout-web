## 2026-08-24 — [FINDING, P0 Platform/Admin] `/admin`, `/admin/users`, `/admin/largo-answer-preview` render fully for non-admin signed-in users instead of redirecting — live authorization bypass

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **Symptom** | Any signed-in member — confirmed down to **free tier, explicit `publicMetadata.role: "member"`** — who navigates to `/admin`, `/admin/users`, or `/admin/largo-answer-preview` on production gets a full `200` render of the real admin page (correct `<title>`, full HTML, no redirect), instead of the expected redirect to `/dashboard`. |
| **Root cause (confirmed divergence, exact line not yet isolated)** | All three pages share the identical pattern: `export const dynamic = "force-dynamic"`, `export const revalidate = 0`, `await requireAdmin()` as the literal first statement of the component (`src/app/(site)/admin/page.tsx:7-12`, same shape in `admin/users/page.tsx` and `admin/largo-answer-preview/page.tsx`). `requireAdmin()` (`src/lib/admin-access.ts:44-55`) calls `isAdminUser(userId, sessionClaims)` and is supposed to `redirect("/dashboard")` when it returns `false`. **The API-route equivalent, `resolveAdminApi()`/`requireAdminApi()` (same file, lines 66-102), calls the exact same `isAdminUser()` predicate and correctly returns `403 {"error":"Forbidden"}` for the identical session/cookie, tested back-to-back.** So `isAdminUser()` itself is computing the right answer (`false`) — the bug is specifically in `requireAdmin()`'s page-rendering path failing to act on that `false`, most likely in how/whether the `redirect()` call from `next/navigation` actually takes effect inside this component tree (a `(site)/error.tsx` boundary exists in the same segment as a possible interaction point, though this was not confirmed as the mechanism — flagging it as the first place to look, not asserting it as proven). This needs someone with production log/debugger access to isolate the exact line; what is proven here is that the divergence is between the two gate implementations, not in the shared predicate. |
| **Evidence — measured, not inferred** | Live production, three independently-minted non-admin Clerk sessions (fresh emails, one with `publicMetadata: {tier:"premium"}` — role absent — repeated 3x for consistency, one with a fully separate identity, one with **explicit** `publicMetadata: {role:"member", tier:"free"}`): all 5 attempts across 3 identities returned `200` with the real admin page title (`"Admin · BlackOut"`, `"User management · Admin · BlackOut"`, `"Largo Answer Preview · Admin · BlackOut"`) and full page length (~53-54KB), never a redirect. Decoded the actual JWT from one session: `{"role":null,"tier":"free", ...}` — `roleFromSessionClaims` correctly maps `null` → `"member"`, `adminFromJwtRole("member")` returns `false` definitively (the JWT fast-path, no Clerk Backend fallback needed). **Same session, same cookie, immediately before and after the page request**: `GET /api/admin/health` → `403`, `GET /api/admin/me` → `403`. Ruled out CDN/edge caching as the cause: a fully unauthenticated request (zero cookies) to `/admin` correctly gets `307` to `/sign-in?redirect_url=%2Fadmin` with `cf-cache-status: DYNAMIC` — so the origin is generating a per-request response, this isn't a stale cached page being served to everyone. |
| **Severity qualifier — bounded, not a full data leak (for now)** | `AdminAnalyticsDashboard` (rendered inside `/admin`) is a `"use client"` component — it fetches its data via the same client-side calls to `/api/admin/*` routes, which **are** correctly gated (confirmed 403 above). So this is not currently a full admin-data leak: what leaks is the admin console's UI shell, navigation structure, and labels to any signed-in member, and the client-side data fetches inside it will themselves 403 in the browser. **This bound is fragile, not safe**: the root cause is that the page-level gate does not function at all, so any future change that adds server-side data fetching to one of these three pages (a very ordinary Next.js pattern) would leak real admin data immediately, with no new bug introduced — the existing one would simply stop being cosmetic. |
| **Blast radius** | Confirmed on all 3 admin pages that call `requireAdmin()` directly (`/admin`, `/admin/users`, `/admin/largo-answer-preview`). `/admin/x-intel` and `/admin/x-intel/[id]` are a **separate, independent** gap noted below. `/admin/track-record` redirects unconditionally to `/admin?tab=track-record` regardless of auth (no gate of its own), inheriting whatever `/admin` does — currently also exposed as a result. Every `/api/admin/*` route (44 checked) uses `resolveAdminApi`/`requireAdminApi`/`getAdminApiActor` and was independently verified live to correctly return 401/403 for the same non-admin sessions across a 13-route sample spanning the highest-risk ones (`run-migration`, `cron/run`, `users/[id]/sign-in-link`) — so the API layer is not implicated. |
| **Related, separate gap found in the same sweep** | `src/app/(site)/admin/x-intel/page.tsx` and `.../x-intel/[id]/page.tsx` are `"use client"` components with **no server-side admin gate at all** (no `requireAdmin()` call, and the shared `admin/layout.tsx` is a bare pass-through that only imports CSS — it does not gate). Unlike the three pages above, this isn't a broken redirect; there is simply no page-level check to break. Site middleware still blocks a fully unauthenticated visitor (redirects to `/sign-in`), but a signed-in non-admin reaches the page shell; the underlying `/api/admin/x-intel/queue` data endpoint is correctly gated (`403` confirmed live), so the same "shell leaks, data doesn't" bound applies. Filed together because the fix likely wants to be the same shape (a real gate on the `admin` layout or every page under it), not because the mechanism is identical. |
| **Deliberately NOT fixed here** | `src/lib/admin-access.ts` and every affected `page.tsx` are outside the QA/Adversarial lane's ownership boundary (platform/auth code, not QA tooling) — routed per the brief's standing instruction. Given the severity, this was escalated directly rather than only queued: filed immediately as this finding, no code touched. A plausible fix shape for whoever owns this: (1) root-cause why `redirect()` inside `requireAdmin()` doesn't take effect in this exact render path — check whether the `(site)/error.tsx` boundary or something else in the segment is intercepting the `NEXT_REDIRECT` throw; (2) as a belt-and-suspenders fix regardless of the exact mechanism, consider having `requireAdmin()` return an explicit non-content sentinel the caller checks rather than relying solely on a thrown redirect signal for something this security-sensitive; (3) add a real gate to the bare `admin/layout.tsx` (or to the two ungated x-intel pages directly) so the admin section fails closed by construction instead of per-page opt-in, which is what let 2 of these 5 pages ship with no gate at all rather than a broken one. |
| **Status** | OPEN — routed to the owning lane (Platform/Auth). Reproduction is deterministic (5/5 attempts across 3 independent non-admin identities). This is a live, currently-exploitable production authorization defect and should be treated as urgent. |

## 2026-09-03 — [FINDING, P1 Public Gamma / Homepage] ISR homepage's direct call to the live-compute GEX snapshot builder tripped Next's "Dynamic server usage" bailout, which got silently swallowed and poisoned the shared 5s snapshot cache for every reader — FIXED

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **What prompted this** | Operator escalation (2026-09-03, "Fresh check at 9:45 PM PT") upgrading a recurring "homepage gamma panel flashes 'no options-chain data'" report from a normal P1 to a production incident requiring root cause + monitoring, having reproduced it across repeated checks spanning much of the day. |
| **Symptom** | The public homepage gamma promo (`HomeGammaPromo`/`HomeLiveDeskStrip`, seeded via `page.tsx`) intermittently flips from a genuinely live SPX gamma read to "No options-chain data for this ticker — dealer gamma profile unavailable" and back, at all hours (confirmed both during and outside RTH — not an overnight 0DTE-rollover artifact, an earlier hypothesis this investigation explicitly ruled out after a full 24h CloudWatch sweep showed the failure recurring at every hour). A live browser capture (T=0/3s/8s/15s) showed the exact flip; direct polling of the public API confirmed the API itself alternates, not a client-side bug; a direct curl to both `api.massive.com` and `api.polygon.io` confirmed the underlying options chain data is healthy (250 real contracts returned for the same strike band) — ruling out an upstream data problem. |
| **Root cause** | `src/app/(marketing)/page.tsx` is ISR (`export const revalidate = 3600`) and called `buildPublicGexSnapshot("SPX")` (`src/lib/public-gex-snapshot.ts`) directly for its SSR seed. On a shared-cache miss, that function's live-compute path calls `fetchGexHeatmap` → `buildGexHeatmapUncached` → `fetchHeatmapBand` → `polygonFetchUrl` (`src/lib/providers/polygon-options-gex.ts`), which issues `fetch(url, { cache: "no-store" })`. Firing a `no-store` fetch from a page Next.js is still trying to render **statically** trips Next's internal `DynamicServerError` bailout signal (`"Dynamic server usage: Route / couldn't be rendered statically because it used ... no-store fetch"`) — this is framework control flow, not a real network failure, and is meant to propagate up so Next can fall back the route to dynamic rendering. `polygonFetchUrl`'s `catch (err) { console.warn(...); return null; }` (documented contract: "never throws, so best-effort callers degrade cleanly") swallows this framework signal identically to a genuine timeout, logging `"[polygon-gex] chain fetch threw from api.massive.com /v3/snapshot/options/I:SPX: Dynamic server usage: Route / couldn't be rendered statically..."` and returning `null`. That cascades to `emptyHeatmap()`'s "no options-chain data" read, which `buildPublicGexSnapshot` then **writes to the shared 5s Redis cache** (`public-gex-snapshot:SPX`) — poisoning it for every other reader, including the client's own live poll (`/api/public/gex-snapshot`) and `/tools/gamma-snapshot`, until the next successful compute overwrites it. |
| **Evidence** | Live CloudWatch sweep of `/ecs/blackout-production` over a rolling 24h window, filtered on `"Dynamic server usage" and "Route /"`, shows this recurring at all hours — most recently `2026-09-03 04:43:07.079` and `04:43:06.723` (two hits ~350ms apart, one per concurrent request racing the same cache-miss window), plus `03:55:03` and `03:42:17` the same night — all identical `[polygon-gex] chain fetch threw from api.massive.com /v3/snapshot/options/I:SPX: Dynamic server usage: Route / couldn't be rendered statically be…`. `Route /` is the tell: `/tools/gamma-snapshot` (`export const dynamic = "force-dynamic"`) and the `/api/public/gex-snapshot` Route Handler (inherently dynamic) are structurally immune to this bailout — only the ISR homepage can ever produce it, which matches the log 100% of the time. |
| **Blast radius** | Only `page.tsx`'s call site was affected — confirmed by code inspection that the other two callers of `buildPublicGexSnapshot` are immune: `src/app/(marketing)/tools/gamma-snapshot/page.tsx` (`dynamic = "force-dynamic"`) and `src/app/api/public/gex-snapshot/route.ts` (a Route Handler, never statically rendered). No other ISR/static page in the repo calls `buildPublicGexSnapshot`. The shared-cache poisoning meant the blast radius of each individual trip was every reader for up to 5s (`CACHE_TTL_SEC`), not just the homepage's own render. |
| **Fix** | Added `readPublicGexSnapshotSeed(ticker)` to `public-gex-snapshot.ts` — a cache-only read for ISR/static pages that never calls `fetchGexHeatmap`/the live-compute path: shared-cache hit → last-known-good (marked `degraded`) → a warming placeholder. It can never trip the bailout and never writes a broken result back to the shared cache. `page.tsx` now calls `readPublicGexSnapshotSeed("SPX")` instead of `buildPublicGexSnapshot("SPX")`. This is safe because the client components (`HomeGammaPromo`/`HomeLiveDeskStrip`) already self-heal via their own mount-time fetch against the real dynamic API route — the SSR seed only ever needed to be "best cached value available," not "freshly computed." `buildPublicGexSnapshot` itself, `polygonFetchUrl`'s catch, and the pre-existing `noteWarmingAndMaybeAlarm`/`shouldAlarmPublicGexWarming` freshness-SLO alarm are all left untouched — they are correct for the two genuinely dynamic callers, and the alarm path is unreachable from the new cache-only seed by design (it only fires from `resolveMiss`, which only the live-compute callers can reach). Deliberately NOT touched: `polygonFetchUrl`'s broad catch itself (still correct/needed for the two dynamic callers that legitimately want best-effort degrade-to-null on a real network failure). |
| **Regression guard** | `src/lib/public-gex-snapshot-seed.test.ts` (new) — 3 tests using the repo's existing `mock.module` pattern (mirrors `public-gex-snapshot-degraded.test.ts`), with `fetchGexHeatmap` mocked to **throw** if ever called: cache-hit, last-known-good fallback, and cold-cache-warming-placeholder, each asserting `fetchCalls === 0`. `src/app/(marketing)/homepage-gamma-seed.test.ts` (new) — source-text regression asserting `page.tsx` calls `readPublicGexSnapshotSeed` and never `buildPublicGexSnapshot` (comment blocks stripped before matching, since the incident trace comment in `page.tsx` itself names `buildPublicGexSnapshot` in prose as the thing not to call). Confirmed RED pre-fix (`git stash` the two source-file edits with the new tests kept: the seed test file doesn't exist / `page.tsx` still imports `buildPublicGexSnapshot`, both fail for the right reason) and GREEN post-fix (4/4 across both new files, plus the full run below). |
| **Gates** | `npx tsc --noEmit` clean (Node 20.20.2). Full `npm test` (`scripts/run-tests.mjs`, the correct entrypoint): PASS — see run output attached to this PR. |

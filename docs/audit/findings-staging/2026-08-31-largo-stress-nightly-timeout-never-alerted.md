## 2026-08-31 — `largo-stress-nightly.yml`'s timeout is its DOMINANT outcome (15/19 runs) and never opened an ops-auto-fix issue — FIXED (alerting only)

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **What prompted this** | Following up on the previously-flagged fire-time drift (`2026-08-31-largo-stress-nightly-schedule-drift.md`, PR #3238) — waiting for a new run to fire so PR #3227's `issues: write` permissions fix could finally be confirmed end-to-end. Run #19 fired at 14:17:38 UTC and its job logs showed something more serious than schedule drift. |
| **Root cause** | `.github/workflows/largo-stress-nightly.yml` sets `timeout-minutes: 45` on the job and gated its "Open ops issue on failure" step on `if: failure()`. When a job hits `timeout-minutes`, GitHub Actions marks the in-progress step (and the job) **`cancelled`**, not `failed` — `failure()` evaluates to `false` for a timeout, so the alert step was silently **skipped**, not run, on every single timeout. |
| **This is not a rare edge case — it is the modal outcome** | Pulled all 19 recorded runs (`list_workflow_runs`, 2026-08-13 → 08-31) and their conclusions/durations: **15 of 19 (79%) ended `cancelled` at almost exactly 45.3 minutes** (08-14, 08-15, 08-16, 08-18, 08-20 through 08-29, 08-31). Only 3 ended `failure` (fast crashes, <28min) and **exactly 1 of 19 ended `success`** (08-17, 26.6min). None of the 15 timeout runs ever opened an ops-auto-fix issue — this workflow has been effectively unmonitored for at least the full 19-run history, despite the earlier `issues: write` fix (PR #3227), because that fix only helps once the alert step actually *runs*, and a timeout never let it run at all. |
| **Why the timeout is (almost) guaranteed, not incidental** | Read run #19's live job log directly. `LARGO_STRESS_BANK=all` runs the full merged bank (`bank1:109 + bank2:100 + bank3:193 + bank4:121 = 523` questions) through `scripts/largo-stress-run.mjs` at the harness's own hardcoded `concurrency=1`, each live probe taking ~18,000-90,000ms (`✓ 23460ms OK`, `✓ 86945ms OK`, etc. — real samples from the run). At even an optimistic 30s/probe average, 523 sequential probes need **~4.4 hours** — the 45-minute budget was never enough to finish even one full "all banks" pass, regardless of any other issue. **A second, compounding failure mode was also visible in the same run**: partway through (14:51:14 UTC, ~33 minutes in), the harness's Clerk session hit a re-establish throttle (`[clerk-session] refresh returned no JWT; re-establish throttled (Ns left)`) that never recovered for the rest of the run — the remaining ~12 minutes produced **282 consecutive immediate 401/SKIP results** (zero real signal) before the 45-minute wall finally killed it. |
| **What was fixed this pass (alerting only)** | Changed the ops-issue step's condition from `if: failure()` to `if: failure() || cancelled()` — the standard GitHub Actions idiom for also catching a `timeout-minutes` kill. A future timeout will now correctly open an `ops-auto-fix` issue instead of vanishing silently. Added `src/largo-stress-nightly-timeout-alerting.test.ts` (2 tests, git-stash red/green verified: fails without `cancelled()` in the condition, passes with it) so this exact silent-alerting-gap shape — the same class of bug the `issues: write` permissions fix (PR #3227) closed one layer down — cannot regress unnoticed. |
| **What was deliberately NOT fixed this pass** | The actual timeout cause (523-question `all`-bank scope at `concurrency=1` structurally exceeding 45 minutes, and the unrecovering Clerk re-establish throttle once it triggers) is a scope/ops decision — raise `timeout-minutes`, shrink the nightly bank selection, raise the harness's own concurrency, or fix the session-refresh throttle recovery in `scripts/largo-stress-run.mjs` — none of which is a "small self-contained bug" DISCOVERY should decide unilaterally. This fix restores VISIBILITY into the existing failure mode; it does not change the timeout budget or run scope. Whoever owns the Largo nightly gate should treat the next `ops-auto-fix` issue this opens as expected, not a new regression, until one of those follow-ups lands. |
| **Blast radius check done this pass** | Grepped for other workflows in this repo using `timeout-minutes` together with an `if: failure()`-only alerting step — `largo-stress-nightly.yml` is the only one carrying this specific combination; not generalizing the regression test into a repo-wide ratchet (unlike the sibling `issues: write` test) because `cancelled()` is not universally the right requirement for every workflow's alert step — a human-triggered cancellation is a legitimate reason NOT to alert in some workflows, so this stays scoped to the one file with the evidenced problem. |
| **Status** | FIXED (alerting restored) — the underlying timeout root cause remains OPEN, flagged above for whoever owns the Largo nightly stress gate's scope/timing |

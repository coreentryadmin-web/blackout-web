## 2026-09-04 — [PERF, P1 cron] desk-warm still firing off-hours after #3512 — `force=1` was a fully unthrottled bypass

> **kind:** FINDING

| Field | Value |
|-------|-------|
| **Status** | FIXED |
| **Root cause** | `#3512` (14c5d815d5, merged 06:40 UTC / deployed ~07:32 UTC) correctly removed the `CACHE_WARM_ALWAYS` leftover-env-var bypass from `shouldRunCacheWarmer`'s **normal (non-forced)** path. That fix is genuinely intact and working — see Evidence. But `force=1` was *always* a completely separate, unconditional bypass of the same hours check (`if (force) return true;` in `cache-warmer-gate.ts`), and `cron-dispatch.ts` marks `desk-warm` `force: true` for every in-app dispatcher, with the same query param documented as open to any `CRON_SECRET` holder for on-demand/debug warms. Nothing capped how *often* `force=1` could be replayed. The only existing protection (`OVERLAP_LOCK`, `desk-warm:running`, `sharedCacheSetNx`) guards solely against a second run starting while the first is still in flight, and is released the instant each run completes — often well under a second on an already-warm cache (`elapsed=67ms`, `363ms`, `491ms` observed live). So any caller replaying `?force=1` in a loop could re-trigger the full 5-way UW/Polygon-bound fan-out (`loadMergedSpxDesk` + 2× `fetchGexHeatmap` + `loadBootstrapBundle`×2 + `warmFlowsMemberCaches` + `prefetchSpxDeskEnrichment`) as fast as it could send requests, with nothing in the code capping the rate — indistinguishable in production impact from the original `CACHE_WARM_ALWAYS` bug, just via a different, still-open path. |
| **Evidence** | Live CloudWatch, `/ecs/blackout-production`, 2026-09-04: **314** `"[cron/desk-warm] background done"` completions between 00:29 and 07:59 UTC — deep overnight, weekday, entirely outside the 4:00 AM–8:00 PM ET extended-warm window — median 40s apart, some under 15s. Positively **ruled out** as the source, with direct log evidence, each of the three documented trigger paths: (1) **EventBridge** — `blackout-production-desk-warm`'s rule is `cron(*/5 11-21 ? * MON-FRI *)` (confirmed via `list_rules`/`list_targets_by_rule`, single target = `hit-cron` Lambda) and the Lambda's own log group (`/aws/lambda/blackout-production-hit-cron`) shows **zero** desk-warm invocations anywhere in the 00:00–08:00 UTC window (confirmed the Lambda itself was alive and firing OTHER crons on their normal 5-min cadence throughout); a full `list_rules` sweep of all 47 rules found no second rule targeting the path. (2) **rth-warm-leader** — its own `isEtExtendedWarmHours()` gate (`tick()`, line 127) kept it **fully silent**: zero `"[rth-warm-leader]"` log lines of *any* kind (not even leader-acquisition) between 00:01:40 and 08:00:02 UTC — activity resumes at exactly 08:00:02, the precise ET-4am boundary, which is direct proof the shared `isEtExtendedWarmHours` gate is correct on the deployed image. (3) **cron-staleness-watchdog self-heal** — confirmed via Lambda logs the watchdog cron *did* fire every 5 min all night (25/25 invocations, `200` each), yet zero `"self-heal"`/`"cron-staleness-watchdog"` log lines appear anywhere in the app log group in the same window — consistent with `admin-cron-health.ts`'s `evaluateJob`, where `market_hours_stale` for a `market_hours_only` job is `false` by construction outside cash RTH (`offWindow` is true, so `marketHoursStale = job.market_hours_only && !offWindow && …` short-circuits false), so `healTargets` can never include `desk-warm` off-hours. AWS account/infra also independently ruled out: exactly 9 ECS tasks running (8 `web` + 1 `market-worker`, both matching their service definitions — no stray/zombie task), 0 non-terminated EC2 instances, exactly 1 Lambda function in the account, 0 EventBridge Scheduler schedules. The only remaining explanation consistent with all of this evidence is a direct external HTTP caller holding `CRON_SECRET` and passing `?force=1` — the repo's own `scripts/site-latency-audit.mjs` / `scripts/latency-burst-audit.mjs` / `scripts/compare-latency-envs.mjs` / `scripts/validate-deploy.mjs` are the only code in the repository that constructs that exact request, none of them wired into any scheduled CI job (all four are one-shot/manual), so this is very likely one of them being run repeatedly against production by tooling/another session — not a scheduled or code-triggered path this repo owns. |
| **Blast radius** | The SAME `force: true` pattern in `cron-dispatch.ts` (and hence the same unthrottled-replay exposure) also covers `heatmap-warm`, `meridian-warm`, `zerodte-warm`, `coaching-alerts`, `bie-full-state-snapshot`, `swing-active-refresh`, and `nighthawk-playbook`. This fix is deliberately scoped to `desk-warm` only (the one with measured live evidence and the tightest legitimate cadence — rth-warm-leader's 90s heal threshold, the shortest of any watched key), per the single-issue-PR convention. The other six force-dispatchable crons carry the identical structural gap and are good candidates for the same fix as a follow-up, once/if the same pattern is confirmed live against them. |
| **Fix** | Added a second, independent guard in `src/app/api/cron/desk-warm/route.ts`: `RERUN_COOLDOWN_KEY = "desk-warm:cooldown"` claimed via the same atomic `sharedCacheSetNx` primitive as `OVERLAP_LOCK`, TTL `RERUN_COOLDOWN_SEC = 60`, checked *before* the overlap lock and before any dispatch — even when `force=1` legitimately cleared the hours gate. Unlike `OVERLAP_LOCK`, this key is **not** deleted on completion (no `sharedCacheDel` for it anywhere) — it is meant to persist for its full 60s TTL so the floor holds regardless of how fast an individual run finishes, which is exactly the gap that let the pathological pattern run at a 40s median instead of ≥60s. Fails OPEN on a Redis error, same posture as `OVERLAP_LOCK` (a missed rate limit is safer than a wedged cron). 60s was chosen to sit strictly below every legitimate cadence so it never blocks real traffic: rth-warm-leader's own heal threshold for this key is 90s (`RTH_WRITER_HEAL_AFTER_MIN["desk-warm"]`) and EventBridge's own schedule is every 5 minutes — neither path would ever re-request this key inside 60s. The hours gate itself (`shouldRunCacheWarmer`/`isEtExtendedWarmHours`) was left completely untouched, since it was independently proven correct by the rth-warm-leader silence evidence above — widening or touching it would have been fixing something that already works. |
| **Fix rationale — what was deliberately NOT done** | Did not widen or add a second time-of-day check to `shouldRunCacheWarmer`/`isEtExtendedWarmHours` — that logic is proven correct live (see Evidence) and the actual gap is orthogonal to hours entirely (a *rate* limit, not an *hours* limit): `force=1` is documented, intentional, always-on behavior for legitimate on-demand warms, and removing it would break real debug/deploy-validation use. Did not touch `OVERLAP_LOCK`'s own semantics (immediate release in `finally`) — that guard's job (block a second run while the first is genuinely still in flight) is still correct and still needed for slow runs beyond the new 60s cooldown window; the two guards are complementary, not redundant. Did not attempt to identify or block the specific external caller (no visibility into it from this codebase/session), since the fix that actually bounds the measured production impact — CPU/latency saturation from repeated full fan-outs — is capping the *rate*, which works regardless of who the caller turns out to be. |
| **Tests** | `src/app/api/cron/desk-warm/route.test.ts` — extended with a source-shape regression test (`force=1 is rate-limited by a minimum re-run cooldown, independent of the hours gate`, mirroring the file's existing pattern for the overlap lock — Next.js `app/api/*/route.ts` files cannot export extra symbols, so this pattern uses source-text assertions the same way the pre-existing overlap-lock tests in this file already do) plus a genuinely behavioral test (`the cooldown primitive genuinely refuses a second claim of the same key inside its TTL`) that exercises the real `sharedCacheSetNx`/`sharedCacheDel` primitives (real in-memory NX+TTL semantics in the test environment, since no `REDIS_URL` is set) and asserts a second claim of the same key genuinely fails while the first stands.

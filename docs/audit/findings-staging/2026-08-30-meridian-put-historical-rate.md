## 2026-08-30 — [FINDING, P2 Meridian] Put idea "historical base rate" silently folded flat prints into "down" — FIXED

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **Symptom** | `buildMeridianSummary`'s PUT idea reported a `historicalRate` (the "N/M of this name's last prints reacted down" confidence input, shown in `MeridianEarningsSummaryPanel.tsx` and weighted 20% into `combineConfidence`) that did not match the number/denominator in its own adjacent `why` bullet on the exact same panel — the two are computed from the same `ReactionStats`, but disagreed whenever a name's earnings-print history contained an exactly-zero-move session. |
| **Root cause** | `src/lib/meridian/meridian-summary-core.ts`, in the `build()` closure: `const historical = reaction.upRate == null ? null : side === "call" ? reaction.upRate : round(1 - reaction.upRate, 4)`. `reactionStats()` computes `up = count(m > 0)`, `down = count(m < 0)`, and `sample = moves.length` — a print with `session_change_pct === 0` (or its `next_day_change_pct` fallback) counts toward `sample` but toward **neither** `up` nor `down`. So `1 - upRate` equals `(down + zeroCount) / sample`, not `down / sample`, and silently attributes every flat print to the "down" side. The `why` bullet two lines below computed the honest number directly (`reaction.down / reaction.sample`), so the bug was visible as a live self-contradiction on the panel, not just a wrong-but-consistent number: e.g. for 3 up / 2 down / 1 flat (sample 6), the displayed rate read 50% while the bullet beneath it said "2/6 reacted down" (33%). The call side has no equivalent bug — it uses `reaction.upRate` directly, which is already `up/sample`. |
| **Blast radius** | Two effects, both PUT-side only: (1) the displayed `historicalRate` percentage on `MeridianEarningsSummaryPanel.tsx` disagreed with the printed `why` bullet on the same card, for any name whose earnings history includes a flat print; (2) `combineConfidence`'s 20%-weighted historical component fed the inflated `(down+zero)/sample` value into the PUT idea's overall confidence score, systematically overstating put confidence (never understating — the folded-in zero count only ever pushes the number up) whenever `zeroCount > 0`. Exactly-zero `session_change_pct`/`next_day_change_pct` values are a real, reachable case (a name can genuinely close flat), not a synthetic edge case. |
| **Fix** | Added a `downRate` field to `ReactionStats` (`down / moves.length` when `moves.length >= minSample`, else `null`), computed alongside the existing `upRate` inside `reactionStats()` — same gating, same rounding, symmetric with the call side. Changed the PUT branch of `build()`'s `historical` assignment from `round(1 - reaction.upRate, 4)` to `reaction.downRate` directly, mirroring how the call side already uses `reaction.upRate` directly. No other call site reads `ReactionStats.upRate` or constructs the object, so this is additive and touches no other consumer. |
| **Why this fix and not an alternative** | Computing `historical` inline as `round(reaction.down / reaction.sample, 4)` at the call site (without touching the type) would also have fixed the bug, but `downRate` as a sibling field keeps `ReactionStats` symmetric with its own `upRate` and keeps the `minSample`-gating logic (which the type's own doc comment on `upRate` calls out as deliberate — "a rate from 2 prints is noise") in exactly one place instead of duplicating the guard at every call site. |
| **Why not caught earlier** | `meridian-summary-core.test.ts` had prior coverage for `reactionStats()`'s `up`/`down`/`sample`/`upRate` counts and for the PUT idea's degenerate cases (too-small sample, no walls), but no existing test constructed a `prints` list containing an exactly-zero reaction — so the `1 - upRate` vs `down/sample` divergence, which is a no-op when `zeroCount === 0`, never had a fixture that could expose it. |
| **Regression guard** | Two new tests: `reactionStats: downRate is down/sample, NOT 1-upRate` (unit-level, 4 prints with 1 exactly-zero, asserts `downRate=0.25` against the old code's `1-upRate=0.5`), and `summary: put historicalRate is down/sample, matching its own 'why' bullet — not 1-upRate` (end-to-end through `buildMeridianSummary`, 6 prints with 1 exactly-zero, asserts `historicalRate` matches the `why` bullet's own `2/6` numbers). Both confirmed FAILING against the pre-fix code (`git stash` toggle, 2/36 failures) and PASSING post-fix. |
| **Gates** | `npx tsc --noEmit` clean · `npx eslint` clean on both touched files · `meridian-summary-core.test.ts` 36/36 pass · full `npm test` **11421 pass / 0 fail / 2 skipped** (Node 20.20.2). |
| **Status** | FIXED |

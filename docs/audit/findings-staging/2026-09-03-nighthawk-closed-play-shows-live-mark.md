## 2026-09-03 — [FINDING, P2 correctness, Night Hawk] a 0DTE play the 1s live-marks lane just closed keeps streaming a fresh, non-stale mark/P&L to `/api/market/zerodte/marks` (SSE + REST) for up to ~10s after it actually closed — FIXED

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **What prompted this** | User QA report (2026-09-02) flagged the homepage claim "Real-time P&L marks, not end-of-day summaries" for validation against actual Night Hawk / SPX Slayer behavior. Live production verification (temp Clerk admin+premium user, `/api/market/zerodte/marks`, `/api/market/zerodte/board`, `/api/market/spx/play`, off-hours 2026-09-03) found no anomaly directly (market was closed for hours by test time, well past this bug's window), but confirmed contract identity (OCC vs strike/expiry) and entry-basis pinning are both correct, and prompted a closer read of `src/lib/zerodte/live-marks.ts` for the "closed row still looks live" failure mode the task called out as most likely. |
| **Investigation** | `src/lib/zerodte/live-marks.ts` runs two independently-clocked mechanisms: a 1s poller tick (`runZeroDteMarkTick`) that quotes contracts and derives each play's status via an in-process `latchMemo` (updated every tick, including the tick a play crosses its stop/target/thesis-break and flips to CLOSED — persisted to the DB immediately, per `statusChanged`), and a 10s "active set" cache (`getActivePlays`/`ACTIVE_SET_TTL_MS`) that decides which ledger rows are tracked at all (`toActivePlay` drops `status === "CLOSED"` rows, but only as of whichever DB fetch populated the cache). Because `ACTIVE_SET_TTL_MS` (10s) is longer than one tick (1s), a play the 1s lane has ALREADY determined is CLOSED (and already persisted as CLOSED to the DB) stays in the cached `entered`/`plays` array — and therefore in `buildZeroDteLiveMarksPayloadFrom`'s output — until the next 10s DB refetch evicts it. In the meantime the mark store keeps receiving fresh WS/REST ticks for that OCC (the poller quotes everything in the stale cached set), so the payload row kept computing a moving `mark`/`live_pnl_pct` and `stale:false` off the CURRENT quote — even though `buildZeroDteLiveMarksPayloadFrom` already had access to the fresher truth via its own `latchedStatus` callback (which reads `latchMemo`, not the stale cached `p.status`) and used it correctly for the row's `status` field, just not to decide whether the row belongs in the payload at all. |
| **Root cause** | `buildZeroDteLiveMarksPayloadFrom` (`src/lib/zerodte/live-marks.ts`) computed `status = latchedStatus?.(p) ?? p.status` (the fresh, 1s-latched status) but never used that fresher status to exclude the row — it kept building and emitting a full live mark/P&L row for it regardless. `toActivePlay`'s own contract elsewhere in this file is explicit ("CLOSED = frozen by design"), but that guard only fires on the NEXT ledger refetch (up to `ACTIVE_SET_TTL_MS` = 10s later), not on the SAME tick the closure is discovered. |
| **Why this matters** | This is the literal failure mode the task was checking for: a member watching the live board sees an already-closed 0DTE play continue to render as an actively-updating "● LIVE" position (client `markStreamKind` checks `live` before `playClosed`, and a fresh `mark_as_of` from this bug makes `live` true) for up to ~10 seconds after it closed, with a mark and P&L that have nothing to do with the actual exit — directly contradicting "real-time marks, not end-of-day summaries" in the other direction (showing *too* live, not too stale). This reproduces on every single close during RTH, not just as a rare race — the window is however much of the rolling 10s active-set cache remains unexpired at the moment of close. |
| **Fix** | `buildZeroDteLiveMarksPayloadFrom` now drops a row from the `marks` array entirely once its resolved `status` (preferring `latchedStatus`, the same fresher signal it already computed) is `"CLOSED"` — so a play exits the live lane the same 1s tick the 1s lane discovers the close, not on the next 10s cache refresh. `idle` correctly flips to `true` if that was the only tracked play. Left the 10s active-set cache, the poller's own quoting loop, and the persist/heartbeat logic untouched — this is a single, localized filter at the one shared build site both the SSE push and the REST fallback serialize (per the file's own "round HERE, not in the routes" convention), so both transports are fixed by the one change. (Investigated a related second symptom — the persist loop's own heartbeat can, in a narrower timing overlap, re-write `last_mark` with a still-moving quote for an already-closed row — but did NOT change that here: an existing test in `live-marks.test.ts` explicitly asserts the current heartbeat-continues-past-CLOSED behavior, so changing it is a separate, larger decision than this fix and is left as a follow-up rather than bundled into a single-issue PR.) |
| **Blast radius** | One file (`src/lib/zerodte/live-marks.ts`), one function. Both consumers of `buildZeroDteLiveMarksPayloadFrom` — `getZeroDteLiveMarksFrame` (SSE, `/api/market/zerodte/marks/stream`) and `getZeroDteLiveMarksJson` (REST fallback, `/api/market/zerodte/marks`) — share this one build, so both are fixed together; no client-side change was needed since the wire payload itself no longer carries the stale-but-fresh-looking row. SPX Slayer's play/option-mark path is a structurally different engine (`spx-play-engine.ts`, no shared active-set cache) and was verified separately (live, off-hours) to correctly return `open_play: null` with no leftover premium once a session/play closes — not affected by this root cause. |
| **Regression guard** | `src/lib/zerodte/live-marks.test.ts`: new test `"buildZeroDteLiveMarksPayloadFrom: a play the 1s lane already latched CLOSED is dropped from the payload, even while the 10s active-set cache still carries it"` — seeds a fresh (non-stale) mark for an OCC whose ledger row's OWN `status` is still `"HOLD"` (simulating the un-refetched 10s cache), passes a `latchedStatus` callback returning `"CLOSED"`, and asserts the row is excluded (`marks.length === 0`, `idle === true`); a sibling assertion confirms a still-open latched status (`"HOLD"`) still rides through normally. Confirmed RED pre-fix via `git stash` on `live-marks.ts` alone (assertion `1 !== 0` — the CLOSED-latched row appeared in the payload) and GREEN post-fix, full file 33/33 passing. |

Full `npm test` on Node 20.20.2: 11976 pass / 5 fail / 2 skipped — the 5 failures are the pre-existing, same-day-documented `zerodte-service.test.ts` sandbox artifact (Polygon/`POLYGON_API_BASE` placeholder host + `postgres.railway.internal` unreachable from this sandbox — see the 2026-09-03 `vector-pick-sweep` finding's own Gates note for the same failure signature), in a file this change does not touch and does not import into (confirmed no reference to `buildZeroDteLiveMarksPayloadFrom` from that file's import graph). |

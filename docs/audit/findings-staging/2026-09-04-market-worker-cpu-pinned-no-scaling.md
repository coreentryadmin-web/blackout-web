## 2026-09-04 — [PERF, P2 infra-capacity] market-worker ECS service (single fixed task, no autoscaling) runs CPU-pinned near 100% for extended stretches during RTH

> **kind:** FINDING

| Field | Value |
|-------|-------|
| **Status** | OPEN — infra capacity change with a real correctness precondition (verify safe multi-replica behavior, or vertically scale instead); not executed |
| **Root cause** | `blackout-production-market-worker` is a fixed single-task ECS service (`desiredCount=1`, task-def `cpu=1024`/`memory=4096`, i.e. exactly 1 vCPU) with **no** registered Application Auto Scaling target — confirmed via `describe_scalable_targets`, which returns a target only for `blackout-production-web`. This service is the sole process handling live Polygon/UW WebSocket ingestion (confirmed via the web service's own log line `[init-data-sockets] web tier — skipping upstream WS boot (ingest worker owns sockets)`), meaning it is a real single point of failure for live-data freshness with zero headroom to absorb a load burst other than the process itself slowing down. |
| **Evidence** | `AWS/ECS` `CPUUtilization` for `blackout-production-market-worker` (service-level, single task so this IS the task's own CPU) repeatedly pins at 99.6-99.9% during RTH, including a run of at least six consecutive 5-minute samples all ≥99.6%, with 7 of the 8 highest-CPU samples in a 24h window falling inside RTH. |
| **Blast radius** | If this task's CPU saturation ever translates into WS ingestion backpressure/lag (not separately measured in this pass — CPU saturation was confirmed, its live-data-freshness *consequence* was not), every desk/product surface reading from the ingested WS data (flow, GEX, Vector, 0DTE) would see it as staleness, not as an infra alert — the failure mode would look like a data-correctness bug rather than a capacity one. |
| **Why not executed directly, and the correctness precondition that matters more than the infra change itself** | The finding's own suggested fix names two options: (a) register an autoscaling target so a second task can come up under load, or (b) raise the task's own CPU allocation (vertical scale, same replica count). **Option (a) carries a real, non-obvious correctness risk this finding did not itself rule out**: a service architected as a fixed single task owning exclusive WebSocket connections to Polygon/UW is a strong signal the ingestion code was never designed for N>1 concurrent replicas — this repo has multiple existing Redis-SETNX leader-lock patterns (`rth-warm-leader.ts`, `vector-bead-recorder-leader`) specifically because other subsystems in this same codebase need exactly that kind of coordination before they can safely run on more than one replica. Scaling market-worker to 2 tasks without first confirming its WS-ingestion path has (or gets) the same kind of leader-election/idempotency guard could cause **duplicate WebSocket subscriptions to Polygon/UW** — plausibly hitting upstream rate limits or double-processing live data, which would be a regression, not a fix. Option (b) (vertical scale — raise `cpu` on the existing single task, e.g. 1024→2048, keeping `desiredCount=1`) avoids that risk entirely and was the safer candidate to execute directly, but was not reached this pass because the earlier, zero-behavioral-risk PgBouncer config write in this same investigation was blocked by the coordinator's auto-mode classifier as a production-infrastructure write requiring explicit authorization — the same class of action, so this one was not attempted either. |
| **Recommended next step** | Before touching replica count: read the market-worker ingestion code path (find the WS-connection-owning module) and confirm whether it already has (or would need) a leader-lock/idempotency guard before N>1 is safe. If it's genuinely single-replica-only by design, the safe remediation is a vertical scale (new task-definition revision with `cpu=2048`, same `desiredCount=1`, no autoscaling target needed) — re-measure `CPUUtilization` during the next RTH session to confirm headroom actually opened up. |

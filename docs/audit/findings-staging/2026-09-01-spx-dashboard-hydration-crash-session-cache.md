## 2026-09-01 — [P1, production, /dashboard] SPX desk hit React #418 hydration crashes on essentially every reload during/after an active session — three sessionStorage reads during the hydration render — FIXED

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **Context** | Follow-up to the same day's `(marketing)` hydration fix (see `2026-09-01-marketing-nav-hydration-crash-signed-in-members.md`). Before writing that finding up, checked production's own error telemetry (`GET /api/admin/errors`, admin-only, backed by `captureError`/`fetchRecentErrorEvents`) for the SAME defect class elsewhere, rather than assuming the marketing fix was the whole story. It was not: `/dashboard` — the SPX Slayer flagship desk, the page a signed-in member lands on — had **30 React error #418 events over the last 5 days, 100% of them `/dashboard`**, out of only 38 `Error`-named frontend events total in that window. Nothing else came close. |
| **Root cause** | `/dashboard`'s page (`src/app/(site)/dashboard/page.tsx`) is `force-dynamic` (not ISR like the marketing pages), so this is a DIFFERENT mechanism than the earlier fix, not a recurrence of it — but the SAME general defect shape: a client-only read executed during the render React uses for hydration reconciliation. Found three independent instances, all in the SPX desk's data hooks (`src/features/spx/hooks/`), all reading `sessionStorage` via `@/lib/session-cache`'s `readSessionCache()` (which returns `undefined` server-side — `typeof window === "undefined"` — but a real cached payload client-side whenever the member has a same-trading-day snapshot, since these hooks write to it every ~7.5s / on every poll while the desk is live): <br>1. `useMergedDesk.ts` — `const deskStable = useRef<SpxDeskPayload \| undefined>(readSessionCache(...))`. `deskStable.current` feeds directly into `deskLoading`, which gates which of two **structurally different trees** `SpxDashboard` renders — a tiny loading-skeleton `<div>` vs. the full multi-panel desk (`SpxDashboard.tsx:211-217` vs. `227-480`). Any member reloading (or reopening the tab) during/shortly after an active session hits this: server always sees no cache → skeleton; client's first hydration render sees the real cached desk → full desk. Guaranteed structural mismatch, not a maybe. <br>2. `useSpxPlay.ts` — `const [cachedPayload] = useState(() => sessionActive ? readSessionCache(...) : undefined)`, the exact `useState`-lazy-initializer anti-pattern from the marketing fix, feeding `SpxPlayVerdictBar`'s `play`/`playLoading` props. <br>3. `useSpxPlay.ts` — a `fallbackData: sessionActive ? readSessionCache(...) : undefined` option passed to the same hook's `useSWR` call, which SWR treats as the initial `data` value — same divergence, different mechanism (SWR's own hydration path instead of React's `useState`/`useRef`). |
| **Evidence** | Production telemetry (not inference): 30 `React error #418` events on `/dashboard` over 2026-08-28→09-01, roughly continuous through trading-hours-adjacent timestamps on every one of those 5 days (e.g. 09-01 alone: 14:25, 16:36, 18:43, 19:13, 19:14, 19:42, 19:45, 20:03, 21:24 UTC) — not clustered around deploys, ruling out the transient deploy-window chunk-hash-mismatch mechanism also observed this session (see the `ChunkReload` volume note below) as the cause of *these* specific crashes. Live browser reproduction of `/dashboard` itself was attempted but not completed in this sandbox (the CONNECT-tunnel Chromium harness exhausted the agent proxy's tunnel pool after a few rapid repeated navigations — a known sandbox limitation, not a signal about production) — the root cause here was established by direct source reading of the exact hook chain SpxDashboard depends on (`useMergedDesk` → `deskStable` → `merged` → `deskLoading` → the conditional render at `SpxDashboard.tsx:211`), confirmed against `readSessionCache`'s actual server/client behavior in `src/lib/session-cache.ts:43-45`, and corroborated by `SpxSessionTimeBar.tsx:60-61`'s own comment on the correct pattern ("Clock + feed state are client-only... start null/empty so SSR markup is stable and the first client tick fills them in") — proof the codebase already knew this exact rule, just didn't apply it consistently across every hook that reads the session cache. |
| **Fix** | Same shape in all three: the ref/state now starts at a literal safe default (`undefined`/`null`) identical to what `readSessionCache` returns server-side, and a `useEffect` running post-mount performs the actual sessionStorage read and populates it — a normal client-side re-render, not part of hydration, so React is free to change the DOM there. `useMergedDesk.ts` additionally needed a one-shot `cacheHydrated` state flag threaded into the `merged` `useMemo`'s dependency array, since the memo reads `deskStable.current` directly (a ref, which React doesn't track) and needs an explicit signal to recompute once the effect populates it. `useSpxPlay.ts`'s `fallbackData` option was removed outright rather than reworked — it was fully redundant with `cachedPayload` (now safely hydrated), which already folds the cached play into the merged result via `mergePlayWithCache`. |
| **Blast radius checked** | Grepped every `readSessionCache(` call site in `src/features/spx/` (5 total): the 3 fixed above; `spx-largo-feed-cache.ts`'s `readLargoFeed()`, whose only call site (`SpxSessionTimeBar.tsx:77`) is already correctly inside a `useEffect`, not an initializer — confirmed safe, left untouched; and `useStablePlayConfirmations.ts`'s `useRef<PlayConfirmationLayer \| null>(loadLayer())`, the same anti-pattern a fourth time — fixed identically even though it's currently **dead code** (`SpxTradeAlerts`, its only consumer, was removed from the flagship desk per that component's own 2026-07-13 "DESK CONSOLIDATION" comment and is not currently mounted on `/dashboard`) — fixed rather than left latent for whenever that panel returns, per this repo's policy of fixing every call site of a shared root cause, not just the one that fired. |
| **Regression guard** | New/extended tests in `useMergedDesk.test.ts` (new file), `useStablePlayConfirmations.test.ts` (new file), and `useSpxPlay.test.ts` (extended) — this repo's existing source-text-regex convention (no DOM renderer available in the plain `node:test` setup). Verified all 7 new assertions FAIL against the pre-fix source (`git stash` the three source fixes only, keep the tests, confirm 7 fail / 3 pre-existing pass; restore, confirm 10/10 pass) before relying on them. Full suite: 11563 pass / 0 fail / 2 skip (Node 20). `tsc --noEmit` clean. `eslint` clean on all six touched/added files. |
| **Note — a separate, already-self-healing issue observed in the same investigation** | Production telemetry also showed 422 `ChunkReload` events (a DIFFERENT, already-existing, working recovery mechanism — `src/app/layout.tsx`'s inline mid-deploy chunk-recovery guard) over the same ~4.5-day window, spanning 76 of 113 possible hours, concentrated on `/` (129), `/upgrade` (39), `/sign-in` (15), `/nighthawk` (16), `/dashboard` (14). This is the ALB round-robining requests across old+new ECS task revisions during a rolling deploy with no session affinity, so a client's HTML (from one task revision) can request a JS chunk that lands on the OTHER revision, which doesn't have that exact hash on disk. The existing guard self-heals it (one capped, guarded `location.reload()`), confirmed working during this session (live-reproduced a blank `/sign-up` mid-deploy, confirmed the guard's telemetry beacon fired, confirmed it cleared on retry, and cross-confirmed against `ecs describe-services` showing an actual `IN_PROGRESS` rolling deployment at that exact time). Not fixed here — no code defect, the self-heal works as designed — but the volume (roughly one every ~15 min of deploy-adjacent time) suggests the underlying durable fix (ALB target-group stickiness, or a shared/CDN-backed static asset store so old and new task revisions don't diverge) is worth a dedicated follow-up given how frequently this repo deploys; flagging here rather than opening a half-considered infra PR mid-sweep, since that fix has real fleet-wide blast radius (ALB routing behavior) and deserves focused attention, not a rushed change alongside this one. |
| **Status** | FIXED (the three live hydration-mismatch instances + the one dead one). The ChunkReload/ALB-stickiness item above is explicitly NOT part of this fix — noted for a future dedicated pass. |

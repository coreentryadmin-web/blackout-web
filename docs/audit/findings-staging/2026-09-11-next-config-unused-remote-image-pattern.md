## 2026-09-11 — [FINDING, P3 security, follow-up to PR #4804] `next.config.mjs`'s `remotePatterns` allowed an external host (`images.unsplash.com`) no code anywhere actually uses — removed

> **kind:** `FINDING`

| | |
|---|---|
| **Severity** | P3 — no active vulnerability today (PR #4804 already patched the Next.js AVIF RCE this surface would have been relevant to), but it was unnecessary attack surface for any FUTURE Next.js image-processing CVE, for zero product benefit. |
| **What this closes** | PR #4804 (critical Next.js Image Optimization RCE patch, merged earlier today) explicitly flagged an unresolved follow-up in its own "Blast radius" section: *"next's Image Optimization API is used wherever the app renders next/image against any AVIF-capable source — worth a follow-up check (separate from this fix) on whether any user-influenced image URL reaches that pipeline, to bound real-world exploitability further."* This entry is that follow-up check. |
| **What was checked** | `grep -rn "from \"next/image\"" src` — exactly ONE file in the entire codebase imports `next/image` (`src/components/landing/RedesignHome.tsx`), and every `<Image src=...>` in it resolves to a compile-time-constant local asset path from `src/lib/images.ts`'s `IMAGES`/`MARKETING_MODULE_GALLERY` constants (`/images/marketing/*.webp`, `/images/blackout-emblem.webp`) — no dynamic, user-influenced, or externally-sourced `src` anywhere in the app's own component code. |
| **The real attack surface wasn't component usage — it was `remotePatterns`** | Next.js's `/_next/image?url=<url>&w=...&q=...` optimizer endpoint is a public HTTP route that accepts ANY `url` matching `next.config.mjs`'s `images.remotePatterns` allowlist, regardless of whether the app's own React components ever reference that URL — an attacker hits the endpoint directly. `remotePatterns` listed `{ protocol: "https", hostname: "images.unsplash.com" }`. `git log -S"images.unsplash.com" -- next.config.mjs` traces it to the repo's very first commit ("init BlackoutTrading.com — Next.js 14 full stack") — Next.js starter-template boilerplate, never removed. A repo-wide `grep -rn "unsplash" src` (beyond just `<Image>` usages) returns zero hits anywhere else — no test, no doc reference, nothing. This was live, unused, reachable configuration: any request to `/_next/image?url=https://images.unsplash.com/<anything>` would have been processed by Next's image pipeline, whether or not the app itself ever generated that URL. |
| **Fix** | `remotePatterns` in `next.config.mjs` is now `[]`. New `next.config.test.ts` parses the array out of the config source and asserts every listed hostname has at least one real reference somewhere in `src/` — so a future legitimate external image source (added alongside a real `<Image src="https://...">` call site) passes normally, while a re-introduced unused entry (scaffold boilerplate, a copy-pasted example, a half-finished feature) fails loudly instead of sitting silent for years the way this one did. |
| **Evidence** | RED→GREEN via `git stash`: with the original `images.unsplash.com` entry restored, the new test fails (`remotePatterns lists "images.unsplash.com" but nothing in src/ references it`); with the fix applied, it passes. `node -e "import('./next.config.mjs')..."` confirms the config still loads cleanly with `remotePatterns: []`. `npx tsc --noEmit`: clean. |
| **Why P3, not higher** | Not a live vulnerability by itself — Next's own AVIF RCE (the concrete threat this pattern would have been reachable for) is already patched by PR #4804 in this same repo, today. This is a pure defense-in-depth / attack-surface-reduction fix: removing an unused allowlist entry so the NEXT Next.js image-processing CVE (there will be one eventually) has one fewer live, externally-reachable host to be exploitable through, for a feature the product doesn't use. |

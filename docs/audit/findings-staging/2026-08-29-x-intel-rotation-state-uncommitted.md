## 2026-08-29 — [FINDING, P3 tooling/CI-waste] X-content rotation-state files never got committed by the scripts that mutate them — 9 redundant standalone chore PRs in one day — FIXED

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **Symptom** | `git log` shows nine separate merged PRs on 2026-08-29 alone, all titled "chore(docs): commit stray x-intel rotation state" (#3087, #3113, #3132, #3140, #3141, #3142, #3145, #3147, #3148, #3153 — 9 counting from #3113 forward, plus an earlier #3087), each one a standalone commit whose only content is a diff to `data/x-intel/creative-rotation.json` and `data/x-intel/post-rotation.json`. Every one of those PRs still runs the full `verify` CI suite (`.github/workflows/ci.yml` has no path filter — it triggers on every `push`/`pull_request` regardless of what changed) for a pure two-file data diff with zero code change. |
| **Root cause** | The four X-content posting CLIs (`scripts/audit/x-post-now.mjs`, `x-social-post.mjs`, `x-deep-post.mjs`, `x-quad-post.mjs`) build a post by calling into `scripts/audit/lib/x-social-creative.mjs`'s `saveCreativeState()` and `scripts/audit/lib/x-social-post-kit.mjs`'s `saveRotation()`, both of which `writeFileSync` their LRU rotation state (which combo/shot/hook was just used, so the next post doesn't repeat it) straight to a git-tracked path under `data/x-intel/`. Neither function — nor any of the four CLI scripts — ever ran `git add`/`git commit` on that write. The mutation was left as an uncommitted diff in whatever container ran the script, with no mechanism to ever land it on its own. |
| **Blast radius beyond the CI waste** | Because each agent session in this fleet runs in an ephemeral, freshly-cloned container (per the environment's own operating model — no persistent disk across sessions), an uncommitted write here is not just untidy, it is at risk of being **lost outright** the moment that container is reclaimed, unless some unrelated later session happens to notice the dirty tree in time and sweep it into a chore PR before that happens. That silently defeats the entire point of tracking rotation state — "never the same four screenshots twice" only holds if the state actually survives between runs. |
| **Second contributing factor found while investigating (left unchanged)** | `scripts/audit/lib/x-social-post-kit.test.mjs` and `x-social-creative.test.mjs` exercise `nextPanelPack()`/`nextWhopHook()` etc. directly, which write to the *real* `data/x-intel/*.json` paths (not a temp fixture) as a side effect of `saveRotation`/`saveCreativeState` resolving `join(process.cwd(), ...)`. Confirmed live: running `npm test`/`node --test` on either suite from the repo root dirties `data/x-intel/creative-rotation.json` and `post-rotation.json` on disk, reverted manually before committing this fix. This means even a lane that never touches X-content, but runs the full suite locally, can independently contribute to the same "stray diff" pattern. Not fixed here (would mean adding path injection/mocking to two test files whose only failure mode today is a same-directory local diff, not a wrong assertion) — noted as a natural follow-up if it recurs. |
| **Fix** | New `scripts/audit/lib/x-intel-state-git.mjs` exports `commitXIntelStateIfChanged({ cwd })`, which `git status --porcelain -- data/x-intel`, and only if that's non-empty stages and commits just that directory with a fixed message. It is called once at the very end of each of the four CLIs' own `main()` — both the success path and the `.catch()` handler, since rotation state may already have mutated before a later screenshot-capture step throws. It is a **local commit only — it never pushes**; pushing stays owned by whichever branch/PR flow the calling session is already driving, so this can't land an unreviewed commit on `main`. |
| **Why the commit call sits in the CLIs, not the shared library** | `saveCreativeState`/`saveRotation` are imported and called directly by the unit test suites above. Wiring the git commit into those functions would have made `npm test` itself create real git commits as a side effect — a new, worse bug. Scoping the call to the four CLI entry points (never imported by any test) keeps the fix inert during test runs, confirmed by re-running both existing suites after the change: they still dirty the two JSON files locally (the pre-existing, unrelated issue above) but no commit is produced. |
| **Regression guard** | `scripts/audit/lib/x-intel-state-git.test.mjs` (4 cases), run against a disposable temp git repo created and destroyed per test — never the real repository: commits a real change and leaves the tree clean afterward, is a true no-op (no new commit) when nothing changed, never throws when run outside a git repo entirely, and leaves an unrelated file outside `data/x-intel/` untouched and uncommitted. |
| **Gates** | `npx tsc --noEmit` clean · `npx eslint` clean on all six touched/added files · `npm test` **11396 pass / 0 fail / 2 skipped** (Node 20.20.2), including the new `x-intel-state-git.test.mjs` (4/4) and the pre-existing `x-social-post-kit.test.mjs`/`x-social-creative.test.mjs` (re-confirmed they dirty the real `data/x-intel/*.json` files as a side effect but no commit results, per the point above — reverted before this PR was opened). |
| **Status** | FIXED. |

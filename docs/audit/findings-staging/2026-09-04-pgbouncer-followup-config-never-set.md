## 2026-09-04 — [PERF, P1 infra-config] PgBouncer connection-budget follow-up config from PR #3499 was never set — zero-headroom condition (and correlated ALB 5xx) still live

> **kind:** FINDING

| Field | Value |
|-------|-------|
| **Status** | OPEN — requires production Secrets Manager + ECS task-definition writes, blocked by the coordinator's auto-mode classifier; needs explicit operator authorization or manual execution |
| **Root cause** | `src/lib/db.ts` computes `SAFE_PG_POOL_MAX_DEFAULT` from `REPLICA_COUNT_MAX` and `PGBOUNCER_RESERVED_FOR_OTHER_SERVICES`, added by PR #3499 (merged 2026-09-04) specifically to close a real gap: `blackout-production-web`'s own Application Auto Scaling target runs `MinCapacity=8`/`MaxCapacity=12`, but the pool math previously only ever read `REPLICA_COUNT` (the steady-state floor, 8) — so `PG_POOL_MAX=2 × 8 = 16` plus `market-worker`'s `PG_POOL_MAX=4 × REPLICA_COUNT=1 = 4` already summed to exactly `20` (`PGBOUNCER_DEFAULT_POOL_SIZE`), leaving zero headroom **before** counting web's real autoscaling ceiling (12) or a rolling-deploy overlap. #3499 shipped the code to make this visible via two `console.warn` checks, but its own write-up says explicitly this leaves current pool sizing unchanged until an operator sets the two new env vars — and as of this writing, neither has been set. |
| **Evidence** | Live Secrets Manager `blackout-production/app/env` (checked 2026-09-04): `REPLICA_COUNT=8`, `PG_POOL_MAX=2` (web, sourced via `valueFrom` in the ECS task definition), `REPLICA_COUNT_MAX`=unset, `PGBOUNCER_RESERVED_FOR_OTHER_SERVICES`=unset, `LastChangedDate=2026-09-02` (i.e. never touched since #3499 merged). `blackout-production-market-worker`'s task definition (revision 816) carries `REPLICA_COUNT=1`/`PG_POOL_MAX=4` as **literal** env entries (not secret-sourced) — confirmed via `ecs describe-task-definition`, so market-worker's own values live in its task-def, not the shared secret. Application Auto Scaling `describe_scalable_targets`: web `MinCapacity=8`/`MaxCapacity=12`; **no scalable target registered for market-worker at all**. Live CloudWatch: `AWS/ApplicationELB` `HTTPCode_Target_5XX_Count` on `blackout-production-app` totaled 90 over a 24h window, clustered during RTH with a 10-event single-5-min-bucket spike; `/ecs/blackout-production` logs show hundreds of `[db] transient query error (attempt 1/3): timeout exceeded when trying to connect` + `Cannot use a pool after calling end on the pool` lines in the same window, with a direct ~15-second cluster of ~20 such lines landing inside the exact 5-min ALB bucket that recorded the 10 real 5xx responses. ECS was independently observed mid-rolling-deploy with `runningCount=9` against `desiredCount=8` (one replica over the count the pool math assumes) — the exact overrun scenario #3499's fix targets. |
| **Blast radius** | Both `blackout-production-web` and `blackout-production-market-worker` share the same `PGBOUNCER_DEFAULT_POOL_SIZE=20` backend budget. `SAFE_PG_POOL_MAX_DEFAULT` is currently a no-op for actual connection counts on both services (both set `PG_POOL_MAX` explicitly, which takes precedence per `db.ts`'s own logic) — its only live effect right now is the two diagnostic `console.warn` checks, which stay silent until the two new env vars are set. So this is currently a **pure observability gap**, not (yet) a behavior change waiting to happen — but the underlying oversubscription risk it was built to surface is real and already correlating with production 5xx. |
| **Recommended remediation (values computed, not yet applied)** | Because `web` sources every env var via `valueFrom` against the shared secret while `market-worker` overrides `REPLICA_COUNT`/`PG_POOL_MAX` as **literal task-def env** (confirmed different sourcing mechanisms per service — see Evidence), the two new keys need **different values per service** and cannot both live as one shared secret key: <br>• **web**: add `REPLICA_COUNT_MAX=12` (web's own real ASG `MaxCapacity`) and `PGBOUNCER_RESERVED_FOR_OTHER_SERVICES=4` (market-worker's own consumption: `REPLICA_COUNT=1 × PG_POOL_MAX=4`) to the shared secret, **plus** a new `secrets` entry in web's task definition pointing at each new key (adding a value to the secret's JSON alone does nothing — ECS only injects keys explicitly listed in a task definition's `secrets` array). <br>• **market-worker**: add `REPLICA_COUNT_MAX=1` (no ASG target registered, so its ceiling equals its fixed floor) and `PGBOUNCER_RESERVED_FOR_OTHER_SERVICES=24` (web's worst-case consumption at ITS ceiling: `REPLICA_COUNT_MAX=12 × PG_POOL_MAX=2`) as new **literal** task-def env entries, matching market-worker's existing pattern for these two vars. <br>Both require registering a new task-definition revision for the affected service and an `update_service` call to roll it out (a standard, low-risk ECS deploy — same image, two new env vars) — not a pure "edit a secret value" operation. |
| **Why not applied directly** | Attempting to write these values live (Secrets Manager `put_secret_value` on `blackout-production/app/env`) was blocked by this coordinator's auto-mode permission classifier as a production-infrastructure write requiring explicit authorization. Per this session's operating discipline (CLAUDE.md's own AWS-change guidance plus the harness's own risk-tiering), that block is respected rather than routed around — this finding documents the exact remediation so a human (or a differently-authorized session) can apply it directly, or explicitly authorize it. |

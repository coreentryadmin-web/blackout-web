## 2026-08-31 — [FIX, P2 reliability] Pool-teardown race no longer fails the victim caller outright — `Cannot use a pool after calling end on the pool` is now treated as retryable — FIXED

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **Follows up on** | `docs/audit/findings-staging/2026-08-31-db-pool-reset-race-cascading-failure.md` (PR #3241, DISCOVERY lane write-up) — a live CloudWatch sweep caught a real 17-second burst (12:20:52–12:21:09 UTC, 2026-08-31) where 5 unrelated subsystems (`spx-play-store`, `rth-warm-leader`, `cron/flow-ingest`, `api-telemetry-persist`, and notably `error-sink` — the error-capture pipeline itself) all failed on the DB simultaneously, root-caused to `src/lib/db.ts`'s `resetPoolForRetry()` unconditionally tearing down the module-level shared `Pool` singleton whenever any single caller hits a transient error, with no coordination against other callers concurrently holding/using that same pool reference. |
| **Root cause (recap)** | Caller A's query genuinely times out (real PgBouncer/RDS blip) → A's `dbQuery` retry loop calls `resetPoolForRetry()`, which calls `pool.end()` and nulls the module-level `pool`. Caller B, mid-flight on the SAME pool object at that exact moment, hits `Cannot use a pool after calling end on the pool` — a synchronous client-side throw from the `pg` library, not a real DB error. `isTransientPgError()` did not recognize this message, so B got **zero retries** and failed immediately, purely as collateral damage from A's unrelated recovery logic. |
| **Fix (this PR)** | Added `/Cannot use a pool after calling end on the pool/i` to `isTransientPgError()` in `src/lib/db-transient.ts`. This is fix direction (2) named in the original write-up — "the cheapest one, doesn't touch pool lifecycle semantics at all." A victim caller now treats this specific synthetic error as retryable: `dbQuery`'s existing retry loop calls `resetPoolForRetry()` again (a harmless no-op — `pool` is already `null`) and re-derives a fresh pool via `getPool()` on the next attempt, instead of failing outright on an error the database itself never raised. |
| **What was deliberately NOT changed** | `resetPoolForRetry()`'s teardown logic itself is untouched — the pool-identity guard (fix direction 1: only end/null `pool` if it still `===` the specific instance the failing caller was operating on) and any generation-counter/quiescence-window approach to `getPool()` are real design decisions that need load-testing against realistic concurrent production traffic this sandbox cannot safely generate, exactly as the original write-up said. This PR fixes the caller-visible symptom (an unrelated victim failing outright) without touching the pool lifecycle module that every one of the ~74 `dbQuery` call sites across ~32 files depends on. |
| **Evidence** | `src/lib/db-transient.test.ts` — new test `isTransientPgError: pool-teardown race (...)` asserts `isTransientPgError(new Error("Cannot use a pool after calling end on the pool"))` is `true`. Git-stash red/green proof: fix stashed → 5 pass / **1 fail** (the new test); fix restored → **6/6 pass**. `npx tsc --noEmit` clean (Node 20.20.2). |
| **Blast radius** | Single function (`isTransientPgError`), single file. Every `dbQuery` caller across the app now gets this specific error class retried instead of failed — strictly widens what recovers automatically, never narrows it (all previously-transient patterns are untouched). |
| **Status** | FIXED — the specific victim-caller-fails-immediately symptom from the 2026-08-31 CloudWatch burst is addressed. The underlying shared-mutable-singleton teardown race in `resetPoolForRetry()` itself remains OPEN and is intentionally left to whoever owns `src/lib/db.ts` for the fuller concurrency-safe redesign (pool-identity guard / generation counter) — this PR narrows the blast radius of a live incident, it does not close the root design question. |

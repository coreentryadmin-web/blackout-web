## 2026-09-02 — [FINDING, P1 performance/infra] `vector-pick-sweep` cron had no overlap guard — 5-minute sweeps on a 2-minute schedule stacked concurrent runs, contributing to a measured ALB p99 latency spike — FIXED

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **What prompted this** | User asked for a broad live latency/performance sweep across the whole product. Started from real CloudWatch data rather than guessing: `AWS/ApplicationELB` `TargetResponseTime` on `blackout-production-app`'s target group over the last 6h showed **p50 stayed ~50-90ms** (healthy) while **p99 spiked to 40-65s** and **Maximum hit 78-111s** during a ~2-hour window (2026-09-01 20:00-22:00 UTC) — a classic long-tail problem, not a systemic one (`AWS/ECS` CPU/Memory utilization for the web service stayed low on average, 10-20%/15-18%, ruling out fleet-wide resource saturation as the primary cause). |
| **Root cause** | Pulled real app logs for that exact window (CloudWatch `/ecs/blackout-production`, filtered on `elapsed=`) and found `[cron/vector-pick-sweep] done ... elapsed=301362ms` — **5 minutes 1 second** for a single sweep pass. `cron-registry.ts` schedules this cron `schedule_cron_utc: "1-59/2 11-21 * * 1-5"` — **every 2 minutes** during RTH. `src/app/api/cron/vector-pick-sweep/route.ts` had **no overlap guard**: the handler always dispatches a fresh `runVectorPickUniverseSweep()` via `after()` regardless of whether a previous sweep is still running. With a 5-minute runtime against a 2-minute schedule, at least 2 (often more) sweep instances were running concurrently, cluster-wide, at any given moment during RTH. |
| **Why this shows up as ALB tail latency, not CPU load** | Each sweep instance is I/O-bound (sequential Polygon/UW fetches per ticker across ~84 universe/hot/zerodte tickers, batched at `SWEEP_CONCURRENCY=4`), so it doesn't peg CPU — it mostly *waits*. But every one of those waits goes through the SAME cluster-wide rate limiters every member-facing request also depends on: `uw-rate-limiter.ts` (`GLOBAL_MAX_RPS=2`, `GLOBAL_MAX_CONCURRENCY=2-3`, Redis-coordinated) and the equivalent `polygon-rate-limiter.ts`. `queue-budget.ts`'s own header (added for a previously-fixed, related 504 tail — PR #1817) documents exactly this shape: healthy requests pay ~0ms admission wait, but under saturation every caller queues up to a 20s bound before either proceeding or failing fast. Two or three overlapping sweeps hammering the same 2rps/2-3-concurrent global ceiling is the kind of saturation that pushes ordinary member requests toward that 20s queue ceiling on top of their own real fetch time — consistent with the 40-65s p99 measured (queue wait + real work, not a single pathological upstream call). |
| **Fix** | Added a cross-replica overlap guard using the same `sharedCacheSetNx` (Redis `SET key val EX ttl NX`) idempotent-skip pattern already used by `swing-discovery`/`banger-discovery`/`thermal-discord`/`darkpool-discord`/`data-correctness`/`helix-discord-digest` for this exact problem shape. The `GET` handler now attempts to claim `vector:pick-sweep:running` (480s TTL, matching the cron's own `stale_after_min: 8` alerting threshold as a safety-net ceiling) before dispatching; a lost race returns `{ skipped: true, reason: "previous sweep still in flight" }` instead of starting a second concurrent sweep. The lock is released in a `finally` block inside `runPickSweep` so a thrown error still frees the next scheduled fire. Fails OPEN on a Redis error (`.catch(() => true)`) — a missed overlap guard is a lesser problem than a cron permanently wedged shut by a stuck lock key. |
| **Blast radius** | `src/app/api/cron/vector-pick-sweep/route.ts` only — the underlying `runVectorPickUniverseSweep()` (`vector-pick-sweep.ts`) is unchanged; this only prevents a second copy of it from starting while one is already running. Every member-facing route that depends on the shared Polygon/UW rate limiters benefits indirectly (less contention during RTH), but no other route's code changed. |
| **Regression guard** | `src/app/api/cron/vector-pick-sweep/route.test.ts` (5 tests, source-text-regex convention — same as `vector-bead-record/route.test.ts` — used because the route imports `server-only` transitively and can't be directly imported by a plain `tsx --test` run): the acquire call happens before dispatch, a lost race returns the skip response before reaching `after(dispatch)`, the guard fails open on a Redis error, the release runs in a `finally` block, and the TTL matches the cron's own staleness threshold. Verified via git-stash: 5/5 fail pre-fix, 5/5 pass post-fix. |
| **Not fully closed** | This removes ONE concrete, measured contributor to the p99 tail (overlapping sweeps). It does not claim to be the only contributor — `queue-budget.ts`'s own header notes route-level attribution for the broader 504/tail volume is still pending ALB access-log analysis. A natural follow-up (not done here, to keep this PR single-issue) is auditing OTHER RTH-frequency crons (`vector-full-state-snapshot` ~5min schedule, `bie-full-state-snapshot` ~5min, `zerodte-warm`, `desk-warm`, `uw-cache-refresh` — all of which also logged multi-second-to-tens-of-seconds `elapsed=` times in the same window) for the identical missing-overlap-guard shape. |

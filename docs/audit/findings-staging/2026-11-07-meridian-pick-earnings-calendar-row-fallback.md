## 2026-11-07 — `pickEarningsCalendarRow` served an unrelated future print's numbers when no row matched the requested event date — FIXED

| **Status** | Fixed |
|------------|-------|
| **Symptom** | `pickEarningsCalendarRow(rows, eventDate)` in `src/lib/meridian/meridian-benzinga-earnings-core.ts` is the sole source of `MeridianEarningsEnrichment.earnings_calendar` (`loadMeridianEarningsEnrichment` → `MeridianEventDetailPanel`/`MeridianEarningsEstimatesPanel`/`MeridianEarningsSummaryPanel`/`MeridianEarningsTabs`) for a specific earnings-event detail page (`loadMeridianEarningsEventDetail(ticker, eventDate)`, keyed off a fixed date carried in the URL/route). When no row in the fetched Benzinga window carried a `date` exactly equal to the requested `eventDate`, the function fell back to `rows[0]` instead of reporting absence. |
| **Root cause** | `const match = rows.find((r) => r.date === eventDate) ?? rows[0] ?? null;` — the `?? rows[0]` fallback hands back whatever row happened to be first in the array on any non-match, with no relation to the date actually being asked about. The one real caller, `loadBenzingaTickerEarnings` (`meridian-benzinga-earnings.ts`), fetches with `sort: "date.desc"` and an open-ended upper bound (`dateGte` only, no `dateLte`), so in production `rows[0]` is the **most future** row in the fetched window — typically the next quarter's *projected* print, a completely different fiscal period from the one requested. A non-match is reachable in practice: Benzinga routinely revises a report date by a day (confirmed vs. projected), and this exact file already documents and fixes the identical "date moved after the member's view was built" failure mode twice elsewhere — `parseNextEarningsFromBenzinga`'s header ("Benzinga leaves a same-day row's `date` unchanged after it reports...") and the sibling `pickUpcomingEarningsRow` in `meridian-ticker-lookup-core.ts` (#7100), which already returns `null` on no match rather than guessing. This function was the one place in the same file family that still substituted an unrelated row instead of reporting absence. |
| **Evidence** | `npx tsx --experimental-test-module-mocks --test src/lib/meridian/meridian-benzinga-earnings-core.test.ts` — new test gives it a 2026-08-26 request against rows dated 2026-08-25 (the real, shifted date for that quarter) and 2026-11-25 (a later, unrelated projected print). Before the fix: returns the 2026-11-25 row's `estimated_eps`/`fiscal_period` as if they were the requested event's numbers (confirmed RED via `git stash` on just `meridian-benzinga-earnings-core.ts`: 35 pass / 1 fail). After the fix: returns `null` (36/36 pass). `npx tsc --noEmit` clean; full `npm test` run clean (see PR). |
| **Blast radius** | Every consumer of `MeridianEarningsEnrichment.earnings_calendar` for a specific event-detail view is affected on a date mismatch: `earnings_yoy` (`computeEarningsYoY(earnings_calendar)`), `post_print` (`postPrintSurpriseLean(earnings_calendar)`), and the three UI panels that read `enrichment.earnings_calendar` directly (`MeridianEventDetailPanel`, `MeridianEarningsEstimatesPanel`, `MeridianEarningsSummaryPanel`, `MeridianEarningsTabs`) would all have silently rendered a different quarter's estimates/actuals/surprise labelled as the event the member opened. The fix touches only the one pure function; every caller already treats a `null` `earnings_calendar` as a normal, handled case (it is a nullable field on `MeridianEarningsEnrichment`), so no caller needed a signature or null-handling change. |
| **Fix rationale** | Drop the `?? rows[0]` fallback — `eventDate` truthy with no exact match is a real "we don't have this event's row" answer, the same honest-absence discipline `parseNextEarningsFromBenzinga` and `pickUpcomingEarningsRow` already apply one function away in the same file family. No alternative (e.g. "nearest date" fuzzy-matching) was implemented: inventing a *plausible-looking* nearby row would reintroduce the same class of silent mislabeling this fix removes, just with a smaller blast radius instead of none. |
| **Verify** | `npx tsx --experimental-test-module-mocks --test src/lib/meridian/meridian-benzinga-earnings-core.test.ts`; `npx tsc --noEmit` clean; full `npm test` run clean (see PR). |

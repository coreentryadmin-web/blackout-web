## X-content: two dormant-but-real bugs — a no-op "diversity" enforcement in the capture harness, and a stale stub reimplementing (and un-fixing) the session-claim horizon check — FIXED

> **kind:** `FINDING`

Thirteenth product-surface pass in the "check product by product" audit sweep — X-content, the one product surface not yet directly audited today. Both findings are currently dormant (neither module has a live caller yet, per repo-wide grep), matching this repo's own established precedent (the capture-catalog ticker-filter finding) that "wired to nothing yet, but wrong, and would ship wrong the moment it's wired" is reportable.

| Field | Detail |
|---|---|
| **Finding 1 — symptom** | `attachmentsFromCaptures`'s `requireDiversity` flag (`capture-harness.ts`) never changed the output. The module's own docstring says it enforces "don't stack same source," but `fresh.slice(0, Math.min(fresh.length, maxAttachments))` and `fresh.slice(0, maxAttachments)` are byte-identical for every input — `Array.prototype.slice` already clamps its end index to the array length by spec — so the condition gated between two provably identical branches. |
| **Finding 1 — root cause** | Neither branch ever looked at `source_surface` when selecting which captures to keep; both just took the first N in array order. A package built from `[helix, helix, thermal, vector]` with `maxAttachments=3` shipped `[helix, helix, thermal]` — vector silently dropped, helix duplicated. `validateAttachmentConstraints` downstream only rejects the fully-degenerate case (`unique.size === 1`, every attachment from the same surface); two-of-three-same-surface passes it cleanly, so nothing else in the pipeline would have caught this. |
| **Finding 1 — fix** | Added `selectDiverseCaptures(captures, max)` — takes at most one capture per distinct source first, only reaching into the leftover (duplicate-source) pool if there aren't enough distinct sources to fill the requested count. |
| **Finding 2 — symptom** | `validateSessionClaim` (`validators.ts`) unconditionally returned `null` for every `session_claim: true` row, regardless of what horizon its evidence carried. Its own comment claimed "we log and let human review catch it" — it never logged anything. |
| **Finding 2 — root cause** | The exact rule this stub describes wanting to implement ("look at `underlying_evidence` and check none of it is read at `all` horizon") was already correctly built — including today's earlier fix extending it to `monthly` — in `queue-types.ts`'s `readyBlockReason`. `validators.ts`'s copy was never updated to match: a bug already fixed in one file, reimplemented (and left un-fixed) in a sibling — the exact class (f) this session has now found repeatedly across every product surface. |
| **Finding 2 — why this matters** | `queue-store.ts` currently only calls `readyBlockReason`, so this stub causes no live harm today — but it is exported under the canonical-sounding name `validateSessionClaim`/`validateQueueRow`, and any future caller reaching for "the" row validator would silently readmit the exact opposite-story/far-dated-aggregate defect this lane already paid to fix once. |
| **Finding 2 — fix** | Extracted the far-dated-horizon check out of `readyBlockReason` into a new exported `sessionClaimFarDatedViolation(row)` (`queue-types.ts`) — behavior-preserving refactor, confirmed by the full existing `readyBlockReason` test suite passing unmodified — and had `validateSessionClaim` import and call it instead of its own dead stub. |
| **Blast radius** | `capture-harness.ts` (single function), `validators.ts` + `queue-types.ts` (extraction, no behavior change to the already-live `readyBlockReason` path). Neither finding has a live production caller today. |
| **Why not caught earlier** | Finding 1: `capture-harness.test.ts`'s "returns max 3 attachments" case only used 4 already-distinct surfaces, which happens to hide the no-op (both branches return the same thing when there's nothing to diversify against). Finding 2: `validators.test.ts` had zero tests for `validateSessionClaim`. |
| **Regression guard** | Finding 1: two new tests — mixed-source captures prefer distinct surfaces over duplicating one; falls back to duplicates only once distinct sources are exhausted. Finding 2: four new tests on `validateSessionClaim` (no claim → pass; all-expiry-only claim → fail; monthly-only claim → fail; 0dte claim → pass). Confirmed **failing** against pre-fix code (`git stash` toggle: 3 failures) and passing post-fix (99/99). |

## 2026-09-20 — [FINDING, P2 correctness] Vector universe snapshot let a "complete" fan-out replace stored spot data with null — FIXED

> **kind:** `FINDING`

| Field | Value |
|-------|-------|
| **Status** | FIXED |
| **What prompted this** | An earlier audit cycle's lead: `GET /api/market/vector/universe` showed 18 of 55 tickers (including COIN, MSTR, PLTR, JPM, GS) with `spot:null`, while a same-moment direct call to `GET /api/market/gex-heatmap?ticker=COIN` returned a real, live spot. Investigated per the standing performance/latency audit mandate to confirm whether this was a live upstream gap, a cron-cadence artifact, or a real bug, per the task's "repro before concluding anything" instruction. |
| **Live repro** | Minted a temp Clerk premium+admin session (`scripts/audit/lib/audit-auth-fetch.mjs`), hit `GET /api/market/vector/universe`, then immediately (same session, 0.6–3.3s later) hit `GET /api/market/gex-heatmap?ticker=<X>` for COIN/MSTR/PLTR/JPM/GS. Universe served 18/55 rows `spot:null, asOf:null` (`attempted:55, produced:55` — a "complete" build by row count). All four of COIN/MSTR/PLTR/JPM resolved a real spot on the direct route within ~0.6–1s (`available:true`, e.g. COIN spot 194.6); GS genuinely had no chain (`available:false` on BOTH routes — a real absence, correctly excluded from the bug). This confirmed a genuine same-tick disagreement, not merely staleness: dated rows in the SAME snapshot (AAPL, SPY, …) carried real, recent `asOf` timestamps, so the null rows were not simply "the whole snapshot is old" — they were specific rows a recent build failed to resolve. |
| **Root cause (two layered gaps in the SAME "produced vs. complete" distinction)** | (1) `buildVectorUniverseRow` always returns a row object, even when `fetchGexHeatmap` blocks past its `gexHeatmapMaxBlockMs` budget and falls back to `spot:null` — so `buildVectorUniverseSnapshot`'s `produced` count (rows.length) counts these exactly like a resolved row. `isCompleteBuild(attempted, produced)` in `src/features/vector/lib/vector-universe-merge.ts` only ever checked ROW-COUNT completeness ("did every ticker return SOME row"), never whether the row carried usable data — so a build where every one of 55 tickers "produced" a row, but 18 of them null-spot, still satisfied `isCompleteBuild` and took `refreshVectorUniverseSnapshot`'s outright-REPLACE branch (`persistVectorUniverseSnapshot(snap)`), bypassing `mergeUniverseSnapshot` entirely — the exact carry-forward protection the file's own header documents building for this class of incident (the 2026-08-18 "4-row build must not erase a 64-row roster" fix) never triggered, because that fix only ever guarded against a build losing ROWS, not a build producing null rows. (2) Even on a build that DOES route through `mergeUniverseSnapshot` (e.g. one with a genuine fan-out row-count loss), the merge's fresh-rows loop had its own gap: an undated fresh row (`spot:null, asOf:null` — a re-attempt that produced no new evidence) unconditionally overwrote whatever the previous-rows loop had already carried forward for that ticker, INCLUDING a still-good, genuinely-DATED row from an earlier successful cycle. So even with gap (1) fixed, a null-spot re-attempt for a previously-healthy ticker would still wipe its last known-good spot on the very next merge. |
| **Fix** | `isCompleteBuild` now takes an optional third argument, `producedWithUsableData`, and requires it to also clear `attempted` before allowing an outright replace; defaults to `produced` so every existing 2-arg call site keeps its old behavior unchanged. `buildVectorUniverseSnapshot` computes and returns a new `producedWithSpot` field (`rows.filter(r => r.spot != null).length`) alongside the existing `attempted`/`produced`, and `refreshVectorUniverseSnapshot` passes it through. Separately, `mergeUniverseSnapshot`'s fresh-rows loop now checks whether the carried entry it is about to touch is itself dated (a real, not-yet-expired `asOf`) before letting an undated fresh row overwrite it — if so, the carried row is left exactly as-is (already counted as `carried`, not double-counted as `refreshed`) rather than replaced with the undated re-attempt. A genuinely stale carried row (already dropped by the previous-rows loop) is unaffected — an undated re-attempt for it still behaves exactly as before, so the universe can still shrink for tickers that are truly gone. |
| **Blast radius** | `isCompleteBuild` and `mergeUniverseSnapshot` have exactly one production caller each (`refreshVectorUniverseSnapshot` / `buildVectorUniverseSnapshot`+`ensureTickerInUniverseSnapshot`, all in `vector-universe.ts` — confirmed via `grep -rl` on both symbols across `src/`), so both fixes are scoped to the Vector universe scanner snapshot only. No other snapshot type shares this merge helper. |
| **Fix rationale** | Considered instead just shortening `gexHeatmapMaxBlockMs` or widening the existing `retryNullSpotRows` in-build retry pass (added 2026-09-12, PR #4881) — rejected as the primary fix: both only reduce HOW OFTEN a ticker ends the build still null, they do not stop a build that still has null rows (which will keep happening under real concurrency/cold-cache conditions) from wiping out previously-good data with zero protection. The completeness-gate and merge-overwrite gaps are the actual reason the existing carry-forward design — built and documented specifically for this failure class — never engaged; fixing them closes the gap structurally rather than just making it rarer. Left `retryNullSpotRows` untouched; it still reduces how often this path is even taken. |
| **Regression guard** | `src/features/vector/lib/vector-universe-merge.test.ts`: new test `isCompleteBuild also requires the produced rows to carry USABLE data, not just exist` (21/21 rows produced but only 15/21 with usable spot → `false`; all three bars clear → `true`; 2-arg call unchanged); new test `an undated fresh row must NOT overwrite a still-good dated carried row for the same ticker` (COIN spot 194.6 dated, re-attempt spot:null/asOf:null → merged row keeps spot 194.6, `carried:1, refreshed:0`); new test `an undated fresh row STILL overwrites once the previously-carried row has genuinely gone stale` (proves the fix is not a new ratchet — a truly-expired ticker still re-enters undated and can still shrink out). RED→GREEN proven via `git stash push -- src/features/vector/lib/vector-universe-merge.ts src/features/vector/lib/vector-universe.ts` (tests left in place): 15/17 pass pre-fix (the two new tests fail — `194.6 !== null` and the `isCompleteBuild` 3-arg case), 17/17 pass post-fix (`git stash pop`). Full `src/features/vector/lib/vector-universe-merge.test.ts` + `vector-universe.test.ts`: 34/34 pass. `npx tsc --noEmit`: clean (Node 20.20.2, `/opt/node20`). |
| **Live evidence captured** | `GET /api/market/vector/universe` (2026-09-20, ~11:06 UTC, weekend/off-hours): `attempted:55, produced:55`, 18 null-spot rows — `ABBV,ANET,COIN,CVX,GILD,GLD,GS,IBIT,JPM,LLY,MRK,MS,MSTR,NDX,ORCL,PLTR,VRT,XOM`. `GET /api/market/gex-heatmap?ticker=COIN` (0.6s later): `available:true, spot:194.6, asof:"2026-09-20T11:05:57.223Z"`. Same for MSTR (153.19), PLTR (177.45), JPM (349.46) — all resolved within ~1s of an uncontended, solo call. GS: `available:false` on both routes — genuine absence, not this bug. |
| **RTH validation** | After deploy: poll `GET /api/market/vector/universe` during RTH a few times ~5 min apart. A ticker that was static-allowlist with a real spot in one build should not flip to `spot:null` in the next build unless it has genuinely been unrefreshed for the full `UNIVERSE_ROW_MAX_AGE_MS` (15 min) — a single bad build cycle for a previously-healthy ticker must no longer null it out immediately. Cross-check any ticker that DOES show `spot:null` during RTH against a direct `GET /api/market/gex-heatmap?ticker=<T>` call — if the direct route resolves a real spot within a few seconds while the universe row stays null for more than ~15-20 minutes straight, this fix did not fully take effect and needs a follow-up. |

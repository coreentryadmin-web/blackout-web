## 2026-09-18 — [FINDING, P0 0DTE] `zerodte-warm`'s cooldown + overlap lock had no judgment about whether the background work they protect ever completes, letting a wedge persist for up to 15 minutes — FIXED (circuit breaker only, not the underlying deploy-churn cause)

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **What this resolves** | Live P0 issue #5213 ("RTH stale cron: zerodte-warm"), root-caused during a DISCOVERY cycle (full mechanism in the earlier finding `2026-09-18-zerodte-warm-background-silent-kill-under-deploy-churn.md`, merged via #5215, and posted to the issue). `zerodte_scan_heartbeat` was stuck 50+ minutes during live RTH while `cron_job_runs` kept logging `ok`/`skipped` every cycle — the board itself stayed fresh (member-poll traffic hits `scanZeroDteBoard()` through a separate, unguarded path), masking that the cron's OWN dedicated ledger-persistence work had gone dark. |
| **Root cause** | `RERUN_COOLDOWN_KEY` (60s) and `OVERLAP_LOCK_KEY` (900s TTL) both exist to stop legitimate overlapping runs, but neither has any way to know whether the background work they protect (`dispatchWarm()` → `warmZeroDteBoard()` + `refreshZeroDteBoardSnapshot()`, ~4-5 min measured) ever actually finishes. When that background chain is silently killed mid-flight (its hosting ECS task recycled for a deploy — container `stopTimeout` is unset, defaulting to 30s, nowhere near the ~4-5 min the work needs), `OVERLAP_LOCK_KEY`'s `.finally()` release never runs, and the lock pair then blocks every subsequent attempt for up to its own 900s TTL regardless of how stale the scan heartbeat gets. |
| **Fix** | `src/app/api/cron/zerodte-warm/route.ts`: gated to cash RTH only (`isEtCashRth()` — off-hours staleness is expected and already suppressed elsewhere in `admin-cron-health.ts`), if `loadZeroDteScanHeartbeat()` reports `critical_stale`, atomically claim a short-TTL steal-attempt key (`STEAL_ATTEMPT_KEY`, 30s NX) so exactly one concurrent invocation performs the clear even if many replicas observe `critical_stale` at once, then clear both `RERUN_COOLDOWN_KEY` and `OVERLAP_LOCK_KEY` before falling through to the existing, unchanged claim logic below. |
| **Fix rationale** | This is a circuit breaker for the SYMPTOM (a wedge persisting for the rest of the lock's TTL), not a fix for the underlying cause (short `stopTimeout` colliding with sustained high-frequency deploy churn recycling the task mid-background-chain). That root cause is a real infra/architecture call — extend `stopTimeout`, make the background work resilient to mid-chain kills via checkpointing, or reduce deploy frequency during high-merge-velocity sessions — left undecided here, same as the original finding's own "what was NOT done" section. The steal-attempt's own short TTL (30s) and RTH gate keep the breaker narrowly scoped: it can only ever fire when the heartbeat is genuinely >10min stale during live trading hours, never as a routine path. |
| **Blast radius** | `src/app/api/cron/zerodte-warm/route.ts` only. Two pre-existing tests in the same file were updated (not weakened) to reflect the now-intentional narrow exception: the cooldown key may be released early, but only from inside the new guarded steal block, never from the routine cooldown-check path. |
| **Regression guard** | New test asserts the RTH gate, the heartbeat check, the atomic steal-attempt claim, that only the winner clears both keys, and that the steal-and-clear runs before the normal cooldown claim. RED→GREEN via `git stash`: 8/11 pass pre-fix (3 fail — the new test plus the two updated pre-existing ones), 11/11 post-fix. `tsc --noEmit` clean. `play-engine-heartbeat.test.ts`/`et-market-hours.test.ts` clean (12/12). Full `npm test` on Node 20: 14838 pass / 0 fail / 3 skipped, exit 0. |
| **Status** | FIXED (circuit breaker). Underlying deploy-churn/`stopTimeout` root cause remains open — flagged for the 0DTE lane's own architecture call, not addressed here. |

## 2026-09-01 — [FINDING, P2 db/infra] The DB retry/pool-safety fixes (#3242, #3259) only cover a small minority of `db.ts` — ~137 call sites still bypass `dbQuery` entirely — OPEN, write-up only

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **What prompted this** | Following up on this session's own earlier finding (the DB pool-teardown-race, PR #3241/#3242) and another lane's deeper structural fix on top of it (PR #3259, `resetPoolForRetry` pool-identity guard) — both landed and were re-verified live this session. A fresh CloudWatch sweep today (2026-09-01 ~15:45 UTC, well after both fixes were live) still showed `[play-engine-heartbeat] init hydration failed: Error: Cannot use a pool after calling end on the pool` as a raw, terminal, unretried failure — the exact error signature both fixes were supposed to make retryable/non-cascading. Traced why it still surfaces unretried. |
| **Root cause — most of `db.ts` never goes through the function that got fixed** | `dbQuery()` (`src/lib/db.ts:2414`) is the ONLY function in this file with retry logic, transient-error classification (`isTransientPgError`, extended by #3242), and pool-identity protection (added by #3259). Both fixes are real and correct — but they only help callers that actually call `dbQuery()`. Grepped the whole file for direct pool access bypassing it: **134 call sites** call `(await getPool()).query(...)` directly, **2 more** via an optional-injected-client pattern (`(db ?? await getPool()).query(...)`), and **3** call `(await getPool()).connect()` for a dedicated transaction client — **~139 total call sites, none of which get any retry, any transient-error classification, or any protection from the pool-identity race**, across roughly the entire surface of this file. `getMeta`/`setMeta` (`db.ts:2606-2620`, used by `play-engine-heartbeat.ts`'s `ensureInitialized`/`recordPlayEngineTick`) is one concrete, live-confirmed example: a single unretried `.query()` call, so the exact race #3259 patched for `dbQuery` callers still throws straight through to the caller here. |
| **Scope of what's affected** | This is not a handful of obscure helpers — a sample of the surrounding function names at these call sites (grep + `awk` over the file) includes `deleteUserDataForClerkId`, `pingDatabaseConnectivity`, `getMeta`/`setMeta`, `fetchRecentFlows`, `fetchTrailingSessionSkew`, `fetchRecentHelixSignalOutcomes`, `fetchPendingHelixSignalCheckpoints`, `updateHelixSignalCheckpoint`, `insertFlowAlert`, `insertSpxSignalLog`, `insertShadowFactorObservation`, `insertSpxEngineSnapshot`, `fetchRecentSpxEngineSnapshots`, `insertPlaybookShadowObservation`, `loadPlaybookInstanceStates`, `loadPlaybookTriggerCountsByPb`, `patchPlaybookInstanceBlocked/Opened`, `loadTriggeredPlaybookInstances`, `finalizePlaybookCounterfactualIfActive`, `patchPlaybookInstanceCounterfactualEval`, `fetchPlaybookEvidenceRows` — and that's only the first ~25 of ~137 matches. HELIX signal tracking, SPX engine snapshots, playbook shadow-mode instrumentation, flow-alert ingestion, and the play-engine heartbeat itself are all exposed to the exact class of transient-blip and pool-teardown-race failures the two recent fixes were written to eliminate — just not for these call sites. |
| **Why this is real, not theoretical** | The `play-engine-heartbeat` failure above is live, today, post-both-fixes. This session has independently observed the underlying transient-blip pattern (RDS/PgBouncer connection drops, `timeout exceeded when trying to connect`, `Cannot use a pool after calling end on the pool`) recurring periodically in production CloudWatch logs across multiple days this session — it is not rare. Every one of the ~137 unprotected call sites will surface that exact class of failure directly to its caller, unretried, every time a transient blip lands on it. |
| **Why not fixed directly this cycle** | ~137 call sites across the single largest, most business-critical file in the codebase is far outside "small self-contained bug" — it is a mechanical but very large refactor (swap `(await getPool()).query(...)` for `dbQuery(...)` at each site, checking each call's return-value shape and error-handling assumptions still hold, and separately deciding how to handle the 3 `.connect()`-based transaction call sites, which need retry semantics scoped to connection acquisition only, not mid-transaction — a naive blanket swap there would be wrong). A change of this size and blast radius, touching the DB layer every product line depends on, belongs to whoever owns `db.ts`, done deliberately with real test coverage per call site, not shipped unilaterally by an hourly sweep. |
| **Suggested fix direction** | Two complementary options for the owning lane: (1) **Mechanical migration** — replace each bare `(await getPool()).query(...)` with `dbQuery(...)`, which is a drop-in return-shape match (`dbQuery` already returns the same `QueryResult`-shaped object) for the ~136 non-transaction call sites; do it in reviewable batches rather than one giant diff. (2) **For the 3 `.connect()` sites** — wrap just the `.connect()` acquisition in the same retry/identity-guard logic (a `getPoolClient()`-style helper mirroring `dbQuery`'s pattern), leaving the transaction body itself unretried (retrying mid-transaction is a correctness hazard, not a reliability win). A regression test in the spirit of `src/findings-hygiene.test.ts`'s workflow ratchets — grepping `db.ts` for `getPool()).query` outside of `dbQuery`'s own definition — would keep this from silently regressing as new functions get added the old way. |
| **Status** | OPEN — flagged for whoever owns `src/lib/db.ts`; no code change made this cycle |

## 2026-09-04 — [FINDING, P2 correctness, Meridian/Largo pre-earnings pack] `expected_move_pct` keeps serving CURRENT chain IV — mislabeled as the market's pre-print expectation — for an event that has already printed, hours after the real move already happened — FIXED

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **What prompted this** | Standing live correctness sweep of the four desks not yet checked this session (Thermal, Helix, Meridian, Largo — SPX Slayer/Night Hawk/Legacy/Vector already covered by the recurring 4-engine monitor). Authenticated via `mintClerkPremiumSession` (one temp Clerk admin+premium user, deleted after) and pulled live production data across all four; this was the one genuine correctness defect found. |
| **Live evidence** | `GET /api/market/meridian/event?id=earnings:LULU:2026-09-03` on production, 2026-09-04 ~02:23 UTC. LULU reported real Q2 results and a steep FY guidance cut (real catalysts on the SAME payload: "Lululemon Stock Tumbles on Weak Outlook", guidance cut from $10.95–11.15 to $9.48–9.73 EPS) at 20:06–20:25 UTC that day — hours before this request. The event's own `pack.history[0]` already carries the REAL graded result for that exact date (`report_date: "2026-09-03", surprise_pct: 16.3, beat: true`). Yet `pack.expected_move_pct` still read **50.3** under `kind: "pre_earnings"`, `days_until: 0`, rendered by `LargoPreEarningsPackCard.tsx` as **"Options-implied move ~50.3%"** — worded, and framed, as the market's expectation going INTO a print that had already happened and already moved the stock double digits. |
| **Root cause** | `preEarningsPackForLargo` (`src/lib/largo/pre-earnings-pack.ts`) calls `loadEarningsExpectedMovePct(t, resolvedDate)`, which is unconditional on print timing: it reads the LIVE Polygon option chain's CURRENT ATM IV for whichever expiry brackets `resolvedDate` (`loadEarningsExpectedMove`'s own doc comment: "ATM IV from the live Polygon chain"). For a genuinely upcoming print this is exactly the right number. Once the print has already happened, the SAME code path instead measures POST-print IV — the market's forward-looking vol for whatever expiry is nearest right now, elevated here specifically because of a real ongoing crash — while the pack keeps calling itself `pre_earnings` and keeps serving that number under the same "Options-implied move" framing, with **no field anywhere on the pack recording whether the print has already happened.** |
| **Same defect class, different call site** | `docs/audit/FINDINGS.md` (2026-08-21) already fixed the sibling case — the `expected_vs_realized` comparison banner was passing this exact same `pack.expected_move_pct` through as if commensurable with a REALIZED reaction from a past quarter, fixed by adding a `same_event` flag and withholding the implied move on cross-event pairs ("a number a consumer must not pair does not belong in the block"). That fix patched the COMPARISON banner only (`MeridianEarningsTabs.tsx`'s own comment there literally says "never from `pack.expected_move_pct`, which is the implied for the UPCOMING print" — an assumption that was never revisited for the pack's OWN direct consumers). It never reached `pack.expected_move_pct` itself, which two OTHER consumers still read directly and unconditionally: `LargoPreEarningsPackCard.tsx`'s own "Options-implied move" line, and `meridian-earnings-intel.ts`'s `input.pack.expected_move_pct` fallback (which also derives an up/down expected-move PRICE BAND from it: `spot × (1 ± em/100)`). |
| **Fix** | Added `earningsAlreadyPrinted(resolvedDate, printHistory)` to `src/lib/largo/pre-earnings-history-rows.ts` (the already-extracted, dependency-free module `pre-earnings-pack.ts`'s own header explains was pulled out specifically so logic like this could be unit-tested — `pre-earnings-pack.ts` is `server-only` and reaches its data through dynamic `@/` imports that make it impractical to exercise directly in a test). Detection is exact, not heuristic: `print_history` only ever contains rows Benzinga confirms with a real `actual_eps`/`actual_revenue` (`benzingaRowsToPrintHistory`'s existing filter), so a history row dated exactly `resolvedDate` is proof the print already has real numbers on file. `preEarningsPackForLargo` now computes `alreadyPrinted` from the already-fetched `history` and serves `expected_move_pct: alreadyPrinted ? null : expected_move_pct` — WITHHOLD, not relabel, matching the precedent above. |
| **Why withhold rather than relabel** | Every existing consumer already renders a null `expected_move_pct` correctly and gracefully: `LargoPreEarningsPackCard.tsx` falls back to "Expected move unavailable", `MeridianEarningsIntelPanel`'s `em != null` guard hides the badge entirely, and `meridian-earnings-intel.ts`'s fallback chain and price-band derivation both already treat null as "nothing to show." So withholding needed zero consumer-side changes to produce an honest result — the same reasoning the 2026-08-21 fix used for the sibling defect. |
| **Blast radius** | `src/lib/largo/pre-earnings-pack.ts` (`preEarningsPackForLargo`) and `src/lib/largo/pre-earnings-history-rows.ts` (new exported helper). Downstream, corrects: `LargoPreEarningsPackCard.tsx`'s "Options-implied move" line; `meridian-earnings-intel.ts`'s `expected_move_pct` fallback AND its derived expected-move price band (`positioning.spot_up`/`spot_down` or equivalent, computed off the same number); `MeridianEarningsIntelPanel`'s `tickerExpectedMovePct` prop. Left deliberately unchanged: the `expected_vs_realized` banner (already correct via the 2026-08-21 `same_event` fix), the pack's `flow`/`positioning` descriptive wording (e.g. "Balanced flow ahead of earnings" for an already-printed event) — a related but separate cosmetic-wording issue, out of scope for a single-issue PR — and every genuinely-upcoming print, which is unaffected (no history row shares its future date, so `alreadyPrinted` is `false` and the live chain-IV number still serves exactly as before). |
| **Regression guard** | New `earningsAlreadyPrinted` describe block in `src/lib/largo/pre-earnings-history-rows.test.ts` (+5 tests): the exact LULU shape (resolved date matches the freshest graded history row → printed); a genuinely upcoming date with no matching history row → not printed; a null resolved date never reads as printed; empty history never reads as printed; an OLDER date matching an EARLIER (not just the freshest) history row also reads as printed. Confirmed RED pre-fix via `git stash` (isolated to `pre-earnings-history-rows.ts` + `pre-earnings-pack.ts`, keeping the test): all 5 new tests failed with `earningsAlreadyPrinted is not a function`; GREEN post-fix (`git stash pop`): 18/18 pass in the file. |

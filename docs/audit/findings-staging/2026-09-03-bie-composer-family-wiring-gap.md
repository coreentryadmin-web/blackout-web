## 2026-09-03 — [FINDING, P2 BIE/Largo, cross-product] 10 of 12 `compose*Read` narrative-answer functions across BIE are fully built, several tested, but never wired into Largo's live tool/dispatch surface — OPEN, write-up only

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **What prompted this** | A background dead-code sweep of Thermal flagged `composeThermalRead` (`src/lib/bie/thermal-read.ts`) as untested and uncalled, with the `thermal_read` BIE intent that `router.ts` classifies never dispatching to it. Investigating why turned up a much larger pattern than one Thermal-specific gap. |
| **The mechanism, verified by direct read (not the sweep's assumption)** | `classifyBieIntent` (`router.ts`) is called only from `src/lib/largo/tool-defs.ts`, `calibration.ts`, and `db.ts` — never from anything that dispatches to a `compose*Read` function by intent. The live answer path for BIE/Largo questions is the agentic tool-calling loop: an intent's raw data tools (`TOOLS_BY_INTENT` in `live-data-enrich.ts`, e.g. `thermal_read: ["get_gex_heatmap", "get_positioning", "get_gex_matrix_changes"]`) get fed to Largo, which composes the natural-language answer itself. Hand-written `compose*Read` functions are a **different, earlier mechanism** — a full pre-written narrative composer — and are only reachable when explicitly wired as the implementation of one specific Largo tool. Confirmed exactly two are wired that way: `composeWallDynamicsRead` (dynamic-imported once, `run-tool.ts:1731-1732`) and `composeCortexRead` (imported and called once, `src/lib/largo/product-reads.ts:56,607`). |
| **The other 10, checked individually via `grep -rn "\bcompose<Name>Read\b" src` (excluding each function's own definition file and its own `.test.ts`)** | Every one of these returns literally zero matches outside its own definition — `composeHelixRead` (`helix-read.ts`, **has** a test), `composePlayEngineRead` (`play-engine-read.ts`, no test), `composeRecordRead` (`record-read.ts`, **has** a test), `composePlatformRead` (`platform-read.ts`, no test), `composeClarifyRead` (`clarify-read.ts`, no test), `composeGridRejectionsRead` (`grid-rejections-read.ts`, no test), `composeTechnicalsRead` (`technicals-read.ts`, no test), `composeNighthawkEditionRead` (`nighthawk-edition-read.ts`, **has** a test), `composePlaySuggestRead` (`play-suggest-read.ts`, no test), `composeThermalRead` (`thermal-read.ts`, no test). Each is a real, non-trivial function (fetches live data via Largo tools/providers and formats a structured multi-paragraph answer) — not a stub. `router.ts`'s `bieFollowups()` switch DOES have a case for every one of these intents (suggested follow-up questions), which is almost certainly what made the sweep initially read `thermal_read` as "wired" — that switch only supplies follow-up-question chips, not the actual answer composer. |
| **Why this reads as "designed ahead, not abandoned," same as the X-intel precedent** | Two siblings (`wall-dynamics-read.ts`, `cortex-read.ts`) with the identical shape and calling convention (`BieComposed` return type, same `composers-shared.ts` imports) ARE fully wired and live. That strongly suggests all 12 were meant to become individually-selectable Largo tools or answer paths, and the rollout stalled after the first two — not that the other 10 were abandoned mid-design. Three of the ten (`helix-read`, `record-read`, `nighthawk-edition-read`) have real test coverage, which further argues "finished, waiting to be wired" over "half-built and dropped." |
| **Why write up, not wire up directly** | Wiring even one of these into the live surface means deciding: does it become a new Largo tool (Largo already carries 135 tools per `tool-count-claims.test.ts` referenced in the in-flight SPX backlog PR #3381 — a tool-count budget concern the owning lane is actively tracking), or does it replace/supplement the existing tool-calling answer for that intent? Getting that wrong risks a behavior change to a live, member-facing chat surface (BIE/Largo) with no way to validate the "right" answer shape from this sandbox alone. That is squarely a product-architecture call for the Largo/BIE lane, not something to unilaterally wire in from a dead-code sweep. |
| **Blast radius / what's NOT claimed** | This is not a correctness bug — nothing currently broken is caused by these being unwired; `thermal_read` and the other 9 intents still get answered fine via the live tool-calling path. It is a "known-good, fully-written capability sitting idle" finding, same category as the X-intel `scoreAttachmentPackage`/`viewsForSurface` entry from 2026-09-02. |
| **Suggested next step** | For the BIE/Largo lane owner: (1) decide whether any of the 10 unwired composers still represent a deliberately better answer path than the current tool-calling composition for their intent (if so, wire the highest-value ones the same way `composeCortexRead`/`composeWallDynamicsRead` are wired); (2) for any confirmed genuinely superseded by the tool-calling loop and never going to be used, delete them — that decision needs the lane's own memory of why `wall-dynamics`/`cortex` were the two chosen to ship, which isn't recoverable from this repo alone. |
| **Status** | OPEN — flagged for the BIE/Largo lane owner; no code change made here. |

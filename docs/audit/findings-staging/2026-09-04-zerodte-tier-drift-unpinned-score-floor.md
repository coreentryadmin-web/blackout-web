## 2026-09-04 — [BUG, P2 member-facing] Night Hawk merit tier drifted retroactively because the G-3 score floor was never pinned into entry_context, falsifying the code's own "can never disagree" invariant

> **kind:** FINDING

| Field | Value |
|-------|-------|
| **Status** | FIXED |
| **Found by** | Parallel live-production audit workflow, 2026-09-04 (Night Hawk 0DTE merit-tier honesty area), independently confirmed by 2 adversarial verifiers who each pulled live production data and reproduced the claim byte-for-byte. |
| **Evidence** | Live `GET /api/market/zerodte/record?days=90` (90-day, 361-372 graded plays depending on run): 10 BREAKOUT-origin plays committed 2026-08-25 (APLD, ASST, CLSK, COIN, LUNR, MRNA, MSTR, OKLO, RIOT, RKLB, scores 50-61) show `entry_context.tier.tier` (frozen at commit) = "A" while the API's own live-recomputed `play.tier` (`record.ts:611`, `tierFromEntryContext` called fresh) = "B" for the SAME row, SAME evidence. ASST: frozen blob reads `{"label":"Mid score band","detail":"Score 59 in 65-74..."}` (score 59, discovery_origin=["BREAKOUT"]) — today's `scoreFloorForOrigin(["BREAKOUT"])` = 65, so 59<65 now hits "Score below floor" (-2 pts) instead of "Mid score band" (+1 pt), a 3-point swing that flips `TIER_A_MIN_POINTS=4` total from 4 (A) to 1 (B). `docs/audit/FINDINGS.md`'s own 2026-08-25 entry independently confirms the timeline: WS-20 lowered `ZERODTE_SCORE_FLOOR_BREAKOUT` 65→50, then it was restored 50→65 the same/next cycle — the floor these 10 rows committed under (50) no longer matches the floor `tierFromEntryContext` reads today (65). Cross-surface confirmation: the Play Terminal/command-deck (`zerodte-sources.ts:166`, `adapters.ts:257,428,476` — "the terminal reads the letter grade") renders the frozen `entry_context.tier` blob verbatim, while the track-record page (`record.ts:611`) and admin tier-export (`tier-export.ts:80`) both recompute live via `tierFromEntryContext` — two live UI surfaces showing two different tiers for the same historical play right now. |
| **Root cause** | `tierFromEntryContext` (`src/lib/zerodte/tiers.ts`) re-derives the tier from a pinned `entry_context` blob by calling `scoreFloorForOrigin(origin)`, which reads the CURRENT module-level constants `ZERODTE_SCORE_FLOOR`/`ZERODTE_SCORE_FLOOR_BREAKOUT` (`gates.ts` — the latter `envInt(...)`-overridable and already changed once in production). The blob pins `discovery_origin` and `score`, but NOT the numeric floor that was actually in effect at commit time — so when the floor constant changes, every historical BREAKOUT/PIN-origin row's *retroactively recomputed* tier can silently flip, even though the play's own pinned evidence never changed. This directly falsifies the explicit invariant `entry-context.ts`'s own comment claims ("the pinned tier and a retroactive re-derivation of the same row can never disagree ... one blob→input mapping, one assignZeroDteTier call") — that reasoning only holds AT THE INSTANT of commit, since `tierFromEntryContext` is not actually pure over its blob argument; it also reads external mutable state. A secondary, independently-reachable defect in the same function: the "Mid score band" factor's detail text was hardcoded `"Score X in 65-74"` regardless of the actual floor in effect, so whenever `floor != 65` a score well below 65 (as low as 50 in this incident) got mislabeled as being in the specific, unrelated 65-74 band and credited with that band's 50%-WR statistic — a self-contradicting evidentiary claim served to members, not just a stale number. |
| **Fix** | Pinned the G-3 score floor actually applied at commit into the blob: added `score_floor?: number \| null` to `ZeroDteEntryContext` (`entry-context.ts`), computed via `scoreFloorForOrigin(play.discovery_origin)` — now exported from `tiers.ts` — alongside the existing `discovery_origin` pin, before `tierFromEntryContext` runs at commit. `tierFromEntryContext` now PREFERS the blob's own pinned `score_floor` when present (a valid finite number, including 0) over recomputing via `scoreFloorForOrigin(origin)` — that IS the invariant the existing comment already claims, now actually enforced. Rows committed before this field existed (no `score_floor` in the blob) fall back to the exact prior behavior (recompute from today's constants) — same posture as `discovery_origin`'s own documented "pre-WS-20 rows carry none" fallback, so this doesn't retroactively fix already-drifted legacy rows but stops any FUTURE drift for every row committed from here forward. Also fixed the secondary defect: the "Mid score band" detail text now reads the dynamic band (`${floor}-${SCORE_PRIME_MIN - 1}`) instead of a hardcoded `"65-74"`. |
| **Blast radius** | 2 files changed (`tiers.ts`, `entry-context.ts`) + their test files. `record.ts` and `tier-export.ts` (the live-recompute consumers) need NO code change — they call `tierFromEntryContext(row.entry_context)` on whatever blob is stored, so they automatically start reading the pinned `score_floor` the moment a row carries one, with zero call-site changes. `zerodte-sources.ts`/`adapters.ts` (the frozen-blob consumers) are similarly untouched — they already read `entry_context.tier` verbatim. `runner-profile.ts`'s `projectRunnerProfileForCandidate` (the other production caller of `assignZeroDteTier`) was deliberately left unchanged: it projects a LIVE WATCH/SKIP card's tier for TODAY's candidate using TODAY's floor, which is correct behavior for a not-yet-committed play — there is no "retroactive" re-derivation to protect against there, since nothing has been pinned yet. Does not retroactively repair the 10 already-drifted 2026-08-25 rows (or any other historical row committed before this fix) — those keep disagreeing across surfaces exactly as measured; a backfill of `score_floor` for historical rows (derivable from `committed_at_et` + the known floor-change timeline) is a natural follow-up, deliberately left out of scope here to keep this PR to the forward-looking root-cause fix. |
| **Tests** | 6 new tests: 2 in `entry-context.test.ts` (`buildZeroDteEntryContext` pins `score_floor` matching `scoreFloorForOrigin` for BREAKOUT/FLOW/no-origin; 2 pre-existing `deepEqual` fixtures updated to include the new field), 4 in `tiers.test.ts` (a pinned `score_floor` overrides today's recompute — reproduces the exact live ASST shape: score 59, floor 50 at commit vs floor 65 today, proving the SAME score+origin now yields tier A when read with the pinned floor vs tier B without it; `score_floor: 0` is honored, not treated as absent; the "Mid score band" detail text reads the actual pinned floor, not a hardcoded "65-74").

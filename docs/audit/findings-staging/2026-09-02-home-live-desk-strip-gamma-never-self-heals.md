## 2026-09-02 — [P1, correctness/perf] Homepage gamma strip could freeze on "GEX snapshot initializing" for up to ~3 hours after a transient backend stall — FIXED

> **kind:** `FINDING`

| Field | Value |
|-------|-------|
| **Reported by** | User, repeated live checks of the production homepage over several hours: the gamma chip under the hero read "GEX snapshot initializing" / the same content elsewhere read "Snapshot warming up — check back shortly" — a state the user correctly said had "survived multiple checks across several hours" and should not be treated as a transient rendering hiccup. |
| **Root cause** | The homepage route (`src/app/(marketing)/page.tsx`) is `export const revalidate = 3600` (Next.js ISR — regenerated at most once per hour) and, per `HomeGammaPromo.tsx`'s own existing comment, is ALSO force-cached at the Cloudflare edge for `edge_ttl 7200` for anonymous visitors (bypassed only by a `__session` cookie). So whatever `buildPublicGexSnapshot("SPX")` returned at the moment a given ISR regeneration ran gets frozen into the served HTML for up to ~3 hours (1h ISR + up to 2h edge cache) for any anonymous visitor or crawler. This session's own earlier CloudWatch sweep today independently confirmed multi-minute ALB tail-latency episodes (`AWS/ApplicationELB` `TargetResponseTime` p99 15-65s, Max 90-118s, recurring across the day — the already-OPEN #3319/#3324/#3327/#3335/#3337/#3363 chain) caused by overlapping crons — a plausible, evidenced trigger for an SSR request landing during exactly such a window and getting the "warming/empty" snapshot baked into the cached page. `HomeGammaPromo.tsx` (the academy-section gamma panel) already had a fix for this exact class of staleness — a client-side mount-fetch + 5s poll that self-heals a bad seed as soon as a real browser loads the page. `HomeLiveDeskStrip.tsx` (the thin strip directly under the hero — the component whose exact string "GEX snapshot initializing" the user quoted) had NO client-side code at all: it was a pure server-rendered-props component with no `"use client"`, no hooks, nothing — so even once the backend fully recovered, a visitor loading the STALE cached HTML would see the frozen failure state forever, because nothing on the page ever asked for fresh data again. |
| **Live verification at investigation time** | `GET /api/public/gex-snapshot?ticker={SPX,SPY,QQQ}` (the live, `cache-control: no-store` / `cf-cache-status: DYNAMIC` endpoint both components poll) returned `available:true` with real spot/wall/flip data for all three tickers — confirming the backend itself was healthy at check time, and that the symptom is specifically about a frozen client-side/cached-HTML seed never refreshing, not an ongoing upstream outage. `/api/admin/errors?hours=24` showed zero `public-gex-snapshot:warming` alarm events (the code's own >5-minutes-stuck alarm, `PUBLIC_GEX_WARMING_ALARM_SEC=300`) in the last 24h, which is inconsistent with a genuine sustained multi-hour total fetch failure and consistent instead with "the backend recovered but the cached page never re-asked." |
| **Fix** | Converted `HomeLiveDeskStrip` to a client component carrying the exact same self-heal pattern already proven in `HomeGammaPromo`/`GammaSnapshotWidget`: fetch `/api/public/gex-snapshot?ticker=SPX` immediately on mount (correcting a stale seed on the very first paint, not after waiting out an interval), then poll every 5s while the tab is visible, pausing when backgrounded. No change to `public-gex-snapshot.ts`'s existing last-known-good fallback machinery (`resolveMiss`/`loadLastGood`/`persistLastGood`) — that backend-side fallback was already correctly implemented; the gap was purely that one homepage component never asked it for a fresh read after the initial ISR-cached seed. |
| **Verification** | New regression test in `HomeLiveDeskStrip.test.ts` (source-text assertions, matching this file's existing convention — no React Testing Library in this repo): asserts the component is `"use client"`, fetches the live no-store endpoint, runs the refresh in a `useEffect`, and polls on the same 5s cadence as the underlying snapshot cache. **Proved fail-before/pass-after via `git stash`**: pre-fix, the new subtest failed (1/2); post-fix, both pass. `npx tsc --noEmit` clean. Full `npm test` + `npm run build` run (build in progress at write time — see PR CI for the authoritative build result, since converting a props-only component to `"use client"` is exactly the kind of change a build can catch that a unit test can't). |
| **Scope note** | This fix is specific to `HomeLiveDeskStrip` (the hero strip). `HomeGammaPromo` (academy section) already had this pattern. The dedicated `/tools/gamma-snapshot` page's own widget (`GammaSnapshotWidget.tsx`) already had it too — that page is `export const dynamic = "force-dynamic"` (no ISR) so its SSR seed is fresh on every request regardless, and its client widget also polls; if the user's "Snapshot warming up" observation on that specific page was a genuine one-off backend miss rather than the homepage's frozen-ISR-seed problem, it would have self-corrected within 5s on any tab left open — the persistent multi-hour symptom is best explained by the homepage's ISR+edge-cache freeze this fix addresses. |
| **Status** | FIXED — PR pending (branch `fix/home-live-desk-strip-gamma-never-self-heals`). |

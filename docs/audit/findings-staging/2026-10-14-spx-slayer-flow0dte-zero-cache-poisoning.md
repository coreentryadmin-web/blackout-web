## 2026-10-14 — [SPX Slayer] `flow_0dte_net` periodically caches a degraded zero aggregate for the full 2-min TTL, corrupting the live score factor and gate blocks — FIXED

> **kind:** `FINDING`

### Root cause

`fetchUwFlow0dte` (`src/lib/providers/unusual-whales.ts`) and the `uw-cache-refresh` cron both
write the SAME shared Redis key (`UW_KEYS.flowPerStrike`) with `aggregateFlowPerStrikeRows(rows)`
— a sum of `call_premium`/`put_premium` across whatever rows the UW
`/flow-per-strike-intraday` endpoint returned that poll. Neither write path distinguished a
genuinely empty/degraded upstream read (0 rows) from a real "no flow" reading — both produce the
identical `{call_premium: 0, put_premium: 0, net: 0}` shape, and either writer would cache it
verbatim under the 120s TTL, serving it as valid to every reader for the full 2 minutes.

Live evidence (5-engine monitor cycle, 2026-10-14, 14:42-14:55 UTC polling `GET
/api/market/spx/desk`): `flow_0dte_net`/`call`/`put` flipped between a real multi-hundred-million
value and exactly 0/0/0 at least 4 times in 15 minutes — e.g. net=1,486,641,556 → 0/0/0 for ~2min
→ net=1,486,643,018 → 0/0/0 again → net=1,487,327,474 → 1,487,447,216 → 0 again. Every response
carried `feed_stalled:false` and `data_quality:{missing:[]}` regardless of which value was being
served — the bad poll was accepted as valid, not flagged degraded. CloudWatch confirmed the
backing UW call itself was completing with `status=200` throughout, so this was never a visible
HTTP failure — the zeroed aggregate was a real, accepted response from a bad/empty poll.

This directly corrupts SPX Slayer's live trading signal: the desk score's "0DTE flow" factor
(worth ±14 points) and the play gate's "0DTE flow opposes direction" block both read this field
— flipping to 0 for ~2 minutes at a time changes a real trading recommendation purely as a
caching artifact, not a real change in market flow.

### Fix rationale

Added `isDegenerateFlowAggregate()` (both sides exactly 0) as a shared guard at BOTH write sites:
- `fetchUwFlow0dte`: on a degenerate poll, substitutes a per-process `lastGoodFlow0dteByTicker`
  sticky value (same in-process "last good" pattern `spx-desk.ts` already uses for GEX
  walls/flip/unified tape) before the result ever reaches the cache-writing layer — so the GOOD
  value gets re-cached, not the zero. A genuinely cold-start degenerate poll (no prior good value
  yet) is still served honestly as zero — never fabricate a non-zero number that wasn't measured.
- `uw-cache-refresh` cron: skips the `uwCacheSet` write entirely on a degenerate poll, leaving
  whatever is already cached to count down on its own TTL rather than extending a bad value's
  life by rewriting it.

Did not touch `uwCacheGet`'s generic null-check contract (shared by 8+ files, dozens of call
sites) — the fix is scoped entirely to this one shared aggregate's two writers.

### Blast radius

`aggregateFlowPerStrikeRows`'s return shape and `fetchUwFlow0dte`'s public contract are both
unchanged — only its internal substitution behavior on a degenerate result changes. Both real
callers (`spx-desk.ts`'s `resolveFlow0dte`, Largo's `run-tool.ts` per-ticker flow lookup) get the
same improved behavior automatically, with no call-site changes needed.

### Alternative approaches not taken

1. **Change `uwCacheGet`'s generic `result != null` write-skip check to also skip on an
   empty/zero shape** — too broad; this helper backs many unrelated UW fetchers where an empty
   result can be a legitimate, cacheable "no data" answer. Scoping the fix to this one aggregate's
   known-degenerate shape avoids changing behavior for every other caller.
2. **Treat a 0-row upstream response as a hard error and retry inline** — adds latency to the live
   desk read path for a condition that's already transient and self-correcting on the next poll;
   the sticky-substitution approach gets the same correctness without a slower request.

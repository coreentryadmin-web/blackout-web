## Meridian: `print_history_summary`'s "avg reaction" pooled still-forming and assumed-session reactions the sibling code was built to exclude — FIXED

> **kind:** `FINDING`

Tenth product-surface pass in the "check product by product" audit sweep (a fresh Meridian data-integrity pass, after SPX Slayer/Helix/Vector/Meridian/Night Hawk/Thermal/Largo/X-content earlier today).

| Field | Detail |
|---|---|
| **Symptom** | `printHistorySummary` (`src/lib/meridian/meridian-earnings-history.ts`) computes the "avg reaction" line shown in the earnings History tab's summary card (and passed unchanged into Largo's pre-earnings pack) by averaging every row with a non-null `reaction_pct` — including a print whose reaction is still intraday-forming (`reaction_settled: false`) or whose BMO/AMC timing was never resolved (`reaction_basis: "assumed_report_session"`). |
| **Root cause** | The filter (`rows.filter((r) => r.reaction_pct != null)`) never checks `reaction_settled`/`reaction_basis`. This is the identical defect `settledReactions()` (`meridian-reaction-display.ts`) exists to prevent — its own doc comment says pooling either into "what this company usually does on earnings" "launders an unknown into a statistic." The guard is already correctly used by the sibling function computing the same kind of number for peers (`summarizePeerReaction`, `meridian-sector-core.ts`) and by the same History tab's own chart (`MeridianEarningsHistoryPanel.tsx`) — but `printHistorySummary` reimplemented the pooling logic itself and dropped the filter. |
| **Why this matters** | A same-day print still moving (e.g. -9.4% and falling) getting averaged in as final can flip the SIGN of "avg reaction" — the exact number a member uses to size an earnings play against the market's implied move. Traced with concrete inputs: three real settled reactions (+3.0, -2.0, +1.0) average to a correct +0.67%; adding one unsettled -9.4% print flips the buggy average to -1.85% — sign inverted, magnitude off by ~2.5x. This string is rendered directly next to the correctly-filtered chart on the same tab, so a member could see the two disagree on direction for the same name. It also flows unchanged into Largo's pre-earnings pack (`src/lib/largo/pre-earnings-pack.ts`), so the same wrong number is what Largo would quote when asked "how does this name usually react to earnings." |
| **Fix** | `printHistorySummary` now calls `settledReactions(rows)` (imported, not reimplemented) before filtering on `reaction_pct != null` — the same two-step pattern `summarizePeerReaction` already uses. Exported `printHistorySummary` (previously module-private) for direct unit testing. |
| **Blast radius** | Single function. Consumers: the History tab's summary card, `pre-earnings-pack.ts`, `run-tool.ts` (Largo) — all read the string unchanged, so the fix propagates without further changes. |
| **Why not caught earlier** | No test exercised `printHistorySummary`'s `avgMove` against an unsettled or assumed-session row — only `meridian-sector-core.test.ts` and `meridian-reaction-display.test.ts` tested the settled-filter behavior, never this function specifically. |
| **Regression guard** | New `meridian-earnings-history.test.ts`, 3 tests: an unsettled print must be excluded from the average (confirmed **failing** pre-fix — the exported function didn't even exist yet, confirming the whole change is needed — and passing post-fix); an assumed-report-session print must be excluded; a plain all-settled case is unaffected. |
| **Gates** | `npx tsc --noEmit` clean · `meridian-earnings-history.test.ts` 3/3 pass (Node 20.20.2). |
| **Status** | FIXED |

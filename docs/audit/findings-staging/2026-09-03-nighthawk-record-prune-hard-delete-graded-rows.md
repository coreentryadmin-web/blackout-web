## 2026-09-03 — [FINDING, P1 Trust/Compliance, Night Hawk] Admin edition rebuild could hard-delete an already-graded play from the public ledger — FIXED

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **What prompted this** | A user QA report flagged the integrity promise on `/methodology` / `/track-record` — *"No cherry-picking, no deleted calls — the full ledger, always"* (`src/components/landing/MethodologyContent.tsx:19`, SPX Slayer's copy; Night Hawk's sibling paragraph makes the same claim for its own ledger) — and asked for it to be technically verified rather than taken on faith. This entry covers the sweep across every `UPDATE`/`DELETE` against `nighthawk_play_outcomes`, `zerodte_setup_log`, and `spx_play_outcomes` (grep evidence below), plus the WS-10/WS-11 regrade paths and the two admin regrade routes. |
| **Root cause** | `pruneNighthawkPlayOutcomesForEdition` (`src/lib/db.ts`) is the sync-side cleanup `syncNighthawkPlayOutcomes` (`src/features/nighthawk/lib/play-outcomes.ts:543`) calls right after every edition publish/rebuild, to drop stale ticker rows a re-run no longer publishes for that `edition_for`. It issued a bare `DELETE FROM nighthawk_play_outcomes WHERE edition_for = $1::date AND NOT (ticker = ANY($2::varchar[]))` — **no guard on `outcome`**. Every other write against this table enforces its invariant in the SQL itself, not in the caller: `upsertNighthawkPlayOutcomes`'s own `ON CONFLICT ... DO UPDATE ... WHERE nighthawk_play_outcomes.outcome = 'pending'` two calls above this one in the same function, `updateNighthawkPlayOutcome`'s identical `WHERE id = $1 AND outcome = 'pending'`, `reanchorNighthawkEntryBand`'s same guard, and `regradeLegacyNighthawkOutcome`'s COALESCE-pinned `legacy_grade` preservation. The prune DELETE was the one write path in this file that instead relied on caller discipline (in practice: same-day rebuilds only ever run before that edition's plays grade, so `outcome` happens to still be `'pending'` for every row a normal rebuild touches). That discipline has exactly one documented, live escape hatch: `POST /api/admin/nighthawk/run?asOfEt=<past date>&persist=1` (`src/app/api/admin/nighthawk/run/route.ts`) — edition-builder.ts's own "admin recovery only" path — re-runs the *entire* synthesis pipeline against a PAST `edition_for` whose plays have long since graded, and there is no reason to expect the reconstructed pick list to exactly match the original (different live-API state, different candidate ranking, non-determinism in the synthesis step). Any ticker present in the old graded set but absent from the freshly rebuilt list was **hard-deleted** by the unguarded prune — win or loss, methodology stamp, `legacy_grade`, `debrief`, everything — silently, with zero trace. |
| **Evidence** | `grep -n "UPDATE (nighthawk_play_outcomes|zerodte_setup_log|spx_play_outcomes)" src/lib/db.ts` plus `grep -rn "DELETE FROM (nighthawk_play_outcomes|nighthawk_editions|zerodte_setup_log|spx_play_outcomes|spx_open_play)" src` — the **only** hard `DELETE` against any of the three products' ledger tables in the whole codebase was this one call, at `src/lib/db.ts:8954` (pre-fix). Confirmed reachable: `route.ts` always calls `buildEveningEdition({ force: true, asOfEt, persist })`; `edition-builder.ts`'s `historical = asOfEt !== todayEt()`, `dryRun = historical && persist !== true` — with `persist=1`, `checkpointing = true`; `job?.status === 'published' && opts.force` (true for any real past date) resets the job and re-runs the full pipeline, ending in `upsertNighthawkEdition` (unconditional `ON CONFLICT DO UPDATE`, no guard at all — see Blast radius) then `syncNighthawkPlayOutcomes` → the unguarded prune. Also confirmed this is not a hypothetical concern for this route: `src/app/api/admin/nighthawk/run/route.test.ts`'s own regression-test header describes a **prior, separate** bug in the same route (`persist: persist \|\| true` — unconditionally `true` regardless of the query param) that "silently overwrote a past published edition" on every historical rebuild until fixed; that fix closed the accidental-trigger path but never touched the prune's missing guard underneath it. |
| **Blast radius** | Scoped to `pruneNighthawkPlayOutcomesForEdition` only — no other UPDATE/DELETE against any ledger table in this sweep had the same gap (see "Verified already correct" below). Related but **not fixed here, deliberately**: `upsertNighthawkEdition`'s `plays`/`recap_headline`/`recap_summary` columns (the edition's *display* JSON, `nighthawk_editions` table) are also unconditionally overwritten on every rebuild with no guard and no history. This is a narrower, already-acknowledged risk of the same admin recovery tool (the route's own dry-run default and the edition-builder's "CLOBBER GUARD" comment show the team already reasoned about accidental overwrite here), and — unlike the DELETE — it never touches the numeric grading ledger: `/track-record`, `/admin/track-record`'s per-play "receipts" (`src/app/api/track-record/plays/route.ts`), and the headline win-rate stats (`analytics.ts`'s `getNighthawkMetrics` → `fetchNighthawkOutcomeAnalytics`) all read `nighthawk_play_outcomes` directly, never `nighthawk_editions.plays`. Flagged here as a follow-up candidate, not bundled into this single-issue fix. |
| **Fix** | Added `AND outcome = 'pending'` to the DELETE's WHERE clause — the same guard every sibling write on this table already uses. A still-`pending` row (the case this function exists to clean up: a same-day re-run whose ticker set shrank before anything graded) is unaffected; a row that has already resolved to `target`/`stop`/`open`/`ambiguous`/`unfilled` now survives the prune unconditionally, regardless of whether the new play list still names its ticker. |
| **Regression guard** | `record-honesty-contract.test.ts` — new source-text contract test (same idiom this file already uses for `updateNighthawkPlayOutcome`/`regradeLegacyNighthawkOutcome`'s SQL guards), asserting the DELETE's WHERE clause includes `AND outcome = 'pending'`. Confirmed RED pre-fix (`git stash` the `db.ts` change, test fails with the un-guarded DELETE text) and GREEN post-fix; 14/14 in the file. |
| **Gates** | `npx tsc --noEmit` clean (Node 20.20.2). Full `npm test` run — see this PR for the pass/fail count (same pre-existing sandbox-only DB-connectivity signatures as every other run this session, unrelated to this change, if any appear). |
| **Verified already correct — no gap found (documented per the standing INTENTIONAL-DESIGN discipline)** | The rest of the sweep the QA report asked for came back clean, and is recorded here as evidence rather than assumed: **(1) Night Hawk overwrite-in-place.** `upsertNighthawkPlayOutcomes`'s `ON CONFLICT DO UPDATE` on `direction/conviction/entry_range/target/stop/score/sector` is guarded `WHERE outcome = 'pending'` — once a row grades, a force-rebuild's refreshed values can never land on it. `publish_context` (the publish-time evidence snapshot) is separately COALESCE first-write-wins. **(2) Night Hawk regrade.** `regradeLegacyNighthawkOutcome` pins the pre-update outcome/hit-flags/methodology into `legacy_grade` (COALESCE first-write-wins, `jsonb_build_object` over the pre-UPDATE tuple) *before* overwriting, and is SQL-guarded to `outcome <> 'pending' AND grade_methodology <> CURRENT` — a promoted row can never match again. Both grades stay inspectable forever (`legacy_grade` + current columns); this is a genuine versioned-history model already in production, not a gap. **(3) `reanchorNighthawkEntryBand`.** Guarded `WHERE outcome = 'pending'`; its own comment states "the published edition is never mutated — only the grading-side entry band," confirmed structurally (it writes only `nighthawk_play_outcomes`, never `nighthawk_editions`). **(4) SPX Slayer (`spx_play_outcomes`).** `closePlayOutcomeRow` writes `exit_price/pnl_pts/outcome/closed_at` exactly once, guarded `WHERE open_play_id = $1 AND outcome = 'open'` — idempotent by construction, same discipline as Night Hawk. `entry_price/stop/target/grade/headline/entry_path` are set once at INSERT (`insertOpenSpxPlay`/`insertPlayOutcomeRow`) and never written again by any UPDATE in the file — trailing-stop management (`updateOpenSpxPlayRow`) only touches the separate working table `spx_open_play`, never the ledger. No DELETE against `spx_play_outcomes` or `spx_open_play` exists anywhere in the codebase. **(5) 0DTE (`zerodte_setup_log`) grading.** `gradeZeroDteSetupRow` has no SQL-level guard, but its one call site (`scan.ts:1979`) is fed exclusively by `fetchUngradedZeroDteRows`'s `WHERE graded_at IS NULL` — grading is terminal in practice (weaker than a SQL guard, not a live gap today; worth hardening opportunistically but out of scope for this single-issue PR). No DELETE against `zerodte_setup_log` exists anywhere in the codebase. **(6) `regrade-index-roots` admin route** (`resetNullGradedZeroDteRows`) is provably scoped to `graded_at IS NOT NULL AND close_price IS NULL` — rows that were stamped "graded" by the pre-`polygonSpotTicker`-fix bug with **no real grade data**, never a row carrying a genuine close/win/loss. **(7) `regrade-stuck-outcomes` admin route** (`regradeStuckNighthawkOutcomes`) only selects `outcome = 'pending'` rows stuck past the resolver's lookback, and persists through the same SQL-guarded `updateNighthawkPlayOutcome` — it can never touch an already-graded row. |

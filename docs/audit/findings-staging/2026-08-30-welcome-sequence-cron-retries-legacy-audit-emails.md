## 2026-08-30 — [FINDING, P2 ops/billing-infra] Welcome-sequence cron indefinitely retries legacy audit-account emails, burning a real Resend failure every hour — FIXED

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **Symptom** | Live CloudWatch sweep of `/ecs/blackout-production` found 36 `[resend] send failed { statusCode: 422, name: 'validation_error', message: "Invalid \`to\` field. Please use our testing email address instead of domains like \`example.com\`..." }` lines clustered in a single hour (2026-08-29 06:00–07:00 UTC). |
| **Root cause** | `src/app/api/webhooks/clerk/route.ts` gates `startWelcomeSequence` behind `isInternalAuditEmail(email)` (added 2026-08-28, per `docs/audit/findings-staging/2026-08-28-ops-alert-audit-account-noise.md` and its two follow-ups) — but that gate only stops a **new** audit/test-harness account from being inserted into `welcome_sequence_state` going forward. It does nothing about rows already sitting in that table from before the gate existed: `internal-audit-email.ts`'s own doc comment says ~30 ad-hoc `scripts/audit/*.mjs` harnesses have been minting throwaway Clerk accounts against **production** for a long time, several using literal `@example.com` addresses (e.g. `helix-interaction-audit.mjs`). `processDueWelcomeSequenceSteps` (`src/lib/welcome-sequence.ts`, the **hourly** cron at `/api/cron/welcome-sequence`) selects every row whose `next_send_at` is due and sends the next step — with no `isInternalAuditEmail` check anywhere in that path. Worse, a failed send **deliberately** leaves `next_send_at` untouched ("so the cron retries this same step rather than silently skipping it") — so every legacy audit-account row burns one real, guaranteed-to-fail Resend API call **every single hour**, for up to `MAX_STEP_LATENESS_DAYS` (7 days = up to 168 attempts per row) before the staleness cutoff finally retires it. |
| **Why this matters beyond noise** | The file's own `MAX_STEP_LATENESS_DAYS` comment already names the real risk: *"A 99.9% bounce rate on a transactional template is a real sender-reputation risk (Gmail/Yahoo suspend bulk senders on complaint/bounce rate), not just wasted send volume."* That comment anticipated exactly this failure mode but the fix (the `isInternalAuditEmail` gate) was applied only at the table's entry point, not at the point where a stale, pre-existing row is actually processed — so the sender-reputation risk it warned about was still live for any row older than the gate. |
| **Fix** | Added the same `isInternalAuditEmail` check inside `processDueWelcomeSequenceSteps`'s per-row loop. A matching row is marked `completed_at = NOW(), next_send_at = NULL` (same "mark complete, don't delete, don't retry" pattern already used for the staleness cutoff and the defensive `steps_sent`-overflow branch — not a third way to exit the drip) and skipped **before** attempting a send, so it costs zero Resend calls instead of one per hour. |
| **Blast radius** | Single function, single call site — `processDueWelcomeSequenceSteps` has one caller (`src/app/api/cron/welcome-sequence/route.ts`). No other cron or email path shares this exact table-scan pattern. `startWelcomeSequence` itself was not touched — its caller already gates correctly for new signups; this fix only closes the gap for pre-existing rows. |
| **Why not caught earlier** | The existing test suite (`welcome-sequence.test.ts`) never constructed a `selectRows` fixture with an audit-shaped email, so the always-attempt-a-send behavior for a legacy row was never exercised. Its own fixtures happened to use `trader@example.com` as the "real member" placeholder throughout — which is itself an instance of the exact ambiguity this fix resolves (a `@example.com` address reading as a normal test fixture rather than the literal domain `isInternalAuditEmail` now treats specially) — so those fixtures were updated to `trader@gmail.com` to keep meaning what they always meant. |
| **Regression guard** | Two new tests: a legacy audit-account row (`helix-interaction-audit@example.com`) is retired with zero send attempts and `{processed:1, sent:0, failed:0}` (a skip is not a bounce); a real member's email sharing no audit pattern still sends normally. Both confirmed against the actual `isInternalAuditEmail` implementation, not a stub. |
| **Gates** | `npx tsc --noEmit` clean · `npx eslint` clean on both touched files · `welcome-sequence.test.ts` 13/13 pass · full `npm test` **11425 pass / 0 fail / 2 skipped** (Node 20.20.2). |
| **Status** | FIXED |

## 2026-09-01 — [FINDING, P4 CI/tooling] `off-hours-health.yml` also drifts 30min-6h from its `0 */6 * * *` schedule — confirms the fleet-wide hypothesis the earlier finding left open — OPEN, write-up only

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **What this follows up on** | `docs/audit/findings-staging/2026-08-31-largo-stress-nightly-schedule-drift.md` (PR #3238) measured `largo-stress-nightly.yml`'s single daily slot drifting from ~55min-late (normal GitHub Actions jitter) to 5.5-12.5h late starting 2026-08-27, and explicitly named the open question: *"Whether this is `largo-stress-nightly`-specific or a repo-wide `schedule:` trigger degradation is unconfirmed"* — `off-hours-health.yml` (`0 */6 * * *`) was one of two workflows named as spot-checked for "is it running/succeeding" but NOT yet checked for fire-time drift specifically. This entry does that check. |
| **The data** | Pulled the last 20 `off-hours-health.yml` runs (`list_workflow_runs`) and computed each run's drift from its nearest nominal 6-hour slot (00:00/06:00/12:00/18:00 UTC). Drift ranges from **29min to 356min (5h56m)**, and — the key finding — it clearly **worsens over time in step with the fleet's commit velocity**: runs from 2026-08-25/08-26 (before the fleet ramp-up) cluster at 39-112min; runs from 2026-08-27 onward (after the ramp-up the earlier finding dates) cluster at 150-356min, roughly 3-6x worse. All 20 sampled runs still completed successfully (`conclusion: success`) — no missed-alert bug like `largo-stress-nightly.yml` had (that one is already fixed, PR #3247); this is purely corroborating evidence for the drift mechanism itself. |
| **Why this matters (narrowly)** | It upgrades the earlier finding's hypothesis — GitHub Actions deprioritizing `schedule:`-triggered runs under high repo Actions load — from "consistent with the timing on one workflow" to "reproduces on a second, differently-shaped workflow (4x/day vs 1x/day) with the same before/after 2026-08-27 step-change and the same direction of correlation." A single-workflow data point could have had a workflow-specific explanation (a slow step, a runner queue this workflow specifically competes for); a second, unrelated workflow showing the same pattern makes a repo-wide GitHub Actions scheduling-queue explanation much more likely than a per-workflow one. |
| **Why not fixed / no code change** | Same reasoning as the original finding: there is nothing in this repository to fix — `off-hours-health.yml`'s `cron: "0 */6 * * *"` is valid and unchanged, and the delay lives in GitHub's own Actions scheduler queue, not in this workflow's config. This entry exists purely to record the confirming measurement so the original finding's "unconfirmed" scope question can be marked resolved. |
| **Suggested next step (unchanged from the original finding)** | Still owned by whoever handles CI tooling: (1) if the queue-priority hypothesis needs a definitive answer, GitHub support or watching whether drift recovers once fleet commit velocity drops are the two ways to get one; (2) decide whether any single-daily-slot scheduled workflow (`largo-stress-nightly.yml` being the one with real stakes, since a multi-hour-late "nightly" degrades its early-warning value) needs to move off GitHub Actions `schedule:` for time-sensitivity. A 4x/day health check drifting a few hours is lower-stakes than a 1x/day stress gate drifting the same amount, so this confirmation doesn't raise the original finding's urgency — it just resolves its scope question. |
| **Status** | OPEN (scope question from the 2026-08-31 finding now CONFIRMED repo-wide-consistent, not workflow-specific) — still flagged for the CI/tooling owner, no code change made |

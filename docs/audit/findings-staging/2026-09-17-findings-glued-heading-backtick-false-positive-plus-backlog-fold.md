## 2026-09-17 — [FINDING, P2 audit-tooling] `GLUED_HEADING`'s glued-heading detector had a false-positive that would have let `repairGlued` corrupt a legitimate backtick-quoted heading reference — found while folding a 330+ file findings-staging backlog

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **What prompted this** | `docs/audit/findings-staging/` had accumulated **380 files** (oldest since 2026-09-04) — the fold pipeline (`scripts/audit/findings-fold-staging.mjs`, "typically run by the coordinator after a merge wave") had clearly not kept pace. Ran it to clear the backlog. 49 of 379 real staged files were valid and fresh; `npx tsx --test src/findings-hygiene.test.ts` then failed on the folded result. |
| **Root cause** | `findings-hygiene.test.ts`'s "entry headings are never glued onto the end of another line" check, and the **production** `GLUED_HEADING` regex it mirrors (`scripts/audit/lib/findings-merge-core.mjs`, used by `findings-merge-resolve.mjs` to auto-repair FINDINGS.md merge conflicts), both matched any full-date-shaped `## YYYY-MM-DD — [` string not at line start — including one **quoted verbatim inside backticks** as evidence in a later entry (e.g. this session's own `"The stale entry \| \`## 2026-09-02 — [FINDING, ...] ... — OPEN\`."`, citing a prior entry's exact stale heading text). Four such quotes existed in the folded batch alone. The check's own comment already excluded one legitimate mid-line case (the "How to read this file" section's ellipsis-shaped examples, which don't match the strict date pattern) but never considered a REAL, full-shaped heading quoted as evidence — a pattern this repo's own PR write-up policy encourages ("evidence... whatever actually proved the bug") and that this session's own stale-status re-verification findings use throughout. |
| **Why this matters beyond the test failure** | `countGlued`/`repairGlued` are not test-only — they are **production repair logic** invoked by the merge-conflict resolver on real PR merges. Unpatched, `repairGlued` would have spliced a blank line + a brand-new `## ` heading into the MIDDLE of the quoting entry's own markdown table cell the next time that entry's branch went through a three-way merge resolution, and `splitEntries` (which drives the resolver's entry-boundary logic) would then read the spliced-in text as a real new entry boundary — silently fragmenting the quoting entry into a headless orphan. That is the exact "silent damage" failure mode `repairGlued`'s own docstring says it exists to FIX, self-inflicted on perfectly healthy input. |
| **Evidence** | Live repro this session: folding the real backlog produced 4 genuine backtick-quoted-heading matches (`docs/audit/FINDINGS.md` post-fold, lines 530/1326/1368/2193 — confirmed each is immediately preceded by a backtick character, never true adjacent-markdown gluing). RED→GREEN proven directly (not via `git stash`, since the fix is the production regex itself): added `countGlued does not flag a heading quoted verbatim in backticks as glued` to `src/findings-merge-resolve.test.ts` — failed (`1 !== 0`) against the unpatched `GLUED_HEADING`, passed after adding the `(?<!\`)` negative lookbehind. Full `src/findings-hygiene.test.ts` + `src/findings-no-loss.test.ts` + `src/findings-fold-staging.test.ts` + `src/findings-merge-resolve.test.ts` (32 tests): 1 fail pre-fix (the exact false positive), 32/32 pass post-fix. `npx tsc --noEmit` clean. |
| **Fix** | `GLUED_HEADING` regex (`findings-merge-core.mjs`) gained one more negative lookbehind, `(?<!\`)`, alongside the existing `(?<!^)(?<!\n)`. Distinguishing signal: a genuinely glued heading is raw adjacent markdown from a dropped newline (this file's own fixture: `"FIXED. \|## 2026-08-21 — [FINDING, ..."` — never backtick-preceded); a legitimate quote is always wrapped in a code span. `findings-hygiene.test.ts`'s mirrored check got the identical exclusion so both stay in lockstep (the test file's own comment already noted the two must not drift). |
| **Fix rationale — what was deliberately NOT done** | Did not weaken the match shape further (still requires the full `## YYYY-MM-DD — [` pattern, not a bare `## `) — that would reopen exactly the false-negative risk the existing shape-matching was chosen to avoid. Did not try to detect fenced (triple-backtick) code blocks here — unlike `findings-fold-staging.mjs`'s own separate fenced-code-block fix (2026-09-17, same session, different function: counting `## `-level sub-headings inside a staged file's OWN Evidence section), this defect is about a SINGLE-backtick inline code span on one line, a narrower and simpler case that a one-character lookbehind fully covers. |
| **The backlog fold itself** | 49 fresh staged findings folded into `FINDINGS.md` this pass (2026-09-04 through 2026-09-17, multiple lanes) — `docs/audit/FINDINGS.md` +2985 lines, 49 staged files deleted. **330 staged files remain**, all correctly left in place by the script's own "skip invalid, never delete" safety design — every one failed the pre-existing "no heading / no kind line / more than one `## ` line" validity check, a SEPARATE, larger authoring-hygiene problem across many lanes' staged files that this fix does not address (out of scope: 330 files is a real, substantial backlog of its own, likely worth a dedicated pass by whoever owns the staging convention, not something to force-normalize blindly in the same PR as a merge-tooling correctness fix). |
| **Suggested next step** | (1) Whoever runs the next fold should expect ~330 files to still be skipped and investigate the shape of the authoring defect at that scale — is it a widespread convention drift, or a stale copy of the staging README template being followed. (2) Consider whether `findings-fold-staging.mjs` should be run on a schedule (a cron/workflow) rather than only "typically after a merge wave" by whichever lane remembers to, given how large the backlog grew between manual runs. |
| **Status** | FIXED — merge-core regex + hygiene-test regex both patched, regression test added, RED→GREEN proven. Backlog partially cleared (49/379 folded); the remaining 330-file authoring-hygiene backlog is a separate, larger finding, flagged not fixed. |

## 2026-09-03 — [FINDING, P2 performance/correctness, marketing/research] `research/gamma-levels/[ticker]` has the same ISR + `no-store` fetch + broad-catch cache-poison shape #3383 just fixed on the homepage — live occurrence NOT confirmed, flagged for the owning lane — OPEN, write-up only

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **What prompted this** | #3383 (merged this session) root-caused the homepage's warming-placeholder-forever bug: an ISR page (`revalidate`, no `dynamic = "force-dynamic"`) whose live-compute path issues a `fetch(..., {cache: "no-store"})`. During Next's attempted *static* render (first on-demand generation, or a background revalidation), that trips Next's internal `DynamicServerError` bailout. A broad `try/catch` somewhere in the call chain swallows that framework control-flow signal identically to a real network failure, falls through to a degraded/empty result, and that result gets written to a shared cache — poisoning it for every subsequent reader until the next successful compute. Per the standing performance/correctness audit mandate ("measure before guessing... sweep the whole product"), I read for other instances of the exact same shape rather than assuming #3383 was the only one. |
| **Same shape, confirmed by direct code read** | `src/app/(marketing)/research/gamma-levels/[ticker]/page.tsx`: `export const revalidate = 3600;` `export const dynamicParams = true;`, deliberately no `generateStaticParams` (the file's own comment explains why: pre-rendering at build time would bind every page to whether *CI's* build environment can reach Postgres/Polygon, which it can't). Both `generateMetadata` and the page body call `loadGammaLevelsResearch(symbol)` (`src/lib/research/gamma-levels.ts:185-218`), which checks `sharedCacheGet(cacheKey)` first (cache key `research:gamma-levels:v1:<SYMBOL>:<windowSessions>`) and on a miss calls `loadWindowBars(symbol, sessions)` (line 142-175). That function calls `fetchIndexDailyBars`/`fetchStockDailyBars` (`src/lib/providers/polygon.ts:1067,1083`), both of which route through the shared `polygonGet` helper (`polygon.ts:27-39`) whose `fetch` call is `cache: "no-store"` (`polygon.ts:33`) — the exact primitive #3383 implicated. `loadWindowBars`'s own `try/catch` (`gamma-levels.ts:160-173`) is a broad catch: on ANY thrown error it `console.warn`s `"[research-gamma] bar load failed"` and returns an **empty Map**, no rethrow, no distinction between "Polygon really failed" and "Next just bailed out of static rendering." That degraded (bars-empty) result then flows into `buildGammaLevelsResearch` and gets written via `sharedCacheSet(cacheKey, research, CACHE_TTL_SEC)` (line 216, `CACHE_TTL_SEC = 3600` = 1 hour) — the exact "swallow the framework signal → cache the degraded result" shape #3383 fixed on the homepage. |
| **Confirmed NOT already dynamic for some other reason** | Read `MarketingPageShell.tsx` (the page's shell) and the page file itself end to end: no `cookies()`, `headers()`, or other dynamic-API call anywhere in the render tree that would already force this route dynamic and make the `no-store` fetch moot. The page is a plain ISR page exactly like the pre-fix homepage was. |
| **Live occurrence — NOT confirmed, and that itself is informative** | Tried to reproduce #3383's own evidentiary bar (a live CloudWatch hit) and could not: `filter_log_events` on `/ecs/blackout-production` for `"Dynamic server usage"` (24h, unquoted and quoted), `"DynamicServerError"` (7d), and even the bare substring `"gamma-levels"` (7d) all returned **zero events**. Sanity-checked the query mechanism itself works (an unfiltered pull over the same log group returns dozens of events per 30 minutes — mostly cron/background-job lines like `[cron/platform-warm]` and `[polygon-gex] full-chain escalation`), so this isn't a broken filter syntax; the honest read is that **this route logged nothing at all in the sampled window** — including the `console.warn` this bug's own catch block would emit on ANY failure, real or bailout. That's consistent with this being a low-traffic long-tail SEO page (unlike the homepage, which every visitor hits, so its revalidation attempts fire "at all hours" per #3383's own confirmed evidence) rather than a route that's actively firing and silently degrading. **This is a latent structural risk, not a live-confirmed incident** — flagging it as such rather than overclaiming. |
| **Why this one is worse in one dimension and better in another than the homepage case** | Worse: the cache TTL here is 3600s (1 hour) vs. the homepage seed's much tighter window, so a poisoned entry would persist far longer once it happens. Better/narrower: this cache key is per-ticker (`...:v1:<SYMBOL>:60`) with a single reader (this loader — confirmed via `grep -rln "loadGammaLevelsResearch\|research:gamma-levels" src --include="*.ts" --include="*.tsx"` finding only the page and the loader itself), so a poisoned entry degrades one ticker's page rather than a surface every visitor sees, and there's no existing pre-warm cron or alternate dynamic caller (unlike the homepage, which had `/tools/gamma-snapshot` + an API route already structurally immune to redirect live-compute obligation to). |
| **Why write up, not fix directly** | #3383's fix (a cache-only reader with shared-cache → last-known-good → warming-placeholder fallback that never calls live-compute) worked for the homepage specifically because a pre-warming cron and an already-dynamic API route already existed to carry the live-compute obligation. Neither exists for `research/gamma-levels` today — building one, or the alternative (`dynamic = "force-dynamic"`, trading away ISR/edge caching and adding live Postgres+Polygon latency to every page load of an SEO page where fast/cacheable delivery matters), is a real architecture trade-off for a page whose bug is not live-confirmed, not a small self-contained fix. Per this lane's standing policy, that decision belongs to the owning lane, not a unilateral pick here. |
| **Suggested next step** | For whoever owns the research/SEO pages: (1) decide cache-only-reader-with-pre-warm vs. `force-dynamic` for this route (or a scoped `try { ... } catch (err) { if (err instanceof Error && err.digest === "DYNAMIC_SERVER_USAGE") throw err; ... }` re-throw guard in `loadWindowBars`'s catch, which would let Next itself handle the bailout correctly instead of swallowing it — the narrowest possible fix, worth strong consideration since it doesn't require inventing a pre-warm cron for a page that may see too little traffic to justify one); (2) if traffic to this page grows (SEO ramp), re-run the CloudWatch check above — a future positive hit would upgrade this from latent to confirmed. |

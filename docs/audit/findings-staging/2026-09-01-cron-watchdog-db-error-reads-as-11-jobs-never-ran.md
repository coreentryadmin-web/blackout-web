## 2026-09-01 — [P2, ops/alerting] cron-staleness-watchdog conflates "DB read failed" with "job has never run", turning one Postgres blip into a false 11-job alarm — FIXED

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **Context** | Live 0DTE/Vector deep-dive session. User shared a screenshot of the ops Discord `#website-logs` channel showing a "⚠️ Cron health: 2 job(s) need attention" alert plus a separate large block listing **11 jobs** (`largo-cleanup`, `largo-morning-brief`, `nighthawk-playbook`, `platform-warm`, `swing-discovery`, `db-cleanup`, `membership-reconcile`, `welcome-sequence`, `cron-staleness-watchdog` itself, `nighthawk-morning-confirm`, `alert-outcome-sync`) all flagged **"NEVER logged a run — job may not be scheduled at all"**, timestamped 7:11-7:16 AM PT (14:11-14:16 UTC). |
| **First hypothesis, ruled out with real data** | `node scripts/audit/cron-schedule-coverage.mjs --infra=../blackout-infra` (this repo's own tool for exactly this question) confirmed only **2** of the 11 are genuinely unscheduled (`largo-morning-brief`, `welcome-sequence` — no EventBridge rule at all, a real pre-existing gap, separate issue). The other **9** ARE scheduled per blackout-infra. Hitting `GET /api/admin/cron-health` live moments later showed **all 11 as `healthy`** with real, recent `last_run_at` timestamps (minutes to a few days old) — proving the "NEVER logged a run" alarm was a **false positive**, not a real provisioning gap. |
| **Root cause** | `admin-cron-health.ts`'s `buildCronHealthSnapshot()` wraps `fetchCronJobLastRuns()` in a try/catch; on a thrown query it sets `dbSnapshotError` (a string) but leaves `lastRuns` at its initial value `[]` rather than propagating the failure per-job. `evaluateJob()` then receives `lastByKey[job.key] === undefined` for **every single job in the registry** — indistinguishable from "genuinely zero rows in `cron_job_runs`, ever" — and returns the worst-case label ("NEVER logged a run — job may not be scheduled at all") for each one. `cron-staleness-watchdog/route.ts` filters `snapshot.jobs` into `problems` and fires the Discord alert **without ever checking `snapshot.db_snapshot_error`**, even though that field is already computed and returned in the JSON payload. The timing lines up exactly with the same 13:31-14:12 UTC Postgres/Redis connection-storm incident (ops #3257) already fixed this session in PR #3259 (`resetPoolForRetry` pool-identity guard) and PR #3260 (Redis leader-lock connection leak) — the watchdog's own DB read almost certainly hit the identical `timeout exceeded when trying to connect` / `Cannot use a pool after calling end on the pool` errors visible in CloudWatch at that moment, and this is the alerting-layer consequence of the same root outage. |
| **Blast radius** | Every job in `CRON_JOBS` (52 routes) is vulnerable to the same false alarm on any future transient DB read failure during this watchdog's own tick — not just the 11 that happened to alarm this time (which ones alarm vs. get silently suppressed as `unknown`/"not due yet" depends on each job's own schedule window at the exact moment the DB read fails, per `notDueYet`'s off-window/off-schedule-idle-gap check). |
| **Fix** | `cron-staleness-watchdog/route.ts`: check `snapshot.db_snapshot_error` immediately after `buildCronHealthSnapshot()` returns. When set, post ONE clear "DB snapshot read failed" Discord alert carrying the actual error, skip deriving `problems`/`rth_stale`/self-heal targets from the tainted `snapshot.jobs` list entirely, log the run, and return — letting the next scheduled tick re-evaluate once `cron_job_runs` is readable again. `admin-cron-health.ts` itself is unchanged — `db_snapshot_error` was already correctly computed and returned, just never consumed by its one caller that alerts. |
| **What was deliberately NOT changed** | The 2 genuinely-unscheduled jobs (`largo-morning-brief`, `welcome-sequence`) found by `cron-schedule-coverage.mjs` are a real, separate, pre-existing gap — not touched here, since fixing them means adding EventBridge rules in blackout-infra terraform (per this repo's standing terraform caution: codify as a record, do not `terraform apply` against drifted state) and is out of scope for this alerting-correctness fix. Flagging for the coordinator/infra lane to pick up separately. |
| **Regression guard** | No new unit test added — the route has no existing test file, and building a harness (`after()`, Discord notify, DB, error-sink mocks) from scratch was judged disproportionate to a single early-return branch, matching the same call made earlier this session for the Redis-leak fix (PR #3260) on the same principle. Verified via `npx tsc --noEmit` (clean) and the full existing `admin-cron-health.test.ts` suite (7/7 pass, unaffected — only `route.ts` changed), plus live confirmation that the `db_snapshot_error` field genuinely reaches the route today (empty/absent under the current healthy DB state, matching the new code's no-op branch). |
| **Status** | FIXED — PR pending. |

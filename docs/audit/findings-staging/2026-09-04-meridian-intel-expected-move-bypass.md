## 2026-09-04 — [BUG, P1 member-facing] Meridian intel layer reintroduced the already-printed expected-move defect PR #3474 fixed at the pack layer

> **kind:** FINDING

| Field | Value |
|-------|-------|
| **Status** | FIXED |
| **Evidence** | Cursor's peer review on merged PR #3474 (posted 02:57 UTC, after the PR had already auto-merged at 03:00 UTC in the same webhook race) flagged: `loadMeridianEarningsIntel` (`src/lib/meridian/meridian-earnings-intel.ts`) re-fetches live chain IV via `loadEarningsExpectedMovePct` whenever `pack.expected_move_pct` is `null` — which, after #3474's own pack-layer fix, is now *exactly* the already-printed case. Confirmed directly against `origin/main`: line 86-88 (pre-fix) unconditionally called the live fetch on a null pack value, with no `earningsAlreadyPrinted` gate anywhere in the file. |
| **Root cause** | #3474 correctly withheld `pack.expected_move_pct` for an already-printed event (the LULU live case: post-crash chain IV served as "Options-implied move ~50.3%" hours after the print), but the intel loader independently re-derives the *same* field from TWO live sources whenever the pack value comes back null: (1) `loadEarningsExpectedMovePct`, a fresh chain-IV read, and (2) the `vectorCoversPrint` fallback, a still-live Vector weekly quote. Both silently reintroduce the identical stale-IV defect — `vectorCoversPrint` only checks that the expiry hasn't *expired* yet, which says nothing about whether the company has already *reported* — on every consumer of `intel.expected_move_pct`: `MeridianEarningsSummaryPanel`, `MeridianEarningsIntelPanel`, and the derived `expected_move_band` price range, even though the pack-only `LargoPreEarningsPackCard` was fixed. |
| **Fix** | Added `earningsAlreadyPrinted(input.pack.earnings_date, input.print_history)` gate before the `Promise.all` (skips the live fetch entirely when already printed) and extracted the final `expected_move_pct`/`expected_move_source` derivation into a new pure helper `resolveIntelExpectedMove` (`meridian-earnings-intel-core.ts`) that unconditionally returns `{null, null}` once `alreadyPrinted` is true — closing BOTH the `earningsEm` fetch path and the `vectorCoversPrint` fallback path with one gate, since both carry the identical defect. Extracted rather than inlined because `meridian-earnings-intel.ts` is `server-only` with dynamic `@/` imports and can't be exercised in a test — the same reason `earningsAlreadyPrinted` itself was split into `pre-earnings-history-rows.ts` in #3474. |
| **Blast radius** | `meridian-earnings-intel.ts` (2 call sites) + new helper in `meridian-earnings-intel-core.ts`. Deliberately left `vector_move_pct` (a separate report-pillar field, lines 239-255, with its own pre-existing dedicated expiry-covering suppression logic for a different defect class) untouched — out of scope for this fix, not mentioned by the reviewing comment, and not audited closely enough here to safely change. Also fixed one now-brittle raw-source-text test (`meridian-em-scope.test.ts`) that matched the exact prior inline `const expected_move_source = earningsEm != null \|\| vectorCoversPrint ? ...` expression in `meridian-earnings-intel.ts`; updated to read the same logic from its new home in `meridian-earnings-intel-core.ts`. |

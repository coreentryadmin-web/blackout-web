## 2026-09-03 — [FINDING, P1 Correctness] 136 raw `pool.query` call sites across `db.ts` — including `getMeta`/`setMeta` — bypassed `dbQuery`'s transient-error retry; live-confirmed cause of an SPX Slayer 0DTE play flickering to the degraded placeholder during RTH — FIXED

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **What prompted this** | Standing 10-min "4-engine live monitor" cycle. `/spx/play` was polled 5x over ~75s; 2 consecutive polls returned the fully-degraded placeholder (`available:false`, `session_phase:"closed"`, empty factors/gates) **during live RTH**, flanked by CloudWatch `[db] transient query error (attempt 1/3): Cannot use a pool after calling end on the pool` (16:45:51, 16:47:09 UTC) and `[play-engine-heartbeat] init hydration failed/persist failed: Error: Cannot use a pool after calling end on the pool` (16:35:49 UTC). |
| **Root cause** | Earlier the same day, `recordCronJobRun` was fixed for this exact bug class (its own findings-staging entry, 2026-09-03-cron-job-run-log-bypasses-retry.md): a raw `(await getPool()).query(...)` call bypasses `dbQuery`'s transient-error retry loop (`isTransientPgError` + `resetPoolForRetry`), so the documented client-side use-after-teardown race (`resetPoolForRetry()` tears down the shared module-level pool as soon as ANY caller sees a transient error, with no coordination against other concurrent callers still holding that same pool reference) surfaces as a bare, unretried failure instead of self-healing on a fresh pool. That fix touched exactly one function. A full sweep of `db.ts` for the same raw pattern (`grep -c "(await getPool()).query"`) found **136 more call sites**, including `getMeta`/`setMeta` — the shared key-value store `play-engine-heartbeat.ts`'s `recordPlayEngineTick`/`loadPlayEngineHeartbeat` (and 50+ other callers across the app) go through for every persisted read/write, with **no retry on any of them**. This is the direct, evidence-correlated cause of the live SPX flicker: a heartbeat/meta read or write racing another caller's pool reset surfaced as a bare failure on whatever request happened to hit it, including a member-facing `/spx/play` poll. |
| **Fix** | Swept the whole file rather than chasing each call site as its own future live incident (this repo's PR write-up policy explicitly calls out "duplicated logic in a second file counts — fix and note all of them, not just the one you tripped over" — here it was the same file, 136 times). Two shapes needed different treatment: (1) a plain raw pool query with no transaction involvement converts straight to `dbQuery`; (2) a `db?: Db`-optional helper (`setMeta`, `closeOpenSpxPlayRow`, `closePlayOutcomeRow`, `insertSwingPosition`, `gradeSwingPosition`) keeps two paths — a caller-supplied transaction client MUST stay on that exact connection (`dbQuery` always grabs the shared pool, which would silently escape the transaction), so only the no-`db` common case now routes through `dbQuery`. One deliberate exception was kept: `pingDatabaseConnectivity`, a raw connectivity PROBE for admin health/status — wrapping it in `dbQuery`'s retry+backoff would mask a real outage behind a false-healthy read for several seconds, defeating the point of a health check. |
| **Evidence the mechanical conversion was correct** | `(await getPool()).query<T>(text, values)` and `dbQuery<T>(text, values)` return the identical shape — `dbQuery` literally does `return await activePool.query<T>(text, values)` internally — so the substring replacement `(await getPool()).query` → `dbQuery` is a byte-exact behavioral no-op on the success path, only adding retry-on-transient-failure. One call site (a `spx_playbook_shadow_observations` reader) relied on TypeScript inferring its generic return type from the function's declared return signature rather than an explicit `<T>` argument; `dbQuery`'s own default generic (`QueryResultRow`) broke that inference, caught immediately by `tsc --noEmit` and fixed by adding the explicit `<T>`. |
| **Blast radius** | Every persisted read/write in `db.ts` that didn't already use `dbQuery` — SPX play-engine heartbeat/meta (the live-confirmed trigger), Night Hawk 0DTE meta reads, swing position commit/grade/close, Helix signal outcomes, and dozens more. All were previously one unlucky concurrent-caller pool reset away from a bare, unretried failure surfacing as whatever user-facing symptom that code path produces on error (a degraded placeholder here; elsewhere likely a swallowed `console.warn` per the existing `recordCronJobRun` pattern). No query text, parameters, or transaction semantics changed — this is purely adding the same retry every other write in the file already had. |
| **What was deliberately left unchanged** | `pingDatabaseConnectivity` (documented above). The `db ??` dual-path helpers keep their transaction-client branch exactly as before — `dbQuery` was never substituted there, only added as the alternate no-db path. |
| **Regression guard** | `src/lib/db.test.ts`, 4 tests: (1) a whole-file sweep asserting every remaining raw `(await getPool()).query` match falls inside `pingDatabaseConnectivity`'s own body — not a count, so a new stray raw call anywhere else fails it even if the ping's own call happens to vanish; (2) `getMeta`/`setMeta` both route their no-transaction path through `dbQuery`, and `setMeta` still special-cases a supplied client; (3) the four `db?: Db`-optional swing/SPX writers all keep their transaction-client branch and route the no-db path through `dbQuery`, with an explicit assertion that no `executor`/raw-pool shortcut survived. Confirmed RED pre-fix (`git stash -- src/lib/db.ts`, 3/4 new tests failed) and GREEN post-fix (20/20 in `db.test.ts`). |
| **Gates** | `npx tsc --noEmit` clean (Node 20.20.2). `npx tsx --test src/lib/db.test.ts`: 20/20 pass. Full `npm test` run alongside this PR (see PR for the pass/fail count). |
| **Status** | FIXED |

## 2026-09-03 — [FINDING, P2 Performance] ALB p99/Max latency sustained elevation (~11:00-11:42 UTC) correlates with ~2x full-chain GEX escalation rate — root cause NOT conclusively pinned, OPEN for follow-up

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **What prompted this** | Standing performance/latency audit mandate (30-min coordinator cycle). `AWS/ApplicationELB` `TargetResponseTime` on `blackout-production-app` showed a sustained, worsening tail-latency pattern across four consecutive 10-min windows (11:00-11:40 UTC): p50 stayed healthy (~0.08s) but p90 climbed to 1.5-2.4s, p99 to 49-73s, and Max hit 87-118s repeatedly — a magnitude well beyond the day's prior baseline (Max typically 3-27s, occasional deploy-correlated spikes to ~20s). |
| **What was ruled out** | (1) Cron overlap/overrun — `elapsed=` grep across the window found nothing exceeding ~37s (`cron/meridian-warm`), all well within their own schedule margins; no cron close to violating its interval. (2) Application crash errors — CloudWatch grep for `TypeError`/`Unhandled`/`undefined is not` returned 0 hits throughout. (3) Unhealthy ALB targets — all 8/8 targets `healthy` via `describe_target_health`. (4) Recent task restarts — all 8 ECS tasks had been running 50-80+ min with no recent churn, ruling out cold-start JIT/module-warming latency. (5) Traffic surge — `RequestCount` stayed in the normal 380-545/10min band, no meaningful surge. |
| **What correlates, not yet proven causal** | `[polygon-gex] full-chain escalation ADOPTED for <ticker>` log rate (from `fetchHeatmapBand` in `src/lib/providers/polygon-options-gex.ts`, an existing, pre-dating-today code path — see its own comment referencing #2084/2026-08-12) roughly DOUBLED: 1310 escalations in a 50-min pre-window baseline (09:00-09:50 UTC) vs 2516 in the 52-min elevated-latency window (10:50-11:42 UTC), plus 205 `NO-OP` escalations (an extra unfiltered full-chain Polygon fetch that gets discarded — pure wasted cost) in the same window. Each `ADOPTED`/`NO-OP` escalation is an EXTRA unfiltered `/v3/snapshot/options/<underlying>` Polygon fetch beyond the normal banded one, plus the GEX/greeks recompute over the larger contract set — real CPU + upstream-latency cost, and `ECS` `CPUUtilization` for `blackout-production-web` climbed in the same window (avg 6-7% → 14-15%, Max 57% → 89%). |
| **Why NOT closed as root-caused** | The escalation logic itself is unchanged by today's merges (#3381/#3394/#3395/#3396/#3397 — none touch `polygon-options-gex.ts`, confirmed by grep). The doubled rate could be: (a) organic pre-market ramp as more of the universe gets actively warmed approaching the 13:30 UTC / 9:30 ET open (this measurement window is ~07:00-07:42 ET, i.e., getting closer to open), or (b) a genuine new inefficiency exposed by increased warm-cron coverage. Per the standing mandate's own discipline ("never fix from a guess when the metric is one API call away", "do not add a fix to a cron/route not actually measured to be at risk") — no code change was made without a clearer causal link. |
| **Evidence for follow-up** | Compare the SAME escalation-rate measurement against an equivalent time-of-day window from a PRIOR trading day (same ~07:00-07:42 ET pre-market slot) to separate "organic daily pre-market ramp" from "new regression" — that comparison was not available from this sandbox in the time budget for one coordinator cycle. If the rate is confirmed elevated beyond the normal daily pattern, the next step is identifying which warm cron(s) are driving the higher escalation volume (the `[polygon-gex]` log lines don't carry a calling-cron tag) and whether `shouldEscalateToFullChain`'s "escalate at ANY price" breadth (from #2084) is now firing on a wider ticker set than intended. |

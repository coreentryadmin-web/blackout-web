## 2026-08-29 — [FINDING, P2 Swing] Archetype tie-break could return a label whose own fit never cleared the evidence floor — FIXED

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **Symptom** | `classifyArchetype` (`src/lib/swing/archetype.ts`) could return a non-null `archetype` at a `confidence` below `EVIDENCE_FLOOR` (0.35) — directly contradicting its own header doc's "NULL WHEN THIN" guarantee ("if no fit clears a minimal evidence floor... the verdict is `archetype:null`") and the inline comment on the guard itself ("the best fit is below the minimal evidence floor"). |
| **Root cause** | The tie-break (lines 187-190) can hand the label to `winner`, a *different* archetype than the one that set `topFit` — any contender whose fit is within `MARGIN_EPS` (0.05) of `topFit`, picked by `ARCHETYPE_PRIORITY` order rather than raw fit. But the floor guard two lines later checked `topFit < EVIDENCE_FLOOR`, not `winnerFit < EVIDENCE_FLOOR` — the fit of the archetype that actually gets *returned*. Since `winnerFit <= topFit` is not required to hold above the floor independently, a winner whose own fit sat below 0.35 could still be classified and returned, riding an unrelated archetype's higher fit across the line. |
| **Concrete repro** | `nearRangeExtreme01/breakoutQuality01/volumeExpansion01 = 0.36` each (BREAKOUT fit = 0.36, sets `topFit`) plus `catalystInWindow01 = 0.32` (EVENT_DRIVEN fit = 0.32). `0.36 − 0.32 = 0.04 ≤ MARGIN_EPS`, so EVENT_DRIVEN is a tie-break contender, and EVENT_DRIVEN precedes BREAKOUT in `ARCHETYPE_PRIORITY`, so it wins. Pre-fix: returns `{ archetype: "EVENT_DRIVEN", confidence: 0.32, ... }` — a label at confidence 0.32, below the 0.35 floor it exists to enforce. |
| **Blast radius** | `archetype` is the **calibration partition key** (per the file's own header comment) — `ARCHETYPE_META[archetype].scoreFloor` in `gates.ts` gates entry, and `taxonomy.ts` gives `EVENT_DRIVEN`/`POST_EARNINGS_DRIFT` a looser 1-session-plus-corroboration persistence fast-track vs. the standard 2-session build. A name with genuinely thin catalyst evidence could get mislabeled `EVENT_DRIVEN` — borrowing an unrelated `BREAKOUT`-cluster's strength to clear a floor its own evidence never cleared — and get fast-tracked toward WATCH/COMMIT under a looser persistence rule than its real evidence supports. Only reachable when (a) the true top archetype sits just above the floor and (b) a different, more-specific archetype sits within 0.05 of it but below the floor — a narrow but real window, not a hypothetical one (constructed directly from realistic per-field inputs, not edited internals). |
| **Why not caught earlier** | `archetype.test.ts`'s one tie-break test uses two archetypes at *equal* fit (0.80/0.80), where `winnerFit == topFit` and the two checks are indistinguishable. No existing test exercised the case where the tie-break's chosen winner has a *lower* fit than `topFit` while `topFit` alone still clears the floor. |
| **Fix** | One-line change: `topFit < EVIDENCE_FLOOR` → `winnerFit < EVIDENCE_FLOOR` in the guard (`archetype.ts`, `classifyArchetype`). Since `winner` is chosen only from contenders within `MARGIN_EPS` of `topFit`, `winnerFit <= topFit` always holds, so this is strictly more conservative — it can only turn some previously-classified (but floor-violating) verdicts into honest `null`s; it never turns a correct classification into a null, since when `winner`'s fit equals `topFit` (the overwhelming majority of cases, including every case the existing suite already covered) the two checks agree exactly. |
| **Regression guard** | New test in `archetype.test.ts`: BREAKOUT cluster at 0.36 (sets `topFit`, just above the floor) vs. EVENT_DRIVEN at 0.32 (wins the tie-break via priority, below the floor) — asserts `archetype === null`. Confirmed failing pre-fix (`git stash` on `archetype.ts`) with the wrong label at confidence 0.32, and passing post-fix. |

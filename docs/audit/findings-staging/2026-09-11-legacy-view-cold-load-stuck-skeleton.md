| **Status** | OPEN — reported with moderate confidence; root cause NOT identified in code, deliberately not fixed blind |
| **Severity** | P2 if real (affects any direct/bookmarked/shared link to the Legacy view specifically — `/nighthawk?view=legacy`, and the `PLAYBOOK`/`TONIGHT` aliases per `nighthawk-view.ts`'s `parseNightHawkView`) — not P1, since the in-app tab click path is the normal member flow and was not confirmed broken (see below) |
| **Component** | `src/features/nighthawk/components/NighthawkPageShell.tsx` (the `ssr:false` dynamic import of `NightHawkFeed`, fallback `NightHawkLoadingSkeleton`), `src/features/nighthawk/components/NightHawkFeed.tsx` |
| **Evidence** | Live-tested via `proxy-browser.cjs`/a custom Playwright script through this sandbox's CONNECT-tunnel Chromium, real premium-tier temp Clerk sessions (`mintClerkPremiumSession`), against production (`blackouttrades.com`). **6 attempts at `https://blackouttrades.com/nighthawk?view=legacy`** (mixed mobile/desktop UA, 10-18s waits, one reaching `networkidle`): **0 of 4 screenshot-confirmed attempts rendered the real Night Hawk app shell** — all 4 stayed on the OUTER `NightHawkLoadingSkeleton` fallback (generic "BLACKOUT" marketing-style header, two raw skeleton panels, no "Night Hawk" branding, no desk toggle bar, no `SESSION ANALYTICS` text) even after `networkidle` and 15-18s waits. Console/pageerror capture across these runs was inconsistent: 2 runs clean, 1 run showed a `ChunkLoadError` trying to load Next's own `global-error` chunk (`Loading chunk 4219 failed... missing: .../global-error-e8a9fba76364779c.js`), 2 more runs clean again (GA-collect `net::ERR_ABORTED` only, expected/benign). **Control: `https://blackouttrades.com/nighthawk?view=zero_dte` (2 dedicated screenshot runs) and no-param default (1 run) all rendered the real shell correctly** ("Night Hawk" branding, desk toggle bar with 0DTE/Swings/Legacy tabs, `SESSION ANALYTICS Loading track record…`) within 9-12s, no `networkidle` needed. A separate 3x console-only run against the `zero_dte` control also surfaced one unrelated chunk-load-adjacent error (a 404 + MIME-type refusal on a `layout-*.js` chunk) on run 1 of 3, with runs 2-3 clean — confirming this sandbox's proxy tunnel DOES intermittently fail to serve a Next.js static chunk on ANY view, not just Legacy, which is the confound this finding must be read against. |
| **Why this isn't filed as a confirmed bug** | The observed chunk-load failures are the SAME class of intermittent proxy-tunnel asset-serving flakiness this repo's own environment notes describe (`docs/audit/LIVE-UI-CONNECTION.md`, the proxy-tunnel `Routed: N ok, 0 fail` discipline) — proven by the control test also hitting one (different) chunk-load failure. That means at least some of the observed Legacy failures could be coincidental proxy flakiness landing disproportionately on the Legacy runs by chance, not a deterministic code defect. Against that: the split (0/4 Legacy screenshot successes vs 2/2 zero_dte screenshot successes, run back-to-back in the same session, same auth/tunnel setup) is a large enough gap that pure noise is a weak explanation, but not one this sandbox alone can rule out — the honest read is "probably real, not proven." I did NOT click-test the actual in-app "Legacy" tab from an already-loaded 0DTE view (the normal member navigation path) successfully — one attempt hit a `Legacy` text selector that found 0 matches (possibly a selector issue, possibly the tab genuinely wasn't there yet) and I did not re-run it to a clean result before running low on this cycle's time budget, so **whether the everyday in-app click path is also affected is genuinely unknown, not just unconfirmed** — that is the single most important open question for whoever picks this up. |
| **What a fix would need if confirmed** | Not attempted — the actual root cause inside `NightHawkFeed`'s cold-mount path when `seed.view === "LEGACY"` was not identified (no code path was found that differs by view before the outer `ssr:false` dynamic-import boundary resolves, which is the puzzling part: `ZeroDteDeck`/`HorizonDeck`/`LegacyDeck` are all lazily imported from the SAME `command-deck/containers` module, so there's no obvious reason the OUTER `NightHawkFeed` shell — which doesn't depend on which deck loads — would behave differently by view). Recommended next step: reproduce OUTSIDE this sandbox (a real browser, or Cursor's own tooling) hitting `/nighthawk?view=legacy` directly on a fresh session, ideally with the React DevTools/Network tab open, to settle whether this is a real client-side hang specific to the Legacy cold-load path or purely this sandbox's tunnel. If confirmed real, the natural angle is: capture a HAR/timeline of exactly which requests fire (or don't) for `?view=legacy` vs `?view=zero_dte` on cold load, since the outer skeleton staying up despite `networkidle` implies either a hung Promise inside `NightHawkFeed`'s mount effects or an error being silently swallowed somewhere between the dynamic-import boundary and React's error reporting. |

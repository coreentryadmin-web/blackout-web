## 2026-09-03 — [NEGATIVE-RESULT, checkout/billing] "7-day money-back guarantee" (yearly Premium only) vs "cancel anytime" (monthly Premium, SPX Slayer) — copy is internally CONSISTENT across homepage/pricing/FAQ/refund-policy; no in-repo refund-eligibility gate exists (Whop-side enforcement unverifiable from code)

> **kind:** `NEGATIVE-RESULT`

| Field | Detail |
|---|---|
| **What prompted this** | A user QA report (2026-09-02) flagged the homepage's new "7-day money-back guarantee" claim on yearly Premium, next to "cancel anytime" on monthly Premium and SPX Slayer, asking whether this was intentional or a copy inconsistency — treated as a checkout-adjacent contradiction to verify end-to-end rather than assume correct from the copy alone, in the same spirit as today's 0DTE hard-exit-time contradiction (PR #3367). |
| **Copy audit — consistent everywhere it appears** | `src/components/landing/RedesignHome.tsx`: SPX Slayer (line 469) and Premium Monthly (line 496) both read `"Cancel anytime · No contracts"`; only Premium · Yearly (line 523) reads `"Annual plan: 7-day money-back guarantee · cancel anytime"`. `src/components/landing/RedesignPricing.tsx` mirrors this exactly: SPX Slayer (line 52) and Premium Monthly (line 75) both `"Cancel anytime · no contracts"`; only Premium · Yearly (line 95) `"7-day money-back guarantee · cancel anytime"`. `src/lib/faq/content.ts` (lines 156-161, "Is there a refund if it's not for me?") states the same rule in prose: *"Annual plans: full refund within the first 7 days, no questions asked. Monthly plans are billed cycle-to-cycle with no long-term contract — cancel anytime and you won't be charged again, though the current cycle isn't refunded."* All three surfaces agree on the same two facts: (1) the 7-day guarantee applies to annual Premium only, (2) monthly Premium and SPX Slayer never get a refund, only future-billing cancellation. |
| **Why SPX Slayer never mentions a guarantee at all** | Not an omission — SPX Slayer has no yearly SKU to begin with. `src/lib/plan-matrix.ts`'s `PlanSku` is `"free" \| "spx_slayer" \| "premium_monthly" \| "premium_yearly"`, and `src/lib/pricing.ts`'s `MEMBERSHIP_PRICING` only defines `community` (SPX Slayer, $49/mo) as a single monthly price — there is no `community` yearly price anywhere. The refund-policy's annual clause (below) literally cannot apply to a plan that is never sold annually, so SPX Slayer correctly shows only "cancel anytime" on every surface. |
| **`/refund-policy` matches the homepage claim exactly** | `src/app/(marketing)/refund-policy/page.tsx`: "Monthly Subscriptions" (lines 27-33) — non-refundable once access is granted, no exceptions. "Annual Subscriptions" (lines 35-41) — *"non-refundable after the first 7 days. If you are unsatisfied... within the first 7 days of your annual subscription, contact us for a full refund."* "Cancellation" (lines 43-48) — cancelling stops future billing but does **not** trigger a refund for the current period, access continues to the end of the paid cycle. This is the same two-fact rule as the homepage/pricing/FAQ copy, stated in more detail rather than contradicting it — no "same fact stated two different ways" defect of the kind fixed in PR #3367 was found here. |
| **Whop checkout/webhook integration — reactive only, no eligibility gate in this repo** | `src/lib/whop-checkout.ts` only exposes the three Whop-hosted checkout URLs (`WHOP_CHECKOUT.community/monthly/yearly`) as UI links — no refund logic. The webhook handler, `src/app/api/webhook/whop/route.ts`, branches on `event.type`: `refund.created` / `refund.updated` / `dispute.created` / `dispute.updated` (lines 358-392) call `markMembershipRevoked()` unconditionally — there is no check of billing-cycle age, no `plan`/`product` (monthly vs. yearly) branch, and no day-7/day-8 boundary logic anywhere in that handler or in `src/lib/whop-revocation.ts` (which only stores/checks a revoked-membership denylist). Cancellation is a fully separate event family (`membership.deactivated`, `membership.cancel_at_period_end_changed`) that never calls `markMembershipRevoked` — confirmed by reading every branch of the `try` block, not by assumption — and `src/lib/whop-cancellation-notify.ts`'s own doc comment states cancellation *"happens entirely on Whop's portal — no in-app interception point."* In short: this codebase does not decide who gets a refund; it only reacts, after the fact, to a `refund.*`/`dispute.*` event that Whop already resolved, by revoking the member's entitlement. |
| **Why no day-7/day-8 boundary test was written** | The task asked for a test on the code path that decides refund eligibility. There is no such code path in this repository — refund initiation is either a human at `support@blackouttrades.com` manually approving a request (per the refund-policy page's own "How to Request a Refund" section) or Whop's own dashboard/support tooling, both entirely outside this codebase's control flow. Writing a "day 7 vs day 8" unit test against nonexistent gating logic would test a synthetic function that the live checkout flow never calls — it would prove nothing about production behavior and was deliberately not added. If BlackOut ever builds its own automated refund-eligibility check, this is the place to add that boundary test. |
| **What this does NOT verify** | Whether Whop's own product-level configuration (dashboard refund-window settings, or manual support-side date-checking) actually enforces the 7-day cutoff for the yearly Premium product specifically. That configuration lives entirely inside Whop's platform and is not inspectable via any API this codebase calls — verifying it requires a human with Whop dashboard/support access to (a) confirm whatever automatic refund-window setting exists on the yearly Premium product is set to 7 days (if Whop exposes such a setting at all), or (b) confirm the manual support workflow actually checks the subscription start date against the 7-day window before approving a refund request. **This finding verifies the CODE matches the CLAIM (no contradiction anywhere in the copy, and no code that would violate or auto-grant beyond the stated policy); it does not and cannot verify Whop's own enforcement of the window** — that is a manual follow-up, not a codebase-only claim. |
| **Status** | NEGATIVE-RESULT — the suspected copy contradiction was ruled out (all four surfaces agree); no code change made. Open action item for a human with Whop dashboard access: confirm the 7-day annual-refund window is actually configured/enforced on the Whop side for the yearly Premium product. |

## 2026-08-29 — [FINDING, P2 Largo] Four of #3155's six "fixed" truncation tools were still TRUNCATED live post-deploy — measured caps were 2-17x too generous — FIXED

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **Symptom** | PR #3155 ("Fix 6 Largo truncation issues") shipped fitting/capping for `get_confluence_outcomes`, `get_platform_snapshot`, `get_market_oi_change`, `get_market_stats`, `get_group_greek_flow`, `get_screener`, with its own "Validation" section flagging `⏳ Re-run probe: after deployment (should show all 6 tools COMPLETE)` as not yet done. Re-ran `largo-truncation-probe.mjs` live against production after the deploy completed (`ecr-push-production.yml` run for commit `60fb702a0`, confirmed `completed success`): **only 2 of 6 came back COMPLETE** (`get_confluence_outcomes`, `get_market_stats`). `get_group_greek_flow`, `get_screener`, `get_market_oi_change`, and `get_platform_snapshot` were still `TRUNCATED`, control (`get_zerodte_rejections`) PROVEN in the same run. |
| **Root cause, per tool — MEASURED, not re-guessed** | Wrote a small in-process script calling the real fetchers directly (`UW_API_KEY` is available in this sandbox) rather than estimating from field counts. **`get_screener`**: `fetchUwScreenerStocks(25)` averages **~1956 bytes/entry** (with attached technicals) — the PR estimated ~300-400 bytes, off by ~5x. The shipped 15-entry cap was therefore ~29KB, nearly double the transport cap on its own. **`get_market_oi_change`**: `fetchUwMarketOiChange(30)` averages **~635 bytes/entry**, not the ~300 estimated (~2x off); the shipped 20-entry cap left no headroom for wrapper/response overhead. **`get_group_greek_flow`**: the deeper bug — `fetchUwGroupGreekFlow("mag7")` (the tool's own DEFAULT when no `group` arg is given, not just the "market-wide" case the PR targeted) returns **391 raw rows / ~277KB**, 17x the cap by itself. The PR's fix capped `summary` (an array-of-per-group-summaries fitting function), but `summarizeGroupGreekFlow` actually returns **one aggregate object**, never an array — so `Array.isArray(summary)` is always `false` and that capping branch was dead code from the moment it shipped. The real payload weight, the raw `greek_flow: rows` field, was included **unconditionally and unbounded in both branches**, at every call, regardless of `group`. **`get_platform_snapshot`**: `fitted.spx = raw.spx` copied the SPX desk summary through **verbatim** — the exact same enrichment-tail shape (`unified_tape`, `news_headlines`, `macro_events`, `sector_heat`, `oi_changes`, …) that `get_spx_structure` needed a dedicated fitter (`fitSpxStructureForModel`, `spx-structure-fit.ts`) to trim in an earlier fix. Only the `flows` array was capped; `raw.spx` alone was large enough to blow the transport cap on its own. |
| **Why not caught before merge** | The PR's own probe run (cited in its body) was pre-deploy — it measured the OLD code, correctly showing all 6 TRUNCATED, but the post-deploy re-run that would have caught the 4 remaining failures was left as an open item and never actually performed before merge. |
| **Fix** | Per tool: `get_screener` cap 15 → **6** (measured entry size × 6 ≈ 11.7KB, under budget). `get_market_oi_change` cap 20 → **15** (measured entry size × 15 ≈ 9.5KB). `get_group_greek_flow` — new `fitGroupGreekFlowRowsForModel` (`market-data-fits.ts`) caps the raw `rows` field itself (15 rows, matching the pattern already used for `changes`/`candidates`), applied unconditionally in BOTH branches (the `Array.isArray(summary)` guard on the separate `summary`-capping path is left as-is — harmless, and correctly a no-op for the real single-object return shape). `get_platform_snapshot` — `fitted.spx` now goes through `fitSpxStructureForModel` (the same fitter `get_spx_structure` already uses) instead of being copied verbatim, reusing the existing row-cap/shed/hard-bound logic rather than duplicating it. |
| **Deliberately unchanged** | Did not touch `summarizeGroupGreekFlow` itself, despite finding — while measuring — that it reads field names (`net_delta`, `delta`, `gamma`, `net_gex`, …) that do **not exist** in the real UW group-flow response (`dir_delta_flow`, `total_delta_flow`, `net_call_premium`/`net_put_premium`, `otm_*` — no gamma field at all), so it always computes `0`/`0` and returns `null` for every real call. That's a distinct data-correctness bug (SPX desk's `mag7_greek_flow` and Largo's own "Mag7 dealer greek flow" live-feed line are both silently empty in production) with its own root cause requiring a real field mapping decision, not a capping fix — filed separately as `2026-08-29-summarize-group-greek-flow-field-mismatch.md` rather than folded into this transport-cap PR. |
| **Regression guard** | New `market-data-fits.test.ts` (7 tests) and `platform-snapshot-fit.test.ts` (5 tests): every cap is checked against fixtures sized at the MEASURED live entry byte-size (not a round guess), asserting the fitted payload stays under the 16,384-byte transport cap; `fitScreenerForModel`'s test additionally proves the OLD 15-entry cap would still have exceeded the cap at the measured size, so the test can't have quietly gone vacuous if entry-size assumptions drift again; `fitPlatformSnapshotForModel`'s test reuses the same oversized-SPX-summary shape `spx-structure-fit.test.ts` already established. |
| **Live re-verification** | Not yet re-run post-deploy of THIS fix (deploy takes ~15-40 min per the `ecr-push-production.yml` history observed this session) — flagged in the PR as the explicit follow-up owed, learning directly from #3155 leaving the identical step undone. |

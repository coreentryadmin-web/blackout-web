## 2026-10-18 — [FINDING, P2, Night Hawk Legacy] `resolveLegacyPlayOcc`/`parseOptionsContract`'s year-inference reference date was missed at three live production call sites, rolling an older edition's already-past "Mon DD" expiry label a full year forward — FIXED

> **kind:** `FINDING`

| Field | Detail |
|---|---|
| **Severity** | P2 — a live, reachable production defect (not test-only), but fail-soft: the only observed effect is an all-null mark (legacy-marks correctly returns no data for a non-existent contract) or a heuristic P&L fallback, never a crash or a wrong-but-plausible number. |
| **Trigger** | Standing 5-engine live monitor cycle's Legacy health check (CLAUDE.md's "ASK LARGO × NIGHT HAWK SWINGS"/5-engine mandate), discovered incidentally while cross-checking the legacy-marks mechanism against an older edition beyond the 3 checks the cycle specifically asked for. |
| **Root cause** | `resolveLegacyPlayOcc(ticker, optionsPlay, referenceDate?)` (`src/features/nighthawk/lib/legacy-play-contract.ts`) re-parses a member-facing `options_play` string whose expiry is a bare, year-less "Mon DD" label (`formatOptionsPlay` never prints a year). `parseOptionsContract`'s year-inference rolls the label forward a year whenever it reads as already-past relative to its `referenceDate` (default: real wall-clock now). This was already fixed once, 2026-09-13, at `src/features/nighthawk/command-deck/adapters.ts:1381` (anchored on the edition's own `published_at`) — but the fix was never propagated to three other call sites that re-derive the same OCC/expiry from the same free-text label, all on **live, reachable production paths**, not test-only: <br>1. `src/lib/db.ts`'s `fetchLegacyDiscordLiveRows()` (read by the production `legacy-live-sync` cron, `src/app/api/cron/legacy-live-sync/route.ts`) — spans every `activeLegacyEditionDates()` (up to ~14 trading days back), so a pending play from an older edition whose label's month/day had already passed this year rolled a full year forward. <br>2. `src/features/nighthawk/lib/legacy-discord-trade-notify.ts`'s `legacyInputFromOutcomeRow()` — the **primary** path `legacyInputFromLiveRow()` tries first for every live-sync TRIM/STC Discord notification; its unanchored re-parse of `row.options_play` silently re-broke the OCC even after the `db.ts` fix correctly resolved `row.contract_occ`, because the primary path's result shadowed the (correct) OCC-parse fallback entirely. <br>3. `legacyInputFromPlaybookPlay()` in the same file — feeds `notifyLegacyOutcomeClose()`'s fallback branch for an outcome row from an older edition, same unanchored-parse bug. |
| **Evidence** | Live repro 2026-10-18: `GET /api/market/nighthawk/edition?date=2026-10-14` (plays CLS/VST/AMD, each labeled expiry "Oct 16", edition published 2026-10-13) resolved via the unfixed path to OCCs `CLS271016C00370000`/`VST271016C00162500`/`AMD271016C00617500` — year **2027**, not 2026 — because today (2026-10-18) is after Oct 16's month/day. `GET /api/market/nighthawk/legacy-marks` correctly returned all-null mark/bid/ask for all three as a direct consequence (no such contract exists). RED→GREEN proven: 8 new/updated regression tests across `legacy-play-contract.test.ts` (`publishedAtRef` + an anchored `resolveLegacyPlayOcc` repro) and `legacy-discord-trade-notify.test.ts` (`occFromTradeDiscordInput` + anchored `legacyInputFromOutcomeRow`/`legacyInputFromPlaybookPlay`) failed against unmodified `main` (`git stash` isolating the 4 production files), passed after restoring the fix. `npx tsc --noEmit` clean; `adapters.test.ts` (154 tests) and the full `npm test` run both green (attached to the PR). |
| **Blast radius** | Four production files, all additive/no API-signature breaks for external callers: <br>— `legacy-play-contract.ts`: `publishedAtRef` (previously a private, untested helper duplicated only inside `adapters.ts`) is now exported here and shared. <br>— `adapters.ts`: imports the shared `publishedAtRef` instead of its own local copy — zero behavior change, pure de-duplication. <br>— `db.ts`'s `fetchLegacyDiscordLiveRows()`: now tracks each edition's `published_at` alongside the existing `editionPlayByKey` map and anchors `resolveLegacyPlayOcc`'s third argument on it — same anchor `adapters.ts` already uses. <br>— `legacy-discord-trade-notify.ts`: `resolveLegacyOutcomeExitPremium` now builds its OCC via a new pure, exported `occFromTradeDiscordInput()` straight from the input's already-resolved `expiry`/`top_strike`/`direction` fields instead of re-parsing `options_play` a second time (strictly more robust — no reference date needed at all, since `input.expiry` is already a full `YYYY-MM-DD`); `legacyInputFromOutcomeRow` now anchors on the row's own `created_at` (stamped at edition publish time per the existing PR-N4 comment); `legacyInputFromPlaybookPlay` now anchors on its own `editionFor` parameter (already available, previously unused for this). |
| **Fix rationale** | Two different fix shapes for two different situations, chosen deliberately: where a correctly-resolved structured expiry was already sitting unused in scope (`legacyInputFromOutcomeRow`'s own output, consumed by `resolveLegacyOutcomeExitPremium`), the fix removes the re-parse entirely rather than just passing a reference date — strictly more robust, since it can't be defeated by picking the wrong anchor. Where only the free-text label itself is available (`db.ts`, and the two `parseOptionsContract` call sites), the fix threads the same anchor pattern `adapters.ts` already established in the 2026-09-13 fix, rather than inventing a new convention. Left genuinely out of scope: a fourth, lower-priority duplication noted but not touched — `parseOptionsContract`'s other callers that always operate on same-day/fresh data (never an older edition) were left unanchored, since there is no rollover risk there to fix. |
| **Status** | FIXED — see PR (branch `fix/legacy-occ-year-rollover-anchor`). |

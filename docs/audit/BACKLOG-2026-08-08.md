## 0. Why FINDINGS.md can't currently answer "what's open"

```
351  entries
114  carry a **Status** line
 70  say FIXED
240  carry no status at all
```

The 240 are **not 240 open issues**. Spot-checking them, they are three different kinds of thing
filed under identical formatting:

| Kind | Example | Should it be in FINDINGS? |
|---|---|---|
| Routine pass log | "Post-close fix agent — all validators GREEN" | **No.** CLAUDE.md already forbids docs-only PRs for GREEN audit logs; these leaked in anyway. |
| Negative result | "React #418 … locale/timezone RULED OUT" | **Yes**, but tagged so it never reads as open work. A ruled-out cause is valuable and must not be re-investigated. |
| Real finding | "BREAKOUT ranker measurably worse than random" | **Yes** — this is what the file is for. |

Plus a fourth failure mode among the 114 that *do* have a status: many say `PR pending → CI →
auto-merge` for work that merged days ago. The status was written mid-flight and never revisited.

**This is the highest-leverage item in this document.** While an open P1 is indistinguishable from
a finished chore, real findings sit. The BREAKOUT ranker below has been awaiting a decision since
2026-08-07 for exactly this reason.

### The fix (one focused session, mechanical, low-risk)

1. Classify every heading: `FINDING` / `NEGATIVE-RESULT` / `PASS-LOG` / `OPS-NOTE`.
2. Move `PASS-LOG` entries out to a separate `docs/audit/RUN-LOG.md`. They are noise in a findings
   file; they are useful as a run history.
3. For every `FINDING`, reconcile its claim against git history — the fix either landed or it
   didn't — and stamp `FIXED (<sha>)` / `OPEN` / `SUPERSEDED BY <entry>`.
4. Add a test (mirroring `repo-hygiene.test.ts`) asserting every `## ` heading carries a status
   line and one of the four kind tags. The log cannot rot silently again.

Do **not** attempt this in the same session as feature work. It is a few hundred entries and the
failure mode of doing it halfway — a partially-marked log people then trust — is worse than the
current state, where at least the unreliability is obvious.

### 2.1 "We couldn't load this page" — intermittent, NOT reproduced
Ruled out with evidence: server render (1013 authenticated requests, 0 failures), RSC payloads

### 2.2 EOD pin accuracy — unmeasurable retrospectively, must record forward
Two provable defects fixed (#1922 scenario mislabelling, #1923 forecasting from the wrong expiry).
**Accuracy on a real expiry day remains unknown**, and a backtest is impossible — measured, not
assumed:

```
contracts?as_of=<past expiry>  → returns contracts, NO open_interest field
snapshot for that expiry       → {"results":[]}   (expired, gone)
```

The forecast's whole input is an OI-weighted gamma ladder, and historical OI for expired 0DTE
contracts is unavailable. Nothing persists pin forecasts either (no table, no migration).

**Only honest path:** persist each forecast at emit time (pin, projected close, confidence, band,
regime, magnet, method), grade against the realised close after the bell. Report median absolute
error in points, error by time-of-day, and — the one that matters — whether the stated confidence
band contains the close as often as it claims. Needs a few weeks of sessions before it says
anything, which is the argument for starting it rather than deferring it.

### 2.3 Welcome drip cron — not scheduled
The staleness cutoff (#1920) is merged and deployed. Remaining work is one rule, once the fleet is
at steady state (`describe-services` → one deployment, `COMPLETED`):

```
aws events put-rule --name blackout-production-welcome-sequence \
  --schedule-expression 'cron(0 * * * ? *)' --region us-east-1
aws events put-targets --rule blackout-production-welcome-sequence --region us-east-1 \
  --targets 'Id=1,Arn=arn:aws:lambda:us-east-1:177922194517:function:blackout-production-hit-cron,Input={"key":"welcome-sequence","path":"/api/cron/welcome-sequence"}'
```

Scheduling against a mid-rollout fleet risks hitting a task without the cutoff, which flushes the
backlog the cutoff exists to prevent. Verify steady state first, then watch the first firing and
report retired-vs-sent.

### 2.4 Deploy gate produces false negatives
`ecr-push-production.yml`'s post-rollout asset check retries 10× over ~2.5 min. At 5 desired tasks
the drain routinely outlasts that, so page HTML and chunk requests land on different revisions and
it fails a healthy deploy. Observed on 08-08. Trains everyone to ignore a red deploy. Fix: longer
budget, or check against a single revision rather than through the load balancer.

### 2.5 HSTS — deliberately left as-is (do not "fix")
Origin sends `max-age=63072000`; the edge serves `31536000`. **This is Cloudflare's own HSTS
feature, not the transform rule that was deleted on 08-08** — that rule never set HSTS. Cloudflare
caps `max_age` at 31536000, so matching the origin requires disabling edge HSTS entirely, which
removes the fallback protecting you if the app ever stops sending the header. 1 year is standard
and satisfies preload. **Recommended:** change the origin to `31536000` so code matches reality.

## 3. How to work this list

**Merging PRs — judgement, not a green light.** On 08-08 three well-written, CI-green PRs from a
parallel agent each needed a decision rather than a merge: one would have reverted an explicit
operator decision, one duplicated work already on main, one carried a confidently wrong root-cause
attribution. Before merging anything: does it conflict with a decision the operator has already
made, is it already on main, and does its central claim survive an independent check? Verify the
claim, not the prose — the prose is always good.

**Verify on `main`, not from the merge response.** A merge API returning `merged: true` is not
proof the change landed where you think; stacked branches merge into their parent. Re-read the file
on `origin/main`.

**A test that has never been seen to fail is not a regression guard.** Check out the pre-fix code,
run the new test, watch it fail. Two tests written on 08-08 passed against the broken code and were
labelled as invariants rather than sold as proof.

**Negative results are results.** Record what was ruled out and how, so nobody re-investigates it.
Several entries above exist only because someone did that.
